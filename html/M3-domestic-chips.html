M3 · 国产芯片适配

状态：已完成——第 1–6 周全部为完整内容（加深版）。

前置：M0（度量、profiling、压测脚本）与 M1（vLLM/SGLang 已跑通）。M3 的终点是：同一模型、同一评测集，在 NVIDIA 与至少一种国产芯片上都跑通、压测，并写出一份可复现的对比报告。

模块为 6 周：M2 的深讲标准同样要求 M3 的内容不压缩——第 2 周专讲 CANN/AscendC 到动手移植的程度，第 3 周专讲 Ascend 跑通与 vllm-ascend 插件架构，第 5 周专讲真实移植案例。

诚实声明：国产芯片适配进展极快，任何写死的支持矩阵都会很快过时。本模块不写静态结论，只给方法论和可复现的验证脚本；凡是涉及具体芯片、具体版本的实测结果，都按「某年某月某版本实测」的格式记录，由学习者自己验证后填写。本仓库目前没有任何一条在国产芯片上的实测记录，不要把大纲里的“预期”当成已验证的事实。

为什么单开一个模块

调研结论：国产芯片适配没有任何动手的学习材料，只有框架插件、一张支持状态追踪表和零散厂商文档。M3 要补的就是这一块：从“知道有这些芯片”到“真的在上面跑起模型、量出数字”。

第 1 节 · 国产芯片全景：先列清单，再问“能不能跑推理”

目标：列出一张芯片清单，标出各自的软件栈，并用同一把尺子衡量它们。

怎么做（30 分钟，无硬件可做）：

  1. 打开 awesome-china-gpu（国产芯片推理适配进度追踪表），先看它给的分析框架——Four Walls（四面墙）：生态（ecosystem）、显存（memory）、通信（communication）、精度（precision）。这四面墙就是衡量一块芯片“能不能跑推理”的尺子：生态决定有没有框架插件、显存决定能放多大的模型、通信决定多卡能不能扩展、精度决定量化后准不准。先记下这个框架，后面每一周都会用它来归因。
  2. 按追踪表列出主线芯片：昇腾（Ascend）、寒武纪、摩尔线程、海光、昆仑芯、天数智芯、壁仞、燧原、沐曦。每个只记两项：软件栈叫什么、推理引擎的接入方式是什么（vLLM 插件 / 容器镜像 / 原生框架）。不要展开写参数——参数会过期，接入方式才是地图上稳定的部分。
  3. 注意追踪表的时效：表里引用的引擎对比与支持状态有明确的核实日期（例如 2026 年 6 月的对比表）。抄表的时候把日期一起抄下来，过期即作废——第 5 节会把这条变成制度。

产出：一张芯片清单（芯片 × 软件栈 × 接入方式），并写下 Four Walls 四面墙的定义。

第 2 节 · 软件栈分层：驱动 → SDK → 算子库 → 框架插件 → 推理引擎

目标：画出分层图，并说清每一层坏了会在哪一层暴露出来。

怎么做（30 分钟，无硬件可做）：

  1. 画五层：驱动（认不认卡、能不能分配显存）→ SDK（CANN、DTK、MUSA 这类厂商软件栈：编译器、运行时、算子库）→ 算子库（TBE/AscendC 写的算子、厂商提供的融合算子）→ 框架插件（vllm-ascend、vllm-musa 这类把芯片接进 vLLM 的包）→ 推理引擎（vLLM、SGLang 本身）。
  2. 对每一层问一个问题：“如果这一层缺东西，用户会在哪一层看到症状？”——驱动缺失：卡认不出来；算子库缺失：某个算子回退到 CPU 或低效实现（第 4 周的覆盖分析就是查这个）；插件缺失：引擎根本启动不了。分层图的用处就是定位问题在哪一层，而不是笼统地说“国产芯片不行”。
  3. 用 Four Walls 对照分层：生态墙对应框架插件层、显存墙对应驱动与 SDK 的显存管理、通信墙对应多卡互联（SDK 层）、精度墙对应算子库的量化实现。两张图叠在一起，就是一张“问题定位地图”。

产出：一张分层图 + 每层的“缺失症状”一句话。

第 3 节 · 插件机制：vLLM 是怎么做到一块代码跑多家芯片的

目标：能讲清插件算子的替换点（M2 第 6 周讲的是算子级 CustomOp，这里是平台级插件）。

怎么做（30 分钟，无硬件可做）：

  1. 区分两个层次的“插件”：M2 第 6 周的 CustomOp 是算子级替换（一个 SiluAndMul 换成你的 Triton 版）；这里的 vllm-ascend 是平台级插件——它给 vLLM 提供一整套芯片适配：平台类（NPUPlatform）、算子实现、注意力后端、通信、编译配置。模型代码不用改，换的是底下的整套实现。
  2. 打开 vllm-ascend，看它的顶层结构：vllm_ascend/ 下有 platform.py（NPUPlatform）、ops/（算子）、attention/（注意力后端）、model_executor/、quantization/、patch/、worker/、compilation/、device/、distributed/、profiler/、_cann_ops_custom/、ascend_config.py、meta_registration.py。第 3 周的任务之一就是在这些目录里定位到具体算子的实现位置——先把地图记下来。
  3. 理解注册链：插件被 vLLM 加载后，注册它的平台类；vLLM 启动时按设备选平台，后面的算子分发、注意力后端选择、编译配置都跟着平台走。算子分发发生在平台选定之后——这是第 3 周要展开的细节，本节先记住顺序：先选平台，再分发算子。

产出：一页笔记：平台级插件与算子级 CustomOp 的区别 + vllm-ascend 的目录地图。

第 4 节 · 统一算子层：FlagGems / FlagCX 的思路

目标：讲清统一层解决了什么、没解决什么。

怎么做（30 分钟，无硬件可做）：

  1. 读 vllm-plugin-FL 文档：它提供两个统一库——FlagGems（统一算子库）与 FlagCX（统一通信库），加一个插件把它们接进 vLLM。
  2. 理解它的分发逻辑：优先级分发——先找 FlagGems 的统一实现，没有再找厂商实现，再没有回退到 PyTorch 参考实现，自动 fallback。平台自动检测：启动时识别当前芯片，选对应的后端。支持的平台包括 NVIDIA、Ascend、T-Head、Iluvatar、MetaX、摩尔线程、Tsingmicro、海光、燧原、昆仑芯、阿里巴巴 PPU、CPU ARM64。
  3. 讲清边界：统一层解决的是“一份 kernel 代码跑多家芯片”的问题（写一次，到处跑）；它没解决的是“每家芯片的峰值性能”——统一实现为了可移植会牺牲一部分特化优化，要榨干某块芯片的性能，最终还是要写它的原生算子（第 2 周的 AscendC、第 5 周的移植案例就是这条路）。这与 M2 第 5 周“Triton vs CUTLASS”的取舍是同一个逻辑，换了一块芯片。
  4. 再看 FlagTree：它是 FlagGems 背后的算子开发框架——算子用一套抽象写出来，再针对不同芯片生成实现。第 5 周移植时会再遇到它。

产出：一页笔记：统一层解决了什么、没解决什么 + 分发优先级链。

第 2 节 · TBE 与 AscendC：两代算子抽象长什么样

目标：讲清一个算子的抽象长什么样——定义、编译、调用三段分别是什么。

怎么做（30 分钟，无硬件可做）：

  1. 先讲两代的区别：TBE 是上一代——用 DSL 描述算子（定义输入输出、写计算表达式），再由编译器生成 kernel；AscendC 是当前的主力——用 C++ 直接写算子，算子是一个类，计算过程拆成流水线任务。两代的抽象不同，但链路相同：定义 → 编译 → 调用。
  2. 这条链路的三个环节，每个环节的产物是什么： - 定义：算子的接口（输入输出的 shape 与 dtype）与计算逻辑（AscendC 里是一个带 Init 与 Process 方法的类）； - 编译：AscendC 编译器把算子源码编成可在 NPU 上跑的 kernel（产物是 kernel 二进制 + 注册信息）； - 调用：框架（PyTorch / vLLM）通过算子名找到它，把输入张量传进去，launch kernel。vllm-ascend 的 _cann_ops_custom/ 目录就是自定义算子的落点——第 3 周会在那里定位具体算子。
  3. 对照 M2 的经验：Triton 里你写的是“一个 kernel 函数 + grid”，AscendC 里你写的是“一个算子类 + 流水线任务”。抽象变了，但“写 kernel → 验证 → 接入”这套流程没变——第 5 周的移植案例就是把 M2 的 Triton kernel 沿这条链路搬过去。
  4. 官方文档锚点：AscendC 开发文档（CANN 8.5.0 版）与向量编程指南（80RC2 版）——版本不同，API 细节可能有出入，读的时候以你所装 CANN 版本对应的文档为准： - CANN 8.5.0 AscendC 开发文档 - CANN 80RC2 向量编程指南

产出：一页笔记：TBE vs AscendC 的抽象对比 + “定义 → 编译 → 调用”链路图。

第 3 节 · AscendC 流水线模型：读懂一个向量加法算子

目标：读懂 AscendC 的流水线编程模型，能说出每个部件是干什么的。

怎么做（30 分钟，无硬件可做；代码为示意骨架，可编译版以官方文档为准）：

  1. 打开 CANN 8.5.0 AscendC 开发文档里的向量加法例子（add_custom），先看 kernel 入口——它长这样：
// 示意骨架：结构与名字以 CANN 8.5.0 AscendC 开发文档的 add_custom 为准
extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z) {
    // op.Init(...); op.Process();
}
  1. 理解流水线模型的五个部件（对照文档里的定义）： - TPipe：统一的资源管理——算子里的内存、事件都由它管； - TQue：任务间通信与同步的队列——CopyIn、Compute、CopyOut 三个任务通过它接力； - InitBuffer / AllocTensor：在 Init 里做——给 GlobalTensor 设地址、给队列分配 buffer； - TBuf：临时内存——中间结果放这里； - CopyIn / Compute / CopyOut：Process 里调的三步——把输入从 Global Memory 搬进片上、算、把结果搬回去。这三步与 Triton 的“load → 算 → store”是一一对应的，只是 AscendC 把它显式拆成了三个任务。
  2. 理解核类型：KERNEL_TASK_TYPE_DEFAULT(KERNEL_TYPE_AIV_ONLY) 表示这个 kernel 只用向量核（AIV）。Ascend 的核分两种——向量核（AIV）与矩阵核（AIC，跑矩阵乘）；一个算子用哪种核，在定义时就定下来了。这就是第 4 周覆盖分析时要查的东西：一个算子在芯片侧有没有实现、用的是哪种核。
  3. 对照 M2 的 Triton：Triton 里 block 大小、访存模式由编译器管；AscendC 里流水线的每一步都要你显式写出来。控制粒度更细，代码量更大——这就是移植时要付的代价，第 5 周会逐条记录。

产出：一份 AscendC 流水线模型笔记（五个部件 + 三步流程 + 核类型），能向别人讲清 add_custom 的执行过程。

第 3 节 · 迁移 benchmark 怎么做：读懂 TritonAscendBench 的设计

目标：理解迁移评测的设计——它测什么、怎么判分、没卡时能做什么。

怎么做（30 分钟，无硬件可做）：

第 3 节 · 差异分析：数字不同的原因——归因到具体算子

目标：把差异归因到具体算子，而不是笼统地说“芯片不行”。

怎么做（30 分钟，分析无卡可做；归因需要第 1–2 节的数据与第 4 周的覆盖矩阵）：

  1. 先分两类差异：精度差异与性能差异，归因方法不同。
  2. 精度差异的归因（量化误差的来源）： - 量化方案的差异：两边的量化实现是不是同一套（per-channel / per-token 的 scale 取法、舍入方式）——第 4 周的覆盖矩阵里记了每个算子的实现位置，对照着查； - 低精度算子的差异：FP16 / INT8 的实现是不是同一精度（比如一边用了 FP8、另一边没有）； - 归因方法：二分法——一次只换一个变量（比如先把可疑算子换成 PyTorch 参考实现跑一遍，看差异是否消失），差异消失的那个算子就是回归的来源。归因的终点是一个算子名，不是“精度墙”三个字。
  3. 性能差异的归因（对照第 4 周的结论与 Four Walls）： - 算子覆盖（第 4 周的矩阵：有没有算子回退到 CPU 或低效实现）； - 显存带宽（第 1 周的 Roofline 思路：搬运量有没有变——比如权重精度不同导致搬运量不同）； - 调度（高并发下掉得快的一边，先看它的批处理与 KV 管理）。
  4. 写一份归因记录：每个差异一行——差异（数字）、候选原因（2–3 个）、验证方法（怎么确认是哪一个）、结论（归因到哪个算子或哪面墙，证据是什么）。验证不了的写“待验证”，不要写成定论。

产出：一份差异归因记录（差异 + 候选原因 + 验证方法 + 结论）。
