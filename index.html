边做边学 LLM 推理服务，交付一个真实的推理服务。

一份给想真正跑起 LLM 推理、而不只是读一读的工程师的路线图。每一节都服务于同一个产物：一个 OpenAI 兼容的推理服务——你把它部署到租来的 GPU 上，做埋点、压测到 1000+ 并发，用量化和投机解码优化，在前面放一个成本感知的路由器，最后把它作为一份可复现的 benchmark 发表出来。

另一种做法是做十七个互不相干的小实验，大部分时间都花在搭环境上。一个不断长大的服务能覆盖同样的知识点，最后你手里还留下一个能拿得出手的东西。

本 fork 在上游基础上做了这些改进：中文版；扩展为 M0–M4 五个模块；新增 M2 算子优化与 M3 国产芯片适配；新增第 8 周（续）大规模集群 PD 优化与第 11 周 TensorRT-LLM两处可选加深；论文一律作选读，核心内容写进正文。英文原文见 docs/original-README.md。

前置要求

适合谁

你应该熟悉 Python、了解 Transformer 的架构、会用命令行。不需要有 serving、Kubernetes 或 CUDA 的经验。

如果你已经了解某个主题，标记为略读的课可以压缩。做的课不要压缩，它们才是重点。

设计

路线图为什么是这个顺序

这个顺序是刻意排的，和大多数人写清单的方式不一样。背后有五个决定。

01

Roofline 模型放在最前面

后面每一次优化，都是同一张图上的一个移动。量化打的是解码阶段受显存带宽限制的问题；连续批处理把算术强度往计算上限推；投机解码用便宜的 FLOPs（在显存带宽受限的情况下 FLOPs 是便宜的）换更少的顺序访存；解耦式部署存在，是因为 prefill 受计算限制、解码受带宽限制，两者在一块 GPU 上打架。没有这个模型，后面就是一袋子技巧。

02

度量先于优化

埋点在第 3 周，压测在第 5 周，远在调优旋钮之前。没有它们，后面的一切都无法验证；一份公开的 benchmark，大部分就是一个可信的度量工具加一个模型。

03

PagedAttention 和连续批处理不值得自己重写

vLLM 已经实现了这两者，分块 prefill（chunked prefill）是 vLLM 和 SGLang 默认的调度策略。重写它们，不如读懂 block manager 和调度器，直到你能从代码讲清楚：为什么显存浪费能降到 4% 以下，为什么 GPU 在请求之间不再空转。

04

路由器放在单位经济学旁边

一个按成本、延迟、质量选后端的路由器，是唯一一个把“多少钱”和“延迟预算”写进代码的组件。同一周学经济学，读到的东西会变成路由策略，而不是一篇你点头同意的博客。

05

端侧部署是可选的，放在最后

ONNX Runtime、WebLLM 是客户端和嵌入式运行时，和前面九周搭建的数据中心那套几乎没有共同的操作面。TensorRT-LLM 不属于这一类：它是一台数据中心推理引擎，只是走编译式路线，所以单独放进可选的第 11 周，而不是和端侧工具并列。

第 1 周之前

环境准备

7–8B 的模型大约需要一块 24GB 显卡。按半小时租，用完关机。第 1 周全部、第 3 周大部分、第 6 周的讲座日、第 9 周全部阅读都不需要 GPU。把租卡集中在动手的那几天。

GPU 渠道

只有两节课必须用 H100

  • RunPod，按秒计费
  • Modal，Serverless，最适合跑 benchmark 扫描脚本
  • Lambda 和 vast.ai，按需和市场价 GPU，便宜
  • Colab，纯 Python 的课，不用部署服务

只有两节课必须用 H100：第 5 周的 1000 并发测试，以及第 8 周如果你真的要跑解耦式部署。第 8 周（续）的多节点实测需要多卡集群，租不到就只做部署验证、性能对比待补测。

安装

另加 Docker 和 kind

pip install vllm
pip install guidellm
pip install sglang

另外还需要 Docker（跑 Prometheus 和 Grafana），以及第 8 周用的 kind 或一个小的托管集群。

第 11 周另外需要 TensorRT-LLM：优先用 NGC 预编译容器，或按同一指南用 pip 安装。装之前先核对支持的硬件：文档列出的最老架构是 Ampere A100，FP8 权重需要 Hopper 或更新。

决策点

这些时刻，盲目跟进度是错的。

如果那么
第 5 周。 还没到目标并发，TTFT 就飙升、num_requests_waiting 爬升。服务器在抢占。先停下来调 --max-num-seqs、--gpu-memory-utilization 和分块 prefill。在抢占点上测出来的数据不能发表。
第 6 周。 INT4 换来的吞吐，让质量代理指标掉了超过 1–2%。保留 FP16 或 FP8 作默认。把 INT4 当作缓解显存压力的杠杆，不当作默认的吞吐手段。
第 7 周。 在你真实的请求速率下，投机解码反而变慢了。预期之内。收益出现在低查询率下，GPU 被计算打满时就消失了。把交叉点发表出来，它比加速比更有用。
第 8 周。 Kubernetes 开始整节整节地吃掉你搭集群的时间。用托管集群，或者退回单节点 Docker 加 KEDA 那篇阅读。自动扩缩容的信号比自己搭的集群重要。
第 8 周（续）。 解耦后 TTFT 反而变差。先算传输账：KV 传输时间超过了 prefill 排队省下的时间，解耦在你的 prompt 长度和带宽下不划算。先缩短传输路径（同机、更高速的互联）或退回同机部署，再谈扩池子。

关于来源的说明

这里的每个视频都有具名的讲者——来自大学、引擎团队或会议——并且配有覆盖同样内容的文字材料，所以你可以读而不是看。没有视频达到这个标准的地方，这一周就是纯文字，而不是硬凑。

  • 时间戳是目标值。讲座会被重新上传、重新剪辑，用视频里的章节标记来定位分割点。
  • MIT 6.5940 在 2025 秋没有开课。2023 秋和 2024 秋的录像都存在，任选其一。
  • vLLM 的博客有两种 URL 形式，文档随版本变化。如果链接 404，搜精确标题，不要改路径。
  • 这里引用的性能数字是论文和博客各自宣称的，没有独立复现。把它当作那个来源愿意为之辩护的数字，而不是你硬件上的事实。
  • 每百万 token 的成本和 GPU 每小时价格变化很快。经济学那部分阅读的价值在于方法。每个数字都要按你自己的硬件重新算。
