# 专题 B：大规模集群 PD 与分布式 KV 池 { .chapter-title }

<p class="chapter-summary">当 PD 解耦走出单机、进入百卡千卡集群，调度核心从“算力分配”转向“KV 在哪、搬多慢、值不值得取回”。</p>

[第 11 章](../chapters/chapter-11.md) 从单机与中小规模服务的视角，讲清了为什么必须把算力受限的 Prefill 和带宽受限的 Decode 拆开。但当服务进入数十节点、数百张 GPU 的集群尺度，解耦本身立刻引出四个全新的分布式系统难题：

1. **传输税进 TTFT**：KV 不再驻留本机显存，跨节点搬运直接计入首字延迟；
2. **共享前缀如何资产化**：如果每个节点算完就扔，全集群的系统提示词与多轮历史仍在反复重算；
3. **异构与动态配比**：Prefill-heavy 与 Decode-heavy 负载交替出现，固定卡数比例必然造成一侧过载、一侧空转；
4. **节点故障与长尾雪崩**：某张卡宕机或网络拥塞时，正在传输的 KV、误派的在途请求如何止损。

本专题沿着 **DistServe（拆阶段）→ Splitwise（拆异构硬件）→ Mooncake（以 KV 池为中心的集群架构）** 的演进脉络，把集群级 PD 的调度公式、传输账本、分布式缓存池、卡数配比推导与容错机制一次算透。

---

## B.1 为什么集群尺度必须以 KV 为中心

在同机混跑时代，调度器眼里只有“计算队列”；进入集群级 PD 后，长上下文请求生成的 KV 缓存高达数百 MiB 至数 GiB，搬运成本和重算成本同等量级。**Mooncake** 的核心洞见在于：**把 KV 缓存从引擎内部的临时副产品，升格为集群调度的一等公民**。

  <figcaption><span class="book-figure__label">图 B-1</span>上半部分对比三种调度模式：混跑下长 Prefill 直接阻塞 Decode 制造 ITL 尖峰，切块缓解但仍争算力，PD 解耦彻底隔离两阶段并引入显式 KV 传输段；下半部分展示了 Mooncake 集群五部件如何解耦控制面与数据面——Conductor 只管全局路由与过载预测，KV 数据经 Transfer Engine 在 P 池、共享 DRAM/SSD 池与 D 池之间通过 RDMA 高速流转。</figcaption>
</figure>

这张架构图里五个部件严格遵守**控制面与数据面分离**原则：

- **Conductor（控制面全局调度器）**：掌握全集群前缀缓存元数据与 P/D 实时负载，负责为每条请求挑选一对 `(Prefill 节点, Decode 节点)`，或在过载时提前拒绝；它**绝不经手任何 KV 载荷数据**。
- **Prefill 池（算力型节点）**：拉取命中的共享前缀块，只对未命中的增量部分逐层执行 Prefill，并将新生成的 KV 边算边推出。
- **Decode 池（高带宽节点）**：接收完整 KV 后将请求并入连续批处理，保持低抖动的 ITL 流式输出。
- **Mooncake Store（分布式 KV 池）**：将集群各服务器闲置的 CPU 内存（DRAM）与 NVMe SSD 聚合成统一的可复用 KV 资产池。
- **Transfer Engine（统一数据面）**：承接三条方向各异的数据流——`Store → Prefill`（取回旧前缀）、`Prefill → Decode`（推送新 KV）与 `节点间复制`（热块扩散），向下屏蔽 RDMA/UCX/NVLink/TCP 差异并实现多网卡带宽聚合与自动 failover。

!!! tip "核心直觉：两类架构互补，而非替代"
    **Splitwise** 解决的是“硬件怎么配”（用高算力卡跑 P、高性价比/低功耗高带宽卡跑 D，纠正阶段与硬件的算力错配）；**Mooncake** 解决的是“状态放哪、怎么搬”（用分布式池复用前缀、用 Conductor 按取回成本调度）。两者拼在一起，才是完整的大规模 PD 架构。

## B.2 全局调度器 Conductor：TTFT 估算与过载提前拒绝

当一条请求携带长 Prompt 到达时，最空闲的 Prefill 节点未必是最快的节点——如果另一个稍忙的节点本地恰好缓存了 50% 的前缀，省下的计算时间可能远超排队等待。Conductor 通过把三项异构成本统一折算为毫秒来做全局最优选择：

$$
\text{TTFT}_{\text{est}} = T_{\text{queue}} + T_{\text{prefill}}(\Delta L) + T_{\text{KV,critical}}
$$

其中 $\Delta L$ 是扣除命中前缀后的增量计算长度，$T_{\text{KV,critical}}$ 是落在关键路径上的 KV 等待时间（可能包含远端前缀取回以及 D 侧尚缺 KV 的尾部传输时间；若有逐层计算/传输重叠，仅计入未被掩盖的尾部）。

### 调度决策算例：排队更长的节点反而更快

以 **H100 80GB SXM**（FP16 稠密 $989.5\text{ TFLOPS}$，按 $50\%$ 有效 MFU 计）运行 **Llama-3.1-8B**（$8.03\text{B}$ 参数，每 token KV 为 $128\text{ KiB}$）处理一条 $4096$-token Prompt 为例。权重主导的线性 Prefill 速度约为：

$$
\frac{2 \times 8.03 \times 10^9}{989.5 \times 10^{12} \times 0.5} \times 1000 \approx 0.03246\text{ ms/token}
$$

完整计算 4,096 token 约需 $132.96\text{ ms}$；全量 KV 体积为 $4096 \times 128\text{ KiB} = 512\text{ MiB}$（$0.5369\text{ GB}$），在 $400\text{ Gb/s}$（$50\text{ GB/s}$）InfiniBand 串行线速下耗时 $10.74\text{ ms}$。比较两个候选 Prefill 节点（设目标 Decode 节点尚无前缀缓存）：

| 候选节点 | 排队等待 $T_{\text{queue}}$ | 前缀命中情况 | 增量 Prefill $T_{\text{prefill}}$ | D 侧 KV 传输 $T_{\text{KV}}$ | 串行估计 $\text{TTFT}_{\text{est}}$ | SLO（$\le 150\text{ ms}$）判定 |
| --- | ---: | --- | ---: | ---: | ---: | --- |
| **节点 A** | 20.00 ms | 未命中（算全量 4,096） | 132.96 ms | 10.74 ms | **163.70 ms** | 超标 |
| **节点 B** | 60.00 ms | 本地 GPU 命中 2,048 token | 66.48 ms | 10.74 ms | **137.22 ms** | 达标，选中 |

尽管节点 B 的队列比节点 A 多排 40 ms，但由于省下了一半 Prefill 计算，总 TTFT 反而低 **26.48 ms**，且唯一满足 150 ms SLO。

### 多项式回归预测与“基于预测的提前拒绝”

三项成本中，每一项的估算各有难点：

- **增量计算 $T_{\text{prefill}}$**：Transformer 计算模式规整，Mooncake 利用离线采集的数据拟合**多项式回归模型**，以总长度与命中前缀长度为输入预测执行时间（线上分布漂移时需定期重拟合）；排队时间即为队列内所有待算请求预测耗时之和。
- **传输耗时 $T_{\text{KV}}$**：不仅取决于数据量，更敏感于发送端网卡拥塞，这正是下文引入“热块复制”打散单点带宽热点的直接动因。
- **过载提前拒绝（Prediction-based Early Rejection）**：若所有候选节点都无法满足 TTFT 或目标 Decode 节点的 TBT 约束，Conductor 在入口直接拒绝请求，防止全集群雪崩。但工程实践表明，**仅按瞬时负载拒绝会引发 P/D 两池的反相振荡**——P 池满载拒载导致数十秒后 D 池无请求可跑而饿死，D 池满载拒载又导致 P 池空转。Mooncake 的解法是向前预测“当前请求完成 Prefill 抵达 D 池时刻”的预期 Decode 负载，据此做平滑准入。

!!! warning "常见误区：不要用拒绝请求“美化”吞吐"
    提前拒绝的目的是保护被接纳请求的 SLO 不被拖垮，但**被拒绝的请求属于 SLO 未达成，必须完整保留在总请求分母内**。汇报集群性能时，必须把有效请求容量（goodput）、拒绝率与预测误差一并给出。

## B.3 跨节点传输税与逐层流水重叠

PD 解耦划不划算，第一笔必须算清的是网络传输税。最常见的量级错误来自混淆 **$\text{Gb/s}$（十进制比特）** 与 **$\text{GB/s}$（十进制字节）** 的 8 倍换算，以及二进制 **MiB** 与十进制 **MB** 的换算：

$$
t_{\text{transfer}} = \frac{L \cdot c_{\text{KV}}}{\text{BW}_{\text{byte}}}, \qquad \text{BW}_{\text{byte}} = \frac{\text{BW}_{\text{bit}}}{8}
$$

继续沿用 Llama-3.1-8B（$128\text{ KiB/token}$）在 H100（50% MFU，P 排队 20 ms）上的线性权重模型，把 Prompt 长度与三种典型网络带宽展开，得到串行线速传输时间及其在总 TTFT 中的占比：

| Prompt 长度 $L$ | KV 总量 | 非传输耗时（排队+Prefill） | 10 Gb/s TCP（1.25 GB/s） | 100 Gb/s（12.5 GB/s） | 400 Gb/s IB（50 GB/s） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 512 token | 64 MiB | 36.62 ms | 53.7 ms（59.5%） | 5.4 ms（12.8%） | 1.3 ms（3.5%） |
| 1,024 token | 128 MiB | 53.24 ms | 107.4 ms（66.9%） | 10.7 ms（16.8%） | 2.7 ms（4.8%） |
| 4,096 token | 512 MiB | 152.96 ms | 429.5 ms（73.7%） | 42.9 ms（21.9%） | 10.7 ms（6.6%） |
| 16,384 token | 2,048 MiB | 551.84 ms | 1,718.0 ms（75.7%） | 171.8 ms（23.7%） | 42.9 ms（7.2%） |
| 32,768 token | 4,096 MiB | 1,083.68 ms | 3,436.0 ms（76.0%） | 343.6 ms（24.1%） | 85.9 ms（7.3%） |

读这张表可以立刻建立三条物理边界：

1. **慢网直接判死刑**：10 Gb/s TCP 下，32K Prompt 仅传 KV 就超过 3.4 秒，任何交互式 SLO 都无力回天；跨节点 PD 必须建立在 100–400 Gb/s 级 RDMA 互联之上。
2. **传输占比的渐近律**：线性 Prefill 阶段中，计算量与 KV 体积同步随 $L$ 线性增长，因此同列传输份额随长度趋于平稳；更长序列中 $O(L^2)$ 注意力算力占比抬头后，传输份额还会略降，但绝对毫秒数仍线性上涨。
3. **前缀命中不自动省掉传输**：在 4,096 token 中命中 2,048 token 前缀（$256\text{ MiB}$）可省下 $66.48\text{ ms}$ 的 P 侧算力，但如果目标 D 节点并未驻留这段前缀，这 $256\text{ MiB}$ 仍须经 `P → D` 或 `Store → D` 送达 D 侧。只有所需 KV 已驻留消费端时，对应网络流量才真正归零。

### 现实世界的两个反向修正：有效带宽与逐层重叠

线速表格是重要的量级尺子，但真实集群存在两股方向相反的力量：

- **向下修正——有效带宽低于线速**：协议栈开销、小消息碎片与多租户争用会让实际吞吐低于标称值。例如 Mooncake Transfer Engine 公开测试显示，4×200 Gb/s RoCE（标称 100 GB/s）实测有效聚合约 **87 GB/s（87%）**，8×400 Gb/s（标称 400 GB/s）实测约 **190 GB/s（47.5%）**。
- **向上修正——逐层流水传输（Layer-wise Streaming）**：不必等全部 32 层 Prefill 算完才发送整块 512 MiB！第 0 层刚算完，Transfer Engine 就通过 RDMA 把第 0 层 KV 异步推往 D 节点，与第 1 层的 GPU 计算完全重叠。落入 TTFT 关键路径的，从整段串行耗时缩减为**最后一两层未能被掩盖的尾部传输时长**。

此外，当单条超长 Prompt（如 128K）远超单节点 Prefill 算力时，集群还会采用**分块流水线并行（Chunked Pipeline Parallelism）**把长输入切块跨节点接力计算，仅在块边界同步传递较小的激活值而非每层搬运 KV，代价是切块过细会引入流水线气泡。

## B.4 分布式 KV 池（Mooncake Store）与 Transfer Engine

把闲置 DRAM 和 NVMe SSD 拼成全局 KV 池后，核心机制围绕“块”展开。以典型块大小 **256 token** 为例（Llama-3.1-8B 每块 $256 \times 128\text{ KiB} = 32\text{ MiB}$，4,096 token 对应 16 块），寻址、复制、淘汰与传输全部以块为原子粒度。

### 逻辑块键、热块复制与三级溢出

- **前缀感知哈希（Prefix-aware Hashing）**：每块根据“前缀路径哈希 + 当前块 token 序列”生成全局唯一的**逻辑块键**，用于精确去重与最长前缀匹配；再通过分布式元数据服务映射到持有该块的物理节点、内存地址与副本列表。
- **热块复制与 LRU 淘汰**：系统提示词、热门知识库文档等高频块若只存单副本，必然把所在节点网卡打爆。Mooncake 不依赖复杂离线预测，而是借由请求流自然触发**热块复制**——当某节点拉取热门块计算增量时，副本顺势落盘/留存到该节点分摊后续读压力；空间紧张时，后台按 **LRU（最久未使用）** 优先淘汰未被引用的冷块。热块向外扩散，冷块向下溢出，形成三级存储阶梯：

| 缓存层级 | 物理介质 | 命中收益 | 付出的代价 |
| --- | --- | --- | --- |
| **L1：本地 GPU 显存** | 引擎内置 KV Block Pool | 零重算、零传输，直接参与 Attention | 显存最昂贵、容量最小 |
| **L2：CPU DRAM 池** | 本机或远端节点空闲主存 | 免除 Prefill 重算 | PCIe 拷贝或跨节点 RDMA 传输耗时 |
| **L3：分布式 SSD 池** | 集群 NVMe SSD | 超大历史容量，承载跨小时/跨天长会话 | 读盘延迟 + 跨节点网络传输 |

### 重算 vs 取回：什么时候宁可重算也不读缓存？

前缀缓存命中并不是无条件赚钱的买卖——它是拿**取回时间**去换**重算时间**。以 Llama-3.1-8B 的 2,048-token 前缀（$256\text{ MiB}$）为例，H100 50% MFU 下重算耗时约 **$66.48\text{ ms}$**，对比不同链路的线速取回下限：

- **400 Gb/s IB**：取回仅需 **$5.37\text{ ms}$**（比重算快 $12.4\times$）→ **坚决取回**；
- **100 Gb/s RDMA**：取回需 **$21.48\text{ ms}$**（比重算快 $3.1\times$）→ **通常取回**（需检查队列与网络拥塞）；
- **10 Gb/s TCP**：取回高达 **$214.75\text{ ms}$**（比重算慢 $3.2\times$！）→ **放弃缓存，直接重算更划算**。

### 引擎连接器（Connector）解耦

在现代开源引擎（如 vLLM）中，分布式 KV 池与搬运通道通过**插件化 Connector** 对接（经由 `--kv-transfer-config` 指定角色与后端），将“谁发谁收的解耦协议”与“底层怎么搬数据”分离：

- **`NixlConnector`**：面向 NVIDIA NIXL / UCX / GPUDirect Storage（GDS）生态，适合已有 InfiniBand 与 UCX 基础设施的集群；
- **`MooncakeConnector`**：直接对接 Mooncake Store 与 Transfer Engine，适合需要全局 DRAM/SSD 前缀池与多网卡聚合的长上下文场景；
- **`LMCacheConnectorV1`**：适合与 LMCache 分布式多层 KV 卸载框架协同。

实际部署时，前端通常引入 PD Router/Proxy 关联 P 侧与 D 侧的请求 ID 与协调参数，两侧必须严格锁定相同的模型 revision、Tokenizer 与 KV 精度布局。

## B.5 异构配比、两池卡数推导与故障降级

决定集群投资回报率（ROI）的最后两步，一是算准 P 池和 D 池分别该买多少张卡、买什么卡，二是在节点不可避免地宕机时守住可用性底线。

### 两池卡数公式与 Batch 摊销的决定性作用

在到达率 $\lambda$（req/s）与目标长期装载率 $\rho$（如 $0.8$，留 20% 缓冲吸收到达抖动）下，任一池所需的 GPU 卡数为：

$$
N_{\text{pool}} = \left\lceil \frac{\lambda \cdot t_{\text{gpu}}}{\rho} \right\rceil
$$

沿用全书统一的权重主导 Prefill 模型与带宽主导 Decode 模型（设输入长度 $L$、输出长度 $G$，P 侧产首字故 D 侧执行 $n = G - 1$ 步，批大小 $B$ 摊销权重读取 $W$，累计读取增长中的旧 KV）：

$$
t_P \approx \frac{2 N L}{C \cdot \text{MFU}}, \qquad t_{D,\text{gpu}} \approx \frac{n \cdot W / B + c_{\text{KV}} \left( n L + \frac{n(n-1)}{2} \right)}{\text{BW}}
$$

在 **H100 80GB SXM**（$989.5\text{ TFLOPS}$、$3.35\text{ TB/s}$、50% MFU）运行 Llama-3.1-8B（$W = 16.06\text{ GB}$、$c_{\text{KV}} = 128\text{ KiB}$）下，对比两种典型业务负载形状：

| 负载形状 | P 单请求 GPU 卡时 | D 卡时（$B=1$） | D 卡时（$B=32$） | 理论卡数比 $P:D$（$B=1 \to B=32$） | $\lambda=100\text{ req/s}, \rho=0.8$ 配卡（$B=32$） |
| --- | ---: | ---: | ---: | --- | --- |
| **常规对话（2,000 in / 200 out）** | 64.92 ms | 970.36 ms | 46.16 ms | $1 : 14.95 \;\longrightarrow\; \mathbf{1.41 : 1}$ | **P = 9 卡，D = 6 卡** |
| **长文摘要（4,000 in / 20 out）** | 129.84 ms | 94.07 ms | 5.83 ms | $1.38 : 1 \;\longrightarrow\; \mathbf{22.28 : 1}$ | **P = 17 卡，D = 1 卡** |

!!! note "工程取舍：为什么“1:4 固定配比”是危险的教条"
    1. **Batch 摊销逆转比例**：常规对话下，如果按 $B=1$ 粗算会以为 D 池需要 122 张卡；但 D 池靠连续批处理在 $B=32$ 下摊薄权重带宽后，单请求卡时骤降至 $46.16\text{ ms}$，P 池卡数反而超过 D 池！
    2. **同时过显存容量关**：4,000-token 上下文在 $B=32$ 时仅初始 KV 就占 $15.625\text{ GiB}$，加上生成期增长、权重与工作区，须校核单卡真实 KV 池上限与目标 ITL；而且低到达率或极短输出场景未必能攒满 $B=32$。
    3. **异构选卡（Splitwise 思路）**：如果 D 池长期受带宽/容量限制而算力闲置，可将 D 池换成单位带宽成本更低或功耗更低的型号，P 池保留高算力 SXM 卡，在同预算下显著抬高集群总 goodput。

### 联合扩缩容信号与三层容错边界

单看 TTFT 会滞后（告警响起时队列已堆高），单看 `num_requests_waiting` 会超前（瞬时毛刺误触发扩容）。集群扩缩容必须把**等待深度、延迟与队列斜率**合起来判读，同时配合健康检查与死锁兜底：

| 观测信号 | 根因诊断 | 标准运维动作 |
| --- | --- | --- |
| `num_requests_waiting` 持续攀升 + TTFT 同步恶化 | 真实容量不足 | 定向扩容瓶颈侧（P 排队扩 P 池，D 排队扩 D 池） |
| `num_requests_waiting` 瞬时冲高回落 + TTFT 平稳 | 短暂流量突发 | 保持不动，靠准入缓冲平滑吸收 |
| TTFT 上涨，但排队深度几乎为 0 | 非排队瓶颈 | 排查 Prompt 长度分布右移、前缀命中率骤降或 RDMA 拥塞 |
| TBT/ITL 上涨，TTFT 稳定 | Decode 侧吃紧 | 检查 D 池 batch 膨胀、KV 池紧张或 D 节点掉队 |
| 心跳连续 2 次失败（如 5 s × 2 = 5–10 s） | 节点宕机或失联 | 路由器摘除故障节点，新流切走，在途请求按 ID 幂等重算 |
| D 侧等待 KV 超时（如 SGLang 默认 300 s） | 对端失联死锁兜底 | 强制失败释放 D 侧槽位（可靠性兜底参数，绝非性能优化旋钮） |

**定量评估故障影响面**：假设健康检查周期 5 秒、连续 2 次失败摘除（名义检测窗口上限 10 秒），故障发生前流向该 P 节点的到达率为 $10\text{ req/s}$，每条请求为 4,000-token 无复用输入（单条重算 $129.84\text{ ms}$ + 400 Gb/s 全量传输 $10.49\text{ ms}$）。在 10 秒检测窗口内，至多有 $100$ 条新请求被误派至故障节点，故障摘除后需要健康池额外消化 **$12.98\text{ s}$ 的 P 侧 GPU 卡时** 与 **$1.05\text{ s}$ 的串行网络传输量**（另加故障瞬间已在途的请求），恢复耗时取决于健康 P 池预留的 $1-\rho$ 余量。这正是预留装载率冗余（如 $\rho = 0.8$）与快速隔离路由器的定量价值。

## 本专题小结

大规模集群 PD 的全部设计可以收束为四本可计算的账本：**网络传输下限**（决定能不能拆）、**前缀重算与取回的交叉点**（决定要不要建共享 KV 池）、**含 Batch 摊销的两池卡数比**（决定 P/D 怎么配比与选型），以及**检测窗口内的误派恢复代价**（决定容错与余量怎么留）。至于 DistServe、Splitwise 与 Mooncake 三篇里程碑论文各自的实验条件、测试床与“有效请求容量”口径边界，可移步 [专题 D：各章核心论文精读与数据口径](paper-notes.md) 深入对照。
