# 专题 C：端侧与浏览器 LLM 推理运行时 { .chapter-title }

<p class="chapter-summary">端侧推理绝非数据中心服务的缩小版：没有并发排队，量化是入场门票，冷加载与发热降频成为一等约束。</p>

全书主线聚焦于数据中心的多用户推理服务（vLLM、SGLang、TensorRT-LLM 与国产集群卡）。然而在实际产品落地中，大量离线隐私对话、桌面代码补全、移动终端助手以及零后端成本的网页应用，选择把模型直接搬到用户的手机、笔记本甚至浏览器标签页里执行。

许多熟悉数据中心调优的工程师第一次接触端侧推理时，会下意识地把“连续批处理”“并发拐点”“KV 分页共享”搬过去，结果发现几乎处处失灵。核心原因在于：**两者的模型数学完全相同，但操作面与物理约束截然相反**。本专题系统拆解主流端侧运行时、六大操作面差异、四大硬件约束算术，以及数据中心经验的迁移边界。

---

## C.1 三类代表性端侧运行时版图

面向终端设备的客户端推理生态，按部署形态大致分为三类代表运行时（注意：TensorRT-LLM 是面向 NVIDIA 数据中心 GPU 的服务端引擎，与 vLLM、SGLang 同属 [第 10 章](../chapters/chapter-10.md) 范畴，不归此类）：

| 代表运行时 | 核心定位与载体 | 模型格式与量化主力 | 底层硬件后端 | 典型工程优势与限制 |
| --- | --- | --- | --- | --- |
| **llama.cpp** | 零外部依赖 C/C++ 原生端侧引擎（桌面 / 手机 / 嵌入式） | GGUF 格式；K-quants / I-quants（Q4_K_M、Q3、IQ2 等极低比特） | CPU（AVX-512 / NEON / AMX）、Apple Metal、CUDA、Vulkan、SYCL | 社区跟进新架构最快，`mmap` 秒级加载；多用户高并发服务能力弱于 vLLM |
| **ONNX Runtime GenAI** | 跨平台企业级图执行运行时（Windows / macOS / Android / iOS） | ONNX 计算图 + INT4/INT8 块量化（AWQ / RTN） | DirectML、CoreML、Qualcomm QNN、Android NNAPI、CUDA | 与工业客户端和移动 NPU 生态对接规范，图级融合统一；新模型导出链路相对重 |
| **WebLLM（MLC-LLM + WebGPU）** | 浏览器沙箱内零安装推理运行时 | MLC 编译产物 + 分片权重（q4f16_1 等） | 浏览器 WebGPU API（WGSL Shader） | 打开网页即用、彻底零服务端成本；受限浏览器单页内存上限、首次下载体积与 WebGPU 兼容性 |

这三类运行时的共同特征是**直接运行在不可控的终端用户硬件上**，没有机房恒温供电，没有运维团队统一升级驱动，也没有成百上千的并发请求帮你摊薄显存带宽。

## C.2 数据中心服务 vs 端侧运行时：六大本质操作面差异

把数据中心推理服务和端侧运行时并排拆解，两者的差异全部落在操作面上：

| 操作面维度 | 数据中心推理服务 | 端侧与浏览器运行时 |
| --- | --- | --- |
| **1. 运行位置与供热** | 机房专用加速卡，300–700 W 持续供电与强散热 | 手机、笔记本 CPU/iGPU/NPU 或浏览器沙箱，5–45 W 热包络 |
| **2. 请求来源与并发** | 网络接入，数十至数百用户同时并发，核心靠 Batch 提效 | 本机独占，**绝大多数时刻 $B = 1$**（一次只服务一位用户） |
| **3. 核心体验指标** | TTFT、ITL/TPOT、总吞吐（tok/s）、p99 尾延迟、排队深度 | **能否成功加载**、冷加载耗时、首字等待、内存峰值、热稳态速度与耗电 |
| **4. 容量规划边界** | 并发扫描曲线、SLO 拐点、多请求 KV 池预算 | 设备物理内存上限、App 包体 / 浏览器 Cache 限额、操作系统 OOM 强杀线 |
| **5. 分发与版本控制** | 服务端灰度发布，硬件与驱动环境高度统一 | 模型与运行时随客户端分发，设备型号、驱动与浏览器版本极度碎片化 |
| **6. 典型生产故障** | 队列过载、KV 显存抢占、网络拥塞、多卡通信超时 | 权重下载中断、WebGPU 驱动不兼容、系统内存强杀、连续对话发热降频 |

!!! tip "核心直觉：指标重心从“服务容量”变为“能否活着跑流畅”"
    数据中心服务的核心命题是“在 SLO 内多接几路并发以压低单 token 成本”；端侧运行时的核心命题是“先别被系统 OOM 杀掉，再在单用户 $B=1$ 且不烫手的前提下，把生成速度做到快过人类阅读速度（约 10–15 token/s）”。

## C.3 端侧推理的四大硬约束算术

理解端侧优化的全部技巧，只需算透四笔硬约束账。

### 约束一：内存墙——量化从“优化项”变成“入场门票”

在数据中心里，8B 模型的 FP16 权重（16 GB）只占 A100 80GB 显存的 20%，量化往往是为了提吞吐或装下更大并发；但在端侧，**不量化根本进不了门**。算一笔最直白的体积账：

| 模型规模 | FP16 权重 | INT8 权重 | 4-bit 量化（含 Group Scale） | 典型落点设备 |
| --- | ---: | ---: | ---: | --- |
| **0.5B–1.5B** | 1.0–3.0 GB | 0.5–1.5 GB | 0.35–1.0 GB | 手机 App、浏览器 WebLLM（轻量秒开） |
| **3B–4B** | 6.0–8.0 GB | 3.0–4.0 GB | 2.0–2.8 GB | 旗舰手机（12–16 GB 内存）、主流浏览器 |
| **7B–8B** | 14.0–16.0 GB | 7.0–8.0 GB | 4.5–5.2 GB | 16 GB+ 笔记本（统一内存 / 独显） |

移动操作系统（iOS / Android）通常只允许单个前台 App 占用 3–6 GB 内存，浏览器单标签页的 WebGPU 缓冲区限额往往在 2–4 GB 左右。此外，[第 2 章](../chapters/chapter-02.md) 的 KV 缓存账在端侧丝毫不打折：以 Llama-3.1-8B（$128\text{ KiB/token}$）为例，4,096 token 上下文需 $512\text{ MiB}$，8,192 token 即占 $1\text{ GiB}$，叠加运行时激活缓冲很容易击穿端侧内存红线。因此端侧普遍将 **4-bit 权重量化（W4A16）+ 8-bit/4-bit KV 量化 + 有限上下文滑动窗口** 作为标配组合。

### 约束二：冷加载与首字延迟（TTFT）必须严格分离

端侧用户第一次提问时的等待感由两段性质完全不同的时间拼成：

$$
T_{\text{first-use}} = \underbrace{T_{\text{download}} + T_{\text{disk/mmap read}} + T_{\text{shader/graph compile}}}_{\text{一次性冷加载成本}} + \underbrace{T_{\text{prefill}} + T_{\text{decode},1}}_{\text{每次推理 TTFT}}
$$

- **一次性冷加载**：包括首次网络拉取数 GB 分片权重（WebLLM 存入 IndexedDB / Cache API）、从闪存读入内存，以及 Metal/WebGPU 首次编译计算着色器（Shader）。`llama.cpp` 大量依赖操作系统的 `mmap` 内存映射实现按需页加载与免拷贝，把冷启动压到秒级；
- **单次推理 TTFT**：模型驻留内存后的真实 Prefill 与首个解码步耗时。

如果评测时不把两者拆开，40 秒的首次下载或 8 秒的 Shader 编译会彻底淹没 300 毫秒的 Prefill 差异，导致优化方向完全跑偏。

### 约束三：$B=1$ 无批处理下的极端权重带宽主导

端侧几乎永远运行在 $B = 1$，不存在数据中心的连续批处理来把权重读取摊到 32 条请求上。每生成一个 token，计算单元仍必须把整份模型权重从内存完整扫一遍，算术强度死死钉在 $\text{AI} \approx 1\text{–}2\text{ FLOP/B}$：

$$
\text{Decode 吞吐上限} \approx \frac{\text{有效内存带宽}}{\text{量化后权重字节数} + \text{单步 KV 读取量}}
$$

拿一款 4-bit 量化后约 **$4.8\text{ GB}$** 的 8B 模型，在三类典型端侧带宽下估算纯权重搬运天花板：

- **旗舰手机 LPDDR5X**（标称 ~60–75 GB/s，实际可用约 50 GB/s）：$50 / 4.8 \approx \mathbf{10.4\text{ tok/s}}$；
- **轻薄本统一内存**（如 Apple M 系列基础款 100–150 GB/s，可用 ~110 GB/s）：$110 / 4.8 \approx \mathbf{22.9\text{ tok/s}}$；
- **工作站级统一内存**（如 Apple M Max/Ultra 400–800 GB/s，可用 ~320 GB/s）：$320 / 4.8 \approx \mathbf{66.7\text{ tok/s}}$。

这笔算术直接解释了端侧硬件形态的胜负手：第一，**统一内存架构（Unified Memory）** 让 GPU/NPU 直接共享高带宽主存且免去 PCIe 拷贝，在大容量端侧推理中天然占优；第二，在 $B=1$ 场景下，将权重从 FP16（16 GB）压到 Q4（4.8 GB）几乎直接把解码速度抬高 **3 倍以上**，配合 [第 15 章](../chapters/chapter-15.md) 的**融合反量化算子（Fused Dequant）** 避免把反量化后的 FP16 权重写回内存，是端侧提速的绝对第一杠杆。

### 约束四：功耗、续航与发热降频（Thermal Throttling）

数据中心 GPU 可以在满功耗下 24 小时稳定跑在同一频率；手机和无风扇轻薄本在满载运行 LLM 30–60 秒后，SoC 结温触及温控阈值，系统强制降低 CPU/GPU/NPU 主频与内存频率（降频幅度常达 **30%–50%**）。

因此端侧性能评估必须明确区分两个数字：
- **冷机峰值速度（Burst Speed）**：设备常温下前 1–2 轮短回答的瞬时生成速度；
- **热稳态持续速度（Sustained Thermal Speed）**：连续生成 5 分钟后的稳态 ITL 与机身温度/电量消耗。

在移动端，将长 Prompt 的 Prefill 卸载到高能效比 NPU、Decode 留在高带宽 GPU/CPU，或在后台任务中主动限速以防降频，都是数据中心完全不存在的特有工程权衡。

## C.4 数据中心经验迁移指南：哪些能带走，哪些必须重写

离开机房走向终端时，清晰的迁移边界能帮你省下大量弯路：

| 知识与工程模块 | 能否直接迁移到端侧？ | 工程落地说明 |
| --- | --- | --- |
| **Roofline 三区间判断** | **可直接复用** | Decode 极端受内存带宽限制、长 Prompt Prefill 转向算力受限的物理规律完全不变 |
| **参数与 KV 容量算术** | **可直接复用** | $2 L n_{\text{kv}} d_h b$ 公式一字不改；端侧反而更需精算每一百 MiB 显存 |
| **权重量化与融合反量化** | **高度放大** | W4A16、混合比特（K-quants）与 KV 量化成为端侧第一优先级优化手段 |
| **前缀 KV 复用（Prompt Cache）** | **思想复用，实现简化** | 无需集群分布式池，单用户只需在本地内存/磁盘保留系统提示词与多轮会话 KV 快照即可显著降 TTFT |
| **投机解码（Draft-Verify）** | **条件适用** | 在 $B=1$ 下小模型起草同样存在加速空间，但受限于端侧双模型内存占用，常用轻量 N-gram 或极小草稿头 |
| **连续批处理 / 并发拐点扫描** | **无落点，需舍弃** | 单用户 $B=1$ 无请求级排队与批处理权衡；压测工具（如 `bench_openai.py`）须换为单路本地冷/热/稳态采样 |
| **Prometheus / 集群 PD / K8s 扩缩容** | **完全不适用** | 客户端无中心监控抓取与高速 RDMA 互联，取而代之的是客户端遥测、内存水位保护与离线缓存管理 |

!!! warning "常见误区：不要抄别人的端侧跑分数字"
    数据中心同一型号 H100 跑同一容器，吞吐通常落在同一量级；而端侧设备受具体内存通道配置、后台驻留进程、操作系统温控策略和浏览器 WebGPU 驱动版本影响极大，同一型号手机在充电与未充电、冷机与热机下的 token/s 都能差出近一倍。端侧任何性能结论都必须绑定**具体设备型号、内存规格、运行时版本、量化格式与热状态**。

## 本专题小结

摸清端侧运行时的边界，能让你反过来更深刻地理解数据中心推理架构为什么长成今天这样：数据中心用“大批量 + 高功耗 + 统一调度”把单次权重搬运摊薄给几十个用户；端侧则在“$B=1$ + 严苛内存与功耗墙”的夹缝里，把低比特量化、统一内存带宽与本地缓存压榨到极致。两者同根同源，底层仍是 [第 1 章](../chapters/chapter-01.md) 的 Roofline 物理定律。
