# 统一实验约定：条件、原始记录与验收

从第一份基线到跨芯片终稿，升级同一份实验记录。先写问题、条件与验收门槛，再跑实验；表格里的数字应能回到原始文件，而不是由结论反推。

[快速上手](quickstart.md) · [基线报告模板](modules/M0-foundations/baseline-report-template.md) · [跨芯片报告模板](modules/M3-domestic-chips/cross-chip-report-template.md)

## 1. 先区分被测对象与验证阶段

| 实验类型 | 能得到的证据 | 不能宣称 |
|---|---|---|
| 纸面推导 | 在明确模型/硬件假设下的数量级、上下界 | 实测性能、实际支持能力 |
| CPU mock SSE | 解析、计时、并发脚手架与结果格式 | GPU/NPU 性能、真实服务容量 |
| 参考配方/源码核对 | 接口位置、语法和可执行设计 | 编译通过、后端命中或实机性能 |
| 真实模型/内核实验 | 对应设备、版本、负载下的实际记录 | 未测模型、版本或负载上的通用胜负 |

环境要求、验证阶段和证据等级是三件事。分别写清楚：**语法已核对 → 目标环境编译 → 实际设备执行 → 路径确认 → 性能/质量测量**。只完成前一步不能勾选后一步。

CPU mock 也可以有实际测量记录，但对象必须写 `cpu-mock`；它不能替代真实模型性能表中的空格。

## 2. 每个结果都有条件与编号 { #records }

推荐编号为“平台-实验-并发-重复号”。一次扫描可用统一 `test_id`，每档再结合并发和请求 ID 唯一定位。

| 记录 | 最少包含 |
|---|---|
| 条件文件 `conditions_id` | 日期、平台、设备/数量/互联、模型与权重 revision、tokenizer、精度、驱动/运行时/引擎/插件版本、服务命令 |
| 负载配置 | 实际输入/输出长度、prompt 来源或文件、采样参数、缓存状态、到达模型、客户端并发、请求数、预热/正式窗口、超时 |
| 原始结果 `raw_path` | `test_id`、条件编号、成功/失败/超时、token 来源、逐请求时间与长度、汇总及样本量 |
| 对照记录 | 唯一改动、保持不变的条件、正确性与质量判据、前后测量、调用路径证据 |

[压测客户端](modules/M0-foundations/scripts/bench_openai.py)使用 `--test-id`、`--conditions-id` 和 `--output` 把一次扫描关联到条件文件。保存生成的完整 JSON，不只截取终端表格。

条件编号必须能找到真实条件文件；它不是写在命令里的装饰字符串。报告版本、原始数据文件名和环境锁定文件一起保存。

!!! warning "发布前检查敏感信息"
    条件与结果可能含有 prompt、命令或内部环境信息。不要记录或发布 API key、SSH 凭据、私有模型 token；原始数据需要脱敏时保留方法说明，不悄悄删除影响统计的失败记录。

## 3. 固定口径，但不要制造“固定长度”的假象

- 固定文本不等于固定 token 数。不同 tokenizer、聊天模板或模型会产生不同输入长度。
- `max_tokens` 是上限，EOS 可以提前结束。保存每请求实际 `prompt_tokens/completion_tokens`，没有 usage 时标明估计来源。
- 微基准可以固定长度以隔离变量；服务容量还应覆盖真实长度分布与到达节奏，二者分别报告。
- 明确缓存冷/热、前缀复用开关和命中状态。相同 prompt 的重复测量可能主要测到缓存收益。
- 温度 0 不保证逐位复现；保存相同采样条件，重复运行并报告波动。

## 4. 客户端时间与设备时间分开

| 量 | 本书的客户端口径 | 边界 |
|---|---|---|
| TTFT | 请求发出到首个非空 `delta.content` chunk 到达 | 不是首个 role/usage JSON；可能含排队、网络、缓冲与解析 |
| ITL | 相邻内容 chunk 的到达间隔 | chunk 可以带多个 token，属于 token 间隔的近似，不可还原隐藏间隔 |
| TPOT | 首末内容时间差 / `(实际输出 token 数−1)` | 输出不足两个 token 或只有一个内容 chunk 时不报告；chunk 聚合仍影响近似 |
| 吞吐 | 成功请求的输出 token 总数 / 整个测量窗口 | 失败耗时仍留在窗口；估计 token 与精确 usage 不能混作同等证据 |
| 设备耗时 | Events、设备事件或目标 profiler 的执行时间 | 不等于客户端 TTFT；带 profiler 的测量另作诊断记录 |

同时报时间单位、样本量与分位数算法。本书客户端用线性插值 `(n−1)q`。20 个请求的经验 p99 可以计算，但尾部估计不稳定；不能因为样本数刚过 100 就宣称“p99 已量准”。多个同请求 ITL 样本也不是彼此独立的请求样本。

## 5. 配置并发不是稳态在途数

客户端并发 C 是在途请求的上限，不是设备同时执行的序列数。请求总数 N 小于 C 时连该上限都不可能达到；脚本应拒绝这类配置。

有限工作负载会经历启动、补请求与排空。保存请求数、可达到的上限、观察到的峰值/平均在途数，不把配置 C 直接代入稳态 Little 定律。稳定开放系统使用 `L=λW`；稳定闭环使用观察到的平均在途数、完成率与平均停留时间，并说明失败/超时如何计入。

正式容量测试从低负载扫到拐点及过载段，记录 TTFT/ITL、吞吐、成功率、排队、缓存和抢占。**过载段可发表为边界证据，但不能当满足 SLO 的服务容量。** 1000 个客户端在途请求不等于 1000 条 KV 序列同时驻留，也不是必须达成的考核数。

## 6. 手算是下界与假设，不是跑分

计算与实际搬运的必要时间下界为：

```text
T_compute >= F / P_peak
T_memory  >= D / BW_peak
T_execute >= max(F / P_peak, D / BW_peak)
```

重叠能让串行相加的时间趋近于最大项，不能突破同一运算量、实际搬运量与峰值口径的下界。启动、同步、资源利用不足和数据依赖另计。若算出的字节是逻辑请求量而非实际 HBM 流量，还要核实缓存与复用，不能将它直接视为不可突破的物理限制。

硬件规格至少写明型号、精度、Tensor Core/普通计算、稠密/稀疏和带宽口径。例如 H100 SXM 的 FP16 Tensor Core 稠密峰值约 989.5 TFLOPS，约 494.5 是 TF32 稠密口径，不能互换；参见 [NVIDIA 规格](https://www.nvidia.com/en-us/data-center/h100/)与[架构表](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/)。

驱动、Toolkit 和框架运行时分别记录。容器并不锁住宿主驱动；`nvidia-smi` 的 CUDA 字段只是驱动支持上限。

## 7. 每次优化重新过四道门 { #acceptance }

1. **数值正确性**：相同输入、dtype、形状和精度约定；覆盖零值、极小值、非整除形状、掩码与异常值。容差按算子与数值范围预先规定。
2. **路径真实生效**：注册、启用、分发、设备事件或 kernel 名能对齐；API 成功不等于自写算子被调用。PD 另确认协调协议、外部 KV 命中与传输字节。
3. **任务质量通过**：使用同题配对记录、相同评分和采样条件；优化后的配置重新评测，不能沿用优化前的质量表。
4. **性能/成本满足目标**：同负载对照并重复运行，报中位数/范围、SLO 与负面结果，而不是只报最好一次。

“不显著”不等于“质量通过”。例如准确率越高越好的任务，提前规定允许退化 δ，并用配对数据估计优化后减基线的变化 Δ；只有相应区间满足预定非劣门槛，才可写质量通过。缺少逐题配对数据或样本不足时标为证据不足。

利用率百分比只作初筛。分块后字节数与耗时一起下降时，DRAM% 仍可能很高；等待中的 warp 仍可能驻留。归因使用实际流量、耗时、缓存、就绪/发射/stall 等证据，并做只改一个因素的对照。

## 8. 状态与证据等级 { #evidence }

结果状态采用 `measured / pending / failed / invalid`；另记录证据等级：

| 等级 | 证据 | 写法 |
|---|---|---|
| A | 同条件多次运行的原始数据、条件与日志 | 在本实验条件下测得，并报告波动 |
| B | 单次真实运行或重复不足 | 单次测得，重复性待验证 |
| C | 论文、厂商、他人报告 | 来源宣称，注明它的条件与基线 |
| D | 纸面估算、假设或未运行设计 | 估算/预期，不冒充本机测量 |
| X | 条件不可比或记录不可复现 | 不用于性能或质量结论，只记录原因 |

教学算例统一标 D，不因为“假设来自单次实验”就改标 B。未做对照的机制写候选原因，不写确定因果。

版本或环境改变时重新核对；旧记录仍是旧条件下的证据，不因三个月过去而自动失真。报告注明适用边界与重测触发条件，最终在[第 31 章](chapters/chapter-31.md)将同一份记录升级为可复现终稿。
