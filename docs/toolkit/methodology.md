# 测量口径与对比分析方法 { .chapter-title }

<p class="chapter-summary">性能数字脱离计时边界、控制变量与质量门槛就无法归因；本手册收敛全书统一的测量口径、优化检验法则与 Benchmark 评审准则。</p>

推理工程中一半的争论来自“数字对不上”：客户端测的 TTFT 和服务端 Grafana 面板差出几十毫秒；开启某项优化后吞吐翻倍，上线却发现回答质量悄悄退化；或者同一台机器测出截然不同的 p99。这些问题往往不是工具坏了，而是**计时边界、控制变量与验收门槛没有事先统一**。

本手册将 [第 3 章](../chapters/chapter-03.md)、[第 4 章](../chapters/chapter-04.md)、[第 7 章](../chapters/chapter-07.md) 与 [第 23 章](../chapters/chapter-23.md) 的度量方法浓缩为一套可直接对照查阅的工程参考准则。

## 一、客户端 vs 服务端计时口径边界

同一指标在客户端、服务端引擎与 GPU 硬件上量的是不同区间。把不同观测面的数字混在一张表里比较，会制造根本不存在的“提速”或“回退”。

| 指标 | 客户端流式观测口径 | 服务端 / 设备侧口径 | 关键边界与常见陷阱 |
| --- | --- | --- | --- |
| **TTFT** | 请求发出至收到**首个非空 `delta.content` chunk** | 引擎前端收到请求（含分词、排队、`SCHEDULED` 至首 token） | 首个 SSE 事件可能只含 `role` 或空字符串，绝不能触发 TTFT；客户端比服务端多含网络往返、代理缓冲与反序列化 |
| **ITL** | 相邻两个非空内容 chunk 的到达间隔 | 引擎相邻两次流式发射的时间间隔 | 单个 SSE chunk 可能打包多个 token，客户端 ITL 属于 **chunk 级近似**，切忌拆分虚构逐 token 时间戳 |
| **TPOT** | $\dfrac{t_{\text{last}} - t_{\text{first}}}{N_{\text{out}} - 1}$（要求 $N_{\text{out}} > 1$ 且至少 2 个内容 chunk） | 服务端每完成请求记一个样本 | 仅输出 1 个 token 时数学上未定义（客户端应记 `null` 而非 `0`）；注意 vLLM 指标与 `vllm bench serve` 对 1-token 请求的分母处理差异 |
| **端到端总延迟** | 请求发出至读完 `[DONE]` 或判定失败 | `arrival_time` 至末 token 完成 | 末内容之后还有 `usage` 帧与连接关闭开销，不可用总延迟替代 $t_{\text{last}}$ 算 TPOT |
| **系统吞吐** | 成功请求的输出 token 总数 $\div$ 完整压测窗口时长 | `sum(rate(vllm:generation_tokens_total[w]))` | 失败与超时请求不贡献分子产出，但其占用的窗口时长仍在分母内；输入 tok/s、输出 tok/s 与 req/s 须分开报告 |
| **设备执行耗时** | 无法直接从 HTTP 层观测 | CUDA Events（同步后读差）或硬件 Profiler | **带 Profiler 的耗时绝不当作性能成绩**（尤其 `ncu` 重放内核会扰动缓存与时钟）；计时与诊断必须分两次采 |

### 分位数、长尾与样本量直觉

平均值会瞬间掩盖严重的用户卡顿，而**只看单一 p99 同样有盲区**：

- **分位数算法须注明**：对排序后的 $n$ 个样本，线性插值使用零基秩 $r = (n - 1) q$，而 nearest-rank 使用 $\lceil n q \rceil$。例如 100 个样本中 99 个为 $100\text{ ms}$、1 个为 $200\text{ ms}$，线性插值下均值和 p99 都是 $101\text{ ms}$，但最慢用户实打实等了 $200\text{ ms}$。报告尾延迟时，建议同时列出 **p50 / p95 / p99 / max** 与样本量 $n$。
- **小样本无法锁定 1% 长尾**：若真实尾部事件的发生概率为 $1\%$，随机采样 $n = 100$ 次时，**一次尾部都碰不到的概率高达**：

$$
(1 - 0.01)^{100} \approx 36.6\%
$$

即使采样 1,000 次，期望也仅命中 10 个尾部样本；此外同一请求内部的多个 ITL 样本并非彼此独立。因此正式容量评估需保证充足请求数、执行多次重复并报告中位数与波动范围，绝不拿 20 条冒烟请求的经验 p99 做容量承诺。

## 二、控制变量清单：让性能差异可归因的五条铁律

做任何横向对比（换引擎、换量化、换算子、换芯片）时，必须把非目标变量钉死：

### 1. 模型、权重与 Tokenizer 对齐

- 锁定完全一致的模型仓库 **revision / commit hash**、量化格式参数、Tokenizer 与聊天模板（Chat Template）。
- **固定自然语言原文 $\neq$ 固定 token 数**：不同模型分词器对同一篇文档切出的 token 数差 4% 属常态（见 [专题 A](../topics/advanced-architectures.md)）。比较系统算力/显存结构时对齐 token 数，比较端到端业务效果时对齐同一原文。
- 优先使用服务端返回的 `usage.prompt_tokens` 与 `usage.completion_tokens`；若缺失 `usage` 而退化为字符数估算（如 `len(text) // 4`），中文与代码误差极大，必须显式标出且不与精确统计混用。

### 2. 实际输入输出长度 vs 上限参数

- `--max-tokens` 仅仅是输出上限，模型随时可能提前生成 `EOS` 结束；即使将 `temperature = 0`，跨硬件或跨批大小下微小浮点差异也可能改变停止位置。对比表格中必须报告**实际观察到的输入/输出长度分布**（p50/p95），而非只写配置上限。
- 固定长度合成流量适合受控微基准（隔离长度方差），但生产容量规划必须补充贴近业务的真实长度分布与到达节奏，二者分开汇报。

### 3. 缓存冷热与前缀复用状态

- 服务冷启动的前若干请求会触发内核编译、CUDA Graph 捕获、显存池初始化与 GPU 时钟爬升，必须先执行充分预热再进入正式计时窗口。
- 明确标注**前缀缓存（Prefix Cache / RadixAttention）的开关状态与命中率**。向服务端循环发送同一条 Prompt 测出来的往往只是缓存命中速度，而不是真实 Prefill 算力。

### 4. 并发模型、稳态窗口与 Little 定律边界

- 明确区分**开环压测**（按固定到达率或泊松过程独立发包，最贴近真实线上流量）与**闭环压测**（固定 $C$ 个工作线程，收到一条再发下一条）。
- 客户端并发上限 $C$ **绝不等于**服务端实时 Batch Size，也不等于稳态在途请求数：有限批次压测天然包含前期爬坡与末尾排空阶段。仅在一致的稳态观测边界内，Little 定律才严格成立：

$$
L = \lambda \cdot W
$$

其中 $L$ 为该边界内时间平均在途请求数，$\lambda$ 为实际完成速率，$W$ 为平均停留时间（注意不是 p50 或 p95）。
- **稳态 SLO 容量与过载退化必须分开报告**：当到达率持续高于系统最大吞吐时，队列和延迟随测试时长线性无界膨胀，此时的 p95 只是测试时长的函数。过载段适合作为抢占/恢复边界记录，绝不能当作可持续容量。

### 5. 软硬件栈与算力口径锁定

- 分别记录宿主驱动/固件版本、实际 CUDA Toolkit / Runtime（或 CANN Toolkit / Ops / NNAL）、PyTorch、推理引擎及硬件插件版本号，容器镜像记精确 tag 或 digest（容器锁住用户态，**不锁定宿主驱动**）。
- 注意 **`nvidia-smi` 右上角显示的 CUDA 版本只是当前驱动支持的最高上限**，不代表容器或环境中实际链接执行的 CUDA Runtime 版本。
- 物理下界推导严格遵守 [硬件规格与模型账本速查](hardware-models.md) 的稠密算力与单位约定，记住理论下界由算力与实际访存共同限定：

$$
T_{\text{execute}} \ge \max\!\left(\frac{F}{C_{\text{peak}}},\; \frac{D_{\text{actual}}}{\text{BW}_{\text{peak}}}\right)
$$

其中 $D_{\text{actual}}$ 是穿透至 HBM 的真实流量；若计算逻辑流量时未扣除 L2 缓存复用，实测快于“逻辑下界”说明缓存命中发挥了作用，而非突破物理极限。

## 三、优化四重检验法则

无论是上线一个量化配置、替换一个自定义 Triton/AscendC 算子，还是切到 PD 解耦架构，任何一项工程改动宣称“有效”前必须依次通过四道门：

```text
[1] 数值正确性  ──▶  [2] 路径真实生效  ──▶  [3] 任务质量无退化  ──▶  [4] 同负载性能与成本收益
    覆盖边界形状          杜绝静默回退           同题配对非劣检验          多档重复与负结果留档
```

1. **数值正确性**：在相同输入、dtype、shape 下对照参考实现，显式覆盖零值、极小值、非整除尾块、因果掩码与离群大值；按算子数值域预先规定 `atol` / `rtol`（近零输出切忌仅看相对误差）。
2. **路径真实生效**：HTTP 200 OK 绝不证明新路径被调用。自定义算子需核对插件注册日志、分发钩子与 Profiler 中的真实 kernel 名称；量化需确认没有因计算能力不足静默回退（如 CC < 8.9 时 FP8 回退 W8A16）；PD 解耦需在日志与 trace 中同时看到 P 增量计算、D 外部 KV 命中与实际传输字节。
3. **任务质量无退化**：使用同一批题库、同一采样参数和同一判分脚本做**同题配对评测**，提前定好业务允许的最大退化阈值 $\delta$，用配对差值区间验证非劣。切记统计学铁律：**“检验结果不显著”不等于“质量无损”**（小样本下检验功效不足同样会给出“不显著”）。
4. **同负载性能与成本收益**：在相同软硬件预算与负载下扫描多档并发，每档多次重复报告中位数与波动区间，同时检查 TTFT、ITL/TPOT、吞吐、显存与错误率。若某项优化没变快甚至变慢，同样保留为有价值的工程结论并果断回滚。

!!! tip "关于 Profiler 百分比归因的一条补充原则"
    看到“某算子占 80%”或“DRAM 利用率 85%”时，先追问分母和绝对流量：若优化分块后搬运字节与耗时同步腰斩，DRAM% 反而可能升高；等待访存的 Warp 依然计入 Active Occupancy。性能归因永远结合**绝对耗时、真实读写字节、缓存命中率与调度器 Ready/Stall 计数**，并配单变量对照验证。

## 四、发表或评审一份推理 Benchmark 前的 8 项核心自查

无论是自己撰写技术报告，还是评审第三方厂商的推理跑分图，对照这 8 条清单，十秒内就能看出水分藏在哪里：

- [ ] **是否扫描了请求速率 / 多档并发？** —— 只测单一并发点是轶事，不是容量曲线；没有拐点就无法做容量规划。
- [ ] **是否报告了实际输入与输出 token 长度分布？** —— KV 显存、Prefill 算力与吞吐高度敏感于长度，只写 `max_tokens` 或模糊的“约 1K”会导致结论不可比。
- [ ] **是否同时报告了 p50、p95、p99（及 max 与样本量）？** —— 平均值掩盖长尾，小样本 p99 抖动剧烈，单看一个数字极易误判真实用户体验。
- [ ] **是否把 TTFT 与 ITL / TPOT 分开报告？** —— 把计算密集的 Prefill 和带宽密集的 Decode 揉成一个“总延迟”，会彻底摧毁瓶颈定位与优化方向。
- [ ] **是否区分了稳态 SLO 容量与过载/抢占段，并保留全部失败与超时？** —— 剔除超时请求后算出来的 p95 是幸存者偏差，过载积压延迟不能代表系统长期服务能力。
- [ ] **是否区分了固定长度微基准与真实业务分布？** —— 固定长度适合隔离算子变量，但不能直接外推为线上多变长度流量的并发容量。
- [ ] **跨模型或跨引擎对比 tok/s 前，是否处理了 Tokenizer 与缓存命中差异？** —— 不同分词器与前缀命中率会直接改写分子分母，必须对齐统一文本或显式扣除缓存影响。
- [ ] **是否锁定了完整软硬件版本与可复现启动/压测命令？** —— 引擎默认参数（如分块 Prefill、前缀缓存、CUDA Graph、量化后端）随小版本频繁变化，没有精确命令与版本的跑分无法复现、也无法复查。
