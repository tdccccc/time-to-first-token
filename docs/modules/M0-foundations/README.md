## 第 1 章 · Roofline：先算，再优化

**本章目标。** 给定模型和硬件，不运行推理服务也能判断瓶颈更可能在算力、显存带宽还是启动开销。

### 问题：换更快的卡，为什么有时没用

先看一个具体问题：一个 7B 模型、FP16 权重、batch=1 的解码请求，生成下一个 token 时，GPU 主要在算什么？瓶颈在显存带宽，不在算力：矩阵乘还在做，但每个权重只参与一次乘加，时间主要花在把权重从显存读进来。这个判断不用跑服务，用参数量、精度和硬件的峰值算力、带宽就能算出来。

每生成一个 token，模型都要把约 70 亿个权重参数从显存读进计算单元，每个参数只参与一次乘加：计算量很小，搬运量很大。换一块算力翻倍、显存带宽不变的卡，计算时间减半，总时间却几乎不变。

Roofline 模型就是把这类判断变成算术。它用两个量描述一个 kernel：

- **算术强度（arithmetic intensity）**：每搬运 1 字节数据，做了多少次浮点运算，单位是 FLOP/字节。
- **脊点（ridge point）**：硬件峰值算力除以峰值显存带宽，单位也是 FLOP/字节。

把 kernel 的算术强度和硬件的脊点相比：低于脊点，时间主要花在搬运上，叫**显存带宽受限（memory-bound）**；高于脊点，时间主要花在计算上，叫**计算受限（compute-bound）**。还有第三类边界：kernel 太小，计算和搬运都只要微秒级，真正占时间的是启动和同步，叫**开销受限（overhead-bound）**。开销不在 Roofline 的两根线上，需要单独判断。

两个手算公式：

```text
算术强度 = FLOPs / 搬运字节数
运行时间 ≈ max(计算时间, 搬运时间)   # 大 kernel 的近似
```

这两个公式给的是上限和方向，不是精确预测：真实 kernel 还会有启动、同步、访存合并和重叠执行的开销。

### 例子：7B 模型解码的一次时间账

取 A100 80GB 的公开规格做算例：FP16 稠密算力约 312 TFLOPS，HBM 带宽约 2 TB/s。这是公开规格、用于示例，不是实测；不同卡的数字不同，判断方法不变。

**decode，batch=1。** 每生成一个 token：

- 权重搬运：约 70 亿参数 × 2 字节/参数 ≈ 14 GB。
- 计算量：每个参数一次乘加，一次乘加算 2 FLOP，约 2 × 70 亿 ≈ 14 GFLOP。
- 算术强度：14 GFLOP ÷ 14 GB ≈ 1 FLOP/字节。
- A100 脊点：312 TFLOPS ÷ 2 TB/s = 156 FLOP/字节。
- 计算时间：14 GFLOP ÷ 312 TFLOPS ≈ 0.045 ms。
- 搬运时间：14 GB ÷ 2 TB/s ≈ 7 ms。

搬运时间是计算时间的约 156 倍，decode 落在带宽受限一侧。**只算权重搬运、且一步只生成一个 token** 时，单请求吞吐上限约 1 ÷ 0.007 s ≈ 143 token/s；这个上限不含 KV 读取、调度、kernel 启动与采样，真实服务只会更低。如果测出超过 143 token/s 的单请求吞吐，先检查测量口径（batch 是否真的为 1、是不是一步吐了多个 token、token 数怎么数）。把算力翻倍，0.045 ms 只变成 0.022 ms，总时间仍由 7 ms 的搬运决定：算力不是没用，是当前瓶颈不在它那里。

### 用 batch 与 prefill 看 Roofline 上的位置变化

**增大 batch。** batch=8 时，一次 decode 步骤仍只读一遍 14 GB 权重，但计算量变成 8 × 14 = 112 GFLOP：

- 算术强度：112 GFLOP ÷ 14 GB = 8 FLOP/字节。
- 计算时间：112 GFLOP ÷ 312 TFLOPS ≈ 0.36 ms。
- 搬运时间：仍约 7 ms。

总吞吐约 8 ÷ 0.007 s ≈ 1143 token/s（只算权重，不含 KV），是 batch=1 的 8 倍；但每个请求仍约每 7 ms 得到一个 token，单请求的 token 间隔没有缩短。batch 提高的是权重复用次数，不是单个请求能用的带宽。

那 batch 要多大才会翻到计算受限？只算权重时，令 B × 14 GFLOP / 312 TFLOPS = 7 ms，得 B ≈ 156。batch=156 时计算时间追上搬运时间；更大以后，计算才成为主要成本。这个数是模型和硬件共同决定的，不是通用常数。

**prefill。** 它一次处理整段 prompt，权重仍只读一遍，但计算量随输入长度 N 线性增长。矩阵乘部分约为 2 × N × 70 亿 FLOPs：

| 输入长度 N | 权重计算量 | 注意力部分（估算） | 总计算量（估算） | 算术强度（约） | 判断 |
|---:|---:|---:|---:|---:|---|
| 128 | 1.79 TFLOP | 0.004 TFLOP | 1.80 TFLOP | 128 FLOP/字节 | 略低于脊点，带宽受限 |
| 512 | 7.17 TFLOP | 0.069 TFLOP | 7.24 TFLOP | 517 FLOP/字节 | 计算受限 |
| 1024 | 14.34 TFLOP | 0.27 TFLOP | 14.61 TFLOP | 1044 FLOP/字节 | 计算受限 |
| 4096 | 57.34 TFLOP | 4.40 TFLOP | 61.74 TFLOP | 4410 FLOP/字节 | 计算受限 |

表里的“注意力部分”按 2 × N² × 4096 × 32 估算：32 层、hidden 4096，只计 QK^T 一项，PV、softmax、mask 未计，所以它只表示 N² 的量级，不是完整 attention 的实测 FLOPs。总计算量是权重项加这一项；算术强度用总计算量除以 14 GB 权重搬运量，未计激活与 KV 写入。

令权重计算时间追上权重搬运时间：2N × 7e9 / 312e12 = 14e9 / 2e12，解得 N ≈ 156。短 prompt 的 prefill 仍可能受带宽限制，长 prompt 更可能受计算限制；注意力项随 N² 增长，长上下文下会进一步推高计算占比。只算权重时，batch 阈值、prefill 交叉点和脊点都落在 156：每多一个 token，算术强度就加 1 FLOP/字节，加到脊点就翻到计算侧。

**补上 KV 缓存。** 上面只算了权重，decode 还要读历史 token 的 K、V。以 Mistral-7B 为例：32 层、8 个 KV 头（GQA，grouped-query attention，分组查询注意力：多个 query 头共享一组 K/V 头）、头维 128、FP16，每 token 的 KV 为：

```text
2（K 和 V）× 32 层 × 8 个 KV 头 × 128 维 × 2 字节 = 131072 字节 = 128 KiB
```

上下文 1024 token、batch=1 时，KV 约 128 MiB，和 14 GB 权重相比很小；batch=8、上下文 1024 时，KV 约 1 GiB，decode 一步的搬运量从 14 GB 变成约 15.1 GB，时间约从 7.0 ms 变成 7.5 ms。上下文越长、batch 越大，KV 在搬运账里的占比越高。

如果是 MHA（multi-head attention，多头注意力：每个 query 头各存一份 K/V），同一模型的 KV 会是 GQA 的 4 倍。所以看到一个模型的 KV 数字，先确认注意力结构与头数，不能只拿参数量套。

把 KV 计入搬运量，上面只算权重的上限会下降：batch=8、上下文 1024 时，吞吐上限约 1061 token/s，而不是 1143 token/s。本章的 1143 是只算权重的口径；比较不同来源的数字，先对齐这一点。

### 边界：Roofline 不负责预测什么

Roofline 的用途是排除方向错误，不是替代测量。

- **它不告诉你实测有多快。** 上限和实测之间的差距，来自访存是否合并、占用率、kernel 启动、同步和调度。第 3 章用 profiling 找差距，第 5 章用压测报数字。
- **它不覆盖小 kernel 的启动开销。** 一个只有几十 KB 的逐元素 kernel，计算和搬运可能都远小于微秒，时间由启动与调度决定。推理服务里大量 RMSNorm、激活、采样小算子属于这一类，第 6 章会展开。
- **容量和带宽是两个问题。** 显存容量决定模型和 KV 装不装得下，显存带宽决定 decode 读权重有多快。一块容量大但带宽低的卡，可能装得下模型却仍然跑得慢。
- **算术强度会随 batch、序列长度和缓存结构变化。** 本章的点是示例；实际服务要按自己的 batch、prompt 长度和 KV 配置重算。

## 第 2 章 · 推理度量：四个数，一个分布

**本章目标。** 把“快”拆成四个不会互相掩盖的数，并知道分布比均值重要。

“快”在推理服务里压着四件事：用户等得短、输出流畅、系统单位时间产出多、系统还没被压垮。两个系统分别擅长其中两件时，“哪个更快”没有共同的分母，答案只能是糊涂账。要把“快”变成能比较、能复现的数，得拆成四个各有分工的指标，再补上分布这一层：均值会藏住长尾，而用户记住的往往是最慢的那一次。

### 四个数各自量什么

| 指标 | 英文 | 定义 | 它回答的问题 |
|---|---|---|---|
| 首 token 延迟 | TTFT | 从发请求到收到第一个 token 的时间 | 用户要等多久才看到东西 |
| token 间延迟 | ITL / TPOT | 相邻两个 token 之间的平均时间 | 输出流畅不流畅 |
| 吞吐 | throughput | 单位时间生成的 token 总数 | 系统整体产出 |
| 排队深度 | queue depth | 正在等待的请求数 | 系统是不是已经满了 |

首 token 延迟（TTFT，time to first token）从请求发出算到第一个 token 到达用户手里，里面装着三段：请求在队列里等了多久、prefill 算了多久、第一个 token 生成花了多久。用户对它最敏感：点下发送之后，屏幕多久开始出现字。TTFT 长，用户觉得系统卡；TTFT 短，后面输出慢一点，用户也觉得系统有反应。优化 TTFT 的方向基本就是第 1 章 prefill 那笔账：prompt 越长、prefill 越重，TTFT 越长；队列越堵，等待段越长。

token 间延迟（ITL，inter-token latency，也叫 TPOT，time per output token）量的是 decode 阶段的速度：第一个 token 出来之后，后续 token 一个接一个冒出来的节奏。ITL 为 20 ms 时，文字像打字机一样稳定输出；ITL 抖到 200 ms，文字就一顿一顿往外蹦。它是对整个 decode 阶段取的平均，单步抖动被平均抹掉，要看抖动得看分布。TTFT 与 ITL 必须分开报：TTFT 量 prefill，ITL 量 decode；第 1 章已经算过，小 batch 的 decode 落在带宽受限一侧，prefill 随 prompt 变长翻到算力受限一侧，两个阶段的主瓶颈不同。压成一个“延迟”，两边的结论搅在一起，谁的问题都看不出来。

吞吐（throughput）是单位时间生成的 token 总数，单位 token/s，量的是系统整体产出，不量单个用户的体验。它和前两个数的关系经常被弄反：吞吐高，不代表用户等得短。增大 batch 能推高吞吐——第 1 章算过，batch=8 时总吞吐是 batch=1 的 8 倍——但每个请求自己的 TTFT 与 ITL 可能一点没变，甚至因为排队变长。吞吐是站在系统一边的数，TTFT 与 ITL 是站在用户一边的数，两边都要报，只报一边就是只讲了一半故事。

吞吐的定义里没有“成功”二字：超时和被丢弃的请求如果也算进 token 数，吞吐会虚高，所以报吞吐时要同时报成功请求数，成功多少、失败多少，分母才干净。

排队深度（queue depth）是正在等待的请求数，量的是系统离饱和还有多远。它不直接量速度，量的是压力：排队深度长期为零，系统有余量；它开始往上涨，说明到达的请求超过了系统能处理的速度，TTFT 里等待的部分会跟着涨；涨到上限，新请求会被拒绝或者超时。这个数从服务端指标读，第 9 章的 `num_requests_waiting` 就是它；客户端压测只能从 TTFT 的变化间接推断。第 5 章找的拐点——吞吐不再涨、延迟开始恶化的那个并发数——在排队深度上就是一条分界线：拐点之前基本不动，拐点之后一路往上。压测时盯着排队深度，拐点出现之前就能看到预兆。

### 只报均值为什么不够

报分布，是因为用户感受到的是长尾。p50 是中位数，一半请求比它快、一半比它慢；p95 是 100 个请求里 95 个比它快，剩下 5 个比它慢；p99 是 99 个比它快，只有 1 个比它慢。均值量的是普通情况，p95 与 p99 量的是“倒霉的用户要等多久”——用户印象最深的往往就是最坏的那一次。

均值怎么骗人，两组请求就看得出来。系统 A 的 100 个请求里，99 个 TTFT 是 100 ms、1 个是 200 ms；系统 B 的 100 个请求全是 101 ms。A 的均值是 (99 × 100 + 200) / 100 = 101 ms，B 也是 101 ms，两个系统的均值一模一样。p99 却是 A 为 200 ms、B 为 101 ms，A 的尾巴接近 B 的两倍：A 每 100 个用户就有 1 个要等 200 ms，是其他请求的两倍。均值相同、A 的 p99 接近 B 的两倍，用户体验完全不同，这是只报均值最直接的漏洞。

p95/p99 的具体数值还取决于分位数算法。第 4 章的 `bench_openai.py` 用线性插值，秩按 (n − 1) × q 算、0 对应最小值：20 个请求时，p95 的秩是 (20 − 1) × 0.95 = 18.05，p99 的秩是 (20 − 1) × 0.99 = 18.81，两者的秩都落在最后两个样本之间，p99 基本由最慢的一两个请求决定。样本这么少时，p95 与 p99 只能当尾巴的粗估；换一种分位数算法或换一批请求，数都会动。报数至少要报 p50、p95、p99 三个点：p50 看典型情况，p95 看大多数用户的上限，p99 看尾巴有多长。

### 固定长度与样本量

**固定长度原则**：输入和输出 token 长度固定下来再测。KV 缓存大小完全由这两项决定：输入越长，prefill 的计算量越大，TTFT 越长；输出越长，decode 的步数越多，总延迟越长；KV 缓存占的显存也跟着涨，batch 能开多大都要重算。长度一变，吞吐跟着变，两次压测的数字之间就分不清是优化带来的还是长度带来的。`bench_openai.py` 默认固定 prompt、固定 `--max-tokens`，就是这个原因：先把长度钉死，再谈快慢；钉不死长度的压测，数字没有可比性。

报分布还有一个前提：样本量。p99 的意思是 100 个请求里最慢的那 1 个；样本不到 100 个时，这个位置上就没有一个真实的“1%”，算出来的 p99 只是当前样本里最慢的一两个值，换一批请求就变。想让 p99 稳定，样本量至少要到 100 个量级，p99 才对应至少 1 个真实落在尾巴里的请求；样本量越大，尾巴的估计越稳。压测报告只写 p99 的值、不写样本量，等于只给结论、不给结论的可信度。第 5 章跑基线时每级并发固定跑 20 个请求：这个量级看 p50 与均值够用，看 p95 已经由最慢的一两个请求决定，看 p99 就偏薄——读基线报告时，先看请求数，再信 p99。

### 四个数的联动与结论

四个数之间有联动，压测时要一起看。并发从 1 往上加，吞吐一开始跟着涨，TTFT 与 ITL 基本不动；并发继续加，排队深度开始抬头，TTFT 里等待的部分跟着变长；加到拐点之后，吞吐不再涨，TTFT 与 ITL 一起恶化。第 5 章要找的拐点，就是这条联动链由“吞吐涨、延迟不动”翻成“吞吐不动、延迟涨”的位置。只看吞吐，会把拐点之后的系统当成产出还在涨；只看延迟，会把拐点之前的系统当成已经到顶。第 5 章的基线报告把 TTFT p50/p95/p99、ITL、吞吐和成功请求数放进同一张表，排队深度则看服务端指标。四个数拼在一起，拐点才看得见。

“吞吐高等于体验好”是错的：吞吐是系统产出，体验是用户等待；batch 开大，吞吐涨了，排队深度也涨了，新请求要等更久，TTFT 反而变长。“延迟低等于吞吐高”也是错的：单请求延迟低，可能是 batch=1 跑出来的，系统产出未必高。

读完这一章，手里应该有两样东西：一张四个数的对照表，每个数写清定义、单位、它回答的问题，遇到新指标先往里对号；一份基线报告的指标清单，至少写 TTFT p50/p95/p99、ITL p50、吞吐、成功请求数，再加输入输出长度与每级样本量——长度决定数字能不能比，样本量决定分位数能不能信。第 5 章会用这份清单跑第一份基线。

**延伸**：[NVIDIA：LLM 推理 benchmark 基础概念](https://developer.nvidia.com/blog/llm-benchmarking-fundamental-concepts/)、[Modal：How to Benchmark LLM Engines](https://modal.com/llm-almanac/how-to-benchmark)。

## 第 3 章 · Profiling：看时间花在哪

**本章目标。** 拿到一次推理请求的时间线，能指出时间花在哪个 kernel、哪类访存或哪段等待上，并据此选出下一步动作。

### 三个工具：先看整体，再钻 kernel

上限和外部观测之间还缺一环：一次请求内部的时间去向。Roofline 说 decode 受显存带宽限制，四个度量说 TTFT 是几百毫秒，但都不会告诉你这几百毫秒里哪个算子占了大头、GPU 有多少时间在空等。Profiling（性能分析）补这一环：把一次推理展开成时间线（timeline，按时间排列的调用记录，横轴是时间，纵轴是 CPU 与 GPU 两条泳道），每一段对应一个算子、一次拷贝或一段等待。瓶颈从一句“受带宽限制”变成一个具体的名字：是 attention 里的 softmax，是某个 matmul，还是 GPU 在等 CPU 发下一个 kernel。

三个工具的分工按粒度分层，不重叠：

| 工具 | 看什么 | 什么时候用 |
|---|---|---|
| PyTorch Profiler（`torch.profiler`） | 每个算子的耗时、显存、CPU 与 GPU 时间线 | 第一步。先拿算子级占比：top-3 占得够多才继续往下钻；占比低，说明时间可能不在算子里 |
| `nsys`（Nsight Systems） | 系统级时间线：CPU、GPU、拷贝、kernel 启动，跨进程与库 | 第二步。算子表解释不了时间去向时用它：框架调度、跨进程、启动间隔 |
| `ncu`（Nsight Compute） | 单个 kernel 的细节：占用率、访存效率、指令构成 | 第三步。已经有一个具体 kernel，且它占的时间足够大，才需要问“它为什么慢” |

顺序不能反，理由是一笔账。举例：一个算子占总时间的 5%，把它加速一倍，总时间只从 100% 降到 97.5%，端到端时间少 2.5%；如果 top-3 加起来只有 15%，剩下 85% 分散在大量小算子、启动间隔与空白里，只盯 top-3 找不到答案。先把占大头的那一段找出来，再决定用多细的工具；一上来就钻 5% 的 kernel，花的是最细的工具的时间，省的是最小的一块。这个顺序是一般情况，不是教条：如果症状已经明显在框架层，比如 GPU 空白与请求到达节奏对齐、延迟里有一大段既不在算子里也不在拷贝里，可以直接从 `nsys` 开始。工具由问题决定，不由顺序决定。

`ncu` 的细节读法在第 19 章展开：先读计算单元利用率与显存带宽利用率两个数，判断 kernel 是算受限、访存受限还是延迟受限，再按判断改 kernel。本章的要求到“会读、会定位”为止：`ncu` 回答“这个 kernel 为什么慢”，不回答“哪个 kernel 慢”——后者是 `torch.profiler` 的活。

最小的一次采集长这样：

```python
import torch
from torch.profiler import ProfilerActivity, profile

activities = [ProfilerActivity.CPU]
if torch.cuda.is_available():
    activities.append(ProfilerActivity.CUDA)

model.eval()
# 先空跑几轮，等每步时间稳定
with torch.no_grad(), profile(activities=activities) as prof:
    model(input_ids)
prof.export_chrome_trace("trace.json")
```

这里用一次前向把工具跑通；换成 `generate` 或引擎的请求入口，读法不变。导出的 `trace.json` 用 `chrome://tracing` 或 Perfetto 打开。有 GPU 时保留 `ProfilerActivity.CUDA`，才能看到 GPU 线；没有 GPU 时只剩 CPU 线，它仍然能告诉你算子调用顺序、dispatch 开销和框架层的空白，但显存带宽、kernel 效率和拷贝都看不到。`record_shapes`、`profile_memory`、`with_stack` 这些开关默认先关：它们改的是采集范围，范围越大，开销越大；定位到具体算子后再按需打开。

### 读 trace：CPU 与 GPU 两条线

trace（一次 profiling 录下来的时间线记录）上有两条线，读法不同。CPU 线的宽度是 host 端的时间：Python 调用、算子分发、kernel 启动、同步。GPU 线的宽度是设备端真正执行的时间：kernel 跑了多久、拷贝跑了多久。同一个算子在两条线上的宽度经常不一样；把 CPU 宽度当成计算时间，是最常见的读错。

看四种形状：

- CPU 长、GPU 短：时间花在启动与调度上，不在计算上。kernel 越小，这个比例越难看。
- GPU 一直是大块、块间没有空白：时间确实花在 kernel 执行上，不在等待上。这时排名前几的 kernel 才需要看。
- GPU 有空白，空白正下方 CPU 在 dispatch 或 Python 调用：GPU 在等 CPU 发下一个 kernel，流水线断了。
- GPU 有空白，空白正下方是拷贝或同步：GPU 在等数据搬完，或在等一次同步的结果。

空白本身不是结论，空白的邻居才是。把两条线上下对齐：空白正下方是 Python 调用，说明 CPU 还没把 kernel 发下来；正下方是 `cudaMemcpy` 或 `synchronize`，说明 GPU 在等数据或等同步；正下方什么都没有，可能是依赖前一个 kernel 的结果，也可能是 profiler 的采样窗口断了。单请求的 trace 里有空白很正常；一段空白是不是浪费，看它是否在每一步重复、是否随 batch 增大而消失——batch 一加就消失的空白是流水线气泡，batch 加了还在的空白，才是结构性的等待。

服务里的 trace 比单请求复杂：连续批处理把多个请求的 kernel 混在同一条 GPU 线上，一段 kernel 不一定属于某一个请求。要给请求归因，先让引擎在请求边界打上 NVTX 标记（NVIDIA Tools Extension，NVIDIA 的时间线标记接口：给一段代码起名，用 `nsys` 采时按名字找），或者把 batch 固定为 1 采一次；没有标记时，只能看整体时间去向，不要硬把某段 kernel 算给某个请求。

没有 GPU 也能读一半：在 CPU 上跑一次小模型前向，trace 只有 CPU 线，仍能看到算子调用顺序、dispatch 开销和同步点；GPU 线的读法先按上面的四种形状建立，等有卡再用同一段代码打开 CUDA activity 验证。

### 从最热的算子到下一步动作

找到 top-3 只是中间结果。下一步要回答两件事：这个算子为什么慢，以及改它值不值。

先看它属于哪一类。低算术强度（arithmetic intensity，每搬运 1 字节做多少次浮点运算）的算子，每个元素读进来、算一两次、写回去，时间主要花在搬运上；高算术强度的算子，数据在片上被复用多次，时间主要花在计算上。前者优化搬运，后者优化计算，方向相反。

| 时间线上的样子 | 说明 | 下一步动作 |
|---|---|---|
| 低算术强度算子占大头 | 逐元素、归一化、decode 的 attention：读一次、算一两次、写回 | 融合、量化、减少中间结果写回 |
| 高算术强度算子顶住算力 | matmul、长上下文 prefill 的 attention：数据在片上复用多次 | 换 kernel 实现、调整分块大小、用更合适的精度 |
| 小 kernel 密集、GPU 空白多 | CPU 发射时间接近或超过 kernel 执行时间 | 融合小算子、CUDA Graph、减少每步 Python 开销 |
| GPU 空白下方是拷贝或同步 | 主机与设备之间的拷贝、`.item()`、日志、采样 | 异步拷贝、去掉不必要的同步、把数据留在 GPU |

同一个 attention 不能只按名字分类。prefill 一次处理 N 个 token，Q、K、V 都是 N×d，矩阵乘的复用随 N 增长；decode 一次只处理 1 个 token，却要读整段 KV，每个 KV 元素只参与少量乘加，算术强度低，上下文越长，读的 KV 越多，搬运量跟着涨。batch 增大时线性层的权重复用变多，但 attention 的 KV 读取也随 batch 增长；判断仍要回到具体 kernel 的实测。时间线上看到 attention 占大头，先分清它是 prefill 还是 decode 的 attention，再看 batch 与上下文长度，才能判断是搬运问题还是计算问题。

低算术强度这一侧的动作是减少搬运：融合把几个逐元素算子合成一个 kernel，中间结果不写回显存；量化把权重从 FP16 压到 FP8 或 INT4，同样的参数少搬一半到四分之三；FlashAttention 不减少 FLOPs，减少的是 attention 中间矩阵的显存读写（第 21 章推导）。高算术强度这一侧的动作是让计算更接近峰值：换更好的 kernel 实现、调整分块大小与流水线、用硬件支持的更低精度矩阵乘；如果已经贴着 Roofline 的算力上限，换实现的空间很小，要么换算法减少工作量，要么接受它，去改占比更大的等待。

判断顺序可以固定成四步：先看占比，top-3 加起来不到两成，先别钻 kernel，去看空白与启动开销；再看类型，低算术强度、高算术强度、启动受限还是等待；然后用 Roofline 估一个上限，看还有多少空间；最后只改一个变量，用同一负载重测。改完不回到时间线验证，就不知道改动有没有命中瓶颈——优化动作和瓶颈类型对不上，数字不会动。

### 两个常见误读与操作细节

第一个误读：“profiler 显示某个算子占 80%，所以它就是瓶颈。”这句话缺了分母。80% 可以是占 GPU 时间的 80%，也可以是占端到端延迟的 80%。算例：端到端 100 ms，GPU 真正忙 50 ms，某个算子占 GPU 时间的 80%，即 40 ms，它只占端到端的 40%；另外 60 ms 在 GPU 空白、CPU 调度或排队里。换一组条件，GPU 忙 95 ms，同样 80% 就是 76 ms，占端到端 76%。同一个百分比，分母不同，结论差近一倍。读数前先问：这个百分比的分母是 GPU 时间、CPU 时间，还是端到端延迟？

`torch.profiler` 的表里还有一层分母：`Self CUDA`（自己 kernel 的时间）与 `CUDA total`（含子算子的时间）不是一回事。按 total 排序再把几行相加，父算子会把子算子的时间重复计一遍；排名用 Self，追一个阶段的总时间才用 total。

第二个误读：“GPU 时间线上有空白，说明 GPU 在偷懒。”空白只说明这一段时间没有 kernel 在跑，原因可能是等 CPU 发下一个 kernel、等拷贝、等同步，也可能是依赖上一个 kernel 的结果。单请求的 trace 里有空白是常态；判断它是不是浪费，看两件事：空白是否在每一步重复，以及增大 batch 后空白是否消失。batch 一加就消失的空白是流水线气泡，说明之前 GPU 没吃饱；batch 加了还在的空白，才是结构性的等待，要去查同步、拷贝或调度。

四条操作细节：

1. 先热身再采。第一次前向有 JIT 编译、cuDNN autotune、显存分配和时钟爬升，采到的是冷启动。先空跑几轮，等每步时间稳定，再开 profiler。
2. 带 profiler 的数字不报成绩。profiler 要记录每个 kernel 的起止，`ncu` 还要读硬件计数器、重放 kernel，这些动作本身有开销；重放会扰动缓存状态与时钟，`ncu` 的耗时更不能当性能数字。定位用带 profiler 的 trace，报性能关掉 profiler 用同一负载重跑。
3. 采样频率与采集范围分开调。频率是隔多久采一次（CPU 采样、硬件计数器采样），范围是记录哪些活动、哪些指标、是否带 shape 与调用栈。不同工具的叫法不同，先分清旋钮属于哪一类。频率越高，单位时间记录越密；范围越大，每条记录越重。两者都会让开销上升，但调的是两个旋钮：`torch.profiler` 的 activities、record_shapes、with_stack 是范围，schedule 的 active 窗口是采哪一段；`ncu --set full` 是范围，`--launch-count` 是采几个 kernel；`nsys -t` 是范围，CPU 采样是否开启与采样周期是频率那一侧。
4. `ncu` 读的是 GPU 性能计数器，需要驱动层放开的权限。很多容器与云主机默认禁用（驱动参数限制，或容器权限不足），典型报错是 `ERR_NVGPUCTRPERM`。跑不起来先查权限与容器配置，再查命令，最后才怀疑工具。`torch.profiler` 与 `nsys` 通常只需要 CUPTI 的活动记录，不需要性能计数器；CUPTI（CUDA Profiling Tools Interface，CUDA 的性能分析采集接口：向上提供活动记录与计数器）是这些工具共用的底层接口。

一份能用的 profiling 笔记至少有三行：最热的算子及其占 GPU 时间的比例；GPU 时间线上空白的位置与成因；下一步只改一个变量的动作，以及改完用什么指标验证。三行齐了，才算回答了本章的问题：时间花在哪，下一步改什么。

**延伸**：[PyTorch Profiler 文档](https://pytorch.org/docs/stable/profiler.html)、[Nsight Systems 用户指南](https://docs.nvidia.com/nsight-systems/UserGuide/index.html)、[Nsight Compute 文档](https://docs.nvidia.com/nsight-compute/NsightCompute/index.html)、[GPU MODE lectures](https://github.com/gpu-mode/lectures)（profiling 相关讲座）。

## 第 4 章 · 写压测脚本：`bench_openai.py`

**本章目标。** 读懂并跑通 bench_openai.py 这个只用 Python 标准库的压测脚本，它面向提供 /v1/chat/completions 的 OpenAI 兼容服务，固定输入、输出上限与并发条件；说清首 token 延迟、token 间延迟与吞吐每个数是怎么算出来的。

压测工具的价值不在它测得多快，在它每次测的条件都一样。手动发请求，换个时间、换个 prompt、换个输出长度，数字就全变了，上一轮的数和这一轮比不了。`bench_openai.py`（[源码](scripts/bench_openai.py)）把会变的条件钉死：固定 prompt、固定 `--max-tokens`、固定并发档位与每档请求数，用同一套计时和统计口径输出结果。脚本只用 Python 标准库，不需要 GPU——GPU 在服务端，客户端只负责发请求、读流、记时间。

### 为什么必须是流式

脚本打的是 OpenAI 兼容接口的 `/v1/chat/completions`，请求体里 `stream` 设为 `true`。首 token 延迟（TTFT，Time to First Token）只能从流里读出来：非流式请求要等整个回答生成完才返回，客户端只拿到一个总延迟，第一个 token 什么时候出来藏在里面。流式返回把生成过程一段段推回来，客户端从第一个 chunk 到达起就能计时；这个时刻就是脚本记的 TTFT。

流式响应体是 SSE（Server-Sent Events，服务器推送事件）：一行行 `data: {...}`，最后一行 `data: [DONE]`。脚本逐行读，遇到第一个非 `[DONE]` 的 JSON 记 TTFT，读到 `[DONE]` 或连接结束记总延迟。

chunk 是传输单位，不是 token 单位：一个 chunk 可能带 0 个、1 个或多个 token。脚本把第一个流式 chunk 当作 TTFT 的终点，这个口径要固定；跨服务端比较时，各家的切 chunk 粒度不同，TTFT 的口径也会跟着变，比较前先确认两边都按第一个 chunk 计时。要更严格，可以改成“第一个 `delta.content` 非空的 chunk”；两种口径都能用，但同一份报告里不能混用。

选接口就是选尺子：第 10 章换引擎、第 12 章换量化、第 13 章换解码方法，量的都是同一个 `/v1/chat/completions` 后面的变化。接口与请求字段固定，数字之间才有可比性。

### 三个时间量怎么算

脚本在发请求前记下 `start = time.perf_counter()`；第一个 chunk 到达时记 `ttft = now - start`；最后一个 chunk 到达时记 `total = now - start`。三个时间量由此得到：

- TTFT：从发请求到收到第一个 chunk 的时间。
- 总延迟：从发请求到收到最后一个 chunk 的时间。
- ITL（Inter-Token Latency，token 间延迟）：相邻两个输出 token 之间的平均时间。

ITL 的算式是 `(total - TTFT) / max(tokens - 1, 1)`。分母是 token 数减一：128 个 token 之间有 127 段间隔。脚本用 `max(tokens - 1, 1)` 防止只输出 1 个 token 时除零；只有 1 个 token 时没有间隔，这个 ITL 实际是首 token 到流结束的那段时间，读到时要知道它是边界情况。

设总延迟 12.8 s，TTFT 0.8 s，128 个 token：ITL = (12.8 − 0.8) ÷ 127 = 12 ÷ 127 ≈ 0.0945 s。验算：127 × 0.0945 ≈ 12.0015 s，与 12.0 s 一致。

TTFT 里包含排队、prefill、网络与客户端解析；ITL 里包含 decode 的每一步以及每个 chunk 的网络与解析。两个都是客户端观测值，不是 GPU 时间；要把 GPU 内部的时间拆开，得用第 3 章的 profiler，排队与网络的部分要靠服务端指标或对照实验。第 1 章 Roofline 说 prefill 与 decode 落在不同区间，TTFT 与 ITL 分开报，才给这个结论提供可验证的读数。

脚本算的是平均 ITL，不是每一步的分布；单步抖动被平均掉了。要看抖动，得另外记录每个 chunk 的到达时间，这一版没有做。

### token 数与固定长度

token 数是 ITL 的分母，也是吞吐的分子，数错了两个数都错。脚本的取法分两档：

1. 优先读 `usage.completion_tokens`。请求里带 `stream_options: {"include_usage": true}`，vLLM 等支持这个字段的服务会在最后一个 chunk 里返回 usage；这是服务端自己数的 token 数。
2. 服务端不支持时，按字符数估算：`max(1, len(text) // 4)`，`text` 是所有 `delta.content` 拼起来的文本。`// 4` 是英文经验值，平均约 4 个字符一个 token；中文一个字符往往就是一个 token 甚至更多，字符数除以 4 会低估 token 数。分母被低估，ITL 会偏大；分子被低估，吞吐会偏小。

脚本固定带上 `stream_options`；如果服务端不认这个字段并直接报错，这一级会整级失败——脚本不会自动去掉它再重试，遇到时要么换支持的服务端，要么改脚本去掉该字段，token 数就退化为估算。

估算值在 JSON 里用 `tokens_estimated` 标记：本级只要有一个请求是估算的，整级就标 `true`。TTFT 不受影响，它的算式里没有 token 数。读结果时先看这个标记，再决定 ITL 与吞吐能信几分。

参数与默认值：

| 参数 | 默认值 | 作用 |
|---|---|---|
| `--base-url` | 必填 | 服务地址；脚本拼上 `/v1/chat/completions` |
| `--model` | 必填 | 服务端的模型名 |
| `--max-tokens` | 128 | 输出 token 上限 |
| `--concurrency` | 1 8 32 | 逐级扫描的并发档位 |
| `--requests` | 20 | 每档的请求数 |
| `--timeout` | 300 | 单请求的 socket 超时，单位秒 |
| `--output` | bench-results.json | 结果 JSON 的路径 |

固定长度是脚本的另一条主线。prompt 是脚本里的常量 `Explain why the sky is blue in one short paragraph.`；`--max-tokens` 默认 128。固定 prompt 就是固定 prefill 的输入长度；`--max-tokens` 固定的是输出上限，不是每个请求的实际输出：模型遇到 EOS（end of sequence，序列结束标记）会提前停，实际 token 数以服务端返回的 `completion_tokens` 为准，脚本用它算 ITL 与吞吐。长度决定 KV 缓存大小与 decode 步数，长度一变，延迟与吞吐跟着变，两次结果就没法比。这是第 2 章固定长度原则在脚本里的落地。

温度设为 0，减少采样随机性；温度 0 不等于逐位可复现，生成长度仍可能因 EOS 的位置而变。要严格固定实际长度，得选一个能稳定跑满 `--max-tokens` 的 prompt，或者在脚本里补上每请求长度的记录——当前汇总不保存这个数。

脚本按 `--concurrency` 列表逐级扫：每级提交 `--requests` 个请求，用 `ThreadPoolExecutor(max_workers=concurrency)` 限制同时在途的请求数；所有请求结束后，用整级墙钟时间（wall time，从提交第一个请求到最后一个请求完成的真实时间）算吞吐：`吞吐 = 本级成功请求的 completion_tokens 之和 / wall_s`。并发是客户端同时在途的请求数，不是服务端同时执行的请求数，服务端调度、排队与 KV 限制都会让两者不同；第 5 章会专门看这个差别。

输出分两种。JSON 记录顶层条件（`base_url`、`model`、`max_tokens`、`prompt`）与每一级的汇总：`concurrency`、`ok`、`requests`、`wall_s`、`ttft_s` 的 `mean/p50/p95/p99`、`itl_s` 的 `mean/p50/p95`、`throughput_tok_per_s`、`tokens_estimated`。它不保存每个请求的原始记录；单请求的 `total_s` 也没有进入汇总，只在 `stream_request` 内部参与 ITL 计算。Markdown 表格打印五列：并发、成功、TTFT p50 / p95、ITL p50、吞吐。失败的请求不进延迟与 token 统计，但它们占用的时间仍计入 wall，所以吞吐会被拉低；全失败时该级显示失败原因。

百分位用线性插值，与第 2 章、第 5 章同一口径：先把本级的值排序，算 `rank = (n − 1) × p / 100`，再在相邻两个值之间插值。20 个请求时，p95 的秩是 19 × 0.95 = 18.05，落在下标 18 与 19 之间，取 `0.95 × x[18] + 0.05 × x[19]`；p99 的秩是 19 × 0.99 = 18.81，取 `0.19 × x[18] + 0.81 × x[19]`。样本只有 20 个，p95 基本由最慢的一两个请求决定，p99 基本就是最慢的那一个。表格只印 TTFT 的 p50/p95 与 ITL 的 p50；JSON 里 TTFT 有 p99，ITL 只有 p50/p95，没有 p99。

### mock 验证能证明什么

验证脚本不需要 GPU：起一个本地 mock SSE 服务，让它按固定节奏吐 chunk，看脚本量出来的时间是否与设定一致。仓库里没有现成的 mock 脚本；把下面这段代码复制出来存成 `mock_sse.py` 运行，它监听 8400 端口：

```python
import json, time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class H(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"
    def log_message(self, *a): pass
    def do_POST(self):
        self.rfile.read(int(self.headers.get("Content-Length", 0)))
        self.send_response(200)
        self.send_header("Content-Type", "text/event-stream")
        self.send_header("Connection", "close")
        self.end_headers()
        for i in range(128):
            if i: time.sleep(0.010)
            self.wfile.write(b"data: " + json.dumps({"choices": [{"delta": {"content": "x"}}]}).encode() + b"\n\n")
            self.wfile.flush()
        self.wfile.write(b'data: {"choices": [], "usage": {"completion_tokens": 128}}\n\n')
        self.wfile.write(b"data: [DONE]\n\n")
        self.wfile.flush()
ThreadingHTTPServer(("127.0.0.1", 8400), H).serve_forever()
```

它每 10 ms 发一个内容 chunk，共 128 个；最后补一个 `usage.completion_tokens = 128` 的 chunk 和 `[DONE]`。在 `docs/modules/M0-foundations/` 目录下另开一个终端跑：

```bash
python3 scripts/bench_openai.py --base-url http://127.0.0.1:8400 \
    --model mock --max-tokens 128 --concurrency 1 4 --requests 20 \
    --output mock-results.json
```

预期量级：TTFT 是毫秒级，mock 没有 prefill，首 chunk 在请求到达后立即返回；ITL p50 约为 0.010 s 加上解析与线程调度的开销，通常在 10 ms 出头；总延迟减 TTFT 约为 127 × 0.010 ≈ 1.27 s；吞吐随并发近似线性增长，因为 mock 没有真实瓶颈，每个连接各自 sleep、互不排队。这些是预期量级，不是实测成绩；本机跑出来的数有几毫秒偏差属正常。

数字偏离预期时先查三处：mock 是否真的按 10 ms 间隔发（`time.sleep` 的精度与线程调度会让间隔略长）；mock 是否被串行化（换成单线程 `HTTPServer` 会把并发请求排成队，吞吐就不随并发线性涨）；usage chunk 是否带上。没有 usage chunk，脚本会按字符数估算：128 个单字符 chunk 只估成 32 个 token，分母从 127 变成 31，算出来的 ITL 约是真实值的 4 倍。这不是脚本的 bug，是估算口径的边界；mock 验证时把 usage 带上，才能单独验证时间逻辑。

mock 能证明的是尺子本身：计时逻辑、流式解析、并发脚手架、JSON 与表格输出全通了。不能证明任何真实服务的性能：mock 里没有 prefill 计算、没有 KV 缓存、没有显存带宽、没有调度排队，它的延迟只反映 sleep 与 HTTP 开销。mock 上跑出来的数只验证尺子，不证明任何真实服务性能；真实服务的基线要到第 5 章量。

跑一次 `--help` 与一次 mock 扫描，能解释表里每一列是怎么来的，验证就完成了。后面换引擎、换量化、换解码方法时，被测对象变，脚本与固定条件不变，两次结果之差才能归因到被测对象上。

**延伸**：[vLLM 的 OpenAI 兼容服务器文档](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)（`stream`、`stream_options` 等请求字段）、[WHATWG 的 Server-Sent Events 规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)（`data:` 行与事件流解析）。

## 第 5 章 · 跑出第一份基线

**本章目标。** 在固定硬件、模型、引擎与输入输出长度的条件下扫出一条并发曲线，写出第一份可复现的基线：拐点落在哪个区间、尾部有多长、瓶颈更像算力还是带宽。

基线（baseline）是优化开始前的一组测量快照：模型、引擎、输入输出长度和硬件都固定，只让并发变化。它不负责证明系统快，负责回答三个问题：系统在哪一级并发开始顶不住，最慢的一小部分请求要等多久，当前瓶颈更像算力还是带宽。三个问题分别靠整条并发曲线、TTFT 的分位数与 ITL 的中位数，以及把实测数代回第 1 章 Roofline 与第 3 章 profile 的对照来回答。只报一个平均延迟或一个最高吞吐，这三个问题一个都答不了。第 11 章更大规模的扫描、第 12 章的量化、第 13 章的投机解码，都要拿这份数当分母；基线里混进排队，加速比就会随并发变。

### 先探路，再扫三级

先起一个 OpenAI 兼容的推理服务。主路径是第 8 章用 vLLM 起好的服务；SGLang、llama.cpp 的 server 模式也可以，脚本只认 `/v1/chat/completions` 这一个接口。接口不变，尺子就不变：第 10 章换引擎、第 12 章换量化、第 13 章换投机解码，量的都是同一个接口后面的变化。

服务起来后，先用并发 1 跑一两个请求探路。探路只看三件事：TTFT 是不是明显小于总延迟、ITL 是不是在几十毫秒的量级、成功数是不是满的。它筛掉的是服务没起好、模型名写错、端口不对这类错误，别等三级扫描跑完才发现第一级就是错的。探路还兼作热身：服务刚起来的第一批请求可能触发编译与缓存预热，耗时高于稳定态；一两个请求把一次性开销消耗掉，后面的扫描量的才是稳定态。

探路通过后，把会变的条件钉死：脚本里的 prompt、`--max-tokens`、`temperature`（脚本固定为 0）、模型名、引擎版本、服务启动命令。`--max-tokens` 是输出上限，不是实际长度；EOS（End of Sequence，序列结束符）可能提前结束，实际输出 token 数从 JSON 的 `completion_tokens` 里读，填报告时核对。输入输出长度一变，KV 缓存和吞吐跟着变，两次测量的数就没法比——第 2 章的固定长度原则讲的就是这件事。

还要分清客户端并发与服务端并发：`--concurrency` 是客户端同时发多少路，服务端同时跑几路由调度器、KV 缓存和排队决定。客户端压 32 路，不等于服务端同时跑 32 路；拐点量的是整条链路顶住的位置，不是客户端发了多少路。

探路通过后跑三级并发扫描。示例命令，按你的服务改：

```bash
python3 scripts/bench_openai.py \
  --base-url http://localhost:8000 \
  --model <你的模型名> \
  --max-tokens 128 \
  --concurrency 1 8 32 \
  --requests 20 \
  --output bench-baseline.json
```

1、8、32 是建议的三级，不是标准答案：1 是单请求基线，没有排队与竞争，TTFT 与 ITL 最干净；8 是轻度并发，开始出现批处理与排队；32 是压力档，用来看系统在哪一级顶住。服务容量小，32 可能已经饱和；容量大，32 可能还没到拐点。级距要按你的服务调，目标是让第一级没有排队、最后一级明显饱和，拐点夹在中间。级数多了，时间成本跟着上涨；三级够给出拐点区间，更密的扫描留给第 11 章。

每级固定 20 个请求，是为了让各级的分布可比。20 个请求的样本不算大：p50 够看，p95 由最慢的一两个请求决定，p99 基本由最慢的那一个决定；这组数用来比较不同并发级别，不用来把 p99 精确到毫秒。下一节会把 p95 与 p99 的秩算清楚。

`--output` 指定的 JSON 是原始记录：每个请求的 TTFT、总延迟、ITL、token 数和估算标记都在里面。表格是给人看的，JSON 是以后复算用的；丢了 JSON，表上的数就没法追。

### 报告里必须写什么

结果填进 [baseline-report-template.md](baseline-report-template.md)。模板分五块：环境、测量条件、结果、拐点、结论。每一块都决定这份报告能不能当以后对比的分母；缺一项，这份报告就只能给自己看。

环境栏填日期、硬件、驱动 / CUDA、引擎与版本、模型、服务启动命令。没有日期，就不知道这份数是什么时候量的：驱动、引擎、模型任何一项升级，同一张卡上的数都会变。硬件写卡型号与显存，驱动与 CUDA 版本从 `nvidia-smi` 抄；引擎版本用 `pip show vllm` 这类命令取，不凭记忆；模型注明有没有量化；启动命令要完整，模板点名了 `--max-num-seqs`、`--gpu-memory-utilization` 这些会改变调度与显存分配的参数。少写一项，别人拿着同一份报告也复现不出同一组数。

测量条件栏填压测脚本、输入、并发级别与每级请求数、token 数来源。脚本写 `scripts/bench_openai.py`；如果你改过脚本，在报告里注明改了什么，否则分位数的口径可能对不上。输入写固定 prompt：用脚本默认的 `PROMPT` 就照模板写“见脚本内 PROMPT”，改过就把原文贴进报告；`--max-tokens` 写上限。token 数来源写 `usage.completion_tokens` 还是估计值——脚本读不到 usage 时会按字符数估算，并在 JSON 里把 `tokens_estimated` 标为 true。两种来源的 ITL 与吞吐底气不同，不能混着比。

结果表每级一行：并发、成功数 / 请求数、TTFT p50 / p95 / p99、ITL p50、吞吐。成功数要用来看样本有没有偏：脚本只把成功的请求算进分位数，失败请求多了，剩下的样本就有偏；成功数不满，先查服务，不要拿残缺样本的 p95 当结论。TTFT 的三个分位数从 JSON 里取：终端表格只打印 p50 与 p95，p99 在 JSON 的 `ttft_s` 里。ITL 模板只留 p50，先把 decode 的典型节奏钉住；JSON 里另有 ITL p95，要看向尾部就从那里取。吞吐是整级总 token 数除以整级耗时，是系统产出，不是单请求 token 数除以单请求时间。

p99 在 20 个请求上的位置要算清楚。按第 4 章的算法，p95 的秩是 (20 − 1) × 0.95 = 18.05，p99 的秩是 (20 − 1) × 0.99 = 18.81；两个都落在最慢的两个请求之间，p99 基本由最慢的那一个决定。它的作用是给尾巴留一个锚点：告诉你最慢的请求有多慢，不告诉你 1% 分位在哪里。要把长尾量准，每级请求数要到 100 以上（第 2 章讲过样本量）；这份基线先用 20 个请求换执行时间，引用 p99 时记得测量条件里写的是 20，它只是锚点，不是精确分位。

拐点栏写区间，不写点：吞吐增幅塌下来、延迟开始抬头的那一段并发。模板要求同时写“观察到的瓶颈现象”，例如 `num_requests_waiting` 爬升、KV 缓存利用率到顶、出现抢占；如果没接监控、看不到这些指标，就写“未观测”，不要为了填表编一个。这一栏是把拐点从感觉变成证据的地方。

结论按模板写一句话：在哪个并发区间、TTFT p95 / p99 与吞吐是多少、后续拿它当参照；瓶颈方向如果只是初判，就在这一句后面加“更像带宽”或“更像算力”，不要写成定论——定论要等第 3 章的 profile 或后面的对照实验。

### 拐点怎么读

拐点的定义是两个条件同时成立：吞吐不再随并发增长，延迟开始恶化。只看吞吐，会把饱和段当成“还在涨”；只看延迟，会把任何一次抖动当成到顶。两条曲线要一起看。

下面这组是假想读数，只用来练读法，不是任何系统的实测。假设五级并发逐级翻倍（例如 1、2、4、8、16，级距按你的服务定），吞吐依次为 100、190、260、290、295 tok/s：

| 并发级别 | 吞吐 (tok/s) | 相对上一级的增幅 |
|---|---:|---:|
| 第 1 级 | 100 | — |
| 第 2 级 | 190 | 90.0% |
| 第 3 级 | 260 | 36.8% |
| 第 4 级 | 290 | 11.5% |
| 第 5 级 | 295 | 1.7% |

增幅按（本级 − 上一级）÷ 上一级算：100→190 是 90%，190→260 是 70 ÷ 190 ≈ 36.8%，260→290 是 30 ÷ 260 ≈ 11.5%，290→295 是 5 ÷ 290 ≈ 1.7%。并发每级翻倍，健康的区间里吞吐也应该接近翻倍；增幅从 90% 掉到 36.8%、11.5%，最后 1.7%，说明多出来的并发越来越多地花在排队上。

拐点不在最后一个数上，而在增幅已经明显偏离线性、延迟开始抬头的那一段。按这组假想数，增幅在第 3 到第 4 级之间已经掉到 11.5%，第 5 级只剩 1.7%；如果 TTFT p95 也在这两级之间开始上升，拐点就落在第 3 到第 5 级这一段。报告里写这个区间，并把级号换算成实际并发数，不要写成一个精确的点。第 5 级已经进入饱和段，按模板规则不写进结果表：它多出来的不是服务能力，是排队长度。基线报的是服务能力，不是排队能力；优化的目标是把拐点往右推，不是把排队报得好看。拐点不是失败，它和吞吐一样是基线的一部分。

两个常见误解：只跑并发 1 就报基线，回答不了系统能顶到几并发；把吞吐最高的那一级当基线报，那一级往往已经过了拐点，延迟已经恶化。

延迟先抬头的是哪一个数，指向不同的瓶颈：TTFT p95 先抬头，说明请求开始排队等 prefill；ITL 先抬头，说明批处理变大之后 decode 的节奏被拖慢了。两个都不动而吞吐先塌，先查成功数、客户端、网络和脚本本身——服务端的拐点不会只有吞吐一个信号。

基线还要回答瓶颈更像算力还是带宽。排除排队之后（看并发 1 的数），TTFT 大，压力在 prefill；ITL 大，压力在 decode。第 1 章给物理解释：长 prompt 的 prefill 更容易落到计算受限一侧，并发 1 的 decode 通常落在带宽受限一侧。两边对上，才能写“更像算力”或“更像带宽”。再进一步，拿并发 1 的 1/ITL，去和“权重（加 KV）搬运量 ÷ 显存带宽”算出的上限比：贴得近，decode 已经接近带宽上限，下一步是减少搬运（量化，第 12 章）；离得远，先用第 3 章的 profile 看带宽利用率和时间线空白，不要直接归因到算力。TTFT 随并发上升才变长，是排队；并发 1、热身之后仍然长，按固定 prompt 长度估一遍 prefill 时间，对得上才是 prefill 计算量，对不上先查启动与客户端。报告里写方向时，附上你对照的数（实测 1/ITL 与带宽上限，或实测 TTFT 与 prefill 估算），不要只写结论。

基线跑出来看着不对，比如并发 1 的 ITL 远超探路时的量级，别急着换引擎；先回第 3 章用 profiler 看时间花在哪，再把异常和排查过程照实写进报告。照实写的异常能帮以后的自己排除一个方向，编出来的正常数字会把判断带偏。

### 没有 GPU 时怎么办

暂时没有 GPU，也不能编一份基线。能做的和不能做的要分开：

1. 能做的：按第 4 章的方法起一个本地 mock SSE 服务，把 `bench_openai.py` 跑通，确认计时、流式解析、并发脚手架、JSON 与表格输出都对。mock 的 ITL、TTFT、吞吐只证明尺子没坏，不是被测服务的性能。
2. 报告怎么写：环境栏里没有实测依据的项写“待补测”；结果表里没测的格子写“待补测”；拐点写“未测”，瓶颈现象写“未观测”；结论写“无 GPU，未测；脚本已用 mock 验证”。模板开头就写了“没测的写待补测”，这是一种允许的状态，不是不合格。
3. 触发条件写清楚：拿到一台装得下目标模型的 GPU、能起 OpenAI 兼容服务之后，用同一组参数（并发 1 / 8 / 32、每级 20 个请求、同一 prompt 与 `--max-tokens`）重跑，补齐日期、硬件、驱动、引擎版本、模型与启动命令。触发条件要写到别人能照着判断“现在可以补测了”，不是写“以后再说”。硬件条件至少写清目标卡型号与显存下限；显存要装得下权重、KV 缓存与激活。
4. 不要做的：不要把 mock 的数填进结果表，不要拿 mock 吞吐算加速比，不要用“估计”“大概”造一组数。mock 上没有 prefill 计算、KV 缓存、显存带宽和调度排队，这四样缺一个，数就不是基线。

基线是给未来自己看的一份记录：条件写全，原始 JSON 留着，拐点写区间，长尾写清样本量，瓶颈方向写“更像”并附对照。满足这五条，第 11 章更密的扫描、第 12 章的量化对比、第 13 章的投机解码对比才有同一个分母。没有 GPU 时，记录上写“待补测”和触发条件，也比填一组好看的假数有用。
