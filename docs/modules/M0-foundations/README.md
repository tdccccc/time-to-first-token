## 第 1 章 · Roofline：先算，再优化

**本章目标。** 给定模型和硬件，不运行推理服务也能判断瓶颈更可能在算力、显存带宽还是启动开销。

**本章产出。** 一张标出目标模型 prefill 点与 decode 点的 Roofline 草图，外加一页手算记录：每个点的算术强度、判断依据和一条边界条件。

### 问题：换更快的卡，为什么有时没用

先看一个具体问题：一个 7B 模型、FP16 权重、batch=1 的解码请求，生成下一个 token 时，GPU 主要在算什么？

直觉容易把答案说成“算矩阵乘”。但每生成一个 token，模型都要把约 70 亿个权重参数从显存读进计算单元，每个参数只参与一次乘加。计算量很小，搬运量很大。换一块算力翻倍、显存带宽不变的卡，计算时间减半，总时间却几乎不变。

Roofline 模型就是把这类判断变成算术。它用两个量描述一个 kernel：

- **算术强度（arithmetic intensity）**：每搬运 1 字节数据，做了多少次浮点运算，单位是 FLOP/字节。
- **脊点（ridge point）**：硬件峰值算力除以峰值显存带宽，单位也是 FLOP/字节。

把 kernel 的算术强度和硬件的脊点相比：低于脊点，时间主要花在搬运上，叫**显存带宽受限（memory-bound）**；高于脊点，时间主要花在计算上，叫**计算受限（compute-bound）**。还有第三类边界：kernel 太小，计算和搬运都只要微秒级，真正占时间的是启动和同步，叫**开销受限（overhead-bound）**。开销不在 Roofline 的两根线上，需要单独判断。

两个手算公式：

```text
算术强度 = FLOPs / 搬运字节数
运行时间 ≈ max(计算时间, 搬运时间)   # 大 kernel 的近似
```

这两个公式给的是上限和方向，不是精确预测。真实 kernel 还会有启动、同步、访存合并和重叠执行的开销；精确数字要靠 profiling 和压测，第 3、5 章会做。

### 例子：7B 模型解码的一次时间账

取 A100 80GB 的公开规格作示例：FP16 稠密算力约 312 TFLOPS，HBM 带宽约 2 TB/s。不同卡的数字不同，但判断方法不变。

**decode，batch=1。** 每生成一个 token：

- 权重搬运：约 70 亿参数 × 2 字节/参数 ≈ 14 GB。
- 计算量：每个参数一次乘加，一次乘加算 2 FLOP，约 2 × 70 亿 ≈ 14 GFLOP。
- 算术强度：14 GFLOP ÷ 14 GB ≈ 1 FLOP/字节。
- A100 脊点：312 TFLOPS ÷ 2 TB/s = 156 FLOP/字节。
- 计算时间：14 GFLOP ÷ 312 TFLOPS ≈ 0.045 ms。
- 搬运时间：14 GB ÷ 2 TB/s ≈ 7 ms。

搬运时间是计算时间的约 156 倍，所以 decode 落在带宽受限一侧。理论上限约为 1 ÷ 0.007 s ≈ 143 token/s。这个上限不考虑 KV 读取、调度和 kernel 启动，真实服务只会更低；如果测出超过上限的吞吐，先检查测量口径。

这组数还说明：把算力翻倍，0.045 ms 变成 0.022 ms，总时间仍由 7 ms 的搬运决定。算力不是没用，而是当前瓶颈不在它那里。

### 用 batch 与 prefill 看 Roofline 上的位置变化

**增大 batch。** batch=8 时，一次 decode 步骤仍只读一遍 14 GB 权重，但计算量变成 8 × 14 = 112 GFLOP：

- 算术强度：112 GFLOP ÷ 14 GB = 8 FLOP/字节。
- 计算时间：112 GFLOP ÷ 312 TFLOPS ≈ 0.36 ms。
- 搬运时间：仍约 7 ms。

总吞吐约 8 ÷ 0.007 s ≈ 1143 token/s，是 batch=1 的 8 倍；但每个请求仍约每 7 ms 得到一个 token，单请求的 token 间隔没有缩短。batch 提高的是权重复用次数，不是单个请求的带宽。

那 batch 要多大才会翻到计算受限？只算权重时，需要 7 ms ÷ 0.045 ms ≈ 156。batch=156 时计算时间追上搬运时间；更大以后，计算才成为主要成本。这个数是模型和硬件共同决定的，不是通用常数。

**prefill。** prefill 一次处理整段 prompt，权重仍只读一遍，但计算量随输入长度 N 线性增长。矩阵乘部分约为 2 × N × 70 亿 FLOPs：

| 输入长度 N | 权重计算量 | 注意力部分（近似） | 总计算量（近似） | 算术强度（约） | 判断 |
|---:|---:|---:|---:|---:|---|
| 128 | 1.79 TFLOP | 0.004 TFLOP | 1.80 TFLOP | 128 FLOP/字节 | 略低于脊点，带宽受限 |
| 512 | 7.17 TFLOP | 0.069 TFLOP | 7.24 TFLOP | 515 FLOP/字节 | 计算受限 |
| 1024 | 14.34 TFLOP | 0.27 TFLOP | 14.61 TFLOP | 1044 FLOP/字节 | 计算受限 |
| 4096 | 57.34 TFLOP | 4.40 TFLOP | 61.74 TFLOP | 4410 FLOP/字节 | 计算受限 |

表里的注意力部分是数量级估算，不代表具体 kernel 的实测 FLOPs。按“权重计算时间追上权重搬运时间”解交叉点，N 约为 156：短 prompt 的 prefill 仍可能受带宽限制，长 prompt 更可能受计算限制。注意力项随 N² 增长，长上下文下会进一步推高计算占比。

**补上 KV 缓存。** 上面只算了权重，decode 还要读历史 token 的 K、V。以 Llama-3.1-8B 为例：32 层、8 个 KV 头（GQA，grouped-query attention，多个 query 头共享一组 K/V 头）、头维 128、FP16，每 token 的 KV 为：

```text
2（K 和 V）× 32 层 × 8 个 KV 头 × 128 维 × 2 字节 = 131072 字节 = 128 KiB
```

上下文 1024 token、batch=1 时，KV 约 128 MiB，和 14 GB 权重相比很小；batch=8、上下文 1024 时，KV 约 1 GiB，decode 一步的搬运量从 14 GB 变成约 15 GB，时间约从 7.0 ms 变成 7.5 ms。上下文越长、batch 越大，KV 在搬运账里的占比越高。

如果是 MHA（multi-head attention，每个 query 头各存一份 K/V），同一模型的 KV 会是 GQA 的 4 倍。所以看到一个模型的 KV 数字，先确认它的注意力结构和头数，不能只拿参数量套。

### 边界：Roofline 不负责预测什么

它的用途是先排除方向错误，不是替代测量。

- **它不告诉你实测有多快。** 上限和实测之间的差距，来自访存是否合并、占用率、kernel 启动、同步和调度。第 3 章用 profiling 找差距，第 5 章用压测报数字。
- **它不覆盖小 kernel 的启动开销。** 一个只有几十 KB 的逐元素 kernel，计算和搬运可能都远小于微秒，时间由启动与调度决定。推理服务里大量 RMSNorm、激活、采样小算子属于这一类，第 6 章会展开。
- **容量和带宽是两个问题。** 显存容量决定模型和 KV 装不装得下，显存带宽决定 decode 读权重有多快。一块容量大但带宽低的卡，可能装得下模型却仍然跑得慢。
- **算术强度会随 batch、序列长度和缓存结构变化。** 本章的点是示例；实际服务要按自己的 batch、prompt 长度和 KV 配置重算。

## 第 2 章 · 推理度量：四个数，一个分布

**目标**：把“快”拆成四个不会互相掩盖的数，并知道分布比均值重要。

**怎么做**（60 分钟）：

“这个系统快不快？”——这个问题本身就有问题。快可以指用户等得短，可以指输出流畅，可以指系统单位时间产出多，也可以指系统还没被压垮。四个意思压进一个“快”字，答案就没法比较：A 系统用户等得短、B 系统产出多，哪个“更快”？问法错了，答案一定是糊涂账。这一节做的事，就是把“快”拆开，拆成四个各有分工的数，再补上一个分布的概念——四个数加一个分布，合起来才是对推理速度的完整描述。

| 指标 | 英文 | 定义 | 它回答的问题 |
|---|---|---|---|
| 首 token 延迟 | TTFT | 从发请求到收到第一个 token 的时间 | 用户要等多久才看到东西 |
| token 间延迟 | ITL / TPOT | 相邻两个 token 之间的平均时间 | 输出流畅不流畅 |
| 吞吐 | throughput | 单位时间生成的 token 总数 | 系统整体产出 |
| 排队深度 | queue depth | 正在等待的请求数 | 系统是不是已经满了 |

逐个讲透。首 token 延迟（TTFT，time to first token）从请求发出开始算，到第一个 token 到达用户手里为止。它里面装的东西最多：请求在队列里等了多久、prefill 算了多久、第一个 token 生成花了多久，全算在内。用户对 TTFT 的感受最直接：点下发送之后，屏幕多久才开始出现字。TTFT 长，用户觉得系统“卡”；TTFT 短，哪怕后面输出慢一点，用户也觉得系统“有反应”。优化 TTFT 的方向，基本就是第 1 节 prefill 那笔账：prompt 越长、prefill 越重，TTFT 越长；队列越堵，TTFT 里等待的部分越长。

Token 间延迟（ITL，inter-token latency，也叫 TPOT，time per output token）是相邻两个 token 之间的平均时间。它量的是 decode 阶段的速度：第一个 token 出来之后，后面的 token 一个接一个冒出来的节奏。ITL 决定输出看起来流不流畅——ITL 是 20 ms，文字像打字机一样稳定输出；ITL 抖到 200 ms，文字就一顿一顿往外蹦。注意 ITL 是平均值，它把 decode 阶段每一步的时间取了平均；单步的抖动被平均抹掉了，想看抖动要去看分布，见下文。TTFT 与 ITL 必须分开报：TTFT 量的是 prefill，ITL 量的是 decode，第 1 节已经算过，两个阶段落在 Roofline 的两边，瓶颈完全不同。把它们压成一个“延迟”，等于把 prefill 的结论和 decode 的结论搅在一起，谁的问题都看不出来。

吞吐（throughput）是单位时间生成的 token 总数，量的是系统整体产出，不量单个用户的体验。它和前两个数的关系经常被弄反：吞吐高，不代表用户等得短。增大 batch 可以把吞吐推上去——第 1 节算过，batch=8 时总吞吐是 batch=1 的 8 倍——但每个请求自己的 TTFT 与 ITL 可能一点没变，甚至因为排队而变长。吞吐是站在系统一边的数，TTFT 与 ITL 是站在用户一边的数，两边都要报，只报一边就是只讲了一半故事。还有一点容易忽略：吞吐的定义里没有“成功”二字，超时的请求、被丢弃的请求如果也算进 token 数，吞吐会虚高——报吞吐的时候要同时报成功请求数，成功了多少、失败了多少，分母才干净。

排队深度（queue depth）是正在等待的请求数，量的是系统离饱和还有多远。它不直接量速度，量的是压力：排队深度长期为零，系统有余量；排队深度开始往上涨，说明到达的请求超过了系统能处理的速度，TTFT 里等待的部分会跟着涨；排队深度涨到上限，新的请求会被拒绝或者超时。第 5 节找的“拐点”——吞吐不再涨、延迟开始恶化的那个并发数——在排队深度上表现为一条分界线：拐点之前，排队深度基本不动；拐点之后，排队深度一路往上。压测的时候盯着排队深度，拐点出现之前就能看到预兆。

四个数讲完了，补上分布。**为什么只报均值是错的**：用户感受到的是长尾。报 p50、p95、p99——p95 是“95% 的请求比它快”，p99 是尾巴。p50 是中位数，一半请求比它快、一半比它慢；p95 的意思是 100 个请求里 95 个比这个值快，剩下 5 个比它慢；p99 是 100 个请求里 99 个比它快，只有 1 个比它慢。p95 与 p99 量的是“倒霉的用户要等多久”——均值量的是普通情况，p99 量的是最坏的那 1% 的体验，而用户印象最深的往往就是最坏的那一次。

拿一组数走一遍，均值怎么骗人就清楚了。系统 A 收到 100 个请求，99 个的 TTFT 是 100 ms，只有 1 个是 200 ms；系统 B 的 100 个请求 TTFT 全是 101 ms。算均值：A 是 (99 × 100 + 200) / 100 = 101 ms，B 也是 101 ms，均值完全相同。算 p99：A 的 p99 是 200 ms，B 的 p99 是 101 ms，差了约一倍。只看均值，两个系统一模一样；看 p99，A 系统里每 100 个用户就有 1 个要等两倍的时间。均值相同、p99 差一倍，用户体验完全不同——这就是“只报均值是错的”最直接的证据。报数的时候至少要报 p50、p95、p99 三个点：p50 看典型情况，p95 看大多数用户的上限，p99 看尾巴有多长。

**固定长度原则**：输入和输出 token 长度固定下来再测。KV 缓存大小完全由它们决定，长度一变，吞吐跟着变，数字就没法比较。输入越长，prefill 的计算量越大，TTFT 越长；输出越长，decode 的步数越多，总延迟越长；KV 缓存占的显存也跟着长度走，长度一变，batch 能开多大都跟着变。两次压测如果长度不同，数字之间的差分不清是优化带来的还是长度带来的。`bench_openai.py` 默认固定 prompt、固定 `--max-tokens`，就是这个原因：先把长度钉死，再谈快慢，钉不死长度的压测，数字没有可比性。

报分布还有一个容易被忽略的前提：样本量。p99 的意思是 100 个请求里最慢的那 1 个，样本只有 20 个请求，p99 的位置上根本没有一个真实的“1%”——算出来的 p99 其实就是 20 个里最慢的那一个，换一批请求就变。想让 p99 稳定，样本量至少要到 100 个量级，p99 才对应着至少 1 个真实落在尾巴里的请求；样本量越大，尾巴的估计越稳。压测报告里只写 p99 的值、不写样本量，等于只给了结论、没给结论的可信度。第 5 节跑基线时，每级并发固定跑 20 个请求，这个量级看 p50 与均值够用，看 p99 就偏薄——读基线报告的时候，先看请求数，再信 p99。

四个数之间还有一层联动关系，压测的时候要一起看。并发从 1 往上加，吞吐一开始跟着涨，TTFT 与 ITL 基本不动；并发继续加，排队深度开始抬头，TTFT 里等待的部分跟着变长；并发加到拐点之后，吞吐不再涨，TTFT 与 ITL 一起恶化。第 5 节要找的拐点，就是这条联动链由“吞吐涨、延迟不动”翻成“吞吐不动、延迟涨”的位置。只看吞吐，会把拐点之后的系统当成“产出还在涨”；只看延迟，会把拐点之前的系统当成“已经到顶了”。四个数拼在一起，拐点才看得见——这也是第 5 节要求把 TTFT p50/p95/p99、ITL、吞吐、成功请求数同时填进基线报告的原因。

一个常见的误解：“吞吐高等于体验好”——不对。吞吐是系统的产出，体验是用户的等待。Batch 开大，吞吐涨了，但排队深度也涨了，新来的请求要等更久才轮到，TTFT 反而变长。另一个误解是“延迟低等于吞吐高”：单请求延迟低，可能是 batch=1 跑出来的，系统产出未必高。四个数各有分工，缺一个，结论就偏一面；TTFT 与 ITL 再各配上 p50/p95/p99，一份基线才算完整。

## 第 3 章 · Profiling：看时间花在哪

**目标**：拿到一个推理请求的 timeline，能指出来瓶颈在哪个 kernel、哪次访存、哪段等待上。

**怎么做**（60 分钟）：

第 1 节的 Roofline 告诉你瓶颈在算还是在搬运，第 2 节的四个数告诉你慢到底慢在哪一个指标上——但这两样加起来，还是没有告诉你时间具体花在了哪个算子上。Roofline 是理论上限，度量是外部观测，中间缺了一环：打开黑盒，看一个请求在系统里走过的每一步到底各花了多少时间。Profiling（性能分析）补的就是这一环：它把一次推理展开成一条时间线（timeline），时间线上每一段对应一个算子、一次访存、一次等待，瓶颈从一句“受带宽限制”变成一个具体的名字——比如 attention 占了 60%，或者某个 matmul 占了大头。没有这条时间线，优化就是凭感觉下手；有了它，优化的第一刀落在哪，全由时间线说了算。

先看工具全景，再决定从哪一个下手。三个工具的分工不是重叠的，是按粒度分层的：从粗到细，先看整体，再看系统，最后看单个 kernel。顺序反过来会浪费时间——一上来就钻进单个 kernel 的细节，很可能那个 kernel 只占总时间的 5%，钻得再细也省不出多少时间。

| 工具 | 看什么 | 什么时候用 |
|---|---|---|
| PyTorch Profiler（`torch.profiler`） | 每个算子的耗时、显存、CPU 与 GPU 时间线 | 先看这里：它能告诉你时间花在 attention、matmul 还是 launch 开销上 |
| `nsys`（Nsight Systems） | 系统级时间线：CPU、GPU、拷贝、核函数启动 | 跨进程、跨库的问题，比如服务框架的调度开销 |
| `ncu`（Nsight Compute） | 单个 kernel 的细节：占用率、访存效率、指令 mix | 已经定位到某个 kernel，想知道它为什么慢 |

从 `torch.profiler` 开始，因为它离模型代码最近，成本也最低。用 `torch.profiler` 跑一次小模型的前向（CPU 也行），导出 Chrome trace（`chrome://tracing` 可打开），找到最耗时的三个算子。读 trace 的时候先分清两条时间线：CPU 时间线与 GPU 时间线。CPU 时间线上的算子耗时，包含 Python 调用、算子分发、kernel 启动这些 host 端的开销；GPU 时间线上的耗时，是 kernel 在 GPU 上真正跑的时间。一个算子的 CPU 时间比 GPU 时间长得多，往往意味着时间花在启动与调度上，不是花在计算本身。反过来，GPU 时间线上有大段空白，说明 GPU 在等——等数据、等上一个 kernel、等 CPU 把下一个 kernel 发下来。空白本身就是信息：空白越大，说明流水线断得越厉害。

找到最耗时的三个算子之后，对照第 1 节的 Roofline 做判断：最耗时的算子是算术强度高还是低？Attention 的算术强度随序列长度变化，matmul 的算术强度通常较高，逐元素算子（elementwise）的算术强度很低——每个元素读进来、算一次、写回去，搬运与计算的比值接近 1:1。如果一个低算术强度的算子占了大头，优化方向是减少搬运（融合、量化），不是加算力。融合（fusion）是把几个小算子合成一个 kernel，中间结果不写回显存，搬运直接省掉；量化是把数据从 FP16 压到 INT8，同样的数据量搬运时间减半。两个方向都是冲着“搬运”去的，因为 Roofline 已经告诉你，低算术强度的问题出在搬运那根斜线上，加算力等于往横线上加码，斜线上的瓶颈纹丝不动。反过来，如果最耗时的算子算术强度很高、已经顶在算力横线附近，融合与量化帮不上忙，方向是换更快的算法或者更好的 kernel 实现——判断的第一步永远是先看算术强度，再选优化手段。

`nsys` 的用处在跨进程、跨库的问题上。推理服务不是只有一个进程在跑：服务框架的调度、Tokenizer、引擎内部的调度器、CUDA kernel 的启动，这些分布在不同的进程与库里，`torch.profiler` 只能看到模型内部，框架层面的开销它看不到。`nsys` 给的是系统级时间线：CPU、GPU、拷贝、核函数启动全在一张图上。什么时候需要它？症状在框架层的时候：比如 GPU 时间线上有规律的空白，空白的位置正好对应框架在做调度；或者一次请求的延迟里，有一大段既不在算子里也不在访存里——那段就是框架的开销。`nsys` 的读法和 `torch.profiler` 是一样的：先找时间线上的空白与大块，再问空白是谁造成的、大块对应哪个环节。

`ncu` 是最后一步，也是最细的一步。已经定位到某个 kernel、想知道它为什么慢的时候，才轮到它。`ncu` 给的是单个 kernel 的细节：占用率（SM 上同时驻留的 warp 够不够）、访存效率（带宽用到几成、有没有浪费）、指令 mix（时间花在算术指令、访存指令还是控制指令上）。M2 第 1 周会反复用它：先读 SM 利用率与 DRAM 带宽利用率两个数，判断 kernel 是算受限、访存受限还是延迟受限，再按判断改 kernel。本节的要求到“会读、会定位”为止：知道 `ncu` 回答的是“这个 kernel 为什么慢”，而不是“哪个 kernel 慢”——后者是 `torch.profiler` 的活，分工不要弄混。

动手的时候记下两条坑。第一条，`ncu` 需要 CUPTI 权限，在很多云主机上要管理员权限或特定配置，跑不起来先查权限而不是怀疑工具。CUPTI（CUDA Profiling Tools Interface）是 `ncu` 采集硬件计数器的接口，云主机出于安全考虑常常把它锁住；症状是 `ncu` 报错或者采不到数，看起来像工具坏了，实际上是权限没给够。排查顺序是先确认权限与配置，再检查命令本身，最后才考虑工具的问题——顺序反过来，会在工具上浪费半天。第二条，profiling 本身有开销，采样结果用来定位问题，不用来报最终性能数字。Profiler 要记录每个算子的起止时间、要采样硬件计数器，这些记录动作本身就要花时间、占带宽；开的采样越细，开销越大，对小 kernel 的测量失真也越大。正确用法是两步分开：profiling 找瓶颈，关掉 profiler 再跑一次干净的计时报数字。把带 profiler 的数字当成绩报出去，等于把测量工具的成本算进了被测对象的账里。

还有一个常见的误解：“profiler 显示某个算子占了 80%，所以它就是瓶颈”——这句话只对了一半。80% 这个比例要看分母：占 GPU 时间的 80%，和占端到端延迟的 80%，是两回事。如果 GPU 时间只占端到端延迟的一半，另一半是 CPU 等待与框架调度，那么这个算子只占端到端延迟的 40%，剩下的 60% 在时间线上的空白里。读数的时候先问一句：这个百分比的分母是什么？分母是 GPU 时间、CPU 时间，还是端到端延迟？分母不同，结论不同。时间线上的空白和算子的大块一样值得看：空白是等待，大块是执行，瓶颈可能在任意一边。

读 trace 还有两个实操细节。第一，先热身再采样：第一次前向里有 JIT 编译、缓存预热、内存分配这些一次性开销，采到的时间线会被它们污染。做法是先空跑几遍，等时间稳定下来，再开 profiler 采一次——采到的才是稳定态的分布。第二，看空白的位置，不只看大块的宽度。GPU 时间线上一段空白，对应 CPU 时间线上正在做的事：空白正下方如果是 Python 调用与算子分发，说明 GPU 在等 CPU 发 kernel；空白正下方如果是内存拷贝，说明 GPU 在等数据搬完。空白的“邻居”告诉你等待的原因，盯着空白本身是看不出来的。把这两个细节养成习惯，profiling 笔记里除了“最耗时的三个算子”，还要记一句“GPU 时间线上有没有成片的空白、空白对应 CPU 在干什么”——空白的成因，往往比最耗时算子的名字更能决定下一步往哪改。

**产出**：一份一页纸的 profiling 笔记——工具、命令、你看到的最耗时算子、以及你判断的瓶颈类型。

**延伸**：PyTorch 官方 Profiler 文档、[GPU MODE 讲座](https://github.com/gpu-mode/lectures)中 profiling 相关章节。
## 第 4 章 · 写压测脚本：`bench_openai.py`

**本章目标。** 读懂并跑通 bench_openai.py 这个只用 Python 标准库的压测脚本，它面向提供 /v1/chat/completions 的 OpenAI 兼容服务，固定输入、输出上限与并发条件；说清首 token 延迟、token 间延迟与吞吐每个数是怎么算出来的。

压测工具的价值不在它测得多快，在它每次测的条件都一样。手动发请求，换个时间、换个 prompt、换个输出长度，数字就全变了，上一轮的数和这一轮比不了。`bench_openai.py`（[源码](scripts/bench_openai.py)）把会变的条件钉死：固定 prompt、固定 `--max-tokens`、固定并发档位与每档请求数，用同一套计时和统计口径输出结果。脚本只用 Python 标准库，不需要 GPU——GPU 在服务端，客户端只负责发请求、读流、记时间。

### 为什么必须是流式

脚本打的是 OpenAI 兼容接口的 `/v1/chat/completions`，请求体里 `stream` 设为 `true`。首 token 延迟（TTFT，Time to First Token）只能从流里读出来：非流式请求要等整个回答生成完才返回，客户端只拿到一个总延迟，第一个 token 什么时候出来藏在里面。流式返回把生成过程一段段推回来，客户端从第一个 chunk 到达起就能计时；这个时刻就是脚本记的 TTFT。

流式响应体是 SSE（Server-Sent Events，服务器推送事件）：一行行 `data: {...}`，最后一行 `data: [DONE]`。脚本逐行读，遇到第一个非 `[DONE]` 的 JSON 记 TTFT，读到 `[DONE]` 或连接结束记总延迟。

chunk 是传输单位，不是 token 单位：一个 chunk 可能带 0 个、1 个或多个 token。脚本把第一个流式 chunk 当作 TTFT 的终点，这个口径要固定；跨服务端比较时，各家的切 chunk 粒度不同，TTFT 的口径也会跟着变，比较前先确认两边都按第一个 chunk 计时。要更严格，可以改成“第一个 `delta.content` 非空的 chunk”；两种口径都能用，但同一份报告里不能混用。

选接口就是选尺子：第 10 章换引擎、第 12 章换量化、第 13 章换解码方法，量的都是同一个 `/v1/chat/completions` 后面的变化。接口与请求字段固定，数字之间才有可比性。

### 三个时间量怎么算

脚本在发请求前记下 `start = time.perf_counter()`；第一个 chunk 到达时记 `ttft = now - start`；最后一个 chunk 到达时记 `total = now - start`。三个时间量由此得到：

- TTFT：从发请求到收到第一个 chunk 的时间。
- 总延迟：从发请求到收到最后一个 chunk 的时间。
- ITL（Inter-Token Latency，token 间延迟）：相邻两个输出 token 之间的平均时间。

ITL 的算式是 `(total - TTFT) / max(tokens - 1, 1)`。分母是 token 数减一：128 个 token 之间有 127 段间隔。脚本用 `max(tokens - 1, 1)` 防止只输出 1 个 token 时除零；只有 1 个 token 时没有间隔，这个 ITL 实际是首 token 到流结束的那段时间，读到时要知道它是边界情况。

设总延迟 12.8 s，TTFT 0.8 s，128 个 token：ITL = (12.8 − 0.8) ÷ 127 = 12 ÷ 127 ≈ 0.0945 s。验算：127 × 0.0945 ≈ 12.0015 s，与 12.0 s 一致。

TTFT 里包含排队、prefill、网络与客户端解析；ITL 里包含 decode 的每一步以及每个 chunk 的网络与解析。两个都是客户端观测值，不是 GPU 时间；要把 GPU 内部的时间拆开，得用第 3 章的 profiler，排队与网络的部分要靠服务端指标或对照实验。第 1 章 Roofline 说 prefill 与 decode 落在不同区间，TTFT 与 ITL 分开报，才给这个结论提供可验证的读数。

脚本算的是平均 ITL，不是每一步的分布；单步抖动被平均掉了。要看抖动，得另外记录每个 chunk 的到达时间，这一版没有做。

### token 数与固定长度

token 数是 ITL 的分母，也是吞吐的分子，数错了两个数都错。脚本的取法分两档：

1. 优先读 `usage.completion_tokens`。请求里带 `stream_options: {"include_usage": true}`，vLLM 等支持这个字段的服务会在最后一个 chunk 里返回 usage；这是服务端自己数的 token 数。
2. 服务端不支持时，按字符数估算：`max(1, len(text) // 4)`，`text` 是所有 `delta.content` 拼起来的文本。`// 4` 是英文经验值，平均约 4 个字符一个 token；中文一个字符往往就是一个 token 甚至更多，字符数除以 4 会低估 token 数。分母被低估，ITL 会偏大；分子被低估，吞吐会偏小。

脚本固定带上 `stream_options`；如果服务端不认这个字段并直接报错，这一级会整级失败——脚本不会自动去掉它再重试，遇到时要么换支持的服务端，要么改脚本去掉该字段，token 数就退化为估算。

估算值在 JSON 里用 `tokens_estimated` 标记：本级只要有一个请求是估算的，整级就标 `true`。TTFT 不受影响，它的算式里没有 token 数。读结果时先看这个标记，再决定 ITL 与吞吐能信几分。

参数与默认值：

| 参数 | 默认值 | 作用 |
|---|---|---|
| `--base-url` | 必填 | 服务地址；脚本拼上 `/v1/chat/completions` |
| `--model` | 必填 | 服务端的模型名 |
| `--max-tokens` | 128 | 输出 token 上限 |
| `--concurrency` | 1 8 32 | 逐级扫描的并发档位 |
| `--requests` | 20 | 每档的请求数 |
| `--timeout` | 300 | 单请求的 socket 超时，单位秒 |
| `--output` | bench-results.json | 结果 JSON 的路径 |

固定长度是脚本的另一条主线。prompt 是脚本里的常量 `Explain why the sky is blue in one short paragraph.`；`--max-tokens` 默认 128。固定 prompt 就是固定 prefill 的输入长度；`--max-tokens` 固定的是输出上限，不是每个请求的实际输出：模型遇到 EOS（end of sequence，序列结束标记）会提前停，实际 token 数以服务端返回的 `completion_tokens` 为准，脚本用它算 ITL 与吞吐。长度决定 KV 缓存大小与 decode 步数，长度一变，延迟与吞吐跟着变，两次结果就没法比。这是第 2 章固定长度原则在脚本里的落地。

温度设为 0，减少采样随机性；温度 0 不等于逐位可复现，生成长度仍可能因 EOS 的位置而变。要严格固定实际长度，得选一个能稳定跑满 `--max-tokens` 的 prompt，或者在脚本里补上每请求长度的记录——当前汇总不保存这个数。

脚本按 `--concurrency` 列表逐级扫：每级提交 `--requests` 个请求，用 `ThreadPoolExecutor(max_workers=concurrency)` 限制同时在途的请求数；所有请求结束后，用整级墙钟时间（wall time，从提交第一个请求到最后一个请求完成的真实时间）算吞吐：`吞吐 = 本级成功请求的 completion_tokens 之和 / wall_s`。并发是客户端同时在途的请求数，不是服务端同时执行的请求数，服务端调度、排队与 KV 限制都会让两者不同；第 5 章会专门看这个差别。

输出分两种。JSON 记录顶层条件（`base_url`、`model`、`max_tokens`、`prompt`）与每一级的汇总：`concurrency`、`ok`、`requests`、`wall_s`、`ttft_s` 的 `mean/p50/p95/p99`、`itl_s` 的 `mean/p50/p95`、`throughput_tok_per_s`、`tokens_estimated`。它不保存每个请求的原始记录；单请求的 `total_s` 也没有进入汇总，只在 `stream_request` 内部参与 ITL 计算。Markdown 表格打印五列：并发、成功、TTFT p50 / p95、ITL p50、吞吐。失败的请求不进延迟与 token 统计，但它们占用的时间仍计入 wall，所以吞吐会被拉低；全失败时该级显示失败原因。

百分位用线性插值，与第 2 章、第 5 章同一口径：先把本级的值排序，算 `rank = (n − 1) × p / 100`，再在相邻两个值之间插值。20 个请求时，p95 的秩是 19 × 0.95 = 18.05，落在下标 18 与 19 之间，取 `0.95 × x[18] + 0.05 × x[19]`；p99 的秩是 19 × 0.99 = 18.81，取 `0.19 × x[18] + 0.81 × x[19]`。样本只有 20 个，p95 基本由最慢的一两个请求决定，p99 基本就是最慢的那一个。表格只印 TTFT 的 p50/p95 与 ITL 的 p50；JSON 里 TTFT 有 p99，ITL 只有 p50/p95，没有 p99。

### mock 验证能证明什么

验证脚本不需要 GPU：起一个本地 mock SSE 服务，让它按固定节奏吐 chunk，看脚本量出来的时间是否与设定一致。仓库里没有现成的 mock 脚本；把下面这段代码复制出来存成 `mock_sse.py` 运行，它监听 8400 端口：

```python
import json, time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class H(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"
    def log_message(self, *a): pass
    def do_POST(self):
        self.rfile.read(int(self.headers.get("Content-Length", 0)))
        self.send_response(200)
        self.send_header("Content-Type", "text/event-stream")
        self.send_header("Connection", "close")
        self.end_headers()
        for i in range(128):
            if i: time.sleep(0.010)
            self.wfile.write(b"data: " + json.dumps({"choices": [{"delta": {"content": "x"}}]}).encode() + b"\n\n")
            self.wfile.flush()
        self.wfile.write(b'data: {"choices": [], "usage": {"completion_tokens": 128}}\n\n')
        self.wfile.write(b"data: [DONE]\n\n")
        self.wfile.flush()
ThreadingHTTPServer(("127.0.0.1", 8400), H).serve_forever()
```

它每 10 ms 发一个内容 chunk，共 128 个；最后补一个 `usage.completion_tokens = 128` 的 chunk 和 `[DONE]`。在 `docs/modules/M0-foundations/` 目录下另开一个终端跑：

```bash
python3 scripts/bench_openai.py --base-url http://127.0.0.1:8400 \
    --model mock --max-tokens 128 --concurrency 1 4 --requests 20 \
    --output mock-results.json
```

预期量级：TTFT 是毫秒级，mock 没有 prefill，首 chunk 在请求到达后立即返回；ITL p50 约为 0.010 s 加上解析与线程调度的开销，通常在 10 ms 出头；总延迟减 TTFT 约为 127 × 0.010 ≈ 1.27 s；吞吐随并发近似线性增长，因为 mock 没有真实瓶颈，每个连接各自 sleep、互不排队。这些是预期量级，不是实测成绩；本机跑出来的数有几毫秒偏差属正常。

数字偏离预期时先查三处：mock 是否真的按 10 ms 间隔发（`time.sleep` 的精度与线程调度会让间隔略长）；mock 是否被串行化（换成单线程 `HTTPServer` 会把并发请求排成队，吞吐就不随并发线性涨）；usage chunk 是否带上。没有 usage chunk，脚本会按字符数估算：128 个单字符 chunk 只估成 32 个 token，分母从 127 变成 31，算出来的 ITL 约是真实值的 4 倍。这不是脚本的 bug，是估算口径的边界；mock 验证时把 usage 带上，才能单独验证时间逻辑。

mock 能证明的是尺子本身：计时逻辑、流式解析、并发脚手架、JSON 与表格输出全通了。不能证明任何真实服务的性能：mock 里没有 prefill 计算、没有 KV 缓存、没有显存带宽、没有调度排队，它的延迟只反映 sleep 与 HTTP 开销。mock 上跑出来的数只验证尺子，不证明任何真实服务性能；真实服务的基线要到第 5 章量。

跑一次 `--help` 与一次 mock 扫描，能解释表里每一列是怎么来的，验证就完成了。后面换引擎、换量化、换解码方法时，被测对象变，脚本与固定条件不变，两次结果之差才能归因到被测对象上。

**延伸**：[vLLM 的 OpenAI 兼容服务器文档](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)（`stream`、`stream_options` 等请求字段）、[WHATWG 的 Server-Sent Events 规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)（`data:` 行与事件流解析）。

## 第 5 章 · 跑出第一份基线

**目标**：给后面的所有优化一个"优化前"的数字。没有基线，任何加速比都是空话。

**怎么做**（60 分钟，需一台跑着推理服务的机器；没有 GPU 时按本节末尾的规则走 mock 路径）：

先起一个推理服务：M1 第 2 周的 vLLM 服务，或任何 OpenAI 兼容的服务（SGLang、llama.cpp 的 server 模式都可以）。为什么是"任何 OpenAI 兼容的服务"？脚本只认 `/v1/chat/completions` 这一个接口，换引擎不用换尺子，M1 第 5 周换引擎、第 6 周换量化、第 7 周换解码方法，量的都是同一个接口后面的变化。服务起好之后，先用并发 1 跑一两个请求探路：TTFT 是不是在合理的量级、ITL 是不是在几十毫秒的量级、成功数是不是满的。探路这一步是筛子，筛掉的是服务没起好、模型名写错、端口不对这类低级问题，别等到三级扫描跑完才发现第一级就是错的。

探路的请求还有热身的作用：服务刚起来第一次跑，可能触发编译与缓存预热，耗时会比稳定态高，探路把这部分消耗掉，三级扫描量的才是稳定态，热身的请求不用多，一两个就够了，热身的目的是消耗掉一次性开销，不是再跑一轮基线。报告里还要写清 prompt 原文与 --max-tokens 的取值：固定长度固定的是输入与输出上限，实际输出 token 数以 JSON 里记录的为准，填表时核对实际值，别只抄上限。长度、prompt 与温度这三项是复现条件的另一半，缺了它们，别人拿着同一份报告也跑不出同一组数。另外要分清客户端并发与服务端并发：--concurrency 是客户端同时发出的请求数，服务端同时跑几路还受引擎调度与排队限制，客户端压 32 路不等于服务端同时跑 32 路，拐点量的是整条链路顶住的位置，不是客户端发了多少路。

探路通过之后，跑三级并发扫描，例如：`python3 scripts/bench_openai.py --base-url http://localhost:8000 --model <你的模型名> --concurrency 1 8 32 --requests 20 --output bench-baseline.json`。为什么是 1、8、32 这三级？1 是单请求基线，没有排队、没有竞争，TTFT 与 ITL 最干净，后面所有对比都要回到它身上；8 是轻度并发，开始看到排队与批处理的效果，系统从"一个请求独占"过渡到"多个请求共享"；32 是压力档，逼出拐点，看系统在哪一级顶住。级数为什么不多设几档？每级 20 个请求，级数多了时间成本线性上涨，三级够定位拐点所在的区间，精确的拐点以后再加密。为什么每级固定 20 个请求？样本量相同，分布才可比，第 4 节算过，20 个请求时 p95 的秩是 18.05，基本由最慢的一两个请求决定，样本再少，p95 就只剩一个请求在撑，数字抖得没法读。命令里 --output 指定的 JSON 文件就是这份基线的原始记录，丢了它，表格上的数就没法复算。

把结果填进 [baseline-report-template.md](baseline-report-template.md)：硬件、模型、引擎版本、精确的输入输出长度、TTFT p50/p95/p99、ITL、吞吐、以及——最重要的一点——**拐点**：吞吐不再涨、延迟开始恶化的那个并发数。模板里的每一项为什么要记？硬件与引擎版本是复现条件，同一份数换块卡、换个版本就不是同一份数；精确的输入输出长度是第 2 节固定长度原则的书面记录，长度不写下来，以后的对比没法确认条件相同；TTFT p50/p95/p99 与 ITL 是第 2 节的分布要求，均值藏尾巴，p99 才是用户感受到的尾巴；吞吐是系统产出。拐点怎么认？看两条曲线一起变：吞吐的增幅塌下来，同时延迟开始抬头。读法可以拿一组假想读数练一遍，不是实测，只是练读法：假如某次扫描里并发翻倍，吞吐从 100 到 190、再到 260、290、295，增幅从 90% 收窄到 37%、12%、2%，同时 TTFT p95 开始抬头，拐点就在增幅塌下来的那一级附近。再往上加并发，吞吐不涨、延迟涨，多花的并发纯粹是在排队。拐点本身是基线的一部分，不是失败：知道系统在哪一级顶住，和知道它跑多快一样重要。模板里 TTFT 要报 p50/p95/p99 三个数，读的时候要知道三者的底气不一样：20 个请求时 p95 的秩是 18.05，p99 的秩是 (20 − 1) × 0.99 = 18.81，基本就是最慢的那一个请求。p99 写在报告里，作用是留一个尾巴的锚，不是拿它当精确值去比大小。三级扫描能给出的拐点也是一个区间，不是精确到个位的数：拐点落在 8 到 32 之间，报告里就写 8 到 32 之间，别写成一个假精确的数。延迟先抬头的是哪一个数，也值得记一笔：TTFT p95 先抬头，说明请求开始排队等 prefill；ITL 先抬头，说明批处理变大之后 decode 的节奏被拖慢了。两个数谁先动，指向的是不同的瓶颈，这正是第 2 节把 TTFT 与 ITL 分开报的原因在基线里的落地。

饱和点的数据要丢掉，不要报。饱和点之后吞吐的数字不再代表服务能力的增长，只代表排队在变长：请求在队列里等的时间越拉越长，总延迟与 TTFT 跟着涨，吞吐却原地不动。报它会误导后面的对比：M1 第 6 周量化对比、第 7 周投机解码对比，都是拿优化后的数除以这份基线，基线里混进排队，并发一变加速比就跟着变，结论站不住。只报拐点之前的数据，还有一层意思：基线报的是服务能力，不是排队能力，优化的目标是把拐点往右推，不是把排队报得好看。有两个常见误解：只跑并发 1 就报基线，并发 1 的数再干净，也回答不了系统能顶到几并发，后面一上并发就"变慢"，却不知道那是预期的拐点；把吞吐最高的那一级当基线报，吞吐最高的那一级往往已经过了拐点，延迟已经恶化，拿它当参照，等于拿一个已经排队的系统当"优化前"。

基线报告是写给以后的自己看的：到时候 M1 第 6 周要拿量化后的数除以这份基线，报告里缺了硬件、引擎版本、输入输出长度里的任何一项，对比就没法确认条件相同。基线如果一跑出来就看着不对，比如并发 1 的 ITL 就远超探路时看到的量级，别急着换引擎，先回第 3 节拿 profiler 看时间花在哪：基线的作用不只是记录数字，还包括把异常挡在优化开始之前。数字异常的时候，报告里照实写异常与排查过程，同样是一份合格的基线——照实写的异常能帮以后的自己排除一个方向，编出来的正常数字只会把人带偏。

如果这周还没有 GPU：先用 mock 服务验证脚本（第 4 节的方法），基线报告的硬件栏写“待 M1 第 2 周服务就绪后补测”，不要编数字。这条规则没有例外：没有 GPU 就没有真实服务的数字，mock 只能验证脚本，不能代替基线。硬件栏写"待补测"，是一份诚实的未完成，比一份编出来的"基线"有用得多——编出来的数字会在 M1 第 5 周的对比里露馅，到时候分不清是优化没起作用，还是基线本身就是假的。

**产出**：一份填好的基线报告。交之前对照第 4 节的表格读一遍：每一列的数都有 JSON 里的原始记录撑着，成功数是满的，拐点写的是区间不是假精确的数，硬件栏要么填实，要么写待补测，没有第三种状态。它是 M1 第 5 周压测、第 6 周量化对比、第 7 周投机解码对比的共同参照物。
