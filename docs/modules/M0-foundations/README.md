## 第 1 章 · Roofline：先算，再优化

**本章目标。** 给定模型和硬件，不运行推理服务也能判断瓶颈更可能在算力、显存带宽还是启动开销。

### 问题：换更快的卡，为什么有时没用

先看一个具体问题：一个 7B 模型、FP16 权重、batch=1 的解码请求，生成下一个 token 时，GPU 主要在算什么？瓶颈在显存带宽，不在算力：矩阵乘还在做，但每个权重只参与一次乘加，时间主要花在把权重从显存读进来。这个判断不用跑服务，用参数量、精度和硬件的峰值算力、带宽就能算出来。

每生成一个 token，模型都要把约 70 亿个权重参数从显存读进计算单元，每个参数只参与一次乘加：计算量很小，搬运量很大。换一块算力翻倍、显存带宽不变的卡，计算时间减半，总时间却几乎不变。

Roofline 模型就是把这类判断变成算术。它用两个量描述一个 kernel：

- **算术强度（arithmetic intensity）**：每搬运 1 字节数据，做了多少次浮点运算，单位是 FLOP/字节。
- **脊点（ridge point）**：硬件峰值算力除以峰值显存带宽，单位也是 FLOP/字节。

把 kernel 的算术强度和硬件的脊点相比：低于脊点，时间主要花在搬运上，叫**显存带宽受限（memory-bound）**；高于脊点，时间主要花在计算上，叫**计算受限（compute-bound）**。还有第三类边界：kernel 太小，计算和搬运都只要微秒级，真正占时间的是启动和同步，叫**开销受限（overhead-bound）**。开销不在 Roofline 的两根线上，需要单独判断。

两个手算公式：

```text
算术强度 = FLOPs / 搬运字节数
运行时间 ≈ max(计算时间, 搬运时间)   # 大 kernel 的近似
```

这两个公式给的是上限和方向，不是精确预测：真实 kernel 还会有启动、同步、访存合并和重叠执行的开销。

### 例子：7B 模型解码的一次时间账

取 A100 80GB 的公开规格做算例：FP16 稠密算力约 312 TFLOPS，HBM 带宽约 2 TB/s。这是公开规格、用于示例，不是实测；不同卡的数字不同，判断方法不变。

**decode，batch=1。** 每生成一个 token：

- 权重搬运：约 70 亿参数 × 2 字节/参数 ≈ 14 GB。
- 计算量：每个参数一次乘加，一次乘加算 2 FLOP，约 2 × 70 亿 ≈ 14 GFLOP。
- 算术强度：14 GFLOP ÷ 14 GB ≈ 1 FLOP/字节。
- A100 脊点：312 TFLOPS ÷ 2 TB/s = 156 FLOP/字节。
- 计算时间：14 GFLOP ÷ 312 TFLOPS ≈ 0.045 ms。
- 搬运时间：14 GB ÷ 2 TB/s ≈ 7 ms。

搬运时间是计算时间的约 156 倍，decode 落在带宽受限一侧。**只算权重搬运、且一步只生成一个 token** 时，单请求吞吐上限约 1 ÷ 0.007 s ≈ 143 token/s；这个上限不含 KV 读取、调度、kernel 启动与采样，真实服务只会更低。如果测出超过 143 token/s 的单请求吞吐，先检查测量口径（batch 是否真的为 1、是不是一步吐了多个 token、token 数怎么数）。把算力翻倍，0.045 ms 只变成 0.022 ms，总时间仍由 7 ms 的搬运决定：算力不是没用，是当前瓶颈不在它那里。

### 用 batch 与 prefill 看 Roofline 上的位置变化

**增大 batch。** batch=8 时，一次 decode 步骤仍只读一遍 14 GB 权重，但计算量变成 8 × 14 = 112 GFLOP：

- 算术强度：112 GFLOP ÷ 14 GB = 8 FLOP/字节。
- 计算时间：112 GFLOP ÷ 312 TFLOPS ≈ 0.36 ms。
- 搬运时间：仍约 7 ms。

总吞吐约 8 ÷ 0.007 s ≈ 1143 token/s（只算权重，不含 KV），是 batch=1 的 8 倍；但每个请求仍约每 7 ms 得到一个 token，单请求的 token 间隔没有缩短。batch 提高的是权重复用次数，不是单个请求能用的带宽。

那 batch 要多大才会翻到计算受限？只算权重时，令 B × 14 GFLOP / 312 TFLOPS = 7 ms，得 B ≈ 156。batch=156 时计算时间追上搬运时间；更大以后，计算才成为主要成本。这个数是模型和硬件共同决定的，不是通用常数。

**prefill。** 它一次处理整段 prompt，权重仍只读一遍，但计算量随输入长度 N 线性增长。矩阵乘部分约为 2 × N × 70 亿 FLOPs：

| 输入长度 N | 权重计算量 | 注意力部分（估算） | 总计算量（估算） | 算术强度（约） | 判断 |
|---:|---:|---:|---:|---:|---|
| 128 | 1.79 TFLOP | 0.004 TFLOP | 1.80 TFLOP | 128 FLOP/字节 | 略低于脊点，带宽受限 |
| 512 | 7.17 TFLOP | 0.069 TFLOP | 7.24 TFLOP | 517 FLOP/字节 | 计算受限 |
| 1024 | 14.34 TFLOP | 0.27 TFLOP | 14.61 TFLOP | 1044 FLOP/字节 | 计算受限 |
| 4096 | 57.34 TFLOP | 4.40 TFLOP | 61.74 TFLOP | 4410 FLOP/字节 | 计算受限 |

表里的“注意力部分”按 2 × N² × 4096 × 32 估算：32 层、hidden 4096，只计 QK^T 一项，PV、softmax、mask 未计，所以它只表示 N² 的量级，不是完整 attention 的实测 FLOPs。总计算量是权重项加这一项；算术强度用总计算量除以 14 GB 权重搬运量，未计激活与 KV 写入。

令权重计算时间追上权重搬运时间：2N × 7e9 / 312e12 = 14e9 / 2e12，解得 N ≈ 156。短 prompt 的 prefill 仍可能受带宽限制，长 prompt 更可能受计算限制；注意力项随 N² 增长，长上下文下会进一步推高计算占比。只算权重时，batch 阈值、prefill 交叉点和脊点都落在 156：每多一个 token，算术强度就加 1 FLOP/字节，加到脊点就翻到计算侧。

**补上 KV 缓存。** 上面只算了权重，decode 还要读历史 token 的 K、V。以 Mistral-7B 为例：32 层、8 个 KV 头（GQA，grouped-query attention，分组查询注意力：多个 query 头共享一组 K/V 头）、头维 128、FP16，每 token 的 KV 为：

```text
2（K 和 V）× 32 层 × 8 个 KV 头 × 128 维 × 2 字节 = 131072 字节 = 128 KiB
```

上下文 1024 token、batch=1 时，KV 约 128 MiB，和 14 GB 权重相比很小；batch=8、上下文 1024 时，KV 约 1 GiB，decode 一步的搬运量从 14 GB 变成约 15.1 GB，时间约从 7.0 ms 变成 7.5 ms。上下文越长、batch 越大，KV 在搬运账里的占比越高。

如果是 MHA（multi-head attention，多头注意力：每个 query 头各存一份 K/V），同一模型的 KV 会是 GQA 的 4 倍。所以看到一个模型的 KV 数字，先确认注意力结构与头数，不能只拿参数量套。

把 KV 计入搬运量，上面只算权重的上限会下降：batch=8、上下文 1024 时，吞吐上限约 1061 token/s，而不是 1143 token/s。本章的 1143 是只算权重的口径；比较不同来源的数字，先对齐这一点。

### 边界：Roofline 不负责预测什么

Roofline 的用途是排除方向错误，不是替代测量。

- **它不告诉你实测有多快。** 上限和实测之间的差距，来自访存是否合并、占用率、kernel 启动、同步和调度。第 3 章用 profiling 找差距，第 5 章用压测报数字。
- **它不覆盖小 kernel 的启动开销。** 一个只有几十 KB 的逐元素 kernel，计算和搬运可能都远小于微秒，时间由启动与调度决定。推理服务里大量 RMSNorm、激活、采样小算子属于这一类，第 6 章会展开。
- **容量和带宽是两个问题。** 显存容量决定模型和 KV 装不装得下，显存带宽决定 decode 读权重有多快。一块容量大但带宽低的卡，可能装得下模型却仍然跑得慢。
- **算术强度会随 batch、序列长度和缓存结构变化。** 本章的点是示例；实际服务要按自己的 batch、prompt 长度和 KV 配置重算。

## 第 2 章 · 推理度量：四个数，一个分布

**本章目标。** 把“快”拆成四个不会互相掩盖的数，并知道分布比均值重要。

“快”在推理服务里压着四件事：用户等得短、输出流畅、系统单位时间产出多、系统还没被压垮。两个系统分别擅长其中两件时，“哪个更快”没有共同的分母，答案只能是糊涂账。要把“快”变成能比较、能复现的数，得拆成四个各有分工的指标，再补上分布这一层：均值会藏住长尾，而用户记住的往往是最慢的那一次。

### 四个数各自量什么

| 指标 | 英文 | 定义 | 它回答的问题 |
|---|---|---|---|
| 首 token 延迟 | TTFT | 从发请求到收到第一个 token 的时间 | 用户要等多久才看到东西 |
| token 间延迟 | ITL / TPOT | 相邻两个 token 之间的平均时间 | 输出流畅不流畅 |
| 吞吐 | throughput | 单位时间生成的 token 总数 | 系统整体产出 |
| 排队深度 | queue depth | 正在等待的请求数 | 系统是不是已经满了 |

首 token 延迟（TTFT，time to first token）从请求发出算到第一个 token 到达用户手里，里面装着三段：请求在队列里等了多久、prefill 算了多久、第一个 token 生成花了多久。用户对它最敏感：点下发送之后，屏幕多久开始出现字。TTFT 长，用户觉得系统卡；TTFT 短，后面输出慢一点，用户也觉得系统有反应。优化 TTFT 的方向基本就是第 1 章 prefill 那笔账：prompt 越长、prefill 越重，TTFT 越长；队列越堵，等待段越长。

token 间延迟（ITL，inter-token latency，也叫 TPOT，time per output token）量的是 decode 阶段的速度：第一个 token 出来之后，后续 token 一个接一个冒出来的节奏。ITL 为 20 ms 时，文字像打字机一样稳定输出；ITL 抖到 200 ms，文字就一顿一顿往外蹦。它是对整个 decode 阶段取的平均，单步抖动被平均抹掉，要看抖动得看分布。TTFT 与 ITL 必须分开报：TTFT 量 prefill，ITL 量 decode；第 1 章已经算过，小 batch 的 decode 落在带宽受限一侧，prefill 随 prompt 变长翻到算力受限一侧，两个阶段的主瓶颈不同。压成一个“延迟”，两边的结论搅在一起，谁的问题都看不出来。

吞吐（throughput）是单位时间生成的 token 总数，单位 token/s，量的是系统整体产出，不量单个用户的体验。它和前两个数的关系经常被弄反：吞吐高，不代表用户等得短。增大 batch 能推高吞吐——第 1 章算过，batch=8 时总吞吐是 batch=1 的 8 倍——但每个请求自己的 TTFT 与 ITL 可能一点没变，甚至因为排队变长。吞吐是站在系统一边的数，TTFT 与 ITL 是站在用户一边的数，两边都要报，只报一边就是只讲了一半故事。

吞吐的定义里没有“成功”二字：超时和被丢弃的请求如果也算进 token 数，吞吐会虚高，所以报吞吐时要同时报成功请求数，成功多少、失败多少，分母才干净。

排队深度（queue depth）是正在等待的请求数，量的是系统离饱和还有多远。它不直接量速度，量的是压力：排队深度长期为零，系统有余量；它开始往上涨，说明到达的请求超过了系统能处理的速度，TTFT 里等待的部分会跟着涨；涨到上限，新请求会被拒绝或者超时。这个数从服务端指标读，第 9 章的 `num_requests_waiting` 就是它；客户端压测只能从 TTFT 的变化间接推断。第 5 章找的拐点——吞吐不再涨、延迟开始恶化的那个并发数——在排队深度上就是一条分界线：拐点之前基本不动，拐点之后一路往上。压测时盯着排队深度，拐点出现之前就能看到预兆。

### 只报均值为什么不够

报分布，是因为用户感受到的是长尾。p50 是中位数，一半请求比它快、一半比它慢；p95 是 100 个请求里 95 个比它快，剩下 5 个比它慢；p99 是 99 个比它快，只有 1 个比它慢。均值量的是普通情况，p95 与 p99 量的是“倒霉的用户要等多久”——用户印象最深的往往就是最坏的那一次。

均值怎么骗人，两组请求就看得出来。系统 A 的 100 个请求里，99 个 TTFT 是 100 ms、1 个是 200 ms；系统 B 的 100 个请求全是 101 ms。A 的均值是 (99 × 100 + 200) / 100 = 101 ms，B 也是 101 ms，两个系统的均值一模一样。p99 却是 A 为 200 ms、B 为 101 ms，A 的尾巴接近 B 的两倍：A 每 100 个用户就有 1 个要等 200 ms，是其他请求的两倍。均值相同、A 的 p99 接近 B 的两倍，用户体验完全不同，这是只报均值最直接的漏洞。

p95/p99 的具体数值还取决于分位数算法。第 4 章的 `bench_openai.py` 用线性插值，秩按 (n − 1) × q 算、0 对应最小值：20 个请求时，p95 的秩是 (20 − 1) × 0.95 = 18.05，p99 的秩是 (20 − 1) × 0.99 = 18.81，两者的秩都落在最后两个样本之间，p99 基本由最慢的一两个请求决定。样本这么少时，p95 与 p99 只能当尾巴的粗估；换一种分位数算法或换一批请求，数都会动。报数至少要报 p50、p95、p99 三个点：p50 看典型情况，p95 看大多数用户的上限，p99 看尾巴有多长。

### 固定长度与样本量

**固定长度原则**：输入和输出 token 长度固定下来再测。KV 缓存大小完全由这两项决定：输入越长，prefill 的计算量越大，TTFT 越长；输出越长，decode 的步数越多，总延迟越长；KV 缓存占的显存也跟着涨，batch 能开多大都要重算。长度一变，吞吐跟着变，两次压测的数字之间就分不清是优化带来的还是长度带来的。`bench_openai.py` 默认固定 prompt、固定 `--max-tokens`，就是这个原因：先把长度钉死，再谈快慢；钉不死长度的压测，数字没有可比性。

报分布还有一个前提：样本量。p99 的意思是 100 个请求里最慢的那 1 个；样本不到 100 个时，这个位置上就没有一个真实的“1%”，算出来的 p99 只是当前样本里最慢的一两个值，换一批请求就变。想让 p99 稳定，样本量至少要到 100 个量级，p99 才对应至少 1 个真实落在尾巴里的请求；样本量越大，尾巴的估计越稳。压测报告只写 p99 的值、不写样本量，等于只给结论、不给结论的可信度。第 5 章跑基线时每级并发固定跑 20 个请求：这个量级看 p50 与均值够用，看 p95 已经由最慢的一两个请求决定，看 p99 就偏薄——读基线报告时，先看请求数，再信 p99。

### 四个数的联动与结论

四个数之间有联动，压测时要一起看。并发从 1 往上加，吞吐一开始跟着涨，TTFT 与 ITL 基本不动；并发继续加，排队深度开始抬头，TTFT 里等待的部分跟着变长；加到拐点之后，吞吐不再涨，TTFT 与 ITL 一起恶化。第 5 章要找的拐点，就是这条联动链由“吞吐涨、延迟不动”翻成“吞吐不动、延迟涨”的位置。只看吞吐，会把拐点之后的系统当成产出还在涨；只看延迟，会把拐点之前的系统当成已经到顶。第 5 章的基线报告把 TTFT p50/p95/p99、ITL、吞吐和成功请求数放进同一张表，排队深度则看服务端指标。四个数拼在一起，拐点才看得见。

“吞吐高等于体验好”是错的：吞吐是系统产出，体验是用户等待；batch 开大，吞吐涨了，排队深度也涨了，新请求要等更久，TTFT 反而变长。“延迟低等于吞吐高”也是错的：单请求延迟低，可能是 batch=1 跑出来的，系统产出未必高。

读完这一章，手里应该有两样东西：一张四个数的对照表，每个数写清定义、单位、它回答的问题，遇到新指标先往里对号；一份基线报告的指标清单，至少写 TTFT p50/p95/p99、ITL p50、吞吐、成功请求数，再加输入输出长度与每级样本量——长度决定数字能不能比，样本量决定分位数能不能信。第 5 章会用这份清单跑第一份基线。

**延伸**：[NVIDIA：LLM 推理 benchmark 基础概念](https://developer.nvidia.com/blog/llm-benchmarking-fundamental-concepts/)、[Modal：How to Benchmark LLM Engines](https://modal.com/llm-almanac/how-to-benchmark)。

## 第 3 章 · Profiling：看时间花在哪

**目标**：拿到一个推理请求的 timeline，能指出来瓶颈在哪个 kernel、哪次访存、哪段等待上。

**怎么做**（60 分钟）：

第 1 节的 Roofline 告诉你瓶颈在算还是在搬运，第 2 节的四个数告诉你慢到底慢在哪一个指标上——但这两样加起来，还是没有告诉你时间具体花在了哪个算子上。Roofline 是理论上限，度量是外部观测，中间缺了一环：打开黑盒，看一个请求在系统里走过的每一步到底各花了多少时间。Profiling（性能分析）补的就是这一环：它把一次推理展开成一条时间线（timeline），时间线上每一段对应一个算子、一次访存、一次等待，瓶颈从一句“受带宽限制”变成一个具体的名字——比如 attention 占了 60%，或者某个 matmul 占了大头。没有这条时间线，优化就是凭感觉下手；有了它，优化的第一刀落在哪，全由时间线说了算。

先看工具全景，再决定从哪一个下手。三个工具的分工不是重叠的，是按粒度分层的：从粗到细，先看整体，再看系统，最后看单个 kernel。顺序反过来会浪费时间——一上来就钻进单个 kernel 的细节，很可能那个 kernel 只占总时间的 5%，钻得再细也省不出多少时间。

| 工具 | 看什么 | 什么时候用 |
|---|---|---|
| PyTorch Profiler（`torch.profiler`） | 每个算子的耗时、显存、CPU 与 GPU 时间线 | 先看这里：它能告诉你时间花在 attention、matmul 还是 launch 开销上 |
| `nsys`（Nsight Systems） | 系统级时间线：CPU、GPU、拷贝、核函数启动 | 跨进程、跨库的问题，比如服务框架的调度开销 |
| `ncu`（Nsight Compute） | 单个 kernel 的细节：占用率、访存效率、指令 mix | 已经定位到某个 kernel，想知道它为什么慢 |

从 `torch.profiler` 开始，因为它离模型代码最近，成本也最低。用 `torch.profiler` 跑一次小模型的前向（CPU 也行），导出 Chrome trace（`chrome://tracing` 可打开），找到最耗时的三个算子。读 trace 的时候先分清两条时间线：CPU 时间线与 GPU 时间线。CPU 时间线上的算子耗时，包含 Python 调用、算子分发、kernel 启动这些 host 端的开销；GPU 时间线上的耗时，是 kernel 在 GPU 上真正跑的时间。一个算子的 CPU 时间比 GPU 时间长得多，往往意味着时间花在启动与调度上，不是花在计算本身。反过来，GPU 时间线上有大段空白，说明 GPU 在等——等数据、等上一个 kernel、等 CPU 把下一个 kernel 发下来。空白本身就是信息：空白越大，说明流水线断得越厉害。

找到最耗时的三个算子之后，对照第 1 节的 Roofline 做判断：最耗时的算子是算术强度高还是低？Attention 的算术强度随序列长度变化，matmul 的算术强度通常较高，逐元素算子（elementwise）的算术强度很低——每个元素读进来、算一次、写回去，搬运与计算的比值接近 1:1。如果一个低算术强度的算子占了大头，优化方向是减少搬运（融合、量化），不是加算力。融合（fusion）是把几个小算子合成一个 kernel，中间结果不写回显存，搬运直接省掉；量化是把数据从 FP16 压到 INT8，同样的数据量搬运时间减半。两个方向都是冲着“搬运”去的，因为 Roofline 已经告诉你，低算术强度的问题出在搬运那根斜线上，加算力等于往横线上加码，斜线上的瓶颈纹丝不动。反过来，如果最耗时的算子算术强度很高、已经顶在算力横线附近，融合与量化帮不上忙，方向是换更快的算法或者更好的 kernel 实现——判断的第一步永远是先看算术强度，再选优化手段。

`nsys` 的用处在跨进程、跨库的问题上。推理服务不是只有一个进程在跑：服务框架的调度、Tokenizer、引擎内部的调度器、CUDA kernel 的启动，这些分布在不同的进程与库里，`torch.profiler` 只能看到模型内部，框架层面的开销它看不到。`nsys` 给的是系统级时间线：CPU、GPU、拷贝、核函数启动全在一张图上。什么时候需要它？症状在框架层的时候：比如 GPU 时间线上有规律的空白，空白的位置正好对应框架在做调度；或者一次请求的延迟里，有一大段既不在算子里也不在访存里——那段就是框架的开销。`nsys` 的读法和 `torch.profiler` 是一样的：先找时间线上的空白与大块，再问空白是谁造成的、大块对应哪个环节。

`ncu` 是最后一步，也是最细的一步。已经定位到某个 kernel、想知道它为什么慢的时候，才轮到它。`ncu` 给的是单个 kernel 的细节：占用率（SM 上同时驻留的 warp 够不够）、访存效率（带宽用到几成、有没有浪费）、指令 mix（时间花在算术指令、访存指令还是控制指令上）。M2 第 1 周会反复用它：先读 SM 利用率与 DRAM 带宽利用率两个数，判断 kernel 是算受限、访存受限还是延迟受限，再按判断改 kernel。本节的要求到“会读、会定位”为止：知道 `ncu` 回答的是“这个 kernel 为什么慢”，而不是“哪个 kernel 慢”——后者是 `torch.profiler` 的活，分工不要弄混。

动手的时候记下两条坑。第一条，`ncu` 需要 CUPTI 权限，在很多云主机上要管理员权限或特定配置，跑不起来先查权限而不是怀疑工具。CUPTI（CUDA Profiling Tools Interface）是 `ncu` 采集硬件计数器的接口，云主机出于安全考虑常常把它锁住；症状是 `ncu` 报错或者采不到数，看起来像工具坏了，实际上是权限没给够。排查顺序是先确认权限与配置，再检查命令本身，最后才考虑工具的问题——顺序反过来，会在工具上浪费半天。第二条，profiling 本身有开销，采样结果用来定位问题，不用来报最终性能数字。Profiler 要记录每个算子的起止时间、要采样硬件计数器，这些记录动作本身就要花时间、占带宽；开的采样越细，开销越大，对小 kernel 的测量失真也越大。正确用法是两步分开：profiling 找瓶颈，关掉 profiler 再跑一次干净的计时报数字。把带 profiler 的数字当成绩报出去，等于把测量工具的成本算进了被测对象的账里。

还有一个常见的误解：“profiler 显示某个算子占了 80%，所以它就是瓶颈”——这句话只对了一半。80% 这个比例要看分母：占 GPU 时间的 80%，和占端到端延迟的 80%，是两回事。如果 GPU 时间只占端到端延迟的一半，另一半是 CPU 等待与框架调度，那么这个算子只占端到端延迟的 40%，剩下的 60% 在时间线上的空白里。读数的时候先问一句：这个百分比的分母是什么？分母是 GPU 时间、CPU 时间，还是端到端延迟？分母不同，结论不同。时间线上的空白和算子的大块一样值得看：空白是等待，大块是执行，瓶颈可能在任意一边。

读 trace 还有两个实操细节。第一，先热身再采样：第一次前向里有 JIT 编译、缓存预热、内存分配这些一次性开销，采到的时间线会被它们污染。做法是先空跑几遍，等时间稳定下来，再开 profiler 采一次——采到的才是稳定态的分布。第二，看空白的位置，不只看大块的宽度。GPU 时间线上一段空白，对应 CPU 时间线上正在做的事：空白正下方如果是 Python 调用与算子分发，说明 GPU 在等 CPU 发 kernel；空白正下方如果是内存拷贝，说明 GPU 在等数据搬完。空白的“邻居”告诉你等待的原因，盯着空白本身是看不出来的。把这两个细节养成习惯，profiling 笔记里除了“最耗时的三个算子”，还要记一句“GPU 时间线上有没有成片的空白、空白对应 CPU 在干什么”——空白的成因，往往比最耗时算子的名字更能决定下一步往哪改。

**产出**：一份一页纸的 profiling 笔记——工具、命令、你看到的最耗时算子、以及你判断的瓶颈类型。

**延伸**：PyTorch 官方 Profiler 文档、[GPU MODE 讲座](https://github.com/gpu-mode/lectures)中 profiling 相关章节。
## 第 4 章 · 写压测脚本：`bench_openai.py`

**目标**：有一套自己的、可复现的压测工具，后续所有模块都用它，数字之间才能比较。

**怎么做**（60 分钟，无 GPU 可做，纯 Python）：

这节只干一件事，就是把第 2 节那张表里的量变成一个每次运行都给出同样答案的程序。先读 [scripts/bench_openai.py](scripts/bench_openai.py)，它是本模块的产物，只用 Python 标准库，不需要 GPU 也可以跑通逻辑。脚本量的是四个量：TTFT、总延迟、ITL 和 token 数。为什么要写成脚本，而不是每次手动发请求看一眼？手动发请求看到的数没法复现：换个时间、换个 prompt、换个输出长度，数字全变了，上一周的数和这一周的数比不了。脚本的作用，是把所有会变的条件钉死，只让被测对象变。钉死的东西后面会逐项讲，先把这句话立住：压测工具的价值不在它测得多快，在它每次测的条件都一样。脚本只用 Python 标准库，不需要 GPU 也可以跑通逻辑——GPU 在服务端，脚本这边只有计时与解析。

脚本打的是 OpenAI 兼容接口的 `/v1/chat/completions`，而且是流式。为什么必须是流式？TTFT 只能从流里读出来：第一个 chunk 到达的时刻就是首个 token 产生的时刻。非流式请求要等整个回答生成完才返回，只给一个总延迟，TTFT 藏在里面出不来。流式返回是一行行以 data: 开头的 SSE（Server-Sent Events，服务器推送事件）chunk，最后一行是 [DONE]，表示流结束。脚本逐行读这些 chunk，记下第一个 chunk 到达的时间、最后一个 chunk 到达的时间，三个时间量就从这一行行 chunk 里长出来了。反过来，选接口就是选尺子：M1 第 5 周换引擎、第 6 周换量化、第 7 周换解码方法，量的都是同一个接口后面的变化，接口换了，数字之间就没法比较了。

三个时间量先分清，再算。TTFT 是从发请求到收到第一个 chunk 的时间；总延迟是从发请求到收到最后一个 chunk 的时间；ITL 是相邻两个 token 之间的平均时间，算式是（总延迟 − TTFT）÷（token 数 − 1）。分母为什么是 token 数减 1，不是 token 数？token 之间有几段间隔，数一数就知道了：5 个 token 之间是 4 段间隔，128 个 token 之间是 127 段间隔。拿一组数走一遍：总延迟 12.8 秒，TTFT 0.8 秒，128 个 token，ITL = (12.8 − 0.8) ÷ 127 = 12 ÷ 127 ≈ 0.0945 秒。验算一下：127 × 0.0945 ≈ 12.0015，基本就是 12 秒，账是平的。TTFT 与 ITL 为什么要分开报？第 2 节已经讲过，这里的算式让理由更具体：TTFT 里装的是 prefill 的时间，ITL 里装的是 decode 的节奏，一个管"等多久才看到东西"，一个管"输出流不流畅"。压成一个"延迟"，等于把 prefill 与 decode 的结论混在一起，第 1 节 Roofline 里 prefill 与 decode 分属两个区间的结论也就没法验证了。分开报不是格式要求，是第 1 节的物理结论在测量上的对应物。

token 数是 ITL 的分母，也是吞吐的分子，数错了，两个数全错。脚本数 token 的办法分两档，一档是读数，一档是估算。读数优先：优先读流式最后一个 chunk 的 `usage.completion_tokens`，vLLM 支持 `stream_options.include_usage`，开了这个选项，服务器会在最后一个 chunk 里把用量带回来，这是服务器自己数的，最准。服务器不支持时退一步估算：按字符数估算，并在结果里标明是估计值。估算的办法是字符数除以 4——英文平均约 4 个字符一个 token，这是个经验换算，不是测量。估算值要标明，是因为它是有偏的：中文字符占比高时，一个字符往往就是一个 token 甚至更多，字符数除以 4 会把 token 数低估，ITL 与吞吐跟着被带偏。标明估计值，就是告诉读数的人，这两个数的底气比 TTFT 弱一档。反过来，TTFT 不依赖 token 数，估算再偏也碰不到它：TTFT 只看第一个 chunk 到达的时刻，分母里没有 token 数。读一份压测结果的时候，先看 token 数是实测还是估计，再决定 ITL 与吞吐能信几分，这个顺序就是这一节的读数方法。

固定长度是脚本的另一条主线。脚本固定 prompt 与 `--max-tokens`，按 `--concurrency` 列表逐级扫并发，每级固定 `--requests` 个请求，输出 JSON 与 Markdown 表格。固定 prompt 与输出长度，理由在第 2 节的固定长度原则里：KV 缓存的大小完全由输入输出长度决定，长度一变，吞吐跟着变，数字就没法比较。逐级扫并发，理由是只测一个并发点看不出拐点：并发 1 的数再干净，也回答不了"系统能顶到几并发"，拐点要扫出来，不是猜出来。每级固定 `--requests` 个请求，理由是样本量相同，分布才可比：每级 20 个请求，p50 是第 10 个与第 11 个顺序值的中间，p95 的秩是 (20 − 1) × 0.95 = 18.05，基本由最慢的一两个请求决定。p95 的底气薄到这个程度，读 p95 的时候就要知道，它反映的是尾巴，不是整体。输出分两种，JSON 存每个请求的原始记录与每一级的汇总，留着以后复算；Markdown 表格打印到终端，给人一眼读：并发、成功、TTFT p50/p95、ITL p50、吞吐。表格的每一列都要会读：并发是本级压了多少路；成功是成功数比请求数，失败的请求不进统计，成功数掉了先查服务，而不是先读数；TTFT p50 与 p95 是首 token 延迟的分布，一半请求与 95% 的请求分别比它快；ITL p50 是 decode 节奏的中位数；吞吐是总 token 数除以整级的耗时，是系统级的产出，不是单请求 token 数除以单请求时间——这个区别要分清，ITL 是请求级的，吞吐是系统级的，两个数一个管流畅，一个管产出。

**验证脚本本身**（无 GPU 可做）：用一个本地 mock SSE 服务跑通一次——2026-11-12 已对本地 mock SSE 服务器跑通过：mock 服务每 10ms 吐一个 chunk，脚本测出的 ITL 应为约 0.011s，TTFT 接近 0，并发 4 时的吞吐应约为并发 1 的数倍（mock 服务无真实瓶颈，仅验证测量逻辑）。这三个数每一个都能算出为什么。ITL 约 0.011 秒，是 10ms 的 chunk 间隔加上约 1ms 的开销：理想情况下 ITL 就是 0.010 秒，实测 0.011 秒，多出来的 1ms 是解析 chunk、记时间、拼文本的开销。拿默认输出 128 个 token 走一遍：总延迟减 TTFT 是 127 × 0.011 ≈ 1.397 秒，理想值是 127 × 0.010 = 1.27 秒，两者差 0.127 秒，摊到 127 段间隔上，每段正好约 1ms，账是平的。TTFT 接近 0，是因为 mock 没有真实的 prefill 计算：首 chunk 在请求到达后立即发出，TTFT 里只剩网络与解析的开销，是毫秒级；相对 1.397 秒的总延迟，TTFT 若为 0.002 秒，占比只有约 0.14%。"接近 0"是相对总延迟而言的，不是真的等于 0。并发 4 的吞吐约为并发 1 的 4 倍，也是算出来的：mock 里没有真实瓶颈，4 路并行互不干扰，wall 时间除以 4，总 token 数不变，吞吐就乘以 4。按默认 128 个 token、每级 20 个请求推算，每请求约 1.397 秒，并发 1 时 20 个请求串行，wall 时间约 27.94 秒，总 token 数 2560，吞吐约 91.6 tok/s；并发 4 时 5 批跑完，wall 时间约 6.99 秒，吞吐约 366.5 tok/s，比值正好是 4.00。实测比值偏离 4，先查 mock 本身有没有串行化，而不是庆祝。

mock 验证能证明什么、不能证明什么，要分得清清楚楚。能证明的是尺子本身：计时逻辑、流式解析、并发脚手架、JSON 与表格输出全通了，脚本没有把时间记错、没有把 chunk 解析错。不能证明的是真实服务的任何性能数字：真实服务里有 prefill 计算、KV 缓存、显存带宽、调度排队，mock 里全都没有。打个比方，mock 验证像拿标准砝码校秤：砝码验的是秤准不准，秤准了不代表货物有多重。一个常见的误解：mock 上吞吐高，等于服务快——不是，mock 上跑出来的数只说明尺子没坏，服务的快慢要到第 5 节的真服务上量。尺子与被测对象是两回事，mock 验的是前者。

**产出**：在你自己的机器上跑通 `python3 scripts/bench_openai.py --help`，并理解输出表格里每一列的含义。

## 第 5 章 · 跑出第一份基线

**本章目标。** 在固定硬件、模型、引擎与输入输出长度的条件下扫出一条并发曲线，写出第一份可复现的基线：拐点落在哪个区间、尾部有多长、瓶颈更像算力还是带宽。

基线（baseline）是优化开始前的一组测量快照：模型、引擎、输入输出长度和硬件都固定，只让并发变化。它不负责证明系统快，负责回答三个问题：系统在哪一级并发开始顶不住，最慢的一小部分请求要等多久，当前瓶颈更像算力还是带宽。三个问题分别靠整条并发曲线、TTFT 的分位数与 ITL 的中位数，以及把实测数代回第 1 章 Roofline 与第 3 章 profile 的对照来回答。只报一个平均延迟或一个最高吞吐，这三个问题一个都答不了。第 11 章更大规模的扫描、第 12 章的量化、第 13 章的投机解码，都要拿这份数当分母；基线里混进排队，加速比就会随并发变。

### 先探路，再扫三级

先起一个 OpenAI 兼容的推理服务。主路径是第 8 章用 vLLM 起好的服务；SGLang、llama.cpp 的 server 模式也可以，脚本只认 `/v1/chat/completions` 这一个接口。接口不变，尺子就不变：第 10 章换引擎、第 12 章换量化、第 13 章换投机解码，量的都是同一个接口后面的变化。

服务起来后，先用并发 1 跑一两个请求探路。探路只看三件事：TTFT 是不是明显小于总延迟、ITL 是不是在几十毫秒的量级、成功数是不是满的。它筛掉的是服务没起好、模型名写错、端口不对这类错误，别等三级扫描跑完才发现第一级就是错的。探路还兼作热身：服务刚起来的第一批请求可能触发编译与缓存预热，耗时高于稳定态；一两个请求把一次性开销消耗掉，后面的扫描量的才是稳定态。

探路通过后，把会变的条件钉死：脚本里的 prompt、`--max-tokens`、`temperature`（脚本固定为 0）、模型名、引擎版本、服务启动命令。`--max-tokens` 是输出上限，不是实际长度；EOS（End of Sequence，序列结束符）可能提前结束，实际输出 token 数从 JSON 的 `completion_tokens` 里读，填报告时核对。输入输出长度一变，KV 缓存和吞吐跟着变，两次测量的数就没法比——第 2 章的固定长度原则讲的就是这件事。

还要分清客户端并发与服务端并发：`--concurrency` 是客户端同时发多少路，服务端同时跑几路由调度器、KV 缓存和排队决定。客户端压 32 路，不等于服务端同时跑 32 路；拐点量的是整条链路顶住的位置，不是客户端发了多少路。

探路通过后跑三级并发扫描。示例命令，按你的服务改：

```bash
python3 scripts/bench_openai.py \
  --base-url http://localhost:8000 \
  --model <你的模型名> \
  --max-tokens 128 \
  --concurrency 1 8 32 \
  --requests 20 \
  --output bench-baseline.json
```

1、8、32 是建议的三级，不是标准答案：1 是单请求基线，没有排队与竞争，TTFT 与 ITL 最干净；8 是轻度并发，开始出现批处理与排队；32 是压力档，用来看系统在哪一级顶住。服务容量小，32 可能已经饱和；容量大，32 可能还没到拐点。级距要按你的服务调，目标是让第一级没有排队、最后一级明显饱和，拐点夹在中间。级数多了，时间成本跟着上涨；三级够给出拐点区间，更密的扫描留给第 11 章。

每级固定 20 个请求，是为了让各级的分布可比。20 个请求的样本不算大：p50 够看，p95 由最慢的一两个请求决定，p99 基本由最慢的那一个决定；这组数用来比较不同并发级别，不用来把 p99 精确到毫秒。下一节会把 p95 与 p99 的秩算清楚。

`--output` 指定的 JSON 是原始记录：每个请求的 TTFT、总延迟、ITL、token 数和估算标记都在里面。表格是给人看的，JSON 是以后复算用的；丢了 JSON，表上的数就没法追。

### 报告里必须写什么

结果填进 [baseline-report-template.md](baseline-report-template.md)。模板分五块：环境、测量条件、结果、拐点、结论。每一块都决定这份报告能不能当以后对比的分母；缺一项，这份报告就只能给自己看。

环境栏填日期、硬件、驱动 / CUDA、引擎与版本、模型、服务启动命令。没有日期，就不知道这份数是什么时候量的：驱动、引擎、模型任何一项升级，同一张卡上的数都会变。硬件写卡型号与显存，驱动与 CUDA 版本从 `nvidia-smi` 抄；引擎版本用 `pip show vllm` 这类命令取，不凭记忆；模型注明有没有量化；启动命令要完整，模板点名了 `--max-num-seqs`、`--gpu-memory-utilization` 这些会改变调度与显存分配的参数。少写一项，别人拿着同一份报告也复现不出同一组数。

测量条件栏填压测脚本、输入、并发级别与每级请求数、token 数来源。脚本写 `scripts/bench_openai.py`；如果你改过脚本，在报告里注明改了什么，否则分位数的口径可能对不上。输入写固定 prompt：用脚本默认的 `PROMPT` 就照模板写“见脚本内 PROMPT”，改过就把原文贴进报告；`--max-tokens` 写上限。token 数来源写 `usage.completion_tokens` 还是估计值——脚本读不到 usage 时会按字符数估算，并在 JSON 里把 `tokens_estimated` 标为 true。两种来源的 ITL 与吞吐底气不同，不能混着比。

结果表每级一行：并发、成功数 / 请求数、TTFT p50 / p95 / p99、ITL p50、吞吐。成功数要用来看样本有没有偏：脚本只把成功的请求算进分位数，失败请求多了，剩下的样本就有偏；成功数不满，先查服务，不要拿残缺样本的 p95 当结论。TTFT 的三个分位数从 JSON 里取：终端表格只打印 p50 与 p95，p99 在 JSON 的 `ttft_s` 里。ITL 模板只留 p50，先把 decode 的典型节奏钉住；JSON 里另有 ITL p95，要看向尾部就从那里取。吞吐是整级总 token 数除以整级耗时，是系统产出，不是单请求 token 数除以单请求时间。

p99 在 20 个请求上的位置要算清楚。按第 4 章的算法，p95 的秩是 (20 − 1) × 0.95 = 18.05，p99 的秩是 (20 − 1) × 0.99 = 18.81；两个都落在最慢的两个请求之间，p99 基本由最慢的那一个决定。它的作用是给尾巴留一个锚点：告诉你最慢的请求有多慢，不告诉你 1% 分位在哪里。要把长尾量准，每级请求数要到 100 以上（第 2 章讲过样本量）；这份基线先用 20 个请求换执行时间，引用 p99 时记得测量条件里写的是 20，它只是锚点，不是精确分位。

拐点栏写区间，不写点：吞吐增幅塌下来、延迟开始抬头的那一段并发。模板要求同时写“观察到的瓶颈现象”，例如 `num_requests_waiting` 爬升、KV 缓存利用率到顶、出现抢占；如果没接监控、看不到这些指标，就写“未观测”，不要为了填表编一个。这一栏是把拐点从感觉变成证据的地方。

结论按模板写一句话：在哪个并发区间、TTFT p95 / p99 与吞吐是多少、后续拿它当参照；瓶颈方向如果只是初判，就在这一句后面加“更像带宽”或“更像算力”，不要写成定论——定论要等第 3 章的 profile 或后面的对照实验。

### 拐点怎么读

拐点的定义是两个条件同时成立：吞吐不再随并发增长，延迟开始恶化。只看吞吐，会把饱和段当成“还在涨”；只看延迟，会把任何一次抖动当成到顶。两条曲线要一起看。

下面这组是假想读数，只用来练读法，不是任何系统的实测。假设五级并发逐级翻倍（例如 1、2、4、8、16，级距按你的服务定），吞吐依次为 100、190、260、290、295 tok/s：

| 并发级别 | 吞吐 (tok/s) | 相对上一级的增幅 |
|---|---:|---:|
| 第 1 级 | 100 | — |
| 第 2 级 | 190 | 90.0% |
| 第 3 级 | 260 | 36.8% |
| 第 4 级 | 290 | 11.5% |
| 第 5 级 | 295 | 1.7% |

增幅按（本级 − 上一级）÷ 上一级算：100→190 是 90%，190→260 是 70 ÷ 190 ≈ 36.8%，260→290 是 30 ÷ 260 ≈ 11.5%，290→295 是 5 ÷ 290 ≈ 1.7%。并发每级翻倍，健康的区间里吞吐也应该接近翻倍；增幅从 90% 掉到 36.8%、11.5%，最后 1.7%，说明多出来的并发越来越多地花在排队上。

拐点不在最后一个数上，而在增幅已经明显偏离线性、延迟开始抬头的那一段。按这组假想数，增幅在第 3 到第 4 级之间已经掉到 11.5%，第 5 级只剩 1.7%；如果 TTFT p95 也在这两级之间开始上升，拐点就落在第 3 到第 5 级这一段。报告里写这个区间，并把级号换算成实际并发数，不要写成一个精确的点。第 5 级已经进入饱和段，按模板规则不写进结果表：它多出来的不是服务能力，是排队长度。基线报的是服务能力，不是排队能力；优化的目标是把拐点往右推，不是把排队报得好看。拐点不是失败，它和吞吐一样是基线的一部分。

两个常见误解：只跑并发 1 就报基线，回答不了系统能顶到几并发；把吞吐最高的那一级当基线报，那一级往往已经过了拐点，延迟已经恶化。

延迟先抬头的是哪一个数，指向不同的瓶颈：TTFT p95 先抬头，说明请求开始排队等 prefill；ITL 先抬头，说明批处理变大之后 decode 的节奏被拖慢了。两个都不动而吞吐先塌，先查成功数、客户端、网络和脚本本身——服务端的拐点不会只有吞吐一个信号。

基线还要回答瓶颈更像算力还是带宽。排除排队之后（看并发 1 的数），TTFT 大，压力在 prefill；ITL 大，压力在 decode。第 1 章给物理解释：长 prompt 的 prefill 更容易落到计算受限一侧，并发 1 的 decode 通常落在带宽受限一侧。两边对上，才能写“更像算力”或“更像带宽”。再进一步，拿并发 1 的 1/ITL，去和“权重（加 KV）搬运量 ÷ 显存带宽”算出的上限比：贴得近，decode 已经接近带宽上限，下一步是减少搬运（量化，第 12 章）；离得远，先用第 3 章的 profile 看带宽利用率和时间线空白，不要直接归因到算力。TTFT 随并发上升才变长，是排队；并发 1、热身之后仍然长，按固定 prompt 长度估一遍 prefill 时间，对得上才是 prefill 计算量，对不上先查启动与客户端。报告里写方向时，附上你对照的数（实测 1/ITL 与带宽上限，或实测 TTFT 与 prefill 估算），不要只写结论。

基线跑出来看着不对，比如并发 1 的 ITL 远超探路时的量级，别急着换引擎；先回第 3 章用 profiler 看时间花在哪，再把异常和排查过程照实写进报告。照实写的异常能帮以后的自己排除一个方向，编出来的正常数字会把判断带偏。

### 没有 GPU 时怎么办

暂时没有 GPU，也不能编一份基线。能做的和不能做的要分开：

1. 能做的：按第 4 章的方法起一个本地 mock SSE 服务，把 `bench_openai.py` 跑通，确认计时、流式解析、并发脚手架、JSON 与表格输出都对。mock 的 ITL、TTFT、吞吐只证明尺子没坏，不是被测服务的性能。
2. 报告怎么写：环境栏里没有实测依据的项写“待补测”；结果表里没测的格子写“待补测”；拐点写“未测”，瓶颈现象写“未观测”；结论写“无 GPU，未测；脚本已用 mock 验证”。模板开头就写了“没测的写待补测”，这是一种允许的状态，不是不合格。
3. 触发条件写清楚：拿到一台装得下目标模型的 GPU、能起 OpenAI 兼容服务之后，用同一组参数（并发 1 / 8 / 32、每级 20 个请求、同一 prompt 与 `--max-tokens`）重跑，补齐日期、硬件、驱动、引擎版本、模型与启动命令。触发条件要写到别人能照着判断“现在可以补测了”，不是写“以后再说”。硬件条件至少写清目标卡型号与显存下限；显存要装得下权重、KV 缓存与激活。
4. 不要做的：不要把 mock 的数填进结果表，不要拿 mock 吞吐算加速比，不要用“估计”“大概”造一组数。mock 上没有 prefill 计算、KV 缓存、显存带宽和调度排队，这四样缺一个，数就不是基线。

基线是给未来自己看的一份记录：条件写全，原始 JSON 留着，拐点写区间，长尾写清样本量，瓶颈方向写“更像”并附对照。满足这五条，第 11 章更密的扫描、第 12 章的量化对比、第 13 章的投机解码对比才有同一个分母。没有 GPU 时，记录上写“待补测”和触发条件，也比填一组好看的假数有用。
