### 第 1 节 · 国产芯片全景：先列清单，再问“能不能跑推理”

**目标**：列出一张芯片清单，标出各自的软件栈，并用同一把尺子衡量它们。

**怎么做**（30 分钟，无硬件可做）：

1. 打开 [awesome-china-gpu](https://github.com/bytetora/awesome-china-gpu/blob/HEAD/README.md)（国产芯片推理适配进度追踪表），先看它给的分析框架——**Four Walls（四面墙）**：生态（ecosystem）、显存（memory）、通信（communication）、精度（precision）。**这四面墙就是衡量一块芯片“能不能跑推理”的尺子**：生态决定有没有框架插件、显存决定能放多大的模型、通信决定多卡能不能扩展、精度决定量化后准不准。先记下这个框架，后面每一周都会用它来归因。
2. 按追踪表列出主线芯片：昇腾（Ascend）、寒武纪、摩尔线程、海光、昆仑芯、天数智芯、壁仞、燧原、沐曦。每个只记两项：软件栈叫什么、推理引擎的接入方式是什么（vLLM 插件 / 容器镜像 / 原生框架）。不要展开写参数——参数会过期，接入方式才是地图上稳定的部分。
3. 注意追踪表的时效：表里引用的引擎对比与支持状态有明确的核实日期（例如 2026 年 6 月的对比表）。**抄表的时候把日期一起抄下来**，过期即作废——第 5 节会把这条变成制度。

**产出**：一张芯片清单（芯片 × 软件栈 × 接入方式），并写下 Four Walls 四面墙的定义。

### 第 2 节 · 软件栈分层：驱动 → SDK → 算子库 → 框架插件 → 推理引擎

**目标**：画出分层图，并说清每一层坏了会在哪一层暴露出来。

**怎么做**（30 分钟，无硬件可做）：

1. 画五层：**驱动**（认不认卡、能不能分配显存）→ **SDK**（CANN、DTK、MUSA 这类厂商软件栈：编译器、运行时、算子库）→ **算子库**（TBE/AscendC 写的算子、厂商提供的融合算子）→ **框架插件**（vllm-ascend、vllm-musa 这类把芯片接进 vLLM 的包）→ **推理引擎**（vLLM、SGLang 本身）。
2. 对每一层问一个问题：“如果这一层缺东西，用户会在哪一层看到症状？”——驱动缺失：卡认不出来；算子库缺失：某个算子回退到 CPU 或低效实现（第 4 周的覆盖分析就是查这个）；插件缺失：引擎根本启动不了。**分层图的用处就是定位问题在哪一层**，而不是笼统地说“国产芯片不行”。
3. 用 Four Walls 对照分层：生态墙对应框架插件层、显存墙对应驱动与 SDK 的显存管理、通信墙对应多卡互联（SDK 层）、精度墙对应算子库的量化实现。两张图叠在一起，就是一张“问题定位地图”。

**产出**：一张分层图 + 每层的“缺失症状”一句话。

### 第 3 节 · 插件机制：vLLM 是怎么做到一块代码跑多家芯片的

**目标**：能讲清插件算子的替换点（M2 第 6 周讲的是算子级 CustomOp，这里是平台级插件）。

**怎么做**（30 分钟，无硬件可做）：

1. 区分两个层次的“插件”：M2 第 6 周的 CustomOp 是**算子级**替换（一个 SiluAndMul 换成你的 Triton 版）；这里的 vllm-ascend 是**平台级**插件——它给 vLLM 提供一整套芯片适配：平台类（`NPUPlatform`）、算子实现、注意力后端、通信、编译配置。模型代码不用改，换的是底下的整套实现。
2. 打开 [vllm-ascend](https://github.com/vllm-project/vllm-ascend)，看它的顶层结构：`vllm_ascend/` 下有 `platform.py`（`NPUPlatform`）、`ops/`（算子）、`attention/`（注意力后端）、`model_executor/`、`quantization/`、`patch/`、`worker/`、`compilation/`、`device/`、`distributed/`、`profiler/`、`_cann_ops_custom/`、`ascend_config.py`、`meta_registration.py`。**第 3 周的任务之一就是在这些目录里定位到具体算子的实现位置**——先把地图记下来。
3. 理解注册链：插件被 vLLM 加载后，注册它的平台类；vLLM 启动时按设备选平台，后面的算子分发、注意力后端选择、编译配置都跟着平台走。**算子分发发生在平台选定之后**——这是第 3 周要展开的细节，本节先记住顺序：先选平台，再分发算子。

**产出**：一页笔记：平台级插件与算子级 CustomOp 的区别 + vllm-ascend 的目录地图。

### 第 4 节 · 统一算子层：FlagGems / FlagCX 的思路

**目标**：讲清统一层解决了什么、没解决什么。

**怎么做**（30 分钟，无硬件可做）：

1. 读 [vllm-plugin-FL 文档](https://docs.flagos.io/projects/vllm-plugin-FL/en/latest/overview/features.html)：它提供两个统一库——**FlagGems**（统一算子库）与 **FlagCX**（统一通信库），加一个插件把它们接进 vLLM。
2. 理解它的分发逻辑：**优先级分发**——先找 FlagGems 的统一实现，没有再找厂商实现，再没有回退到 PyTorch 参考实现，自动 fallback。平台自动检测：启动时识别当前芯片，选对应的后端。支持的平台包括 NVIDIA、Ascend、T-Head、Iluvatar、MetaX、摩尔线程、Tsingmicro、海光、燧原、昆仑芯、阿里巴巴 PPU、CPU ARM64。
3. 讲清边界：统一层解决的是“**一份 kernel 代码跑多家芯片**”的问题（写一次，到处跑）；它没解决的是“每家芯片的峰值性能”——统一实现为了可移植会牺牲一部分特化优化，**要榨干某块芯片的性能，最终还是要写它的原生算子**（第 2 周的 AscendC、第 5 周的移植案例就是这条路）。这与 M2 第 5 周“Triton vs CUTLASS”的取舍是同一个逻辑，换了一块芯片。
4. 再看 [FlagTree](https://github.com/flagos-ai/FlagTree)：它是 FlagGems 背后的算子开发框架——算子用一套抽象写出来，再针对不同芯片生成实现。第 5 周移植时会再遇到它。

**产出**：一页笔记：统一层解决了什么、没解决什么 + 分发优先级链。

### 第 2 节 · TBE 与 AscendC：两代算子抽象长什么样

**目标**：讲清一个算子的抽象长什么样——定义、编译、调用三段分别是什么。

**怎么做**（30 分钟，无硬件可做）：

1. 先讲两代的区别：**TBE 是上一代**——用 DSL 描述算子（定义输入输出、写计算表达式），再由编译器生成 kernel；**AscendC 是当前的主力**——用 C++ 直接写算子，算子是一个类，计算过程拆成流水线任务。两代的抽象不同，但链路相同：**定义 → 编译 → 调用**。
2. 这条链路的三个环节，每个环节的产物是什么：
   - **定义**：算子的接口（输入输出的 shape 与 dtype）与计算逻辑（AscendC 里是一个带 `Init` 与 `Process` 方法的类）；
   - **编译**：AscendC 编译器把算子源码编成可在 NPU 上跑的 kernel（产物是 kernel 二进制 + 注册信息）；
   - **调用**：框架（PyTorch / vLLM）通过算子名找到它，把输入张量传进去，launch kernel。vllm-ascend 的 `_cann_ops_custom/` 目录就是自定义算子的落点——第 3 周会在那里定位具体算子。
3. 对照 M2 的经验：Triton 里你写的是“一个 kernel 函数 + grid”，AscendC 里你写的是“一个算子类 + 流水线任务”。**抽象变了，但“写 kernel → 验证 → 接入”这套流程没变**——第 5 周的移植案例就是把 M2 的 Triton kernel 沿这条链路搬过去。
4. 官方文档锚点：AscendC 开发文档（CANN 8.5.0 版）与向量编程指南（80RC2 版）——版本不同，API 细节可能有出入，读的时候以你所装 CANN 版本对应的文档为准：
   - [CANN 8.5.0 AscendC 开发文档](https://www.hiascend.com/document/detail/zh/canncommercial/850/opdevg/Ascendcopdevg/atlas_ascendc_map_10_0002.html)
   - [CANN 80RC2 向量编程指南](https://www.hiascend.com/document/detail/zh/canncommercial/80RC2/developmentguide/opdevg/Ascendcopdevg/atlas_ascendc_10_0021.html)

**产出**：一页笔记：TBE vs AscendC 的抽象对比 + “定义 → 编译 → 调用”链路图。

### 第 3 节 · AscendC 流水线模型：读懂一个向量加法算子

**目标**：读懂 AscendC 的流水线编程模型，能说出每个部件是干什么的。

**怎么做**（30 分钟，无硬件可做；代码为示意骨架，可编译版以官方文档为准）：

1. 打开 CANN 8.5.0 AscendC 开发文档里的向量加法例子（`add_custom`），先看 kernel 入口——它长这样：

```cpp
// 示意骨架：结构与名字以 CANN 8.5.0 AscendC 开发文档的 add_custom 为准
extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z) {
    // op.Init(...); op.Process();
}
```

2. 理解流水线模型的五个部件（对照文档里的定义）：
   - **TPipe**：统一的资源管理——算子里的内存、事件都由它管；
   - **TQue**：任务间通信与同步的队列——CopyIn、Compute、CopyOut 三个任务通过它接力；
   - **InitBuffer / AllocTensor**：在 `Init` 里做——给 GlobalTensor 设地址、给队列分配 buffer；
   - **TBuf**：临时内存——中间结果放这里；
   - **CopyIn / Compute / CopyOut**：`Process` 里调的三步——把输入从 Global Memory 搬进片上、算、把结果搬回去。**这三步与 Triton 的“load → 算 → store”是一一对应的**，只是 AscendC 把它显式拆成了三个任务。
3. 理解核类型：`KERNEL_TASK_TYPE_DEFAULT(KERNEL_TYPE_AIV_ONLY)` 表示这个 kernel 只用向量核（AIV）。Ascend 的核分两种——向量核（AIV）与矩阵核（AIC，跑矩阵乘）；一个算子用哪种核，在定义时就定下来了。**这就是第 4 周覆盖分析时要查的东西**：一个算子在芯片侧有没有实现、用的是哪种核。
4. 对照 M2 的 Triton：Triton 里 block 大小、访存模式由编译器管；AscendC 里流水线的每一步都要你显式写出来。**控制粒度更细，代码量更大**——这就是移植时要付的代价，第 5 周会逐条记录。

**产出**：一份 AscendC 流水线模型笔记（五个部件 + 三步流程 + 核类型），能向别人讲清 `add_custom` 的执行过程。

### 第 4 节 · 一个算子的完整链路：从定义到被 vLLM 调用

**目标**：能画出一个算子从定义到被调用的完整链路，并说清每个环节的产物。

**怎么做**（30 分钟，无硬件可做）：

1. 选一个具体的算子做追踪对象（建议：vllm-ascend 里一个你第 3 周会用到的算子，比如 RMSNorm——M2 第 6 周提到过它是 CustomOp 的可替换面，这里的链路是它的芯片侧版本）。在 `vllm_ascend/ops/` 与 `_cann_ops_custom/` 里找到它的实现位置。
2. 沿链路填这张表：

| 环节 | 产物 | 在哪找 |
|---|---|---|
| 定义 | AscendC 算子类（Init / Process） | 厂商文档或 `vllm_ascend` 的自定义算子目录 |
| 编译 | kernel 二进制 + 注册信息 | CANN 编译流程（文档） |
| 注册 | 算子名 → 实现的映射 | `torch_npu` 的算子注册 / vllm-ascend 的 `meta_registration.py` |
| 调用 | 框架前向里的一次算子调用 | vLLM 模型代码里调用该算子的位置 |

3. 回答三个问题：① 算子名是在哪一层被解析的（框架层还是插件层）？② 如果这个算子在芯片侧没有实现，会发生什么（回退 CPU？报错？静默走低效实现？）——**这个问题的答案就是第 4 周覆盖矩阵里要填的内容**；③ 换一个 CANN 版本，链路的哪一环最可能变（编译产物？注册方式？）？
4. 把答案写下来，标上核实日期与来源（文档链接或源码文件路径）。

**产出**：一张“定义 → 编译 → 调用”链路表 + 三个问题的答案（带核实日期）。

### 第 2 节 · 逐条对照：哪些算子在芯片侧有对应实现，哪些会回退

**目标**：出一份算子覆盖矩阵——每个算子在芯片侧的状态是什么。

**怎么做**（30 分钟，无硬件可做；对照依据是官方文档与插件源码，核实不了的标“待核实”）：

1. 对第 1 节清单里的每个算子（至少覆盖 Top 10），查它在芯片侧的状态，分四档：

   - **插件实现**：vllm-ascend 的 `ops/` 或 `_cann_ops_custom/` 里有实现（第 3 周第 3 节定位过这类位置）；
   - **回退**：没有芯片侧实现，走 CPU 或 PyTorch 参考实现（慢，但能跑）；

| 算子（PyTorch 名） | 耗时占比 | 芯片侧状态 | 实现位置（文件/文档链接） | 核实日期 |

| `aten::mm` | … | 原生实现 | … | 某年某月 |

### 第 3 节 · 迁移 benchmark 怎么做：读懂 TritonAscendBench 的设计

**目标**：理解迁移评测的设计——它测什么、怎么判分、没卡时能做什么。

**怎么做**（30 分钟，无硬件可做）：

1. 打开 [TritonAscendBench](https://github.com/Gxj230958/TritonAscendBench)（评测生产级 Triton kernel 从 GPU 迁移到 Ascend 的可用性），先看规模：101 个任务，分 L1（36 个）、L2（35 个）、L3（30 个）三档难度。
2. 理解它的工作流：`tab init-solution`（生成解法骨架）→ `tab run`（跑评测）→ `tab run-suite`（批量跑）→ `tab package` / `tab validate-submission`（打包与校验提交）。解法的入口是 `npu_triton_impl(inputs) -> dict`——**必须是一个真正的 Triton kernel**，不能是 PyTorch 的取巧实现。
3. 理解它的判分：正确性在 CPU 上对照 PyTorch oracle 判分（有容限分级）；性能需要在 910B 上实测。`tab run` 默认 `--backend npu`，`--backend gpu` 是 CUDA 自查（先确认 kernel 在 GPU 上是对的，再谈迁移）。**没有 NPU 时结果会标 `npu_antihack_unverified`**——不是静默的 GPU 回退，这个标记本身就是诚实设计。
4. 看它的 worked example：`USAGE.md` 里的 `L2_04_silu_and_mul`——一个完整的 silu_and_mul Triton kernel（M2 第 6 周写过同一个算子，第 5 周会移植它）。先读懂这个例子的 kernel 与评测方式，第 5 周直接用它练手。
5. 注意版本：它的 NPU 环境参考配置在 `docker/Dockerfile.npu` 里（CANN 8.5.0、torch_npu 2.8.0.post1、triton_ascend 3.2.0）——与第 2 周的 vllm-ascend 锚点（CANN 9.2.1）**不是同一套版本**。不同工具钉不同版本是常态，记录时写清“这一步用的是哪套版本”，不要混在一起。

**产出**：一页笔记：TritonAscendBench 测什么、怎么判分、没卡时能做到哪一步。

1. 回顾第 1 周第 4 节：FlagGems（统一算子库）+ FlagCX（统一通信库）+ vllm-plugin-FL（接进 vLLM 的插件），分发优先级是 FlagGems → 厂商实现 → PyTorch 参考，自动 fallback。
2. 再看 [FlagTree](https://github.com/flagos-ai/FlagTree)：它是 FlagGems 背后的算子开发框架——算子用一套抽象写出来，再针对不同芯片生成实现。读它的 README，回答：① 一个算子的“统一描述”长什么样；② 针对不同芯片的生成发生在什么时候（编译时？运行时？）；③ 如果某块芯片上统一实现跑不起来，回退链是怎样的。
3. 对照第 2 节的移植：FlagGems 的路线是“**写一次，生成多份**”，第 4 节的路线是“**手写一份，再逐条改**”。两种路线的取舍与 M2 第 5 周“Triton vs CUTLASS”是同一个逻辑：统一实现省人力、牺牲特化性能；手写移植费人力、能榨干单芯片性能。**移植案例要记录的不仅是“改了什么”，还有“为什么这条路线的取舍是这样”**。

**产出**：一页机制笔记（统一描述 → 按芯片生成 → 回退链）+ 两种移植路线的取舍。

### 第 4 节 · 动手：移植 M2 的 SiluAndMul 到 TritonAscendBench 的 L2_04

**目标**：出一份真实的移植记录（含失败的尝试）。

**怎么做**（30 分钟，需 NPU 环境或至少 GPU 自查；无卡时做 GPU 自查 + 移植计划，NPU 步骤标注“待有卡后补测”）：

1. 取 M2 第 6 周写的 Triton 版 SiluAndMul（二维 grid、mask、fp32 SiLU、cast 回输入精度再乘），用 `tab init-solution` 生成 `L2_04_silu_and_mul` 的解法骨架，把 kernel 填进 `npu_triton_impl(inputs) -> dict`。
2. 先跑 GPU 自查：`tab run --backend gpu`——确认 kernel 在 CUDA 上正确。这是迁移的基线：**GPU 上不对的东西，搬到 NPU 上也不会对**。
3. 再跑 NPU：`tab run`（默认 `--backend npu`）。每遇到一个不兼容点，按第 2 节的表头记一行：现象（报错原文）、定位（kernel 里的哪一行、哪个 API）、改法、重测结果。**改完一个测一个，不要攒一堆改动再测**——否则失败归因不清。
4. 判分说明：正确性在 CPU 上对照 PyTorch oracle 判分（有容限分级）；性能需要在 910B 上实测；没有 NPU 时结果标 `npu_antihack_unverified`——**这个标记要原样写进记录**，不要把它当成“通过”。
5. 无卡时：完成第 1–2 步（GPU 自查通过）+ 一份移植计划（按 kernel 的每一行，写出“这一行在 triton-ascend 上可能有什么问题、准备怎么验证”——写“可能”与“准备怎么验证”，不写定论），NPU 步骤标注“待有卡后补测”。

**产出**：一份移植记录（不兼容点逐条：现象 + 定位 + 改法 + 重测结果；无卡时为 GPU 自查结果 + 移植计划）。

### 第 3 节 · 差异分析：数字不同的原因——归因到具体算子

**目标**：把差异归因到具体算子，而不是笼统地说“芯片不行”。

**怎么做**（30 分钟，分析无卡可做；归因需要第 1–2 节的数据与第 4 周的覆盖矩阵）：

1. 先分两类差异：**精度差异**与**性能差异**，归因方法不同。
2. 精度差异的归因（量化误差的来源）：
   - **量化方案的差异**：两边的量化实现是不是同一套（per-channel / per-token 的 scale 取法、舍入方式）——第 4 周的覆盖矩阵里记了每个算子的实现位置，对照着查；
   - **低精度算子的差异**：FP16 / INT8 的实现是不是同一精度（比如一边用了 FP8、另一边没有）；
   - **归因方法**：二分法——一次只换一个变量（比如先把可疑算子换成 PyTorch 参考实现跑一遍，看差异是否消失），差异消失的那个算子就是回归的来源。**归因的终点是一个算子名，不是“精度墙”三个字**。
3. 性能差异的归因（对照第 4 周的结论与 Four Walls）：
   - 算子覆盖（第 4 周的矩阵：有没有算子回退到 CPU 或低效实现）；
   - 显存带宽（第 1 周的 Roofline 思路：搬运量有没有变——比如权重精度不同导致搬运量不同）；
   - 调度（高并发下掉得快的一边，先看它的批处理与 KV 管理）。
4. 写一份归因记录：每个差异一行——差异（数字）、候选原因（2–3 个）、验证方法（怎么确认是哪一个）、结论（归因到哪个算子或哪面墙，证据是什么）。**验证不了的写“待验证”，不要写成定论**。

**产出**：一份差异归因记录（差异 + 候选原因 + 验证方法 + 结论）。

### 第 4 节 · 写报告：按「某年某月某版本实测」的格式，把环境、版本、命令、结果写全

**目标**：写出 **M3 的可交付物：跨芯片对比报告（初稿）**。

**怎么做**（30 分钟，无硬件可做；没有实测数据的章节写框架 + “待补测”）：

1. 用 `docs/modules/M3-domestic-chips/cross-chip-report-template.md` 的模板写报告。模板的每一节都要填：环境（硬件型号、驱动、版本号、核实日期）、模型、评测集、命令（启动命令与压测命令全文）、结果（第 1–2 节的两张表）、归因（第 3 节的记录）。
2. **报告的可复现性标准**：别人拿着这份报告，能在同一版本的软硬件上复现出同一量级的数字——命令要全、版本要全、评测集要定。做不到的章节写“待补测”，不要编数字凑完整。
3. 报告的结论部分只写有证据的结论：有数据的写数据 + 归因；没数据的写“待补测”与下一步计划。

**产出**：**M3 的可交付物：跨芯片对比报告（初稿）**。

## 其他芯片的切入点

本模块以 Ascend 为主线，因为它的生态最成熟、资料最多。其他芯片的切入点供学完主线后扩展（状态以 [awesome-china-gpu](https://github.com/bytetora/awesome-china-gpu/blob/HEAD/README.md) 的最新追踪为准，不要照抄这里的版本信息）：

- **海光 DCU**：DTK（基于 ROCm），vLLM 容器镜像，迁移成本相对低
- **昆仑芯 XPU**：vllm-kunlun 插件
- **天数智芯 Iluvatar**：DeepSparkInference / vllm-iluvatar
- **壁仞 MetaX**：vllm-metax 插件
- **多芯片统一接入**：[vllm-plugin-FL](https://docs.flagos.io/projects/vllm-plugin-FL/en/latest/overview/features.html)（FlagGems 统一算子库 + FlagCX 统一通信库）
