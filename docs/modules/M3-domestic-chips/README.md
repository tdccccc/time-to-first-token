# M3 · 国产芯片适配

> 前置：第一部分（度量、profiling、压测脚本）与第二部分（vLLM/SGLang 已跑通）。本部分的终点：同一模型、同一评测集，在 NVIDIA 与至少一种国产芯片上都跑通、压测，并写出一份可复现的对比报告。
>
> 规则：国产芯片适配进展极快，任何写死的支持矩阵都会很快过时。本部分不写静态结论，只给方法论和可复现的验证脚本；涉及具体芯片、具体版本的实测结果，按「某年某月某版本实测」记录，由读者自行验证后填写。

## 为什么单开一个模块

调研结论：国产芯片适配**没有任何动手的学习材料**，只有框架插件、一张支持状态追踪表和零散厂商文档。M3 要补的就是这一块：从“知道有这些芯片”到“真的在上面跑起模型、量出数字”。

## 第 25 章 · 芯片与软件栈地图：先画地图，再谈适配

第 27 章会把同一个模型真的放到 Ascend 上跑起来，第 26 章会拆开 CANN 的算子链路。在动手之前，有一个更基础的问题：一块没见过的国产芯片摆在面前，怎么判断它能不能跑推理、缺的是哪一层、这个判断能管多久？

难的不是芯片，是缺少坐标系。厂商文档各写各的，支持状态散在追踪表、插件仓库和发行说明里；同一句“支持”，可能指引擎能启动，也可能指某个算子在某个版本上跑通过。没有统一的坐标，适配就退化成每遇到一块新卡都重新打听一遍，打听来的结论还没有地方放。

本章先画这张地图：9 块芯片的清单、4 面墙的判断、5 层软件栈、插件与统一算子层各自的位置，最后合成一张每个格子都带核实日期的表。地图不回答哪块芯片更强，只回答这块芯片走到了哪一步、下一步该查什么。

**本章目标。** 给定一块国产芯片和一个目标模型，能画出它从驱动到推理引擎的五层软件栈，用生态、显存、通信、精度四面墙判断它能不能跑推理，并写出一张每格都带核实日期、过期即作废的软件栈地图。

### 第 1 节 · 国产芯片全景：先列清单，再问“能不能跑推理”

先列名字。[awesome-china-gpu](https://github.com/bytetora/awesome-china-gpu/blob/HEAD/README.md) 这张追踪表的主线芯片列了 9 块：昇腾、寒武纪、摩尔线程、海光、昆仑芯、天数智芯、壁仞、燧原、沐曦。9 是追踪表当时的条目数，不是国产芯片厂商的全集：没有进表的芯片照样存在，进了表也不等于已经支持推理。名单的用处是给地图定横轴，横轴上每多一个点，就多一套要核实的软件栈；9 块芯片，每块记软件栈与接入方式两项，一共 18 个待填格。

判断能不能跑，用四面墙。Four Walls（四面墙）来自 awesome-china-gpu 这张社区维护的追踪表，是它组织支持状态时用的分析框架，不是任何机构发布的官方标准。四面墙是四个问题：生态（ecosystem）、显存（memory）、通信（communication）、精度（precision）。生态墙问有没有框架插件、容器镜像或原生框架把芯片接进主流推理引擎；显存墙问权重、KV 缓存与激活放不放得下；通信墙问一块卡不够用时，多卡并行能不能扩展；精度墙问量化之后输出还能不能用。四面墙缺一面，结论就不完整：生态再好，显存装不下也跑不起来；显存再大，量化后输出乱码也交不了差。

显存墙先算一笔账，因为它是四面墙里最像算术的一面。7B 模型（70 亿参数）在 FP16 下，每个参数 2 字节，70 亿 × 2 = 140 亿字节，即 14 GB。GB 按十进制算，1 GB = 10<sup>9</sup> 字节，与第 1 章 7B 权重 14 GB 的算法一致。同样算法换两个规模：0.5B 模型是 5 亿 × 2 = 10 亿字节，1 GB；32B 模型是 320 亿 × 2 = 640 亿字节，64 GB。同一个 7B 模型压到 INT8，每参数 1 字节，70 亿字节即 7 GB，正好是 FP16 的一半。这些是算例，不是实测：只算权重，不含 KV 缓存与激活，真实占用只会更大。模型规模翻倍，权重显存跟着翻倍；量化把这一格减半，代价记在精度墙上。

生态墙落到清单上，就是“接入方式”那一栏，大体三种：vLLM 插件（引擎原生支持，插件把平台注册进来）、容器镜像（厂商把驱动、SDK、引擎与模型打包，拉下来就能跑）、原生框架（芯片自己的框架，不走 vLLM 这条路）。三种方式没有高下，只有代价不同：插件复用引擎生态，版本要与引擎对齐；镜像开箱即用，版本钉死在镜像里；原生框架自由度大，接引擎的活要自己干。这一栏比峰值算力稳：峰值数字一个季度就可能变，一块芯片走插件还是走镜像，变得慢得多。

通信墙与精度墙算不出一个整齐的数，却一样能挡住推理。通信墙问多卡并行顺不顺：一块卡装不下或单卡跑不快，就要把模型切开分到多张卡上，切开之后卡与卡之间要不断交换中间结果，交换走卡间互联，带宽与延迟由硬件给定。单卡能跑与多卡能扩展是两个结论，清单里分开记。精度墙问量化之后输出还能不能用：权重从 FP16 压到 INT8，每个权重的表示变粗，舍入误差逐层传到输出；误差会不会被模型本身消化掉，要看 scale（缩放系数）的取法与舍入方式，最终要看评测集上的实测。“支持量化”是功能有没有，“量化后可用”是质量够不够。

清单的时效比内容重要。本章引用的支持状态来自一份核实日期为 2026 年 6 月的引擎对比表；凡是写“支持”的地方，都是截至那个日期的核实结果，不是永久结论。几个月后再读，那份表可能已经过期，其中的状态只能当线索，不能当现况。抄表时状态、版本、核实日期三项一起抄；没有日期的“支持”按未知处理，空着比猜一个强。

一个常见的误解：参数表好看，等于能跑推理。峰值算力与显存容量是硬件能力的上限，能不能跑起来还要看另外三面墙。某块芯片跑不起来，先问是哪面墙挡住了，再下结论；笼统地说“这块芯片不行”，等于什么都没说。本节留下的是 9 行清单与四个定义，后面的章节在这张清单上继续填：第 26 章填昇腾那一行的软件栈细节，第 28 章拿四面墙给覆盖矩阵的结论归因，第 30 章与第 31 章的报告里，每条结论都要带核实日期。

### 第 2 节 · 软件栈分层：驱动 → SDK → 算子库 → 框架插件 → 推理引擎

软件栈分 5 层，从下往上是驱动/固件、SDK/运行时、算子库、框架插件、推理引擎。层数有限，分层才用得上：出了问题，候选位置只有这 5 个，逐个排除总能定位。没有分层时，问题只有一个笼统的名字，叫“国产芯片跑不起来”；有了分层，同一个问题会变成“驱动认不出卡”或“插件没把平台注册上”，后者直接指向下一步要查什么。

每一层干什么、坏了长什么样：

| 层 | 负责 | 缺失或版本不对时 |
|---|---|---|
| 驱动 / 固件 | 认卡、分配显存、提供设备接口 | 设备列表里根本没有这块卡，后面所有层都无从谈起 |
| SDK / 运行时 | 厂商软件栈：编译器、运行时、集合通信，CANN、DTK、MUSA 在这一层 | 编译不过，或运行时找不到符号，报错里出现 SDK 自己的组件名 |
| 算子库 | 芯片侧算子实现与融合算子，AscendC、TBE 写的算子在这一层 | 某个算子没有实现，引擎不报错，回退到 CPU 或低效实现，服务能跑但慢 |
| 框架插件 | 把芯片接进引擎：平台类、算子分发、注意力后端、通信配置 | 引擎启动不了，或启动时认不出这个平台 |
| 推理引擎 | vLLM、SGLang 本身：模型结构、调度、KV 缓存、采样 | 长得最像应用问题：某个请求出错、某个配置不生效，根子可能在下面任何一层 |

症状出现的位置与问题所在的位置经常不在同一层。算子库缺一个实现，用户看到的是推理变慢，慢的症状在引擎层，缺的东西在算子库层；驱动没装好，用户看到的是引擎启动失败，失败的症状在引擎层，缺的东西在驱动层。症状在上，根子在下，所以排查方向是自下而上的：先确认卡认不认得出，再确认 SDK 能不能用，再确认算子在不在，最后才看引擎层的配置。底层问题不解决，上层检查全是白做。

拿一个具体症状走一遍。启动时报找不到设备：先看设备列表里有没有这块卡，没有就是驱动层；有卡但 SDK 报找不到符号，是 SDK 层；SDK 正常但某个算子回退到 CPU，是算子库层；算子都在但引擎认不出平台，是插件层。每一层的检查都是同一句：这一层的东西在不在、对不对。顺序不能倒：从引擎层开始查的人，会先怀疑模型代码与启动命令，绕一大圈才发现是驱动没装。

四面墙与五层叠在一起，症状能从“大概是显存问题”收敛到一个格子：

| 墙 | 主要落点 | 问什么 |
|---|---|---|
| 生态 | 框架插件、推理引擎 | 有没有插件或镜像把这块芯片接进引擎 |
| 显存 | 驱动 / 固件、SDK / 运行时 | 显存分不分得出来，KV 缓存放不放得下 |
| 通信 | SDK / 运行时、框架插件 | 多卡互联带宽够不够，集合通信原语齐不齐 |
| 精度 | 算子库、框架插件 | 量化算子写得准不准，量化后输出能不能用 |

显存墙落在两层上不是笔误：分不出来是驱动层，管不好是 SDK 层。同一条墙落在两层，定位时就要多问一句“是分不出来，还是管不好”。定位记录的写法可以现在就定下来：现象写报错原文或症状，定位写层，解法写命令或改动，验证写怎么确认修好了，四列缺一列，记录就不完整。

插件层与引擎层之间还有一条边界，排查时经常用到：问一句“这个问题换一块芯片还会不会出现”。还会出现，多半在引擎层；换了芯片就消失，多半在插件层或更下面。这条边界把“与芯片有关”和“与芯片无关”切开，排查范围立刻小一半。第 27 章会把它变成三层验证：先确认 NPU 可见，再确认 PyTorch 能认 Ascend，最后确认 vLLM 能识别到 NPU 平台，三层缺一不可。

层与层之间的接口是下一个故障点。接口是上一层调用下一层时用的约定：引擎层调插件层的平台接口，插件层调算子库层的算子名，算子库层调 SDK 层的编译与运行时，SDK 层调驱动层的设备与显存接口。接口稳定，各层就能独立演进；版本升级改了接口，上下层对不上，症状会同时在两层出现。第 27 章的版本矩阵——vLLM、vllm-ascend、CANN、torch_npu 四者的版本对齐——查的就是这种错位，具体版本对应关系以各仓库当前文档为准。

### 第 3 节 · 插件机制：vLLM 是怎么做到一块代码跑多家芯片的

“插件”有两个层次，替换的东西完全不同。第 24 章讲的 CustomOp 是算子级替换：一个 SiluAndMul 换成自己写的 Triton 版，换的是一个算子，模型代码与引擎的其他部分都不动。[vllm-ascend](https://github.com/vllm-project/vllm-ascend) 是平台级插件：它给 vLLM 提供一整套芯片适配，包括平台类 `NPUPlatform`、算子实现、注意力后端、通信、编译配置，模型代码不用改，换的是底下的整套实现。一个算子与一整套实现，规模差一个数量级以上，混为一谈是这一节最要防的误解。

从引擎的角度看，平台级插件做三件事：被发现并加载、注册平台类、在平台被选中之后提供该平台的算子与后端。注册链的顺序是：加载 → 注册平台 → 启动时按设备选平台 → 按平台分发算子。先选平台，再分发算子；算子分发发生在平台选定之后，同一个算子名在不同平台下会分发到不同的实现。没有先选平台，分发就不知道往哪分。

插件的目录地图按职责分，下面是 vllm-ascend 的顶层结构（目录名与增删随版本变化，以仓库当前结构为准）：

| 目录 / 文件 | 职责 |
|---|---|
| `platform.py` | `NPUPlatform`：设备识别与平台选择 |
| `ops/` | 芯片侧的算子实现 |
| `attention/` | 注意力后端的选择与实现 |
| `quantization/` | 量化方案 |
| `distributed/` | 多卡并行与通信 |
| `compilation/` | 图编译一类的配置 |
| `_cann_ops_custom/` | 自定义算子 |

目录名本身就是路标：找一个算子的实现，先想它属于哪一类，再去对应的目录里找，比在整个仓库里翻快得多。顶层结构会随版本新增、改名或合并，拿旧地图找新目录会扑空；核对时记下仓库版本与日期，变了的条目随手更新。

拿 RMSNorm 走一遍分发链，顺序就从一条规则变成一条看得见的路。模型前向里调一次 RMSNorm，调用点在模型代码里，名字是统一的；vLLM 启动时已经按设备选定了 NPU 平台，分发时按平台找实现，落到 `ops/` 或 `_cann_ops_custom/` 里的 Ascend 实现，而不是 CUDA 实现或 PyTorch 参考实现。调用点不变，变的只是名字背后挂的是哪一份实现。定位一个算子，就是沿这条路反方向走：从调用点出发，经过分发点，找到插件里的实现文件，记下路径与函数名。

为什么 vLLM 要做成插件机制？给每块芯片各写一个引擎，成本太高。模型代码、调度逻辑、KV 缓存管理、采样逻辑与芯片无关，只需要写一份；平台识别、算子实现、注意力后端、通信原语与芯片有关，收进插件，每块芯片一份。新增一块芯片的成本，因此从“重写一个引擎”降到“写一个插件”。省掉的是引擎公共部分的重复劳动，插件里的算子仍要一个一个写出来。

对照第 8 章在 NVIDIA 上的部署，两条路的模型代码是同一份，差的是底下的栈：NVIDIA 的算子实现与注意力后端在引擎自带的代码里，装好引擎就能认 CUDA；国产芯片的这些实现由插件提供，引擎本身不认这块芯片，要先装插件、注册平台。这个对照也划出了后面几章的位置：第 26 章与第 27 章拆插件下面的 CANN 与部署链，第 28 章量算子覆盖，模型写法始终不变。

一个常见的误解：插件是打补丁，哪里不行贴哪里。补丁的印象是小、临时、绕过问题，而平台级插件是一套完整的、与引擎平行的芯片适配实现，有自己的平台类、算子库、注意力后端与通信配置。把它当成补丁的人，会低估它的规模，也会在读代码时迷路。另一个相关的误解，是以为模型代码要为每块芯片改一版：平台级插件存在的意义，就是让模型代码不用改，改的是底下的栈。

注意力后端单独占一个目录，说明后端选择是平台级的事情：平台选定之后，注意力走哪一份实现也跟着定下来，模型代码里不用为每块芯片写分支。编译配置同理：同一份模型代码在不同平台下编译的配置可能不同，配置错了，编译出来的图可能跑不起来，也可能悄悄走了低效路径。平台级插件接管所有与芯片有关的选择，留给模型代码的是与芯片无关的部分。

### 第 4 节 · 统一算子层：FlagGems / FlagCX 的思路

统一层是两个库加一个插件。按 [vllm-plugin-FL 文档](https://docs.flagos.io/projects/vllm-plugin-FL/en/latest/overview/features.html)可以确认这个结构：FlagGems 管算子、FlagCX 管多卡通信，插件把两者接进 vLLM 的分发链。三者缺一个，统一层就不完整：没有 FlagGems，算子还是要每家各写一份；没有 FlagCX，多卡通信还是要每家各写一份；没有插件，两个库再统一也进不了引擎。

分发是一条三级优先级链：先找 FlagGems 的统一实现，没有再找厂商实现，再没有就回退到 PyTorch 参考实现（fallback）。启动时先识别当前芯片、选出后端，分发链的每一级都按这个后端去找。三级链的含义是：统一实现覆盖常见算子，厂商实现补上统一层没覆盖的部分，PyTorch 参考实现兜底，哪怕前两级都没有，结果也算得出来，只是慢。服务能跑起来的概率很高，跑得快不快，取决于落在哪一级：落在第一级是统一实现的速度，第二级是厂商实现的速度，第三级通常是三者中最慢的。

按同一份文档，支持的平台列了 12 个：NVIDIA、Ascend、T-Head、Iluvatar、MetaX、摩尔线程、Tsingmicro、海光、燧原、昆仑芯、阿里巴巴 PPU、CPU ARM64。名单与数量以当前文档为准，平台增删比芯片型号变化得快。12 个平台共用一套分发链，一个算子写一份就能在这些平台上跑；没有统一层时，同一个算子要写 12 份，改一个 bug 也要改 12 处。

回退的代价可以用一个算例讲清，它不是实测。假设某个算子占总时间的 20%，它的 PyTorch 参考实现比芯片侧实现慢 5 倍：总时间变成原来的 0.8 + 0.2 × 5 = 1.8 倍，也就是慢了 80%。同一个算例换一组数：这个算子只占总时间的 1%，同样慢 5 倍，总时间是 0.99 + 0.01 × 5 = 1.04 倍，只慢 4%。回退本身不可怕，回退落在关键路径上才可怕。判断一个回退要不要紧，要把支持状态与耗时占比一起看：只看状态不看占比，会把小问题当成大问题，也会把大问题当成小问题。

统一层解决的是“一份 kernel 代码跑多家芯片”，没解决的是“每家芯片的峰值性能”。统一实现为了可移植，会牺牲一部分特化优化：一个 kernel 要在 12 个平台上都跑对，就不能用某块芯片独有的指令与访存技巧，写法要取各家都能接受的交集；交集的写法能跑，但跑不到某块芯片的上限。要榨干某块芯片的性能，最终还是要写它的原生算子：第 26 章的 AscendC、第 29 章的移植案例走的就是这条路。这与第 23 章 Triton 与 CUTLASS 的取舍是同一个逻辑，换了一块芯片：一份代码跑多处、省人力，特化为特定硬件、榨性能。

[FlagTree](https://github.com/flagos-ai/FlagTree) 是 FlagGems 背后的算子开发框架：算子用一套抽象写出来，再针对不同芯片生成实现。FlagGems 是生成出来的统一算子库，FlagTree 是写算子与生成实现的框架本身。第 29 章会回答三个问题：一个算子的“统一描述”长什么样，针对不同芯片的生成发生在什么时候，某块芯片上统一实现跑不起来时回退链是怎样的。

FlagCX 管的是多卡之间的集合通信：张量并行把模型切开之后，卡与卡要交换中间结果，交换用的原语由 FlagCX 统一提供，再由各家芯片的后端承接。算子统一解决单卡上的计算，通信统一解决多卡之间的协同，缺一个，多卡推理就接不起来。25.1 的通信墙问“多卡能不能扩展”，落到软件栈上就是这一层。单卡能跑的时候 FlagCX 的存在感很低，一上多卡，它就在关键路径上。

什么时候用统一层、什么时候写原生算子，可以定一条判断规则：先上统一层把服务跑起来，再看 profiling（性能分析）的结果，哪个算子占的时间最多、又落在第三级分发上，就优先写原生实现补上去。统一层管从 0 到 1 的覆盖，原生算子管从 1 到快的峰值；顺序倒过来，先给每个算子写原生实现，人力会陷在覆盖面上，服务迟迟跑不起来。三级分发链还有一个边界情况要标出来：统一实现与厂商实现都没有，落到 PyTorch 参考实现，服务还能跑；如果连参考实现都没有，这一级是往下一级走还是直接报错，文档没有写，这里不猜，标“待核实”，读分发逻辑的源码确认。

### 第 1 节 · CANN 软件栈：先分清每一层是干什么的

**目标**：画出 CANN 的分层，并说清算子开发用的是哪一层。

**怎么做**（60 分钟，无硬件可做）：

先把版本锚点钉死，再谈分层，顺序不能反。vllm-ascend 最新稳定版 v0.30.0（2026 年 10 月）要求 Python 3.12、CANN 9.2.1、PyTorch 2.10.0、TorchNPU 2.10.0.post7，这五个钉点要一起写下来，缺一个都不算钉死。为什么是五个一起？一个版本组合里任何两个组件之间都存在对应关系，五个组件两两之间要核对的关系一共是 C(5,2) = 10 对，Python 与 PyTorch 是一对，PyTorch 与 TorchNPU 是一对，TorchNPU 与 CANN 是一对，CANN 与 vllm-ascend 是一对，剩下的六对也一样要对得上，漏掉任何一对都可能在安装或运行时才暴露出来。这 10 对关系没有一条是靠“版本号看起来接近”就能断定的，唯一的依据是 vllm-ascend 仓库 README 里写明的对应关系，核实日期是 2026 年 11 月。本模块大纲的旧版写的是“CANN 8.5”，已经过期，这个教训就是第 1 周“带日期的地图”制度要防的事：版本号本身会过期，只有“某年某月某版本 + 在哪份文档上核实的”这组信息才有保质期。按第 1 周定下的制度，超过 3 个月未核实的记录视为作废，2026 年 11 月核实的这组锚点，到 2027 年 2 月就要重新核实，11 月加 3 个月是 2 月，这笔账不用查表也能算出来。

版本锚点钉死之后，再看 CANN 的分层。按“从硬件往上”的顺序，这一节讲三层。最下面是驱动与运行时：认卡、分配显存、launch kernel，没有这一层，上面的一切都不存在，对应第 1 周分层图里的驱动层。往上一层是算子库，来源分两类，一类是厂商预置的算子，比如各种融合算子，装好 CANN 就在那里；另一类是你自己写的算子，用 TBE 或者 AscendC 写出来，再往下接编译与注册。最上面是框架适配：TorchNPU 让 PyTorch 认 Ascend，`torch_npu` 的算子注册把算子名与实现连起来，vllm-ascend 的 `ops/` 与 `_cann_ops_custom/` 就落在这一层。算子开发用的是哪一层，答案到这里已经很清楚了：写算子本身落在算子库那一层，算子写完之后要能被框架调到，靠的是框架适配那一层，两层缺一不可，只写算子不做注册，框架找不到它；只做注册没有算子实现，注册指向的是空气。

三层分法与第 1 周的五层分法是什么关系，这个问题值得花一点时间对齐，因为两张图叠在一起才是完整的定位地图。第 1 周的五层是驱动、SDK、算子库、框架插件、推理引擎，CANN 大致覆盖了从驱动往上到算子库这一段，外加 TorchNPU 这一块框架适配，而 vllm-ascend 作为平台级插件坐在框架适配之上，vLLM 本身坐在最上面。定位问题的时候就按这个叠法问：卡认不出来，往驱动与运行时那一层查；某个算子跑不起来，先问算子库里有没有它，再问框架适配层有没有把它注册上；引擎根本启动不了，往插件层查。分层图的用处在于把一句笼统的“国产芯片不行”拆成一个可以逐层排查的位置。上周的 Four Walls 在这里也接得上：显存墙对应驱动与运行时的显存管理，生态墙对应框架插件层，精度墙对应算子库里的量化实现，通信墙对应多卡互联那一部分 SDK——第 6 周写报告做归因时，用的还是这套坐标。

硬件锚点也要和版本锚点写在同一张记录里。vllm-ascend v0.30.0 支持的硬件包括 Atlas 800I A2、Atlas 800I A3、300I Duo、950PR、950DT，数一数是五个型号，其中 800I 分 A2 与 A3 两个子型号，950 分 PR 与 DT 两个子型号。型号清单的意义在于划定范围：支持列表之外的型号能不能跑，本周没有任何依据，不要猜。没有实机时，华为的 HiDevLab 在线开发平台是官方提供的试用入口，先把这个入口记下来，第 3 周跑通时会用到。HiDevLab 上具体能用到哪几个型号、试用额度与排队情况，本周没有核实，写“待补测”，不要凭印象补一句“应该能用”。同样，vllm-ascend v0.30.0 的硬件支持列表本身也是 2026 年 11 月核实的快照，新版本发布后列表可能变化，到期重核的规则与版本锚点一样适用。

两个常见的误解要在动手之前拆掉。其一是“装了 CANN 就等于能跑 vLLM”：CANN 只是栈里的一段，上面还差 TorchNPU 的框架适配与 vllm-ascend 的插件，三层里的任何一层缺了，链路都是断的。其二是“版本号越新越好”：新版本的价值要看对应关系，CANN 9.2.1 配 TorchNPU 2.10.0.post7 是 README 里写明的组合，单把其中一个换成更新的版本，对应关系反而可能断掉，升级的单位是整组版本，不是单个组件。其三是“硬件型号多就等于覆盖广”：五个型号是支持列表的长度，不是实测覆盖的广度，本周没有任何一条实测记录，列表上的型号一个都没跑过，清单与验证是两回事。这三个误解的共同点是把“有”当成“通”，而本周的全部工作恰恰是区分这两者：有文档、有列表、有入口，都不等于链路跑通过。

十对关系里任何一对断掉，症状都会落在不同的层，排查时按分层图问过去，比笼统地重装一遍要省事。Python 与 PyTorch 的对应关系断了，环境本身就立不住；PyTorch 与 TorchNPU 的对应关系断了，框架认不出 Ascend，症状落在框架适配层；TorchNPU 与 CANN 的对应关系断了，算子注册与 kernel 启动之间会出问题，症状落在算子库与框架适配的交界处；CANN 与 vllm-ascend 的对应关系断了，插件启动不了或者算子分发走偏，症状落在插件层。这几句是按分层结构推断的排查方向，不是实测过的故障清单，真正的故障现象要等第 3 周装环境时逐条记录下来，写进踩坑清单里。版本锚点的作用正在这里：出问题时先对照锚点，十对关系里哪一对没对上，先查那一对，而不是把五个组件全重装一遍。

第五个钉点 vllm-ascend v0.30.0 本身也值得单独说一句，因为它很容易被漏掉。前面四个钉点是运行时的组件，vllm-ascend 是插件，它的版本除了要与 CANN、PyTorch、TorchNPU 对应，还要与 vLLM 引擎本身的版本对应，第 3 周的部署差异表里有一行就是讲这个的：插件的版本要与 vLLM 版本对应。只钉四个组件、漏了插件，等于只钉了链路的一半，引擎启动时插件加载失败，前面四层再正确也跑不起来。五个钉点一个都不能少，十对关系一对都不能漏，这组数就是本节开头那笔算术的实际含义。

“把版本号抄下来”与“核实了版本号”是两回事，这个区别要趁现在讲清。抄下来是把五个版本号写进笔记，核实是确认这五个版本号在同一份文档里、同一个时间点上是互相兼容的组合，并且写下文档的来源与核实日期。一张地图上的格子应当长这样：CANN 9.2.1，2026 年 11 月核实，来源是 vllm-ascend 仓库 README。日期与来源缺了任何一样，这个格子都视为未知，三个月后也就是 2027 年 2 月，这个格子到期作废，要重新去 README 里核对一遍。制度的意义在于防止旧版大纲里“CANN 8.5”那种过期信息在笔记里悄悄留下来：没有日期的版本号看起来和刚核实的版本号一模一样，只有日期能区分它们。

没有实机时的试用入口也要讲清它的位置。HiDevLab 是官方提供的在线开发平台，记下来是为了第 3 周有地方动手，但它与 Atlas 实机是两回事：在在线平台上跑通与在实机上跑通，验证的力度不同，写记录时要写清是在哪个环境上验证的。HiDevLab 上具体能用到哪几个型号、试用额度与排队情况，本周没有核实，写待补测，不要凭印象补一句能用。同样，硬件支持列表上的五个型号一个都没跑过，列表是支持范围的声明，不是实测覆盖的证明，第 6 周的报告里引用这份列表时，要写清它是 2026 年 11 月核实的快照，而不是本周的实测结果。

最后把三样东西写进第 1 周的地图里：CANN 的版本、版本之间的对应关系、硬件型号，每一样都标上核实日期（2026 年 11 月，来源：[vllm-ascend](https://github.com/vllm-project/vllm-ascend) 仓库 README）。地图上的每个格子从此都有两行字，一行是状态，一行是日期，没有日期的格子视为未知。这张地图在第 3 周装环境时会被翻出来逐项对照，在第 6 周写报告时会被引用为环境章节的依据，现在多花十分钟把日期写全，后面就不用凭记忆补。

### 第 2 节 · TBE 与 AscendC：两代算子抽象长什么样

**目标**：讲清一个算子的抽象长什么样——定义、编译、调用三段分别是什么。

**怎么做**（60 分钟，无硬件可做）：

一个算子从写出来到被调用，中间要过三道手：定义、编译、调用。TBE 与 AscendC 是两代算子抽象，它们的区别不在链路本身，而在每一道手上你写的东西长什么样。先把链路钉死，再看两代人在同一条链路上各自写什么，这样对比才不会变成两份互不相干的说明书。链路有三个环节，两代抽象乘以三个环节，对照表一共是六个格子，每格一句话，六句话合起来就是本节要讲清的全部内容。六个格子先摆出来，后面的正文再逐格展开，读的时候随时可以回到这张表上核对自己走到哪一格了。

| 环节 | TBE（上一代） | AscendC（当前主力） |
|---|---|---|
| 定义 | 用 DSL（领域专用语言，domain-specific language）描述算子：定义输入输出，再写计算表达式 | 用 C++ 直接写算子：算子是一个类，带 `Init` 与 `Process` 方法 |
| 编译 | 编译器把 DSL 描述生成 kernel | AscendC 编译器把 C++ 源码编成可在 NPU 上跑的 kernel |
| 调用 | 框架通过算子名找到它，把输入张量传进去，launch kernel | 同样走算子名查找与 launch，自定义算子的落点在 vllm-ascend 的 `_cann_ops_custom/` 目录 |

定义这一环先讲。算子的定义由两部分组成，一部分是接口，也就是输入输出的 shape（形状）与 dtype（数据类型），另一部分是计算逻辑，也就是输入经过什么运算变成输出。TBE 的写法是用 DSL 描述这两部分：你写出输入输出长什么样，再写出计算表达式，至于这个表达式最终变成什么样的 kernel 代码，由编译器去生成。AscendC 的写法是用 C++ 直接写：算子是一个类，计算过程拆成流水线任务，类里面最显眼的两个方法是 `Init` 与 `Process`，一个负责初始化，一个负责真正执行。两代写法的差别可以打一个比方：TBE 像是写一份规格说明，告诉编译器“我要算什么”；AscendC 像是亲手写施工图，连“按什么顺序算”都要写出来。规格说明写起来短，施工图写起来长，但施工图里每一个步骤都在你的控制之下。这个比方到第 3 节会再用上，那里会看到施工图具体长什么样——流水线的每一步都要显式写出来。

编译这一环接着讲。TBE 的编译器读 DSL 描述，生成 kernel；AscendC 的编译器读 C++ 源码，编成可在 NPU 上跑的 kernel。两种编译的产物在结构上是同一类东西：kernel 二进制加上注册信息。kernel 二进制是真正能在 NPU 上跑的代码，注册信息是把算子名与这个 kernel 连起来的那张映射表，没有注册信息，框架就算手里拿着二进制也不知道它对应哪个算子。编译这一步还有一个容易被忽略的性质：它把“你写的算子”变成了“芯片能跑的东西”，中间隔着一层编译器，编译器认不认你的写法、支不支持你用的特性，直接决定这个算子能不能走通这条链路。TBE 时代这个性质更明显，因为 DSL 能表达的东西本来就是编译器划定的范围；AscendC 时代你写的是 C++，表达范围宽了，但编译器仍然是守门人，写出来的代码要过编译这一关才算数。编译失败与运行失败是两类不同的失败，前者在链路的第二环就拦住了你，后者要到调用那一环才暴露，排查时先分清失败落在哪一环，再往那一环里找原因。

调用这一环最后讲。框架（PyTorch 或者 vLLM）通过算子名找到算子，把输入张量传进去，launch kernel，这一步两代抽象是一样的。调用成立的前提是前面两环都走完了：定义写对了，编译出产物了，注册信息把名字与实现连起来了，调用时按名字才能找到东西。vllm-ascend 的 `_cann_ops_custom/` 目录就是自定义算子的落点，第 3 周会在那里定位具体算子，本节先把这个目录名记下来：以后在插件里找一个自定义算子，先去这个目录里看一眼。调用还有一个细节值得留意：调用者传进来的是张量，张量的 shape 与 dtype 要与定义时声明的接口对得上，对不上时报错发生在调用现场，但根子在定义那一环，修定义比在调用处打补丁更对症。

链路讲完之后，对照 M2 的经验看这件事。Triton 里你写的是“一个 kernel 函数加 grid”，AscendC 里你写的是“一个算子类加流水线任务”。抽象变了，但“写 kernel、验证、接入”这套流程没变：第 5 周的移植案例就是把 M2 的 Triton kernel 沿这条链路搬过去。搬过去的意思是把同一个算子重新走一遍定义、编译、调用，代码逐行翻译成不了事：Triton 版里由编译器管的那部分，在 AscendC 版里要你显式写出来；Triton 版里一个 kernel 函数加 grid 就能表达的东西，在 AscendC 版里要拆成类与流水线任务。这个对照的意义在于，M2 里学到的判断——瓶颈在访存模式与融合时 Triton 够用，瓶颈下沉到硬件细节时回 CUDA——在这里换了一个版本：抽象层藏住的东西，恰恰是移植时要亲手补上的东西，第 3 节会逐条看到这笔代价。

官方文档的锚点要单独留一段，因为这里藏着本节最容易踩的坑：两个文档的版本并不一致。AscendC 开发文档是 CANN 8.5.0 版，向量编程指南是 80RC2 版，链接分别是 [CANN 8.5.0 AscendC 开发文档](https://www.hiascend.com/document/detail/zh/canncommercial/850/opdevg/Ascendcopdevg/atlas_ascendc_map_10_0002.html) 与 [CANN 80RC2 向量编程指南](https://www.hiascend.com/document/detail/zh/canncommercial/80RC2/developmentguide/opdevg/Ascendcopdevg/atlas_ascendc_10_0021.html)。这两个锚点与第 1 节的版本锚点也不是同一套：第 1 节钉的是 vllm-ascend v0.30.0（2026 年 10 月）对应的 CANN 9.2.1，这里读的是 CANN 8.5.0 与 80RC2 的文档。版本不同，API 细节可能有出入，读的时候以你所装 CANN 版本对应的文档为准。这一点要说得再直白一些：不要动手把 8.5.0“纠正”成 9.2.1，也不要去编一个 9.2.1 版的 AscendC 文档链接，本周没有核实过这样一条链接存在，编出来的链接比缺失的链接更有害。正确的做法是把两个锚点并排记下来，各自标明来源与版本，需要 9.2.1 对应的文档时，等装好环境、拿到确切的文档地址之后再补，补的时候写上核实日期。文档版本与软件版本不一致是国产芯片生态里的常态，第 4 周读 TritonAscendBench 时还会遇到一次，那里的 NPU 环境参考配置是 CANN 8.5.0，与 vllm-ascend 的 9.2.1 也不是同一套，不同工具钉不同版本，记录时写清“这一步用的是哪套版本”，不要混在一起。

几个误解值得在这里拆掉。其一是“AscendC 是新一代，所以用它写的算子自动更快”：抽象换代改变的是表达方式与控制粒度，算子的数学与访存量没有变，快慢要看流水线写得好不好，第 3 节的访存账会给出判断的刻度，没有实测之前，任何“更快”的说法都是待补测。其二是“TBE 是上一代，所以不用学了”：读懂 TBE 的意义在于理解抽象本身——DSL 描述加编译器生成这条路，与 AscendC 的 C++ 直写加流水线任务这条路，对照着看才能明白“算子抽象”这个概念到底在抽象什么；再说，已有的算子库里仍有 TBE 时代留下的实现，读代码时会遇到，认不出来就没法接手。其三是“定义、编译、调用三段是三件独立的事”：三段是同一条链路上的三个环节，定义时就要想着编译能不能过、调用时名字能不能对上，任何一环的改动都可能牵动另外两环，第 4 节沿链路追踪一个具体算子时，这个牵动关系会看得更清楚。

这一节还有一个容易被跳过的点：为什么算子抽象值得单独用一节来讲。M2 里你写 Triton kernel 时，抽象是编译器给你的：写一个 kernel 函数，剩下的事编译器管。到了 AscendC，抽象的边界挪了位置，编译器管得少了，你要写的东西多了。边界挪动之后，哪些事归你、哪些事归编译器、哪些事归框架，这个分工本身就是要学的内容。第 3 节的五个部件与三步流程，就是这个分工的具体化；第 4 节的完整链路，就是把分工放到一个真实算子身上走一遍。读完本节，你应当能不看笔记说出这三句话：TBE 用 DSL 描述算子，AscendC 用 C++ 类加流水线任务来写算子；两代的链路都是定义、编译、调用；编译的产物是 kernel 二进制加注册信息，调用靠算子名找到实现。说得出这三句，对照表里的六个格子就算是装进去了。

**产出**：一页笔记：TBE vs AscendC 的抽象对比 + “定义 → 编译 → 调用”链路图。

### 第 3 节 · AscendC 流水线模型：读懂一个向量加法算子

**目标**：读懂 AscendC 的流水线编程模型，能说出每个部件是干什么的。

**怎么做**（60 分钟，无硬件可做；代码为示意骨架，可编译版以官方文档为准）：

向量加法是读懂 AscendC 的最好入口，因为它的数学简单到没有任何干扰：输出的每个元素就是两个输入对应元素的和，没有归约，没有矩阵乘，没有数值稳定的花招，剩下的全部是流水线模型本身。打开 CANN 8.5.0 AscendC 开发文档里的向量加法例子（`add_custom`），先看 kernel 入口，它长这样：

```cpp
// 示意骨架：结构与名字以 CANN 8.5.0 AscendC 开发文档的 add_custom 为准
extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z) {
    // op.Init(...); op.Process();
}
```

这段代码是示意骨架，不是完整的可编译版本，完整版以官方文档为准。骨架虽短，信息却不少。`add_custom` 是 kernel 的名字，调用方按这个名字找到它。`GM_ADDR` 是全局内存（Global Memory）地址的类型，三个参数 `x`、`y`、`z` 是三个张量在全局内存里的地址，其中 `x` 与 `y` 是两个输入，`z` 是输出。函数体只有两行注释：`op.Init(...)` 与 `op.Process()`，这两行就是 AscendC 算子类的两个核心方法，初始化与执行，骨架把它们写成注释，是因为真正的初始化参数与执行逻辑要对照文档里的完整例子来填，骨架只负责把结构钉死：一个 AscendC 算子，入口是一个 kernel 函数，函数里先初始化、再执行。`extern "C"` 与 `__global__ __aicore__` 是入口的标记，表明这是一个要在 NPU 上跑的 kernel 入口，读到这里不用深究它们的编译器语义，先把它们认作“入口长这样”的固定写法，细节等有卡编译时再核对文档。

入口看完之后，看流水线模型的五个部件。五个部件各管一摊事，分工先说清楚，再看它们怎么接力。TPipe 是统一的资源管理，算子里的内存与事件都由它管，你可以把它理解成算子内部的“管家”，内存从哪里来、事件什么时候触发，都要经过它。TQue 是任务间通信与同步的队列，CopyIn、Compute、CopyOut 三个任务通过它接力：上一个任务做完的东西放在队列里，下一个任务从队列里取，队列同时负责同步，让下一个任务不会在数据还没到位时就动手。InitBuffer 与 AllocTensor 是在 `Init` 里做的事：给 GlobalTensor 设地址，给队列分配 buffer，初始化阶段把执行阶段需要的东西都准备好，执行时不再现找。TBuf 是临时内存，中间结果放这里，算出来的、还没来得及搬回去的东西，先在 TBuf 里落脚。CopyIn、Compute、CopyOut 是 `Process` 里调的三步：把输入从 Global Memory 搬进片上，算，把结果搬回去。五个部件合起来，流水线模型的全貌就出来了：`Init` 里由 TPipe 管着资源、由 InitBuffer 与 AllocTensor 把地址与 buffer 备好，`Process` 里三个任务经由 TQue 接力，中间结果落在 TBuf 里。

三步流程值得对照 Triton 再看一遍，因为对照能帮你把新模型挂到已有的知识上。CopyIn 对应 Triton 里的 load，Compute 对应算，CopyOut 对应 store，三步与“load、算、store”是一一对应的。对应归对应，写法上的差别正是 AscendC 的特点：Triton 里这三步写在一个 kernel 函数里，由编译器去排布搬运与计算；AscendC 里这三步被显式拆成了三个任务，每个任务的边界、队列的交接、buffer 的分配都要你写出来。显式拆分的好处是控制粒度更细，流水线可以排得更紧；代价是代码量更大，每一步都要亲手写，写错任何一步，接力就断在那里。第 5 周移植时会逐条记录这笔代价，本节先把“显式”这个词刻在脑子里：AscendC 里没有“编译器替你管”的部分，流水线的每一步都是你的责任。

光讲结构还不够，把访存账算出来，流水线才有了轻重。取一个算例，输入是 N = 2^20 = 1,048,576 个 fp32 元素，x 与 y 各占 1,048,576 × 4 字节 = 4,194,304 字节，也就是 4 MiB，输出 z 同样是 4 MiB。一次向量加法要读 x 与 y、写 z，访存总量是 4 + 4 + 4 = 12 MiB，加法本身做了 1,048,576 次。算术强度是每次加法对应的访存量倒过来算：1,048,576 次加法除以 12,582,912 字节，约等于 0.083 次加法每字节，也就是每做一次加法要搬 12 个字节。这个数说明了向量加法的性质：它是访存主导的算子，时间花在搬运上，加法本身几乎不花时间，流水线优化的目标首先是让搬运不停下来。分块之后这笔账可以再算细一层，仍用上面这组数，取每块处理 1024 个元素，块数是 1,048,576 / 1024 = 1024 块，每块读 1024 × 4 × 2 = 8,192 字节、写 1024 × 4 = 4,096 字节，每块搬运 12,288 字节，1024 块合起来仍是 12 MiB，总量不变，变的是搬运被切成了 1024 次。块取 4096 个元素时，块数是 1,048,576 / 4096 = 256 块，每块搬运 4096 × 4 × 3 = 49,152 字节，256 块合起来仍是 12 MiB。块大小改的是切分的粒度，不是总量，这个结论后面排流水线时会用到：块大了，每次搬运的量大了，队列里要备的 buffer 也大了；块小了，接力的次数多了，同步的开销占比就上去了。块大小本身没有最优值，只有在具体硬件与具体 buffer 容量下的权衡，至于本节的算例里块取多大最合适，没有实测之前只能写待补测。

尾巴的处理也可以拿一组数走一遍，用的还是 M2 里算过的那组数，换个场景复用一次。向量长 n = 10000，块取 1024 个元素，块数是向上取整的 10000 / 1024 = 10 块，0 到 8 号块各处理满满的 1024 个元素，9 号块只剩 10000 − 9 × 1024 = 784 个有效元素，剩下 240 个位置是凑数的。Triton 里这 240 个位置靠 mask 挡住，AscendC 里尾巴块的有效长度同样要单独处理，处理的手法随写法而定，文档里的完整例子会给出具体做法，本节的示意骨架没有展开到那一步，完整版以官方文档为准。尾巴问题在这里的意义是提醒：分块的算术里永远有一块是不满的，读代码时看到分块逻辑，先问最后一块怎么办，再问中间块怎么接力。

流水线“流水”两个字的意思，也值得拿一组数算清楚，算的时候要先把假设说在前面。假设一个算例：CopyIn、Compute、CopyOut 每步各花 1 个单位时间，一共 4 块要处理。串行做是每块 3 步、4 块一共 3 × 4 = 12 个单位时间。排成流水线之后，第一块走完三步要 3 个单位时间，后面每块各多 1 个单位时间收尾，一共是 3 + (4 − 1) = 6 个单位时间，12 除以 6 是 2 倍。这组数是算例，不是实测：它假设三步耗时相等，假设队列交接没有额外开销，真实的三步耗时并不相等，CopyIn 与 CopyOut 花在搬运上的时间取决于块大小与带宽，Compute 花的时间取决于算子的计算量，向量加法的 Compute 一步几乎不花时间，流水线的瓶颈大概率落在搬运那两步上，具体的耗时分布要等有卡之后用 profiling 量出来，本周一律写待补测。算例的价值在于讲清机制：流水线的收益来自重叠，上一块在算的时候，下一块已经在搬进来了，搬运与计算不再互相等对方；收益的大小取决于最慢的那一步有多慢，三步里任何一步拖了后腿，整条流水线就按那一步的速度走。

核类型是本节的最后一块内容，也是容易读漏的一块。`KERNEL_TASK_TYPE_DEFAULT(KERNEL_TYPE_AIV_ONLY)` 表示这个 kernel 只用向量核（AIV）。Ascend 的核分两种：向量核（AIV）与矩阵核（AIC，跑矩阵乘）。一个算子用哪种核，在定义时就定下来了，`add_custom` 是向量加法，用向量核，标记里写 AIV_ONLY 就是这个意思。一个算子在芯片侧有没有实现、用的是哪种核，是第 4 周覆盖分析时要查的东西：查覆盖矩阵的时候，状态那一列要填的不仅是“有实现”还是“没实现”，还有实现用的是哪种核，因为核类型决定了这个算子的性能天花板落在什么地方。向量加法这样的逐元素算子落在 AIV 上，矩阵乘落在 AIC 上，分工在定义时就定死了，调用时再想换核已经来不及了。

几个误解留到最后拆掉。其一是“流水线三步是三个 kernel”：三步是一个 kernel 里的三个任务，经由 TQue 接力，不是三次 kernel 启动，启动一次，三个任务在里面接力跑。其二是“TQue 只是传数据的”：队列同时管同步，取数据的任务会在数据到位之前等着，没有同步，流水线就是一盘散沙。其三是“AscendC 里什么都要手写，所以比 Triton 慢”：手写的是控制，不是速度，控制粒度细本身不带来快慢，快慢要看流水线排得紧不紧、搬运有没有断档，这些都要实测，写代码时的手感不能代替 profiling 的数字。其四是“向量加法太简单，读懂它没什么用”：向量加法的数学简单，恰恰让流水线模型成了唯一的主角，五个部件与三步流程在这里看得最清楚，换成矩阵乘，数学本身会抢走注意力，流水线反而看不清了。读懂 `add_custom` 的执行过程，标准是能不看笔记讲出这条线：入口三个全局内存地址进来，`Init` 里把地址与 buffer 备好，`Process` 里 CopyIn 把输入搬进片上、Compute 做加法、CopyOut 把结果搬回去，三个任务经由 TQue 接力，中间结果落在 TBuf 里，全程只用向量核。

**产出**：一份 AscendC 流水线模型笔记（五个部件 + 三步流程 + 核类型），能向别人讲清 `add_custom` 的执行过程。

### 第 4 节 · 一个算子的完整链路：从定义到被 vLLM 调用

**目标**：能画出一个算子从定义到被调用的完整链路，并说清每个环节的产物。

**怎么做**（60 分钟，无硬件可做）：

前面三节讲的都是链路的局部，这一节把整条链走通，办法是选一个具体的算子做追踪对象，从它在模型代码里的调用点出发，一路走到它在芯片上的实现，再沿原路走回来。追踪对象建议选 RMSNorm，理由有三层，层层都和前面学过的内容咬合。第一层是熟悉程度：M2 第 6 周提到过 RMSNorm，它是 CustomOp 的可替换面，那里的语境是把一个算子换成你自己写的实现，这里的链路是同一个算子的芯片侧版本，追踪它等于把 M2 里认识的算子放到国产芯片的链路上再看一遍。第二层是代表性：归一化算子在推理里处处出现，每一层 transformer 里都有它，追踪一个到处出现的算子，链路上的每个环节都有真实的调用点可找，不会出现“这个算子只在某个角落被调一次”的尴尬。第三层是定位的便利：vllm-ascend 里它的实现位置落在 `vllm_ascend/ops/` 与 `_cann_ops_custom/` 这两个目录附近，第 3 周的任务之一就是在这些目录里定位具体算子，本节先走一遍定位的路，第 3 周再走就轻车熟路了。追踪对象的选择本身没有唯一答案，换一个算子也能走通这条链，关键是选定一个之后全程不换，链路表里的每一行都填同一个算子的信息，混填两个算子的行，表就失去了对照的意义。

链路表先摆出来，全表四个环节，每个环节两列信息，一共是八个格子，填表就是把这八个格子逐个落实到文件、文档或命令上。

| 环节 | 产物 | 在哪找 |
|---|---|---|
| 定义 | AscendC 算子类（Init / Process） | 厂商文档或 `vllm_ascend` 的自定义算子目录 |
| 编译 | kernel 二进制 + 注册信息 | CANN 编译流程（文档） |
| 注册 | 算子名 → 实现的映射 | `torch_npu` 的算子注册 / vllm-ascend 的 `meta_registration.py` |
| 调用 | 框架前向里的一次算子调用 | vLLM 模型代码里调用该算子的位置 |

定义这一环的产物是 AscendC 算子类，带着 `Init` 与 `Process` 两个方法，找它的地方是厂商文档或者 `vllm_ascend` 的自定义算子目录。定义要回答的第一个问题是接口：这个算子的输入输出各是什么 shape、什么 dtype，RMSNorm 的输入是一张张量、输出是一张同形状的张量，接口本身并不复杂，复杂的是接口背后的约定，比如归一化沿着哪个维度做、权重以什么形式传进来，这些约定写在定义里，调用方按约定传参。定义要回答的第二个问题是计算逻辑：AscendC 的写法是把计算拆成流水线任务，`Init` 里备好地址与 buffer，`Process` 里跑 CopyIn、Compute、CopyOut 三步，第 3 节的 `add_custom` 就是这套写法的最小例子，RMSNorm 的定义是同一套写法的放大版。定义这一环还有一个容易忽略的性质：它同时定了核类型，向量核还是矩阵核在定义时就写死了，后面再想换核，等于把定义重写一遍。

编译这一环的产物是 kernel 二进制加上注册信息，找它的地方是 CANN 编译流程的文档。编译这一步的输入是定义那一环的源码，输出是能在 NPU 上跑的二进制，中间隔着 AscendC 编译器。编译产物有两个部分，二进制是执行的部分，注册信息是寻址的部分，两者缺一不可：只有二进制没有注册信息，框架不知道这个二进制对应哪个算子名；只有注册信息没有二进制，名字指向的是空的。编译还有一个版本敏感的性质：产物是针对某个 CANN 版本编出来的，换一个 CANN 版本，产物很可能要重编，注册方式也可能跟着变，具体哪个环节变，要以新版本的文档为准，本周没有装过两个版本的 CANN 做对照，这里的说法只能写到“可能”这一层，再往下就是待补测。编译失败与运行失败的分界线也在这里：编译过不去，问题在定义与编译这两环；编译过了、跑起来不对，问题多半在定义里的计算逻辑或者调用处传进来的张量上。

注册这一环的产物是一张映射，算子名指向实现，找它的地方是 `torch_npu` 的算子注册与 vllm-ascend 的 `meta_registration.py`。注册是整条链里最容易被低估的一环，因为它不产生任何计算，却决定了调用时到底跑的是哪个实现。模型代码里写的是一个算子名，框架在前向执行到它时，要按名字查表，查到 Ascend 的实现就发给 NPU，查不到就走别的路，这张表就是注册环节维护的东西。读代码时定位注册信息的办法是顺着名字找：先在模型代码里找到算子被调用的那一行，记下它用的名字，再去注册表里查这个名字映射到了哪个实现，查到之后再去实现所在的文件里看定义与编译的产物。顺序反过来也行，先在 `_cann_ops_custom/` 里找到一个实现，再反查它的名字在哪些调用点出现过，两种方向走到的都是同一条链，选一个顺手的方向走到底就行。

调用这一环的产物是框架前向里的一次算子调用，找它的地方是 vLLM 模型代码里调用该算子的位置。调用是链路的最后一环，也是唯一一环能被终端用户直接看到的环节：模型跑起来，前向一层一层算下去，每一层里 RMSNorm 被调一次，调用的次数与模型层数对得上。调用点要记录的信息有三样：调用发生在模型代码的哪个文件、哪一行；传进去的张量是什么 shape、什么 dtype；这次调用最终落到了哪个实现上。三样信息合起来，才能证明链路是通的：只记录调用点，不证明实现落点，链路只走了一半；只记录实现，不记录调用点，链路没有接上模型。定位调用点的方法在第 3 周第 3 节还会再用一次，那里要讲插件怎么 hook 进 vLLM、算子分发发生在哪，本节的定位练习就是那里的预习。

三个问题要沿着链路逐个回答，回答的时候把“已经核实的”与“还没核实的”分开写。第一个问题是算子名在哪一层被解析，是框架层还是插件层。按链路的结构推，解析发生在注册信息所在的那一层：框架拿到算子名之后查注册表，注册表由 `torch_npu` 与插件共同维护，名字解析的结果取决于注册时写进去的映射。至于具体到 RMSNorm，解析链上的每一步分别落在哪个文件里，要读代码才能确认，本周没有在 vllm-ascend 源码里逐行核对过这条解析链，答案先写到结构推断这一层，文件级的位置留到第 3 周定位时补，补的时候写上核实日期与源码文件路径。第二个问题是这个算子在芯片侧没有实现时会发生什么，回退 CPU、报错、还是静默走低效实现，这个问题的答案就是第 4 周覆盖矩阵里要填的内容。本周能给出的只是这个问题的框架：三种可能性的后果完全不同，回退 CPU 是能跑但慢，报错是跑不起来，静默走低效实现是最危险的一种，因为它跑得起来、结果也对，只是慢，而慢的原因藏在链路深处，不查覆盖矩阵根本发现不了。具体到 RMSNorm 会走哪一条，本周没有核实，写待核实，不要猜。第三个问题是换一个 CANN 版本，链路的哪一环最可能变。按链路的结构推，编译产物与注册方式最可能变，因为这两环直接依赖 CANN 的编译器与注册机制；定义与调用相对稳定，定义的接口与调用的算子名是框架层面的约定，版本升级时通常会保持兼容。但这同样是结构推断，不是实测结论，第 1 节钉的版本锚点从 CANN 8.5.0 变到 9.2.1 时，链路的每一环到底变了什么，要等装好环境、对照两个版本的文档之后才能写下来，现在写只能写到推断这一层。

回退的代价值得拿一组数算清楚，算的时候同样先把假设说在前面。这是一个算例，不是实测：假设某个算子占一次前向总时间的 20%，它在芯片侧没有实现，回退之后慢 10 倍。回退前总时间记为 1 个单位，其中这个算子占 0.2，其余部分占 0.8；回退后这个算子变成 0.2 × 10 = 2，总时间变成 0.8 + 2 = 2.8 个单位，整整慢了 2.8 倍。同一个算子如果只占总时间的 5%，回退后总时间是 0.95 + 0.05 × 10 = 1.45 个单位，慢 1.45 倍。反过来，如果回退只慢 2 倍，占 20% 的算子回退后总时间是 0.8 + 0.2 × 2 = 1.2 个单位，只慢 1.2 倍。三组数合起来讲的是第 4 周要用的判断方法：回退的危害不看状态那一列怎么写，而看“状态乘以耗时占比”，一个占 1% 时间的算子回退 CPU 无所谓，一个占 20% 的算子回退就是瓶颈。慢多少倍这个数在算例里是假设的，真实的慢倍数要等覆盖分析时逐个算子量出来，本周的算例只负责讲清乘法的结构。

最后把答案写下来，每一条答案都标上核实日期与来源，来源是文档链接或者源码文件路径，两者都没有的就写待核实。日期的写法沿用第 1 周的制度：某年某月某版本，超过 3 个月未核实视为作废。链路表的价值不在于表本身，而在于它是一张可以逐项打勾的清单：四个环节的产物各有着落，三个问题的答案各有来源与日期，这张表才算填完了。填不完的格子不要空着，也不要编一个答案填进去，写待核实、写下一步去哪里核实，诚实地留空比漂亮地编造有用得多。

**产出**：一张“定义 → 编译 → 调用”链路表 + 三个问题的答案（带核实日期）。

验收标准有四条，每条对应本周的一节，合起来就是“CANN 学到什么程度算够”的答案。能画出 CANN 分层并说清每一层的作用，算子开发用的是算子库那一层、接上框架靠的是框架适配那一层，分层定位的方法从第 1 节来。能讲清 TBE 与 AscendC 的抽象区别，DSL 描述与 C++ 类加流水线任务是两代写法的差别，定义、编译、调用三段是两代共用的链路，对照表里的六个格子要能不看笔记说出来。能读懂 `add_custom` 的流水线，五个部件各管什么、三步流程怎么接力、向量核的标记是什么意思，讲的时候要带着第 3 节算过的访存账：一次 2^20 个元素的向量加法搬 12 MiB、做 1,048,576 次加法，流水线的收益来自搬运与计算的重叠。能画出一个算子从定义到被调用的链路，并说清每个环节的产物，定义是算子类、编译是 kernel 二进制加注册信息、注册是算子名到实现的映射、调用是前向里的一次调用，四条缺一不可。

### 第 1 节 · 环境：CANN + torch_npu + vllm-ascend 的安装链

**目标**：装好一条能跑 vLLM 的 Ascend 环境，并留下一份带版本号的安装记录。

**怎么做**（60 分钟，需 Ascend 环境；无卡时先读文档、拉镜像、做配置检查）：

先看两个数：版本锚点一共 5 个——Python 3.12、CANN 9.2.1、PyTorch 2.10.0、TorchNPU 2.10.0.post7、vllm-ascend v0.30.0（2026 年 10 月）；安装记录里要留的版本项一共 6 项，上面 5 个再加驱动与固件版本。5 和 6 这两个数先钉住，后面所有检查都围着它们转：装环境这件事，在这里衡量的不是东西装没装上去，是 6 个版本号对没对齐。

为什么是“链”，不是“清单”？清单里的项彼此独立，缺一项补一项就行；链里的环一环扣一环，上一环没接好，下一环连装都装不上。CANN（Compute Architecture for Neural Networks，华为 Ascend 的软件栈，驱动之上的 SDK 与算子库）是底座，TorchNPU（PyTorch 的 Ascend 适配，让 PyTorch 能认 NPU 这块设备）站在底座上，vllm-ascend（vLLM 的 Ascend 平台插件）站在 TorchNPU 上。底座的版本错了，上面的适配装上去也认不出卡；适配的版本错了，插件装上去也找不到算子。安装顺序本身就是依赖顺序，倒过来装，报错会告诉你这一点——只不过报错信息通常不会明说“你装反了”，它只会说某个符号找不到、某个库加载失败。把“链”这个字记在心里，报错时先问一句：是不是上一环就没接好？

这就引出了本节最重要的一条工作方法：**安装步骤以 [vllm-ascend](https://github.com/vllm-project/vllm-ascend) 仓库 README 的安装章节为准**，不要照抄书中列出的固定命令。道理很简单：书中的命令只对应写作时的版本；版本往前走一步，命令就可能变。vllm-ascend v0.30.0 要求的那 5 个版本，是第 26 章定下的锚点，对应 2026 年 10 月那个时间点；你真正动手的那天，仓库 README 里的版本要求可能已经变了。书在这里的角色是地图，不是说明书：地图告诉你这条链上有哪几环、每环的版本号要记下来；具体每一步敲什么命令，要去仓库 README 里读当下的版本。照着 README 一步一步走，走到哪一步、输出是什么，当场记下来。

每装一步记一步，记什么？命令本身、输出的关键行、版本号。版本号要查两个地方：`pip list` 里的 `torch`、`torch_npu`、`vllm`、`vllm-ascend` 四个包的版本，以及 `npu-smi info` 给出的驱动与固件版本。四加二，正好是上面那 6 项。为什么连 `pip list` 的输出都要留？因为“装好了”有两种意思：一种是命令跑完了没报错，一种是装上去的版本正是锚点要求的版本。`pip` 在依赖冲突时可能悄悄给你换一个版本，命令退出的状态码还是 0——不查 `pip list`，你就不知道自己装的到底是哪个版本。安装记录的价值就在这里：它不是流水账，是第 6 周写报告时要引用的证据。报告里写“在某某版本上测得某某结果”，版本号就是这句话的落点，落点来自这份记录，而不是凭记忆补写。

装完要验证，验证分三层，一层都不能少。先确认 NPU 可见，也就是 `npu-smi info` 能看到卡；再确认 PyTorch 能认 Ascend，也就是 `torch_npu` 可以 import、能在 NPU 上建一张张量；最后确认 `vllm` 能启动并识别到 NPU 平台。三层验证缺一不可，这句话不是口号，是第 1 周那张分层图的现场应用：卡认不出来，是驱动层的问题；`torch_npu` 认不出来，是框架适配层的问题；vLLM 认不出来，是插件层的问题。每一层查的东西不一样，失败指向的层次也不一样。反过来，如果只验证最后一层，vLLM 启动失败时你根本不知道该往哪一层去查；三层都验过，失败的那一层就是排查的起点。

三层验证还有一笔小账值得算：每层只有过与不过两种结果，三层一共是 2 的 3 次方，8 种状态，其中只有 1 种是全绿，另外 7 种都至少有一层失败。这笔账的用处是定位：8 种状态里，失败的组合不同，排查的方向就不同。举例来说，`npu-smi info` 能看到卡、但 `torch_npu` 认不出来，这是一种状态，问题大概率在 CANN 的环境脚本有没有 source、TorchNPU 的版本对不对得上；`torch_npu` 能建张量、但 vLLM 认不出 NPU 平台，是另一种状态，问题大概率在插件层——vllm-ascend 装没装对、版本与 vLLM 对不对得上。验证记录写下来的时候，把三层的结果各记一行“过 / 不过”，再加一行“失败指向哪一层”，排查就有了起点，而不是对着一条报错从头猜。

无卡的时候怎么办？先读 README 的安装章节与 Dockerfile（如果仓库提供的话），拉取镜像并做配置检查——环境变量、挂载路径、端口，把检查结果写下来；推理启动的部分标注“待有卡后补测”。这条替代路径的边界要划清楚：拉镜像、读脚本、做配置检查，这些是不需要卡就能做的事；启动推理、跑冒烟、看输出，这些是需要卡的事，没卡就不要写“已验证”。配置检查本身也有产出：环境变量对不对、挂载路径存不存在、端口有没有被占用，这些检查项写下来，等有卡的那天，照着检查项走一遍，省掉的是一次次现查文档的时间。

有两个常见误解。一个是“`torch_npu` 装好了，就等于能跑 vLLM”——不对。`torch_npu` 只解决 PyTorch 认不认 Ascend，vLLM 认不认 NPU 平台是插件层另外的事，两层之间没有自动递进。上面那 8 种状态里，就有“前两层全绿、第三层失败”这一种，专门用来提醒这件事。另一个是版本号“差不多就行”——不对。CANN、TorchNPU、vllm-ascend 三者的版本对应关系是这条链上最严的地方，第 4 节会专门收一类坑来讲它。这里先把态度钉住：版本号不是装饰，是安装记录里最值得核对的一栏；对不上锚点的版本，先记下来、问清楚，不要顺手装一个“差不多”的版本再继续往下走。

对照第 2 周的版本锚点：那一周定下 vllm-ascend v0.30.0 与 Python 3.12、CANN 9.2.1、PyTorch 2.10.0、TorchNPU 2.10.0.post7 的对应关系，本周就是把这组对应关系落到一台真实环境上。第 2 周是纸上定锚，本周是动手对齐——锚点定得再准，不落到环境上也只是纸上的数。等第 6 周写报告时，报告里“环境”那一节引用的就是本周这份安装记录：版本号、驱动与固件、三层验证的结果，一行都不能少。

版本漂移怎么办？动手的那天，README 要求的版本与第 2 周的锚点不一致，是完全可能的事。做法是跟 README 走，但把两件事都记下来：锚点要求什么、实际装了什么，以及为什么跟 README 走。锚点是书中定下时的快照，README 是动手时的当下；快照的作用是出发前对齐，不是装完后削足适履。第 6 周报告引用版本号时，引用实际装的版本，不是锚点——报告要对真实环境负责，锚点只负责告诉读者“出发时计划的是这一组版本”。两组数字都留在安装记录里，读者一眼能看出版本是什么时候、为什么变的。

读 Dockerfile 也有方法。先看基础镜像是哪一个——它决定了 Python 与系统库的起点；再看 CANN 是怎么装进去的——在线装还是离线包；再看环境脚本在镜像构建的哪一步被 source、启动命令的入口是什么。读它不是为了背它，是为了拉镜像做配置检查时知道该查什么：环境变量在 Dockerfile 里用 ENV 写了哪些、挂载路径对应镜像里的哪些目录、端口在 EXPOSE 里写了什么。配置检查的结果写下来：哪项对上了、哪项要改、哪项等有卡再验。检查项写得越具体，有卡那天照着走就越快——那天的任务是启动推理，不是现查文档。

**产出**：一份安装记录（含版本号：Python / CANN / PyTorch / TorchNPU / vllm-ascend / 驱动与固件），以及三层验证的结果（每层过 / 不过，失败指向哪一层）。

### 第 2 节 · 部署与冒烟：同一模型在 Ascend 上跑起来

**目标**：同一模型在 Ascend 上跑起服务，同一个 prompt、同一输出长度，确认能出结果。

**怎么做**（60 分钟，需 Ascend 环境；无卡时标注“待有卡后补测”）：

先算一笔模型体量的账，再决定选哪个模型。Qwen2.5-0.5B 的名字里就有答案：0.5B 是 5 亿参数，fp16（半精度浮点，每参数 2 字节）下权重占 5 亿 × 2 字节，等于 1.0×10⁹ 字节，约 0.93 GiB；Qwen3-0.6B 是 6 亿参数，同样算下来是 1.2×10⁹ 字节，约 1.12 GiB。这两个数都是算例——用参数量乘每参数字节数推出来的，不是实测读数。它们的用处是选型：权重 1 GiB 量级的模型，显存占用上留的余地大，部署时显存本身不太可能成为第一个瓶颈；选它们，等于把“模型太大跑不起来”这个变量先排除掉。nano-vllm-ascend 的支持列表里有这两个模型，选支持列表里的模型，能减少模型本身带来的变量——这句话换个说法就是：冒烟这一步要测的是芯片与栈，不是模型，模型越小、越在支持列表里，冒烟结果就越干净。

模型不变，变的只有芯片——这是跨芯片对比成立的前提。M1 里已经在 NVIDIA 上跑通过的同一个模型，拿到 Ascend 上再跑一遍，prompt 相同、输出长度相同，两边的输出才能放在一起对照。如果模型换了，输出不一样时你分不清是芯片的差别还是模型的差别；如果 prompt 或输出长度换了，对照的基准就动了。控制变量这件事在第 6 周会放大成完整的对比方法论，本周先把它落到最小的一步：同一个模型、同一个 prompt、同一输出长度。选模型的时候问自己一句：这个模型在 NVIDIA 上跑通过吗？跑通过，就拿它；没跑通过，先回去在 M1 的流程里跑通，再来 Ascend。

启动服务按 vllm-ascend README 的启动方式走，启动命令与启动日志的关键行记下来。日志里要看的三样东西是：平台识别（服务认出自己跑在 Ascend 上）、加载的算子、显存分配。平台识别是第 1 节第三层验证的延续——服务起来之后，日志里应该有它认出 NPU 平台的痕迹；加载的算子是第 3 节要展开的线索，哪些算子走了 Ascend 实现，启动时就能看到端倪；显存分配是部署的现场感，权重 1 GiB 量级的模型占了多少显存、还剩多少，记一笔，第 6 周做性能对比时这就是基线的一部分。日志很长，全抄下来没有意义，抄关键行：认出平台的那一行、加载算子的那几行、显存分配的那一行。

冒烟用 M0 的 `scripts/bench_openai.py` 发一次请求——同一个 prompt、同一输出长度，先确认能出结果，再看结果对不对。顺序不能反：先确认“能出结果”，再确认“结果对不对”。能出结果是部署的验收，结果对不对是正确性的验收，两关混在一起，失败时分不清是哪一关没过。结果对不对的检查方法是与 NVIDIA 上同一模型的输出肉眼对照一次：同一个 prompt、同一输出长度，两边的输出应该大体一致；明显乱码先停下来查，不要继续压测。乱码不停继续压测，压出来的数字没有任何意义——第 1 周讲过的道理在这里再用一次：先对、再快。肉眼对照不是严谨的精度回归，第 6 周会做正式的精度回归；本周的肉眼对照只负责拦住最粗的错误，比如输出全是乱码、输出提前截断、输出与 prompt 完全无关。

冒烟的耗时要会算，这笔账分两步。第一步是总耗时怎么拆：一次请求的总耗时，等于首 token 延迟（TTFT，从发请求到第一个 token 出来的时间）加上后面每个 token 的间隔（ITL，每多一个 token 的时间）乘以输出长度减一。写成算式就是总耗时 = TTFT +（输出长度 − 1）× ITL。拿一组假设数字走一遍，纯粹是算例、不是实测：假如 TTFT 是 0.5 秒、ITL 是 0.05 秒、输出长度是 32 个 token，总耗时就是 0.5 + 31 × 0.05，等于 2.05 秒。拆开算的好处是定位：总耗时长了，是首 token 慢，还是每个 token 都慢，两个原因指向的地方不一样——首 token 慢多半与 prompt 处理、模型加载有关，每个 token 都慢多半与解码、算子有关。第二步是吞吐怎么换算：吞吐等于输出 token 数除以总耗时，还是上面那组假设数字，32 个 token 除以 2.05 秒，约 15.6 tok/s。再换一组更直观的数：32 个 token 用了 4 秒，吞吐就是 8 tok/s；输出长度翻到 64 个 token、耗时也翻到 8 秒，吞吐还是 8 tok/s——吞吐这个量把输出长度除掉了，两个不同输出长度的请求才能放在一起比。这两组数都是算例，用来演示“输出长度与耗时怎么算”，不是任何一次实测的结果；真正跑起来的那天，TTFT、ITL、总耗时都要从实测记录里取。

记下第一次成功的端到端调用：命令、prompt、输出长度、耗时，只记一次，不做结论。只记一次，是因为样本量是 1：一次成功证明“这条路能走通”，证明不了“这条路一直能走通”，更证明不了“这条路有多快”。不做结论的意思是：不要从一次调用里推出任何关于性能的判断——第 6 周的性能对比要跑三级并发、每级多次测量，那时才轮到结论。本周的记录只要做到一件事：第一次成功的那次调用，命令是什么、prompt 是什么、输出长度是多少、耗时是多少，四项齐全，别人照着这四项能把同一次调用复现出来。复现性就是这份记录的全部要求。

无卡的时候，本节整节标注“待有卡后补测”。这不是偷懒，是诚实：部署与冒烟的每一步都需要卡，启动服务、发请求、看输出，没有卡就没有任何一条可以写成“已验证”。能做的事在第 1 节已经做了——读文档、拉镜像、做配置检查；本节的产出（一次成功的端到端调用记录）只能等有卡的那天再补。反过来也要警惕一种心态：觉得“反正没卡，选模型、写 prompt 也可以先凑合”——选模型与写 prompt 当然可以先准备，但准备不等于验证，写下来的时候要分清哪句是准备、哪句是结论。

有两个常见误解。一个是“冒烟通过了，就等于性能达标了”——不对。冒烟只回答“能不能出结果”，性能要到第 6 周的三级并发压测才回答；一次调用的耗时连“快不快”的边都沾不上，它只是“通没通”的证据。另一个是“输出看起来通顺，就等于数值对了”——不对。肉眼对照只能拦住乱码这种粗错误，数值上的细微偏差（比如某个算子回退到精度更低的实现）肉眼是看不出来的，要等第 6 周的精度回归拿评测集去量。冒烟的定位就是“通没通”，别让它背“对不对”和“快不快”的担子。

对照 M1 的部署流程：那边的启动命令、冒烟方法、记录格式，本周都照着来，只换芯片不换方法。方法不变，两边的记录才能对照；第 5 节那张对照表，填的就是“同一套方法、两块芯片”的差异。M0 的 `bench_openai.py` 也是同一个思路：脚本不变，变的只是它指向的服务地址——脚本是尺子，尺子不变，量出来的数才能比。

prompt 怎么选也有讲究。用 M1 里用过的同一个 prompt，不要现编新的。再往细里说：太短的 prompt（比如一两个词）输出几乎没有信息量，对照不出差别；开放式 prompt（比如“写一首诗”）输出每次都不一样，对照时分不清是芯片差别还是采样随机性。好的冒烟 prompt 是短的、事实性的、有确定性答案倾向的——比如一道简单的算术题或一句常识问答，输出长度固定，答案对错一眼能看出来。输出长度也固定下来，上面算例里用的 32 个 token 就是个合适的长度：长度固定，耗时与吞吐的换算才有共同的分母，两边的数才能放在一起比。

乱码怎么判，也值得先说清楚。“明显乱码先停下来查”里的“明显”，指的是输出里出现大段无法辨认的字符、反复重复同一个词、答非所问到与 prompt 完全无关。个别用词与 NVIDIA 那边不同、表达方式有差异，不算——采样本身就有随机性，同一模型在同一芯片上跑两次，输出也未必一字不差。肉眼对照对照的是“是不是同一个模型在正常工作”，不是“两个输出逐字相同”。这个标准定下来，冒烟时才不会在正常的采样差异上浪费排查时间，也不会把真正的乱码当成“采样波动”放过去。

**产出**：一次成功的端到端调用记录（命令 + prompt + 输出 + 耗时），无卡时标注“待有卡后补测”。

### 第 3 节 · vllm-ascend 插件架构：插件怎么 hook 进 vLLM、算子分发发生在哪

**目标**：能在插件里定位到具体算子的实现位置，并讲清算子分发的链路。

**怎么做**（60 分钟，无硬件可做——读代码）：

先数一数地图上有多少东西。第 1 周第 3 节给过一张目录地图，`vllm_ascend/` 下面一共 14 项：`platform.py`（`NPUPlatform`）、`ops/`、`attention/`、`model_executor/`、`quantization/`、`patch/`、`worker/`、`compilation/`、`device/`、`distributed/`、`profiler/`、`_cann_ops_custom/`、`ascend_config.py`、`meta_registration.py`。14 这个数先钉住，它的用处是防迷路：读代码的时候，看到一个不认识的目录，先问它在 14 项里的哪一项、那一项是干什么的，而不是顺着调用链一路跟下去跟丢了。地图的价值不在于背下来，而在于定位——你现在在哪、要去哪、中间经过哪几站。

本节要回答三个问题，读代码找答案。第一个问题是插件怎么 hook 进 vLLM：启动时 vLLM 怎么发现并加载 vllm-ascend，平台注册发生在哪——`platform.py` 里的 `NPUPlatform` 是怎么被 vLLM 识别的。问这个问题之前，先把“插件”这个词想清楚：插件是独立于 vLLM 主仓库的一个包，vLLM 在启动时发现它、加载它，然后把它认作一个平台。发现与加载的机制，就是你要去代码里找的第一个答案——到 `platform.py` 里看 `NPUPlatform` 的定义，到 `meta_registration.py` 里看注册的动作，再到 vLLM 主仓库里看平台发现的入口。找答案的时候盯住一个关键词：注册。平台注册、算子注册、后端注册，本节的三个问题背后都是同一个动作——某个东西在某个地方把自己登记上去，后面的流程才找得到它。

第二个问题是算子分发发生在什么地方：一次前向里，某个算子（比如 RMSNorm 或 SiluAndMul）是怎么被分发到 Ascend 实现的——分发点在平台层、插件层还是算子注册层。这个问题比第一个更值得慢下来，因为“分发”这个词很容易让人以为它只发生在一个地方。实际上分发是一条链：模型代码里调用某个算子，调用点要决定这次调用走哪份实现；决定本身可能发生在好几个地方——平台层根据当前是什么芯片做选择，插件层把自己的实现登记到某个注册表里，算子注册层在调用时查表找到对应的实现。三处都有可能，答案不是猜出来的，是顺着一次前向跟出来的。跟的方法在下一段，定位一个具体算子，从调用点一路跟到实现文件，分发点就在这条链上——链走到哪一步、实现从哪一步开始是 Ascend 的，分发就发生在哪一步。

第三个问题是注意力后端在哪：`attention/` 目录里是什么——vLLM 的 attention 后端选择是怎么走到 Ascend 的实现的。注意力后端（attention backend，vLLM 里负责执行 attention 计算的那一层抽象，不同芯片可以挂不同的后端实现）值得单独问，是因为 attention 是推理里最重的一块，也是不同芯片差异最大的地方之一。后端选择的意思是：vLLM 不直接写死“attention 怎么算”，而是留了一个后端接口，启动时根据平台选一个后端挂上去；Ascend 的后端实现就在 `attention/` 目录里。读这部分代码的时候，问两个问题：后端接口长什么样（它要求实现提供哪些方法），以及 Ascend 的实现把这些方法落到了哪些文件上。接口与实现分开，是插件架构里最常见的手法——第 1 周讲“平台级插件”时说的就是这件事，本节是它的现场版。

动手定位：选一个具体算子，建议 RMSNorm——M2 第 6 周讲过它是 CustomOp 的可替换面，这里的定位是它的芯片侧版本。从模型代码里的调用点出发，沿着分发链一路找到它在插件里的实现文件，记下文件路径与函数名。定位记录本身就是产出：文件路径加调用链（模型代码 → 分发点 → 插件实现）。为什么选 RMSNorm？因为它在 M2 里已经出现过一次，那次的身份是“可以被替换的算子面”，这次的身份是“被替换之后、芯片侧的那份实现”。同一个算子，两周、两个身份，对照着读，M2 里“CustomOp 是什么”与 M3 里“插件里的实现在哪”就接上了。定位的时候不用贪多，一个算子跟到底，比五个算子各跟一半有用：跟到底的意思是调用链上的每一站都写下来，模型代码里哪一行调了它、分发点在哪个文件、插件实现在哪个文件的哪个函数——链上有任何一站是“大概在那附近”，定位就不算完成。

对照第 2 周第 4 节的“定义 → 编译 → 调用”链路：这个算子的 Ascend 实现在链路的哪一环，它的编译产物在哪。定义、编译、调用是第 2 周讲一个算子从写出来到被 vLLM 调用的完整链路，本节的定位工作就是把 RMSNorm 放到这条链路上：它的定义在插件的哪个文件，它的编译产物是什么、落在哪，调用时 vLLM 是怎么找到编译好的实现的。链路对照的用处是防漏：如果定位记录里只有“实现文件在哪”，没有“编译产物在哪”，链路就是断的——实现写出来了、没编译，或者编译了、调用时没找到，都是部署时会真实遇到的问题，第 4 节收坑的时候还会再碰到它们。

一个常见的误解：“插件就是翻译层”——把插件想成一层薄薄的翻译，以为它只在 NVIDIA 的调用和 Ascend 的调用之间做一对一的转接。不对。上面那 14 项目录已经说明了它的厚度：平台、算子、注意力后端、模型执行器、量化、补丁、工作进程、编译、设备、分布式、性能分析，插件几乎把推理引擎的每一层都包了一层自己的实现。翻译层是薄的，插件是厚的；把它想薄了，读代码时会低估工作量，也会在第 4 周做算子覆盖分析时漏掉整片的目录。另一个容易错的想法是把 `attention/` 目录当成 attention 算子的实现本身——它装的是后端选择与后端实现，是“attention 怎么被调度、怎么被执行”的那一层，具体的 attention 算子实现可能还在 `ops/` 或更底层。目录名是提示，不是答案，答案在文件里。

回头看本周的链条：第 1 节装好了环境，第 2 节跑通了服务，本节是第一次打开盖子看里面——服务能跑起来，是因为这条分发链是通的。读代码的时候带着第 2 节的现场感：启动日志里看到的“加载的算子”，就是这条链上被分发到 Ascend 实现的那些算子；日志里的一行，对应代码里的一站。日志与代码对上，插件架构就不再是地图上的 14 个名字，而是一条走通过的链。

读 `platform.py` 也有方法。先看类定义——`NPUPlatform` 这个类名本身就是线索，类里的方法就是平台要向 vLLM 交代的能力：设备怎么发现、算子怎么注册、分布式怎么初始化。读的时候不用逐行读，先列出方法名，再问每个方法回答了 vLLM 的哪个问题。方法名就是平台的接口清单；清单列出来，第一个问题“插件怎么 hook 进 vLLM”就有了骨架，剩下的工作是把每根骨头上的实现读出来。

跟踪分发链的动手方法也值得写细一点。从模型代码里 RMSNorm 的调用点出发，用搜索找它的定义，再找定义里指向插件实现的那一跳。跟链的时候带一张纸，写下每一站的文件路径与函数名——链越长越要写下来，靠脑子记三站之后就会乱。分发点常常藏在最不起眼的一跳里：一个注册表的查表、一个条件分支、一次工厂函数的调用。找到它，第二个问题就答了一半；再问一句“如果这里换成另一个后端，实现会从哪来”，答上来，分发链才算讲清了。`attention/` 目录的读法也一样：先看目录下有哪些文件，再找后端选择的代码在哪里——启动时根据什么条件选了 Ascend 的后端。条件可能是平台名、设备类型、环境变量，读到条件判断的那几行，后端选择就从概念变成了代码。

**产出**：一张插件架构图 + 一个算子的定位记录（文件路径 + 调用链）。

### 第 4 节 · 踩坑记录：把每个问题和解法写下来

**目标**：留下一份踩坑清单，后面的人不用再踩一遍。

**怎么做**（60 分钟，需 Ascend 环境；无卡时先写“预期坑位”清单，实测后补）：

先把格式钉住，再往里面填内容。每个问题按四列记下来：现象（报错原文或症状）、定位（第 1 周分层图里的哪一层）、解法（命令或改动）、验证（怎么确认修好了）。四列缺一不可，缺一列，清单就少一块用处：没有现象，后面的人对不上自己的报错；没有定位，排查没有起点；没有解法，清单只是问题集；没有验证，修没修好全凭感觉。格式是死的，内容是活的——第 1–2 节遇到的每个问题，都往这个格式里填，填满一行是一行。

三类坑至少要覆盖，算一笔小账：三类乘四列，清单至少是 12 个格子。第一类是版本不匹配：CANN、TorchNPU、vllm-ascend 三者的版本对应关系。第 1 节已经说过，这三者的对应关系是安装链上最严的地方，严到什么程度？严到版本对不上时，报错往往不直接说“版本错了”，而是说某个符号找不到、某个库加载失败——现象与根因之间隔了一层，定位的那一列就是用来捅破这层窗户纸的。记这一类坑的时候，现象一栏写报错原文，定位一栏写“版本对应关系”，解法一栏写换到哪个版本、怎么换，验证一栏写换完之后 `pip list` 里四个包的版本与三层验证的结果。版本号写全，未来的自己与后来的人才能照着复现。

第二类是环境变量与路径：CANN 的环境脚本有没有 source。这类坑的狡猾之处在于它常常表现为第一类坑的样子：库找不到、符号找不到，看起来像版本错了，实际上只是环境变量没进当前 shell。排查的思路是分层：先问 `npu-smi info` 能不能看到卡——能看到，驱动层大概率是好的；再问 CANN 的环境脚本 source 了没有、环境变量里有没有 CANN 的路径——没 source，先 source 再试。定位一栏在这里的价值最明显：同一个报错，定位写“环境变量层”与写“版本层”，解法完全不同；定位写错了，解法就跟着错，时间就花在错误的方向上。

第三类是显存与设备可见性：`npu-smi` 能看到卡但框架看不到。这是最能体现分层图价值的一类坑：设备在驱动层可见、在框架层不可见，问题就卡在驱动层与框架适配层之间——CANN 装没装对、TorchNPU 认不认这张卡、设备权限对不对，都在这一带。排查的时候顺着第 1 节的三层验证往回走：第三层（vLLM 认不出平台）失败，退到第二层（`torch_npu` 能不能建张量）；第二层失败，退到第一层（`npu-smi info` 能不能看到卡）；第一层过了、第二层不过，问题就在两层之间。三层验证在这里从“验收清单”变成了“排查路线图”，同一份记录，两种用法。

无卡时先写“预期坑位”：按 README 的安装章节与 issue 列表，列出最可能遇到的三个问题与排查思路，标上“待实测确认”。“预期坑位”四个字要写清楚它的身份：它是读文档与 issue 列表推断出来的、还没有在实机上遇到过的问题，不是已经踩过的坑。每个预期坑位写三样东西：按文档推断它可能长什么样（现象的猜测）、按分层图推断它可能在哪一层（定位的猜测）、按 README 与 issue 里的讨论推断排查思路从哪一步开始。三个预期坑位对应上面三类坑，每类一个，刚好把最可能出问题的地方先圈出来。实测的那天，预期坑位要逐条对账：遇到了，按四列格式补成正式记录；没遇到，写一句“本次安装未遇到”，不要悄悄删掉——没遇到本身也是信息，说明这条路在这个版本上是通的。

为什么验证那一列不能省？因为“修好了”是最容易自我欺骗的一句话。改了一个环境变量、重新跑了一遍命令、没报错，就觉得修好了——但没报错不等于修好了，可能是报错被绕过去了，也可能是这次运气好没触发。验证一栏写的是“怎么确认修好了”：三层验证重新跑一遍、冒烟重新跑一遍、报错的原文不再出现，写具体动作，不写感觉。验证动作写下来之后，同一份清单交给别人，别人照着验证动作能得出同样的“修好了”，清单才算立住了。

有两个常见误解。一个是“报错原文不重要，知道大概意思就行”——正好相反，报错原文是清单里最值钱的一栏。报错原文是后面的人拿来对号的唯一凭证，意思转述得再准确，也对不上原文里那串版本号、路径与符号名；对不上号，清单就帮不上忙。另一个是“预期坑位写得越像踩过越好”——不对。预期坑位与实测踩坑之间隔着一道线，线的一边是“推断”，另一边是“遇到过”；把推断写成遇到过，清单的可信度就塌了。诚实标注“待实测确认”，不是示弱，是清单的用法说明：读的人知道哪些条目可以直接照着修、哪些条目还要自己验证。

回头看第 1–2 节：安装记录里的版本号、三层验证的结果、启动日志的关键行、第一次成功的调用记录，这些都是第 4 节的原材料——坑不是凭空记的，是从那几份记录里长出来的。反过来，第 4 节的清单也是第 6 周报告的原材料：报告里“遇到的问题与解法”那一节，抄的就是这份清单。本周的四节之间就是这样咬合的：环境、部署、架构各产一份记录，踩坑清单把前三节的问题收拢，下一节的对照表把前四节的差异收拢。

三类坑的排查思路还可以再往细里写，因为“解法”与“验证”两栏的草稿就藏在这里。版本不匹配这一类，先查 `pip list` 里四个包的版本，再对照锚点；对不上，先问是哪个包被换了版本——`pip` 解决依赖冲突时可能悄悄升级或降级某个包，命令退出的状态码还是 0，不查 `pip list` 就发现不了。再决定是钉住版本重装，还是接受新版本并更新锚点记录。接受新版本不是不可以，但要写下来：换了哪个版本、为什么接受、三层验证重跑的结果是什么。环境变量与路径这一类，排查动作是逐项检查：环境脚本 source 了没有（在当前 shell 里看对应的环境变量，值在不在）、路径对不对（目录存不存在）、source 的顺序对不对（装完 CANN 再 source，还是 source 完再装，顺序反了也可能出问题）。设备可见性这一类，排查动作是逐层往回退：`npu-smi` 看得到、框架看不到，查 CANN 与 TorchNPU 的版本对应与环境变量；框架看得到、vLLM 看不到，查插件的安装与版本对应。每一类坑的排查思路写成“先查什么、再查什么”，清单里的“解法”与“验证”两栏就有了现成的底稿。

预期坑位怎么写，也有方法。读 issue 列表的时候，按时间倒序看最近的 issue，先看标题里带版本、安装、启动这些词的，再看讨论里有没有维护者的回复；有回复的 issue 价值最高，回复里常常直接写了“这是版本对应问题”或“先 source 环境脚本”。预期坑位的排查思路就从这些回复里来，写的时候注明来源——README 的哪一节、issue 讨论里的哪句话，等实测时对账也有据可查。来源写清楚，预期坑位就是有出处的推断，不是凭空猜的；出处与推断分开写，读的人分得清哪句是文档说的、哪句是你猜的。

清单的维护还有一点：踩坑清单不是写完就 frozen 的文档，实测中每遇到一个新问题就加一行；第 6 周写报告时，清单就是“问题与解法”一节的底稿。清单越往后越值钱，因为它记的是这条链上真实出现过的问题，不是文档里推测的问题。反过来，预期坑位里没遇到的条目也不要悄悄删掉，写一句“本次安装未遇到”留在那里——没遇到本身也是信息，说明这条路在这个版本上是通的，后来的人看到这一行，就知道这一步可以放心走。

**产出**：踩坑清单（现象 + 定位层 + 解法 + 验证），无卡时为“预期坑位”清单（每条标“待实测确认”）。

### 第 5 节 · 小结：Ascend 与 NVIDIA 的部署差异对照表

**目标**：写出一页部署差异表。

**怎么做**（60 分钟，总结无卡可做；差异表里没有实测过的项标“待补测”）：

对照 M1 里在 NVIDIA 上的部署流程，填这张表：

| 环节 | NVIDIA（M1 的流程） | Ascend（本周的流程） | 差异点 |
|---|---|---|---|
| 驱动与设备可见性 | `nvidia-smi` | `npu-smi info` | 命令与输出格式不同，检查项相同 |
| 框架适配 | PyTorch + CUDA | PyTorch + TorchNPU（CANN） | 多一层 CANN，版本对应关系更严 |
| 引擎插件 | vLLM 原生 | vllm-ascend 插件 | 插件的版本要与 vLLM 版本对应 |
| 启动命令 | `vllm serve ...` | 同命令 + Ascend 平台识别 | 命令相近，底层走的平台不同 |
| 算子实现 | CUDA / Triton | CANN / AscendC / 自定义算子 | 第 4 周要展开的覆盖分析 |

表只有 5 行，但每一行背后都是本周的一节。驱动与设备可见性那一行，是第 1 节三层验证的第一层；框架适配那一行，是第 1 节的整条安装链；引擎插件那一行，是第 3 节的插件架构；启动命令那一行，是第 2 节的部署与冒烟；算子实现那一行，是第 3 节定位过的 RMSNorm 与第 4 周要做的覆盖分析。表是收拢，不是新内容——填表的时候，每一行都能指回本周的一节，指不回去的行，说明那一节还没读透。

一句话结论：部署差异主要在“多出来的层次”（CANN 与插件），而不是模型本身——**模型代码不用改，改的是底下的栈**。这句话是第 1 周“平台级插件”结论的实测版。第 1 周讲平台级插件的时候，它还是个设计思路；本周装了一遍环境、跑了一遍服务、读了一遍插件代码，思路落到了实处：同一个模型、同一个 prompt、同一输出长度，两边都能跑，差别在模型下面的那几层——驱动命令换了、框架适配多了一层 CANN、引擎从原生变成了插件、算子从 CUDA 与 Triton 变成了 CANN、AscendC 与自定义算子。模型本身没动，动的是栈。这个结论值得写下来，因为它决定了第 4 周与第 5 周的工作方向：第 4 周的算子覆盖分析，分析的是栈里的算子；第 5 周的移植，移植的也是栈里的东西，不是模型。

把本周的检查清单并进总清单，加两条：“安装记录的版本号全吗”“能在插件里定位到一个算子的实现吗”。第一条回指第 1 节：6 项版本（Python、CANN、PyTorch、TorchNPU、vllm-ascend、驱动与固件）全不全，全了，安装记录才算立住；第二条回指第 3 节：一个算子的定位记录有没有文件路径与调用链，有了，插件架构才算读进去。两条都是能用“是 / 否”回答的问题——检查清单的每一条都该是这样，答不出来就回去补，而不是凭印象打勾。

最后是诚实标注：差异表里没有实测过的项标“待补测”。本周没有实机，就没有实测记录，表里凡是依赖实测的说法——启动日志的关键行、冒烟的耗时、输出的对照结果——都要等有卡的那天再填。表先按流程对照填好，实测项空着、标上“待补测”，等第 6 周写报告时再回来补。空着不可耻，填上编造的数字才可耻。

## 第 28 章 · 算子覆盖分析

> 硬件：第 1 节需要能跑 profiling 的环境（NVIDIA 卡即可）；第 2–5 节的对照工作无卡可做；芯片侧的核实需要 Ascend 环境或官方文档，核实不了的项标“待核实”。
>
> 本周主线：先拿一张真实的算子清单，再逐条问每个算子在 Ascend 上由谁承接——清单是事实，对照是判断，瓶颈归因是清单与对照相乘之后才配下的结论。

### 第 1 节 · 导出算子清单：用 PyTorch Profiler 导出一次推理的全部算子

**目标**：拿到一份真实的算子清单——一次推理到底调了哪些算子、各占多少时间。

**怎么做**（60 分钟，需 NVIDIA 卡；无卡时先写 profiler 脚本，实测标注“待补测”）：

先把这一节的定位说死：只导出，不分析。导出是一次人口普查（census），分析是普查之后才做的事。普查的价值在于完整——一个算子再小，也要出现在清单上；分析的诱惑在于提前下判断——看到某个算子占了 40% 的时间，手就痒，想立刻说它是瓶颈。这一节把手按住。清单不完整，后面所有的对照都会漏项；清单一旦漏了长尾里某个算子，第 2 节的矩阵就永远少一行，而少的那一行恰好是回退项的概率，并不比任何一行低。先把清单拿全，再谈哪一行重要。

方法复用 M0 第 3 节的 profiling 手法，对 M1 里跑通过的模型做一次前向。复用是有原因的：M0 第 3 节已经解决过“怎么采、采什么、怎么读表”这些基本问题，本周不需要发明第二套 profiling 方法，需要的是把同一套方法对准一个新的问题——一次推理的算子构成。模型沿用 M1 里跑通过的那个，同样有原因：清单的可信度取决于模型本身能不能跑通，一个还没跑通的模型采出来的清单，里面混着报错重试与异常路径，读它等于读一份被污染的样本。先跑通，再采样，顺序不能反。

采之前要先定三个口径，口径不定，清单上的数字就没法互相比较。第一个口径是采哪一次前向：热身（warmup）跑完之后、进入稳定状态的那一次。第一次前向里混着缓存预热与惰性初始化的开销，把它采进来，清单反映的就是“第一次跑”而不是“平时跑”。热身几遍再采，采到的才是稳定态的前向。第二个口径是形状：这一次前向的 batch 与序列长度是多少。Prefill 形状与 decode 形状的算子构成并不相同——序列很长时矩阵乘占大头，单 token 解码时矩阵乘的占比下来了，逐元素算子的相对占比反而上去。清单必须把形状写在表头上，一份没有形状的清单是没有语境的数字，下周换个形状再采，Top 10 很可能换一批名字。第三个口径是按什么时间排序：按 CUDA 核函数（kernel）时间排，还是按 CPU 端的算子时间排。推理延迟由 GPU 端的执行时间决定，排序的依据就取 CUDA 时间；CPU 时间留着排查 launch 开销时再看。两个时间口径排出来的 Top 10 可能不一样，选哪一个要先说清楚，而不是采完了再挑好看的那个。

Profiler 导出的一行里至少有四列：算子名、调用次数、累计耗时、占比。算子名是 PyTorch 层面的名字，例如 `aten::mm`、`aten::bmm`；调用次数是这次前向里它被调了多少次；累计耗时是所有调用加起来的时间；占比是累计耗时除以总时间。还有一列容易被忽略：自耗时（self time）与总耗时（total time）的区别。一个算子如果内部又调了别的算子，总耗时会把子算子的时间也算进来，自耗时只算它自己那一层。排序的时候用自耗时还是总耗时，结果会不一样——一个总耗时很大的算子，可能只是个空壳，时间全花在它调的子算子身上。这一节的清单按自耗时口径取数，理由只有一个：后面第 2 节要逐条对照“这个算子由谁承接”，对照的对象是算子本身，不是它背后的调用树。口径写在清单的表头上，免得下周有人拿总耗时重排一遍，得出另一份 Top 10，还以为清单错了。

拿一组算例把这四列的关系算清楚。假设某次前向的总时间是 50.0 毫秒，耗时前十的算子分别是 21.0、9.0、4.5、3.5、2.5、2.0、1.5、1.0、0.6、0.4 毫秒。先加总：21.0 加 9.0 是 30.0，再加 4.5 是 34.5，再加 3.5 是 38.0，再加 2.5 是 40.5，再加 2.0 是 42.5，再加 1.5 是 44.0，再加 1.0 是 45.0，再加 0.6 是 45.6，再加 0.4 是 46.0 毫秒。Top 10 合计 46.0 毫秒，占总时间 50.0 毫秒的 92.0%。剩下的长尾一共 4.0 毫秒，占 8.0%。占比那一列逐项算出来是 42.0%、18.0%、9.0%、7.0%、5.0%、4.0%、3.0%、2.0%、1.2%、0.8%，十个数加起来正好是 92.0%，与合计对得上。Top 3 是 21.0 加 9.0 加 4.5 等于 34.5 毫秒，占 69.0%——前三名就占了近七成，这组数里清单的头重脚轻非常明显。这组数是算例，不是实测，作用是让你在拿到真实清单的第一时间就能验算：Top 10 加起来对不对得上它声称的占比，长尾还剩多少，有没有哪一行的时间与占比互相矛盾。验算不过的清单，先修清单，再往下走。

调用次数那一列单独看会骗人。同一组算例里，排第一的矩阵乘被调了 48 次，累计 21.0 毫秒，平均每次 0.4375 毫秒；排第六的某个逐元素算子被调了 1000 次，累计 2.0 毫秒，平均每次 0.002 毫秒。单次耗时一比，0.4375 除以 0.002 等于 218.75 倍——矩阵乘调一次的时间，够逐元素算子调两百多次。调用次数排第一的算子，耗时可能只排第六；耗时排第一的算子，调用次数可能只有几十次。按调用次数排序的清单，排出来的是“谁最忙”，按耗时排序的清单，排出来的是“谁最贵”。第 2 节要对照的是“谁最贵”，因为回退的代价是按耗时占比算的，不是按调用次数算的。一个被调 1000 次的算子回退了，每次多花的时间再乘 1000 次，账也要回到累计耗时上算——调用次数本身不决定瓶颈，调用次数乘以单次耗时才决定。

算子名那一列也有坑：PyTorch 层面的名字与芯片侧的承接之间隔了一层映射。Profiler 导出的是 `aten::mm`、`aten::bmm` 这样的名字，而第 2 节要问的是“这个 PyTorch 算子在 Ascend 上由哪个实现承接”。`aten::mm` 与 `aten::bmm` 在名字上只差一个字母，承接却可能完全不同：一个是二维矩阵乘，一个是批量矩阵乘，走的 kernel 路径与分块策略都不一样，清单上必须把它们当成两个算子，合并成“矩阵乘”一类就等于把对照的粒度弄粗了。反过来也有合并的坑：`aten::silu` 与 `aten::mul` 在 profiler 里是两个算子，实际执行时可能被融合成一个 SiluAndMul kernel——清单上是两行，硬件上是一次执行。按算子名逐条数，会把一次融合执行数成两次；按 kernel 数，又会丢掉 PyTorch 层面的调用结构。这一节的清单保留 PyTorch 算子名原样，不提前合并、不提前折算，融合那笔账留到第 2 节对照时再算。清单的任务是如实记录，不是提前聪明。

预期会看到的构成，源文件里已经点过名：矩阵乘（GEMM 类）、attention、归一化（RMSNorm）、激活（SiluAndMul）、各类逐元素算子。预期之所以值得先写下来，是为了对照——真实清单出来之后，先问一句“预期里的名字是不是都在”，再问“有没有预期之外的名字”。预期之外的名字最有信息量：一个没想到的算子进了 Top 10，往往意味着模型里有一段之前没注意到的计算，例如某个 reshape 或类型转换被反复调用。预期是用来发现意外的，不是用来确认自己没错的。清单采完之后，预期之外的行要单独圈出来，第 2 节对照时优先查它们——熟悉的算子对照起来有路可循，陌生的算子才最容易在“待核实”里躺平。

最后是无卡时的退路：先写 profiler 脚本，实测标注“待补测”。脚本本身是可以现在写完的——模型、形状、导出列、排序口径、输出格式，全都不依赖显卡。写完脚本，清单的框架就立住了：表头、列、Top 10 的位置都在，只等有卡跑一遍把数字填进去。待补测不是没做，是把“能做的部分”与“必须等硬件的部分”分开，前者现在交货，后者不硬编数字顶替。清单上任何一行没有实测数字，就写待补测，不拿别的模型、别的形状的数来凑——凑出来的清单比空着的清单更有害，空着至少诚实。

**产出**：一份算子清单（算子名 × 调用次数 × 耗时 × 占比，Top 10 标出），表头注明模型、形状与排序口径（CUDA 自耗时）；无卡时脚本先行，数字标注“待补测”。

### 第 2 节 · 逐条对照：哪些算子在芯片侧有对应实现，哪些会回退

**目标**：出一份算子覆盖矩阵——每个算子在芯片侧的状态是什么。

**怎么做**（60 分钟，无硬件可做；对照依据是官方文档与插件源码，核实不了的标“待核实”）：

覆盖矩阵要回答的问题只有一个：清单上的每个算子，在 Ascend 上由谁承接。这个问题听起来像查表，实际是个判断题——“由谁承接”有四种答案，每一种答案背后的含义、证据要求与风险都不一样。先把四档的定义钉牢，再逐条往里填，顺序不能反。定义不清的矩阵，填得越满越危险，因为每一行都像是有结论，其实只是把不确定藏进了分类里。

第一档是原生实现：CANN 或者 AscendC 里有对应实现，性能有保障。原生这两个字的分量在于“官方实现”——它跟着芯片的软件栈一起发布、一起测试，接口稳定，出了问题有明确的责任方。查它的证据是 CANN 文档与 AscendC 的算子清单，写进矩阵的时候要写清文档链接与版本。性能有保障这四个字也要小心：它保障的是“这个实现是为这块芯片写的”，并不保证它在你的形状下是最快的。原生实现在某个 batch 下可能走通用路径，换个形状才走优化路径——状态是原生实现，性能仍然要实测确认。把“有原生实现”读成“性能没问题”，是这一档最常见的误读。

第二档是插件实现：vllm-ascend 的 `ops/` 或者 `_cann_ops_custom/` 里有实现。插件与原生的区别不在“能不能跑”，而在“谁维护、跟谁走”。插件实现是推理框架一侧为了补齐覆盖而写的定制算子（CustomOp），它跟着 vllm-ascend 的版本走，CANN 升级的时候它可能要跟着改。第 3 周第 3 节定位过这类位置，方法就是那一节的方法：先在 `ops/` 里找，再到 `_cann_ops_custom/` 里找，两个地方都没有，再去文档里找。插件实现的风险不在正确性，而在跟随性——框架升级、芯片驱动升级，插件都可能要重新适配。矩阵里标插件实现的行，要把文件路径写清楚，路径就是它的证据，也是它下次失效时最先要复查的地方。

第三档是回退：没有芯片侧实现，走 CPU 或者 PyTorch 参考实现。回退这两个字容易被读成“跑不起来”，其实正好相反：回退的意思是“能跑，但是慢”。CPU 回退是把计算搬到 CPU 上做，PyTorch 参考实现是用 PyTorch 的通用算子顶上去，两个都是“先保证能跑”的退路。回退的代价不在功能上，在时间上——而时间的代价要到下一段的算式里才算得出来。回退还有一个更隐蔽的形态：静默回退。模型跑起来了，没有报错，速度却比预期慢得多，查了半天才发现某个算子一直在走 CPU。矩阵的意义之一就是把静默的东西显性化：每一行回退都要写出来，写出来的回退才会被当成瓶颈来治，没写出来的回退只会被当成“这块芯片就这么慢”。

第四档是待核实：文档与源码里都没找到明确说法。待核实不是第五种状态，是“现在下不了结论”的诚实标记。查不到与不存在是两回事：文档里没写，可能是这个算子确实没有实现，也可能是实现藏在另一个名字下面，或者文档滞后于代码。把查不到直接写成回退，等于用猜测填了矩阵；把查不到写成待核实，等于把问题留给了下一轮核实。矩阵里待核实的行数本身就是信息：待核实占 Top 10 的一半，说明对照工作只做了一半，结论的置信度也要跟着打对折。核实日期那一列就是为此存在的——每个状态都要有个日期，日期一过，状态就过期。芯片软件栈的版本在变，今天的原生实现，明天可能换了路径；今天查不到的算子，明天可能补了插件。没有日期的矩阵是过期了也不知道的矩阵。

填矩阵的时候，对照的顺序也有讲究：从 Top 10 往下填，先填耗时占比大的行。理由在下一段的算式里：占比大的行，一档之差就是端到端的几成；占比小的行，档位错了也伤不到大局。时间有限的时候，先把贵的算子查实，便宜的算子可以先标待核实——矩阵的填写顺序本身就是一次资源分配。

关键问题是回退的算子在不在关键路径上，判断的方法是把“状态 × 耗时占比”一起看，不要只看状态。算式先摆出来：把一次前向的总时间归一化成 100 份，一个占 20 份的算子回退后慢 10 倍，它的时间从 20 份变成 200 份，总时间从 100 份变成 80 加 200 等于 280 份，端到端慢 2.80 倍。一个只占 1 份的算子同样回退后慢 10 倍，总时间从 100 份变成 99 加 10 等于 109 份，端到端只慢 1.09 倍。同样的回退、同样的 10 倍，账算出来一个是 2.80 倍，一个是 1.09 倍——差的不是回退本身，是回退的算子原来占多少。换一组数再验一次：占 20 份的算子回退后只慢 3 倍，总时间是 80 加 60 等于 140 份，端到端慢 1.40 倍。回退倍数从 10 倍降到 3 倍，端到端从 2.80 倍降到 1.40 倍——瓶颈的定价同时取决于占比与回退倍数，两个数缺一个，结论都下不了。这几组数都是算例，不是实测，它们的任务是把“状态 × 占比”这个乘法刻进判断里：以后看到矩阵里任何一行回退，先问它占多少，再问它慢几倍，两个数都有了，才轮到说“瓶颈”两个字。

这组算式还有一个推论值得注意：占比最大的那个算子，哪怕只慢一点点，账也很大。占 42 份的算子回退后只慢 2 倍，总时间是 58 加 84 等于 142 份，端到端慢 1.42 倍——慢 2 倍听起来不严重，乘上 42% 的占比，端到端还是慢了四成多。反过来，占 1 份的算子就算慢 10 倍，端到端也只慢 9%。优化的优先级就按这个乘法排：先治“占比大 × 回退多”的行，再治“占比大 × 回退少”的行，“占比小”的行无论回退多少倍都可以往后放。矩阵的阅读顺序就是这个乘法的排序，不是按算子名字母排，也不是按档位排。

填覆盖矩阵：

| 算子（PyTorch 名） | 耗时占比 | 芯片侧状态 | 实现位置（文件/文档链接） | 核实日期 |
|---|---|---|---|---|
| `aten::mm` | … | 原生实现 | … | 某年某月 |
| `aten::silu` / `aten::mul` | … | 插件实现 | … | 某年某月 |
| … | … | 待核实 | — | 待核实 |

矩阵的每一列都有它的任务。算子名那一列用的是 PyTorch 名，与第 1 节清单上的名字一一对应——对照的第一步是名字对齐，清单上的 `aten::mm` 与矩阵里的 `aten::mm` 必须是同一个算子，名字一错行，后面的状态就贴错了行。耗时占比那一列从第 1 节清单上抄过来，不重新测，抄的时候连形状一起抄，占比离开形状就没有意义。芯片侧状态那一列只填四档里的一个，不写模棱两可的话——“可能有实现”不是状态，“大概能跑”也不是状态，写不进四档的话就写待核实。实现位置那一列是证据列：原生实现写文档链接，插件实现写文件路径，回退写回退到的路径（CPU 还是 PyTorch 参考实现），待核实写一个破折号——破折号的意思是“这里本该有证据，现在没有”，比空着更诚实。核实日期那一列是有效期列：状态是哪天查的、对照的是哪个版本的文档与源码，日期与版本一起写，过期复查的时候才知道从哪查起。

矩阵填完之后要做一次完整性检查，检查的方法是算术。Top 10 的耗时占比加起来是多少？沿用第 1 节的算例，Top 10 合计占 92.0%，剩下的长尾一共 8.0%。长尾里有多少个算子？假设清单上一共有 97 个算子，Top 10 之外还有 87 个，8.0% 除以 87，每个长尾算子平均占 0.092%。平均数这么小，意味着长尾里单个算子的档位几乎不影响端到端——就算长尾里有一半算子回退，账也大不到哪去。但平均数也会骗人：长尾的分布可能极不均匀，87 个算子里可能藏着一个占 3% 的算子与 86 个占 0.06% 的算子。完整性检查的第二步就是把长尾按占比再排一次，确认 Top 10 的切口没有正好切在两个占比相近的算子中间——第 10 名占 0.8%，第 11 名占 0.79%，切口切在哪，矩阵的覆盖就差多少。Top 10 是工作量的切口，不是物理上的分界线，切口附近的算子值得多看一眼。

还有两个误解值得在填表之前先拆掉。一个误解是“有实现就等于快”。原生实现与插件实现都只回答“有没有人接这个算子”，不回答“接得快不快”。一个插件实现可能只覆盖了某几个形状，换个形状就悄悄回退；一个原生实现可能在小 batch 下走通用路径，性能与回退差不了多少。状态是覆盖问题，速度是性能问题，矩阵只解决前者，后者要等有卡实测。另一个误解反过来：“回退就等于不能用”。回退的模型能跑、结果正确，只是慢。原型验证阶段，回退完全可以接受——先把流程跑通，再逐个消灭回退。把回退当成“不能跑”，会把一个能跑的方案误判成死路；把回退当成“没事”，会把一个慢三倍的方案误判成上线状态。矩阵的价值正在于把这两种误读都挡在外面：回退写在那里，占比写在那里，端到端的账也写在那里，结论自己会说话。

最后是这一节的证据纪律。对照依据只有两类：官方文档与插件源码。论坛帖子、聊天记录里的说法、二手转述，都不能作为状态的证据——它们可以当线索，顺着线索去文档与源码里找，找到才写进矩阵，找不到就写待核实。线索与证据的区别要分清：线索告诉你“去哪找”，证据告诉你“找到了什么”。矩阵里每一行的实现位置列，写的都应该是证据本身，而不是线索的出处。

**产出**：一份算子覆盖矩阵（Top 10 全覆盖，带核实日期），外加一句阅读方法：矩阵按“状态 × 耗时占比”的乘法读，占比大的回退行优先处理。

### 第 3 节 · 迁移 benchmark：读懂 TritonAscendBench 的设计

**目标**：理解迁移评测的设计——它测什么、怎么判分、没卡时能做什么。

**怎么做**（60 分钟，无硬件可做）：

一个 benchmark 的设计，读法是先问它测什么，再问它怎么判分，最后问它在什么条件下会撒谎。三个问题按这个顺序问，读出来的才是设计本身；只看分数不看设计，读出来的只是一张排行榜。TritonAscendBench 测的是生产级 Triton kernel 从 GPU 迁移到 Ascend 的可用性——“可用性”三个字是题眼：它测的是“一个在 GPU 上写好的 Triton kernel，搬到 Ascend 上之后还能不能用”。速度是可用性的一部分，不是全部；一个跑得快但结果不对的 kernel，可用性是零分。

先看规模：101 个任务，分 L1（36 个）、L2（35 个）、L3（30 个）三档难度。三个数先加起来验算：36 加 35 等于 71，再加 30 等于 101，与总数对得上。占比逐项算：L1 是 36 除以 101，约 35.6%；L2 是 35 除以 101，约 34.7%；L3 是 30 除以 101，约 29.7%。三档的占比加起来是 35.6 加 34.7 加 29.7 等于 100.0%，账是平的。L1 与 L2 加起来是 71 个任务，占 70.3%——七成的任务集中在中低两档，最高档只占不到三成。这个分布本身就是设计意图：迁移能力的底盘在中低档，L1 与 L2 测的是“常规迁移能不能成”，L3 测的是“难啃的迁移能不能成”。一个只在 L3 上丢分的 kernel，与一个在 L1 上就丢分的 kernel，问题完全不在一个层次上：前者是攻坚能力，后者是基本功。读分数的时候先按档拆开看，拆开之前不要谈总分。

再看它的工作流。入口命令是 `tab init-solution`，作用是生成解法骨架——一个空的、结构已经摆好的解法，写 kernel 的人往里面填。骨架的意义在于格式统一：所有人的解法长一个样子，评测才能批量跑，分数才能互相比较。骨架生成之后是 `tab run`，跑单次评测；`tab run-suite` 是批量跑，把一整套任务一次跑完；最后是 `tab package` 与 `tab validate-submission`，打包与校验提交——打包是把解法收成可提交的形态，校验是检查提交的格式与完整性，格式不对的提交在判分之前就被拦下来。五个命令连起来是一条流水线：生成骨架、单跑验证、批量验证、打包、校验提交。每一步都有明确的产物，下一步的输入就是上一步的产物，流水线的好处是每一步都能独立重跑——批量跑挂了，回单跑定位；校验不过，回打包检查。工作流的命令要按这个顺序理解，不要只背五个名字。

解法的入口是 `npu_triton_impl(inputs) -> dict`，这个签名本身就是一道防作弊的设计。入口函数接收输入、返回一个字典，评测拿返回的字典与 PyTorch 的参考输出对照。关键约束写在源文件里：必须是一个真正的 Triton kernel，不能是 PyTorch 的取巧实现。为什么要立这条规矩？因为评测测的是“迁移”，不是“在 Ascend 上把结果算出来”。用 PyTorch 的算子拼出正确结果，在 Ascend 上当然也能跑，但它绕过了迁移本身——Triton kernel 的写法、tiling、访存，全部没有被检验。允许取巧的评测，测出来的分数与迁移能力无关，只与“会不会抄近路”有关。入口签名的存在，就是把近路堵死：评测只认 Triton kernel 写出来的结果，PyTorch 的捷径不在入口的验收范围里。这条约束不是对写法的挑剔，是对评测有效性的保护。

判分分两半：正确性与性能。正确性在 CPU 上对照 PyTorch oracle 判分，有容限分级——oracle 是 PyTorch 算出来的参考答案，判分是把 kernel 的输出与参考答案比，误差落在容限里算过，容限之外算不过，分级的意思是误差大小对应不同的档位，而不是一刀切的过与不过。正确性放在 CPU 上判，有两个好处：判分环境与被测硬件解耦，没有 NPU 也能判正确性；判分标准统一，所有人的 kernel 都对着同一个 oracle。在 CPU 上判正确性的另一面是：它判不了性能。性能需要在 910B 上实测——性能是硬件相关的量，离开目标芯片谈性能是没有意义的。正确性与性能分开判，是这个 benchmark 最诚实的一处设计：它不把“在 CPU 上算对了”等同于“在芯片上跑得快”，两个分数各有各的场地。

`tab run` 默认 `--backend npu`，`--backend gpu` 是 CUDA 自查。默认值的选择也有讲究：默认跑 NPU，说明这个 benchmark 的主场就是迁移之后的那一端；GPU 后端是自查用的——先确认 kernel 在 GPU 上是对的，再谈迁移。自查的顺序不能反：一个在 GPU 上就是错的 kernel，搬到 Ascend 上再错一次，排错的时候分不清是迁移引入的问题，还是 kernel 本来就有的问题。先在 GPU 上把正确性钉死，迁移之后如果错了，错的一定是迁移那一步引入的。这个顺序是排错的基本功：每次只动一个变量，动完立刻验证。没有 NPU 的时候，自查就是能做到的最远一步——GPU 上跑通，正确性在 CPU oracle 下通过，NPU 那一步标上标记，等有卡再补。

没有 NPU 时结果会标 `npu_antihack_unverified`，这个标记值得多看两眼。它的意思是：NPU 一侧的结果没有经过验证。标记的存在说明设计者想过一种作弊：没有 NPU 却声称 NPU 上跑通了。防作弊的办法是把无卡运行的结果打上标记——标记本身就是诚实设计的一部分。一个 benchmark 诚不诚实，不取决于它有没有防作弊的墙，取决于它怎么处理“验证不了”的情况：静默地把 GPU 结果当成 NPU 结果，是撒谎；明确地标上未验证，是诚实。读到这个标记的时候，不要把它当成失败，它只是在说“这一步还没做”，与“这一步做错了”是两回事。第 5 周动手的时候，这个标记还会再出现，到时候就知道它不是障碍，是路标。

看它的 worked example：`USAGE.md` 里的 `L2_04_silu_and_mul`——一个完整的 silu_and_mul Triton kernel。这个例子选得有深意：silu_and_mul 是 M2 第 6 周写过的同一个算子，第 5 周会移植它。例子在这里出现，本周的任务就是先读懂它：kernel 本身怎么写，评测怎么跑，判分怎么判。读懂的检验标准是：不看文档，能不能说出这个 kernel 的输入输出是什么、评测拿什么跟它比、哪一步需要 NPU、哪一步在 GPU 上就能完成。读懂之后，第 5 周直接用它练手——本周是读，第 5 周是做，读与做之间隔着一周，隔这一周的原因是：读懂一个完整的例子，比囫囵吞枣地读十个例子更有用。例子里的算子不是随便挑的：silu_and_mul 在第 2 节的矩阵里是插件实现的那一行，在 M2 第 6 周是手写过的 kernel，在第 5 周是移植的对象——同一个算子在三周里以三种身份出现，读懂它就等于把三周串在了一起。

注意版本：它的 NPU 环境参考配置在 `docker/Dockerfile.npu` 里（CANN 8.5.0、torch_npu 2.8.0.post1、triton_ascend 3.2.0）——与第 2 周的 vllm-ascend 锚点（CANN 9.2.1）并不属于同一套版本。不同工具钉不同版本是常态，记录时写清“这一步用的是哪套版本”，不要混在一起。版本这件事上最容易犯的错是“统一强迫症”：看到两个工具的 CANN 版本不一样，就想把它们统一到同一个版本。统一本身没有错，错的是不加验证地统一——TritonAscendBench 的评测结果是在 CANN 8.5.0 下测的，换到 9.2.1 下重测，分数可能变，也可能不变，没测过就不知道。记录的纪律是：每一步写清版本，复现的时候按记录里的版本复现，升级版本是另一项独立的工作，要单独排期、单独验证。版本不是装饰，是实验条件的一部分。

分数的读法也可以先练一组算例，免得第 5 周拿到真实分数时不会读。假设某次批量跑的结果是 L1 通过 30 个、L2 通过 28 个、L3 通过 12 个，逐项算通过率：L1 是 30 除以 36，约 83.3%；L2 是 28 除以 35，等于 80.0%；L3 是 12 除以 30，等于 40.0%。总通过是 30 加 28 加 12 等于 70 个，占 101 个任务的约 69.3%。这组数是读法算例，不是实测，它演示的是拆开读与合起来读的区别：总分 69.3% 看起来平平，拆开看是 L1 与 L2 都在八成上下、L3 只有四成——瓶颈在高难度档，不在基本功。反过来，如果 L1 只有四成、L3 也有四成，总分一样，结论完全不同：基本功就有问题，高难度的分数没有参考价值。同一张总分，拆开之后是两个故事，读 benchmark 的分数要先拆档，再谈总分。

一个常见的误解：“benchmark 的分数就是芯片的速度”。TritonAscendBench 的分数首先是迁移可用性的分数：kernel 能不能搬过去、搬过去对不对，速度是第二步才问的事。一个在 L1 全过、L3 全挂的解法，说明常规迁移没问题，难迁移还没过关；一个正确性全过、性能全挂的解法，说明东西能跑，但是慢。分数要按“正确性先行、性能随后”的顺序读，顺序一反，就会把“能跑但慢”误读成“芯片不行”，或者把“跑得快但不对”误读成“迁移成功”。第 5 周移植的时候，这个顺序还会再用一次：先求对，再求快。

没卡时能做到哪一步，现在可以收拢了：读懂工作流与判分规则，读懂 `L2_04_silu_and_mul` 这个例子，在 GPU 上把 kernel 的正确性自查通过，NPU 一侧的步骤标注 `npu_antihack_unverified`、等有卡再补。能做的部分与不能做的部分分得越清，待补测的清单就越干净——清单上每一项都知道自己在等什么，而不是笼统地写一句“没卡做不了”。

**产出**：一页笔记：TritonAscendBench 测什么、怎么判分、没卡时能做到哪一步。笔记里写清三档任务数（L1 36、L2 35、L3 30，共 101）、工作流命令、判分场地（正确性在 CPU 上对 oracle，性能在 910B 上实测）、版本锚点（CANN 8.5.0、torch_npu 2.8.0.post1、triton_ascend 3.2.0）与无卡标记（`npu_antihack_unverified`）。原始仓库：[TritonAscendBench](https://github.com/Gxj230958/TritonAscendBench)。

### 第 4 节 · 动手：对清单里最耗时的 3 个算子，查它们的芯片侧实现状态

**目标**：出一份“Top 3 算子覆盖分析”。

**怎么做**（60 分钟，无硬件可做；查不到的写“待核实”，不猜）：

第 2 节的矩阵是 Top 10 的全景，这一节是 Top 3 的特写。全景回答“整体覆盖怎么样”，特写回答“最贵的三个算子到底由谁承接”。特写的必要性在第 1 节的算例里已经算出来了：Top 3 合计 34.5 毫秒，占总时间 50.0 毫秒的 69.0%——近七成的时间花在三个算子身上。这三个算子的状态，基本上就决定了整张矩阵的结论；反过来，Top 10 里排在后七位的算子加起来才占 23.0%，它们的状态再差，端到端的账也有限。资源有限的时候，特写优先于全景的细化：先把最贵的三行查实，再回头补后七行。

动手的方法是第 3 周第 3 节的方法，对每个算子做三件事：在 vllm-ascend 的 `ops/`、`attention/`、`_cann_ops_custom/` 里找它的实现，在 CANN 文档里找它有没有原生实现，然后在覆盖矩阵里更新它的状态与实现位置。三件事的顺序也有讲究：先找插件，再找原生，最后更新矩阵。先找插件的原因是插件的位置最具体——文件路径就在那里，有就是有，没有就是没有，查起来最快。原生实现查的是文档，文档的说法可能滞后于代码，也可能把几个算子合在一起讲，查起来要慢一些。更新矩阵放在最后，是因为状态要等两边的证据都齐了再定：插件里找到了，就不用再纠结文档里有没有；插件里没找到、文档里找到了，状态就是原生实现；两边都没找到，写待核实。顺序反过来，先查文档再查插件，结论是一样的，时间花得更多——先查便宜的证据，再查贵的证据。

三个目录的分工要先分清，找的时候才不会走错地方。`ops/` 里是 vllm-ascend 的定制算子，`_cann_ops_custom/` 里也是定制算子一侧的实现，两个地方都是“插件实现”这个档位的证据来源。`attention/` 目录单独拎出来，是因为 attention 在 vLLM 里走后端（backend），不是 CustomOp——第 3 周第 3 节已经讲过这个边界，这里再确认一次。边界的意思是：attention 相关算子的实现不要到 CustomOp 的位置去找，找了也没有；要到 attention 后端里去找。找错地方的后果是“找错了地方之后误判为没有实现”——没找到与不存在之间，差的就是一个正确的查找位置。Top 3 里如果有 attention 相关算子，第一步就是确认它的后端路径，而不是把它当成普通算子去 `ops/` 里翻。

每个算子查完之后，写一句话结论，格式是固定的：“这个算子在 Ascend 上由某某实现承接（文件路径），预计不是瓶颈 / 可能是瓶颈 / 待核实”。一句话里有三个要素，缺一个都不完整：承接方是谁，证据在哪，结论是什么。承接方写实现的名字与位置，证据就是那个文件路径或者文档链接，结论只取三个档位里的一档。一句话结论的价值在于可复核：别人拿着这句话，顺着文件路径能找到同一个实现，顺着占比能算出同一个判断，复核通过，结论才成立。写两句话的结论、写一段话的结论，都不如一句话——多出来的话往往是修饰，修饰里最容易藏进没验证的判断。

三个档位的结论，各自需要什么证据，要先说清楚。预计不是瓶颈，需要两条证据同时成立：实现存在（原生或者插件），而且耗时占比不大，或者实现本身经过验证、性能有保障。只满足一条，结论下不了：实现存在但占比 42%，回退倍数哪怕只有 2 倍，端到端的账也是 1.42 倍（第 2 节算过），这种行不能叫“不是瓶颈”；占比很小但实现状态是待核实，结论只能写“还没查到”——“不是瓶颈”这四个字，证据不足时写不得。可能是瓶颈，同样需要两条证据：回退状态属实，而且耗时占比够大——第 2 节的乘法在这里再用一次，占比与回退倍数两个数都有了，才轮到说“可能是瓶颈”。待核实最简单：任何一条证据缺失，结论就是待核实。待核实不是结论的降级，是证据不足时的唯一诚实选项。

拿第 1 节的算例把 Top 3 的账算一遍，算完就知道特写要盯着谁。Top 3 是 21.0、9.0、4.5 毫秒，合计 34.5 毫秒，占 69.0%。假设排第三的算子占 4.5 毫秒、也就是 9.0%，它的状态是回退、回退后慢 5 倍，端到端的账是这样算的：总时间 50.0 毫秒里，4.5 毫秒变成 22.5 毫秒，其余 45.5 毫秒不变，总时间变成 45.5 加 22.5 等于 68.0 毫秒，是原来的 1.36 倍。一个只排第三的算子，回退 5 倍，端到端慢 36%——排第三尚且如此，排第一的更不用算：占 21.0 毫秒、也就是 42.0% 的算子，回退后只慢 2 倍，总时间是 29.0 加 42.0 等于 71.0 毫秒，是原来的 1.42 倍。两组算例都是算例，不是实测，它们的任务是把 Top 3 特写的优先级算清楚：特写不是因为“前三名”这个名次好听，是因为前三名的占比乘上回退倍数之后，端到端的账最大。查 Top 3 的状态，就是在查端到端时间里最大头的那几笔账由谁来付。

特写里还有一个容易踩的坑：把“清单上的名字”等同于“芯片侧的名字”。第 1 节讲过，profiler 导出的是 PyTorch 算子名，芯片侧的承接要落到“这个 PyTorch 算子由哪个实现承接”。`aten::mm` 在清单上是一行，在芯片侧可能对应多个实现：不同形状走不同 kernel，不同 dtype 走不同路径。查的时候要带着形状去查——清单上的 `aten::mm` 是在哪个形状下被调的，芯片侧的实现支不支持那个形状。形状不带的对照，等于默认“所有形状都有实现”，这个默认是没有证据的。矩阵里的实现位置列，写文件路径的时候最好把形状条件也带上一句，条件写不出来的，状态的置信度就要打折扣。

SiluAndMul 这个算子值得在特写里单独提一句，因为它在三周里出现了三次。第 2 节的矩阵里，它是插件实现的那一行；M2 第 6 周手写过同一个算子的 Triton kernel；第 3 节的 worked example `L2_04_silu_and_mul` 也是它；第 5 周要移植它。如果 Top 3 里有它，特写的工作量会小很多——M2 第 6 周的 kernel 还在，第 3 节的例子也读过了，查它的芯片侧状态有现成的线索可循。如果 Top 3 里没有它，也不用失望：特写的方法是通用的，换一个算子，三个目录、两边证据、一句话结论的流程不变。特写练的是方法，不是某一个算子的答案。

特写查完之后，要回头与第 2 节的矩阵对一次账：特写里写的状态，与矩阵里同一行的状态是不是一致。不一致的时候，以证据更新的那一边为准，矩阵里那一行的状态与核实日期一起改掉，改的理由写在行边上。矩阵不是写完就 frozen 的文档，特写就是一次针对 Top 3 行的复查，复查出不一致是正常的，藏起来才不正常。对账还有第二层意思：Top 3 的三行查实之后，矩阵里剩下七行的置信度也要重新评估——如果三行里有两行是待核实，矩阵整体的结论就要跟着降级，第 5 节归因的时候不能假装矩阵是完整的。

最后是这一节的产出纪律：每个算子只写查到的东西。实现位置写的是文件路径或者文档链接，路径写不出来就写待核实；一句话结论写的是三个档位里的一个，证据不足就写待核实。特写只有三个算子，三个算子的篇幅都很短，短有短的好处：短到每一句话都能被复核，长到藏不进一句没验证的判断。三个算子查完，矩阵里的 Top 3 行就从“填了状态”升级成“有证据的状态”，第 5 节的归因才有东西可贴。

**产出**：一份“Top 3 算子覆盖分析”（每个算子：实现位置 + 一句话结论），结论只取三档——预计不是瓶颈 / 可能是瓶颈 / 待核实；查不到实现位置的算子，结论只能是待核实。

### 第 5 节 · 小结：覆盖矩阵的结论——瓶颈在算子覆盖，还是在调度/显存

**目标**：写出一页结论，用 Four Walls 归因。

**怎么做**（60 分钟，总结无卡可做）：

回到第 1 周的 Four Walls：生态、显存、通信、精度。把覆盖矩阵的结论往四面墙上贴——瓶颈在生态墙（算子没实现、要回退）？还是显存墙（算子有实现，但显存带宽跟不上）？还是精度墙（量化实现有差异）？通信墙（多卡）本周不涉及，先空着。

贴墙的方法是按证据贴，不按感觉贴。生态墙的证据是矩阵里的回退行：某个占 20% 时间的算子回退了，端到端的账是 2.80 倍（第 2 节算过），这就是生态墙的证据——算子没实现，时间花在回退上。显存墙的证据是另一类：算子有实现，但搬运量大、带宽跟不上。本周没有实测带宽数据，显存墙贴不上去，就空着，不硬贴。精度墙同样如此：本周没有量化的实测误差，精度墙也没有证据，先不下结论。通信墙本周不涉及，空着是计划内的空着，不是遗漏。

一页结论的格式是固定的：“本次分析的瓶颈主要在 X 墙，依据是覆盖矩阵里的某几行（算子名 + 耗时占比 + 状态）；Y 墙没有证据，先不下结论”。格式里有两句话，第一句下结论，第二句划边界。只写第一句不写第二句的结论，是不完整的结论——它没说自己没查什么，读的人会以为四面墙都查过了。Y 墙那一句的价值就在于此：它把“没证据”写出来，免得结论被读成比实际更确定的样子。依据那几行要写全三要素：算子名、耗时占比、状态。三要素缺一个，依据就站不住：只有算子名没有占比，不知道它有多贵；只有占比没有状态，不知道它为什么慢；只有状态没有占比，不知道它值不值得治。

还有一句要写在结论的边上：本周的结论是覆盖层面的结论，不是性能层面的结论。矩阵回答的是“有没有实现”，没有回答“实现得快不快”。一个原生实现的算子，在某个形状下可能仍然很慢，慢的原因要等有卡实测才能定位——可能是 tile 配置，可能是访存，也可能是别的原因。本周的归因贴到生态墙上，意思是“覆盖是目前能看到的瓶颈”，不是“性能问题已经排除了”。两句话的结论，边界要划清。

把本周的检查清单并进总清单，加两条：“覆盖矩阵的 Top 10 全了吗”“每个状态都有核实日期或‘待核实’标记吗”。第一条查的是完整性：Top 10 有没有漏行，漏掉的那一行是不是正好在切口附近。第二条查的是诚实性：每一行状态的背后，是一个日期或者一个待核实标记，没有第三种情况。两条都过，本周才算收拢。

**产出**：一页结论（瓶颈归因 + 依据），格式是“瓶颈主要在 X 墙，依据是某几行；Y 墙没有证据，先不下结论”。

### 第 1 节 · 示例：把一个小推理引擎移植到 Ascend

**目标**：读懂把一个小推理引擎搬到 Ascend 上要改的四个地方，并说清每一处改的是哪一层。

**怎么做**（60 分钟，无硬件可做）：

先把体量说清楚，因为体量决定了这一节的读法。打开 [nano-vllm-ascend](https://github.com/linzm1007/nano-vllm-ascend)（教学用 nano-vllm 移植到 Ascend 的 demo，中文 README），它的 README 自己报了行数：整个仓库一共 4652 行，模型目录占 2224 行，除模型外的核心代码约 2428 行。验算一下：4652 减 2428 等于 2224，对得上；2224 除以 4652 约等于 47.8%，2428 除以 4652 约等于 52.2%，两边加起来正好是 100%。这组数的意义在于，教学示例 之所以能当教材，首先是因为它小：要读懂核心流程，只需要读 2428 行。vLLM 的代码库是几十万行量级，新手读它只能在目录里迷路；读 2428 行能画出整条推理链路——体量本身就是教学设计的一部分。读这个仓库的时候，先有这个体量感：你面对的是一份把推理流程摊开给你看的讲义。

再数支持的模型，一共是 8 条：Qwen3-0.6B 与 Qwen3-32B 算 2 条，Qwen2-0.5B 与 Qwen2.5-0.5B 算 2 条，Llama-3.2-1B 算 1 条，Qwen3-30B-A3B MoE 算 1 条，Qwen3-VL 算 1 条，MiniCPM4-0.5B 算 1 条，2 加 2 加 1 加 1 加 1 加 1 等于 8。8 这个数值得停一下：它覆盖了稠密模型、MoE 模型（混合专家模型，推理时只激活部分专家）和多模态模型，说明 示例 的野心在“把几类模型结构都走一遍”，不只在“跑通一个模型”。但也要注意这 8 条里没有长上下文、没有超大模型：教学示例 的模型清单是按“讲得清”挑的，覆盖全不在挑选标准里。读支持列表的时候，顺手问一句“它没支持什么”，比只看“它支持什么”更能看清定位。

移植的改动点可以收进四类，每一类对应栈里的一层。先看框架适配：原版 nano-vllm 是 GPU 推理项目，代码里默认的是 CUDA 调用；搬到 Ascend 上，这些调用要换成 `torch_npu` 的对应接口。最具体的一处是 PageAttention 的 KV Cache（键值缓存，推理时存下来的 K、V，供后续 token 复用）写回：NPU 版调的是 `torch_npu` 提供的 reshape 与缓存接口，把 K、V 写进分页的缓存块里。框架适配改的是“这行代码在跟谁说话”，算法本身没变：原来跟 CUDA 运行时说话，现在跟 CANN 运行时说话。读的时候可以对照第 1 周的五层分层图：框架适配层坏了，症状是引擎根本启动不了或者算子找不到实现，定位的时候先查框架适配层。

再看图编译：这个 示例 带 torchair 图编译。torchair 是 Ascend 上的图编译接口，做法是把一次前向的计算图抓下来，编译成一个可以反复执行的单元，后面每次推理直接重放这张图，不再逐个下发 kernel。为什么推理引擎需要图编译？一次解码前向里有几十个小算子，每个算子单独下发都要经过框架到驱动的一次往返；图编译把这几十次往返收成一次，省的是启动开销，计算本身的量没变。打个比方：逐个下发像每道菜都单独跑一趟厨房点单，图编译像提前把整桌菜的单子一次交过去。图编译的代价是灵活性：图一旦编好，形状变了就得重编——这就是为什么 示例 里 MoE 模型和 VL 模型有“暂时不支持入图”的标注。读到这种标注别跳过：它标出来的正是图编译的边界，形状多变的模型进图要付出额外成本。

然后是注意力后端，这是 示例 里最值得细读的一处，因为它把“同一种计算，三种写法”并排放在了你面前：FlashAttention 库版、NPU 原生版、PyTorch 原生版。README 里的对比表给了两个维度的星级：性能上，库版和 NPU 原生版都是五星，PyTorch 原生版只有两星；可读性上反过来，PyTorch 原生版五星，库版只有两星。两个维度一交叉，取舍就清楚了：跑得快的难读，好读的跑得慢。示例的选择建议也按场景分：生产环境 GPU 用库版，生产环境 NPU 用 NPU 原生版，学习调试用 PyTorch 原生版。读这一节的目标是理解为什么一个引擎要同时留三种实现：attention 是推理里最热的算子，生产要性能、教学要可读，一个实现同时满足不了两头，只好各留一个。移植的时候，attention 是一次“在新芯片上重新选后端”的决定，三个选项的取舍在新芯片上要重新算一遍。

PageAttention 本身也值得用一组数走一遍，因为它是 示例 里唯一自带手算例子的优化。假设序列长度是 1000，最大支持长度是 4096，传统做法按最大长度预分配，浪费是（4096 减 1000）除以 4096，约等于 75.6%。PageAttention 按 block（块）分配，block 大小取 16，1000 除以 16 等于 62.5，向上取整是 63 块，实际分配 63 乘 16 等于 1008 个 token 位置，浪费是（1008 减 1000）除以 1008，约等于 0.8%。75.6% 对 0.8%，省下来的是显存碎片，算力一分没省：原来每条序列都要为“可能长到 4096”预留位置，现在只为“实际长到 1000”多留 8 个位置。这组数也说明了 PageAttention 的定位：它不加速任何一次矩阵乘，它让同样大小的显存能装下更多条并发序列。读 示例 的 PageAttention 实现时，盯住 block 表（block table，逻辑位置到物理块的映射）这个结构：分页思想的核心就是这张表，有了它，同一条序列的 KV Cache 才可以分散在不连续的块里。

最后看自定义算子：示例里给了一个 rms_norm（均方根归一化）算子示例，并且列了三种自定义算子的写法——PyTorch C++ 扩展、AscendC 自定义算子、`torch_npu` 内置算子。三种写法对应三条路：通用扩展、芯片原生、厂商内置。rms_norm 之所以被选作示例，是因为它足够小（一个归一化算子，输入进来、输出出去，没有跨层状态），又足够真（它是每个 Transformer 层里都有的算子）。读它的目标是看清“注册与调用”这个最小闭环：算子在哪定义、在哪注册、模型前向里在哪被调到。对照 M2 第 6 周的 CustomOp：那一周讲的是算子级替换，一个 SiluAndMul 换成你的 Triton 版；这里的自定义算子是同一类问题在 NPU 侧的版本——定义、编译、调用三段，第 2 周第 4 节画过这张链路图，现在可以在 示例 里看到一个活的例子。

定位要再说一遍，因为这一节最容易读偏：它的定位是教学示例，不是生产引擎。“不是生产引擎”具体指什么？它的 bench 数据自己都写着“仅供参考”，它的模型清单只覆盖 8 条，它的 MoE 与 VL 模型明确标了不支持入图——这些标注恰恰是教学示例 的诚实之处。读它的目标止于“看清移植要改哪些地方”。如果读完之后你能把改动点按框架适配、图编译、注意力后端、自定义算子四类列出来，每类说出改的是哪一层、为什么要改，这一节就算读完了；如果读完只记得它支持哪些模型，那这一节就没有达到目的。

还有一个对照值得在收尾时点出来：第 3 周的 vllm-ascend 是平台级插件，把整套 Ascend 适配接进 vLLM 这个大引擎；nano-vllm-ascend 是手写的小引擎，移植是直接改引擎代码。两条路的改动点清单是同一套——框架适配、图编译、注意力后端、自定义算子，一个都不少——差别只在落点：大引擎里这些改动落在插件目录（`ops/`、`attention/`、`_cann_ops_custom/`），小引擎里直接落在引擎代码里。先读小引擎再看大引擎，等于先看一张小地图再看一张大地图，大地图上的目录名就不再是陌生的符号。

**产出**：一份移植关键改动点清单（框架适配 / 图编译 / 注意力后端 / 自定义算子）。

### 第 2 节 · Triton kernel 迁移：从 GPU 到 Ascend 要改什么

**目标**：讲清迁移的方法论——跑通“自查 → 迁移 → 记录”的循环。

**怎么做**（60 分钟，无硬件可做）：

方法论的第一句话是：迁移首先是一套循环动作。自查、迁移、记录三步跑完一圈，下一圈再跑——每一圈只解决一圈里发现的问题。这个循环之所以必要，是因为移植的不兼容点没法靠“想”想全：两种硬件的差异藏在编译器、驱动、算子库的细节里，读文档只能划出可能出问题的范围，具体哪一行会报错，只有跑起来才知道。循环的价值就在这里：它把“不知道”变成了一个可以执行的动作——跑一次，记一次，再跑一次。没有循环的移植只有两种结局：要么在改之前把所有可能的问题都列出来，结果列出一份永远对不上的清单；要么改完一堆再测，测出问题不知道是哪一处改动惹的。循环把这两个坑都绕开了。

循环的第一步是定工具链，而定工具链的第一件事是写清版本号。Ascend 上的 Triton 是 triton-ascend，TritonAscendBench 的 NPU 环境参考配置写在 `docker/Dockerfile.npu` 里：CANN 8.5.0、torch_npu 2.8.0.post1、triton_ascend 3.2.0。这里有一个容易踩的坑：第 2 周的 vllm-ascend 锚点是另一套版本，vllm-ascend v0.30.0（2026 年 10 月）要求 Python 3.12、CANN 9.2.1、PyTorch 2.10.0、TorchNPU 2.10.0.post7。两套版本里的 CANN，一个是 9.2.1，一个是 8.5.0，主版本号 9 减 8 等于 1，相差一个大版本；每套各有三个核心版本号，合起来是六个数字，混在一起就分不清哪一步用的是哪一套。不同工具钉不同版本是常态，第 2 周已经讲过这个道理：CANN 8.5 这个旧写法过期，就是因为版本锚点没有跟上 vllm-ascend 的更新。记录时写清“这一步用的是哪套版本”，这条要求有它的来由——版本号写混了，复现的时候第一步就会卡住，而且卡住的原因看起来和代码完全无关。

循环跑在什么东西上面？跑在 TritonAscendBench 这套评测上。第 4 周第 3 节读过它的设计：它测的是生产级 Triton kernel 从 GPU 迁移到 Ascend 的可用性，一共 101 个任务，分三档难度，L1 是 36 个，L2 是 35 个，L3 是 30 个。验算一下：36 加 35 加 30 等于 101，对得上。再算占比：L1 是 36 除以 101，约等于 35.6%；L2 是 35 除以 101，约等于 34.7%；L3 是 30 除以 101，约等于 29.7%；三档加起来是 100%。三档的数量接近均分，说明这套评测按难度梯度铺开。第 4 节要移植的 `L2_04_silu_and_mul` 是 35 个 L2 任务里的一个，落在中间那档——难度适中，正好适合当作第一次完整走循环的练手对象。选它当案例有理由：太简单的任务走不出循环的完整链路，太难的任务第一圈就会卡在定位上。

评测的工作流是四步：`tab init-solution` 生成解法骨架，`tab run` 跑评测，`tab run-suite` 批量跑，`tab package` 与 `tab validate-submission` 打包与校验提交。解法的入口是 `npu_triton_impl(inputs) -> dict`，它必须是一个真正的 Triton kernel，PyTorch 的取巧实现进不了判分——这条要求是评测的诚实设计：它测的是 kernel 迁移。判分分两条线：正确性在 CPU 上对照 PyTorch oracle 判分，有容限分级；性能需要在 910B 上实测。`tab run` 默认是 `--backend npu`，`--backend gpu` 是 CUDA 自查：先确认 kernel 在 GPU 上是对的，再谈迁移。没有 NPU 的时候，结果会标 `npu_antihack_unverified`——这个标记要原样写进记录，不要把它当成“通过”。

循环的第一步 GPU 自查，值得单独讲透，因为它是最容易被跳过的一步。GPU 自查跑的是 `tab run --backend gpu`，意思是在 CUDA 上先把 kernel 跑对。为什么顺序不能反过来？因为 GPU 自查是迁移的基线：GPU 上不对的东西，搬到 NPU 上也不会对。如果跳过自查直接上 NPU，跑出来的报错里混着两类问题——一类是 kernel 本身写错了，另一类是迁移引入的，两类问题长得一模一样，分不出来。自查的作用就是把第一类问题先清零，让 NPU 上出现的问题只剩第二类。基线的逻辑和 M2 第 6 周的 CustomOp 验证是同一条：先在 standalone 验证 kernel 本身，再谈接入；先在 CPU 上验注册，再进 vLLM 进程验分发。每一层验证只解决一层的问题，层与层之间不互相背锅。

循环的第二步是 NPU 实测，第三步是逐条记录，两步要合在一起理解。实测的时候，每遇到一个不兼容点，就按表头记一行：一共四列，现象（报错原文）、定位（kernel 里的哪一行、哪个 API）、改法、重测结果。四列缺一不可：现象不写报错原文，事后复现的时候就对不上号；定位不写到行与 API，改法就无从谈起；改法不写，重测结果就失去了对照；重测结果不写，这一行就只记下了“遇到过的问题”。还有一条操作上的纪律：改完一个测一个，不要攒一堆改动再测。攒一堆改动的代价是失败归因不清：测出来不对，你不知道是五个改动里的哪一个惹的祸，只能一个一个往回拆——拆的工夫比逐个测的工夫多得多。这条纪律和 M2 第 5 周“一次只改一个参数”是同一条规矩，只是从 CUTLASS 的 tile 配置搬到了移植的不兼容点上。

循环里最重要的一句话，是关于“不猜”的。移植案例的价值不是背下来的清单，是真实跑出来的记录。背下来的清单看起来全，实际上每一行都没有验证过：你不知道它在当前版本上还成立不成立，也不知道它对应的报错长什么样。真实跑出来的记录看起来短，每一行都带着报错原文、定位、改法与重测结果，下一位读者可以按图索骥复现。两者的差别不在行数多少，在有没有证据。第 1 周定下的制度在这里同样适用：没有核实日期的事实陈述视为未知；移植记录里没有实测到的不兼容点，就不要写进去。空着的格子是诚实，填满的猜测是误导。

循环开始之前，还有一个预习动作：第 4 周第 3 节的 worked example，也就是 `L2_04_silu_and_mul` 的参考 kernel。二维 grid、mask、fp32 里算 SiLU 再 cast 回输入精度——这四个特征要先认出来。M2 第 6 周写过同一个算子，第 4 节要移植的就是它：先把两个版本并排看一遍，确认语义一致，再开始动手。并排对照要对什么？对输入输出的形状（输入是 `[M, 2D]`，输出是 `[M, D]`），对 SiLU 的计算位置（fp32 里算），对 cast 的顺序（先 cast 回输入精度再乘）。语义对不上，移植的基线就是错的；语义对上了，GPU 自查才有意义。

**产出**：一份迁移流程说明（GPU 自查 → NPU 实测 → 逐条记录）+ 不兼容点记录表的表头。

### 第 3 节 · 统一算子库：FlagGems 如何让一份 kernel 跑多家芯片

**目标**：讲清统一算子层的机制——写一次，到处跑，是怎么做到的。

**怎么做**（60 分钟，无硬件可做）：

先回到第 1 周第 4 节的结论：FlagGems 是统一算子库，FlagCX 是统一通信库，vllm-plugin-FL 是把它们接进 vLLM 的插件。分发优先级是一条三级链：先找 FlagGems 的统一实现，没有再找厂商实现，再没有回退到 PyTorch 参考实现，自动 fallback。平台自动检测：启动时识别当前芯片，选对应的后端。支持的平台一共是 12 个：NVIDIA、Ascend、T-Head、Iluvatar、MetaX、摩尔线程、Tsingmicro、海光、燧原、昆仑芯、阿里巴巴 PPU、CPU ARM64。12 这个数是理解统一层价值的起点：12 家芯片，每家一个软件栈，每家一套算子实现——没有统一层，一份 kernel 要写 12 遍；有了统一层，一份 kernel 写 1 遍，剩下的 11 遍由生成与分发去解决。人力账可以这样算：手写路线里，一个算子乘以 12 家芯片等于 12 份手写移植；统一路线里，一个算子是 1 份统一描述，加上按芯片生成的 12 份实现。两边的 12 看起来一样，性质完全不同：手写的 12 份是 12 份要人维护的代码，生成的 12 份是编译器按同一份描述产出的结果，改描述一处，12 份跟着变。这组数是算例，说明的只有一件事：统一层省的是“每多一家芯片就要多写一份代码”这笔人力账。

再看 [FlagTree](https://github.com/flagos-ai/FlagTree)：它是 FlagGems 背后的算子开发框架。按它 README 的自我介绍，FlagTree 是一个面向多家 AI 芯片的统一编译器，fork 自 triton-lang/triton，目标是“develop once, run anywhere”，也就是一份代码到处跑。读它的 README，要回答三个问题。先看统一描述长什么样：算子用一套抽象写出来，这套抽象就是 Triton 本身——算子逻辑只写一次，写的是“算什么”；具体到某块芯片上怎么算，交给编译器按后端生成。再往深一层，FlagTree 还给了 TLE（Triton Language Extensions）这套分层扩展，分 Lite、Struct、Raw 三档，从可移植的用法逐级走向面向硬件的精细控制：Lite 档写可移植的算子，Raw 档可以直接表达硬件相关的原语。分层的意义在于，统一描述并不意味着只能写最通用的版本：先写通用的版本，热点处再加特化——统一与特化之间留了一条渐进的路。

再看生成发生在什么时候：编译时。FlagTree 的 README 里，多后端支持是一张分支表：每个后端基于不同版本的 Triton，放在不同的受保护分支里，安装时按后端名选分支、设 `FLAGTREE_BACKEND` 再编译。统一实现针对不同芯片的生成，发生在编译期——选定目标后端，编译器把同一份 Triton 代码 lowering 到该芯片的指令与内存模型上；运行时跑的是已经编译好的实现，不再现场生成。这一点要和 FlagGems 的分发区分开：生成是编译期的事，分发是运行期的事。生成解决的是“一份代码怎么变成多份实现”，分发解决的是“运行时用多份实现里的哪一份”。两个机制各管一段，不要混成一个。

最后看回退链：如果某块芯片上统一实现跑不起来，回退链是怎样的？答案在 FlagGems 的分发优先级里：先找 FlagGems 的统一实现，没有再找厂商实现，再没有回退到 PyTorch 参考实现，自动 fallback。回退链保证的是“能跑”，性能下限不在承诺里：走到 PyTorch 参考实现那一步，语义是对的，速度是参考实现的速度。理解回退链要抓住这个区分：统一层承诺的是覆盖面，性能下限不在承诺里。回退发生了，模型不会报错停下，只会悄悄变慢——这和 M2 第 6 周 CustomOp 的静默失败是同一个模式：后备实现在语义上是对的，只是慢一点，不报错、不警告，只有分发检查或 profiler 能发现它。

把分发链放在一次前向里走一遍，它就不再是抽象的优先级表。模型前向调到 SiluAndMul，插件先查 FlagGems 里有没有这个算子的统一实现，有就用统一实现；没有就去找厂商实现；再没有就回退到 PyTorch 参考实现，整个过程自动发生，模型代码一行不用改。链条上的每一级都在回答同一个问题：“这个算子在当前芯片上有没有更快的现成实现？”查到哪一级停在哪一级，查不到就往下走一级。自动 fallback 的好处是模型不会因为缺一个算子实现就停下，代价是变慢的那一级不会主动告诉你——它只负责让模型跑起来，不负责告诉你“刚才那一步走的是参考实现”。所以读分发链的时候，要同时看到它的另一面：覆盖面是自动的，性能感知不是自动的，想知道自己跑的是哪一级实现，还得靠 profiler 或者分发检查去确认。

再看 TLE 的三档分层，它把“统一与特化”从二选一变成了一条台阶。Lite 档只写可移植的逻辑，一份代码到处跑；跑起来之后发现某个算子在某块芯片上吃不满硬件，再往 Struct 档加结构信息；还要抠硬件原语才进 Raw 档。三档是渐进的，不是一次选定的：先拿 Lite 把覆盖面铺开，热点处再逐级加特化，性能一点一点追回来。这个台阶和 M2 第 5 周的判断标准是通的：瓶颈在覆盖面的时候，Lite 档够用；瓶颈落到单芯片的硬件细节上，才值得往 Raw 档走。台阶的意义在于，特化不用从一开始就全写好，也不用永远不写——写多少特化，取决于瓶颈落在哪一级。

对照第 2 节的移植：FlagGems 的路线是“写一次，生成多份”，第 4 节的路线是“手写一份，再逐条改”。两种路线的取舍与 M2 第 5 周“Triton vs CUTLASS”是同一个逻辑：统一实现省人力、牺牲特化性能；手写移植费人力、能榨干单芯片性能。取舍没有标准答案，只有场景答案：算子要覆盖 12 家芯片、维护人力有限，统一路线合算；算子落在关键路径上、单芯片的峰值性能就是目标，手写移植合算。还有一个中间态值得留意：TLE 的三档分层本身就是中间态——先写 Lite 档的可移植版本把覆盖面拿下来，热点算子再往 Struct、Raw 档加特化，把峰值性能一点一点追回来。中间态的思路和 M2 第 5 周的判断标准是通的：瓶颈在访存模式与融合时，Triton 够用；瓶颈在硬件细节时，回 CUDA 或者 CUTLASS；这里也一样，瓶颈在覆盖面时用统一实现，瓶颈在单芯片峰值时动手写特化。

版本锚点在这里又出现一次，而且是第三套。FlagTree 的 Ascend 分支钉在 Triton 3.5（README 的分支表里写着，2026 年 6 月 8 日升级到 Triton 3.5），而 TritonAscendBench 的 NPU 环境用的是 triton_ascend 3.2.0。3.5 与 3.2.0 各有各的出处：一个是 FlagTree 这个统一编译器的 Ascend 分支钉的 Triton 版本，另一个是 TritonAscendBench 的 NPU 环境参考配置里的 triton_ascend 版本。两套数字不能混用，混用了就会出现“按 3.5 的文档去配 3.2.0 的环境”这种错。写清“这一步用的是哪套版本”，在这一节里又多了一个例子。

还有一个诚实边界要留给这一节：统一层解决的是“一份 kernel 代码跑多家芯片”的问题，它没解决的是“每家芯片的峰值性能”。这句话第 1 周第 4 节已经讲过，这一节的任务是把它讲出机制：统一实现为了可移植会牺牲一部分特化优化，要榨干某块芯片的性能，最终还是要写它的原生算子——第 2 周的 AscendC、第 5 周的移植案例就是这条路。两条路不存在取代关系：统一层决定了移植的起点有多高，手写移植决定了单芯片的天花板有多高。读完这一节，下一节动手的时候，手里就有了两张图：一张是“手写移植要逐条改什么”，一张是“统一实现替你省了什么”。

**产出**：一页机制笔记（统一描述 → 按芯片生成 → 回退链）+ 两种移植路线的取舍。

### 第 4 节 · 动手：移植 M2 的 SiluAndMul 到 TritonAscendBench 的 L2_04

**目标**：出一份真实的移植记录（含失败的尝试）。

**怎么做**（60 分钟，需 NPU 环境或至少 GPU 自查；无卡时做 GPU 自查 + 移植计划，NPU 步骤标注“待有卡后补测”）：

先把要移植的东西说清楚，因为移植的第一步永远是确认语义。SiluAndMul 是 MLP（多层感知机，Transformer 里做逐 token 非线性变换的那部分）里的激活算子，语义在 M2 第 6 周已经定下来了：输入是 `[M, 2D]`，前一半过 SiLU，再乘以后一半，得到 `[M, D]`。SiLU 的定义是 `silu(x) = x · sigmoid(x)`，也就是 `x` 乘以它自己的 sigmoid。先拿几个数手算一遍，算是给后面的对照留一组基准：`silu(1)` 等于 1 除以（1 加 e 的负 1 次方），约等于 0.7311；`silu(2)` 约等于 1.7616；`silu(0)` 等于 0；`silu(-2)` 约等于负 0.2384。再配上第二半的乘法：0.7311 乘 3 等于 2.1932，1.7616 乘 0.5 等于 0.8808。这几个数是算例，不是实测——它们的用处是，GPU 自查对照 oracle 的时候，先拿这几个输入对一遍，手算和程序算对得上，说明对照链路本身没错；对不上，先查对照的写法，再查 kernel。

再算规模，因为规模决定了 kernel 的形状。取一组算例形状，M 等于 512，D 等于 1024：输入一共是 512 乘 2048 等于 1,048,576 个元素，按 fp16（半精度浮点，每个元素 2 字节）算是 2,097,152 字节，正好是 2 MiB；输出是 512 乘 1024 等于 524,288 个元素，1,048,576 字节，正好是 1 MiB。输入是输出的两倍，这个比例是语义自带的：输入里一半是待激活的数据，一半是待相乘的数据，输出只剩一半。grid 的账也可以顺手算了：BLOCK 取 1024 的时候，每行 D 等于 1024 只需要一个列块，grid 就是 512 乘 1 等于 512 个程序；换一组更大的算例形状，M 等于 4096，D 等于 4096，每行要 4096 除以 1024 等于 4 个列块，grid 就是 4096 乘 4 等于 16384 个程序。两组数放在一起，grid 的结构就清楚了：二维 grid 是行乘列块，行数跟着 M 走，列块数跟着 D 除以 BLOCK 走。

融合省了多少访存，是这个算子最值得算的一笔账，同样拿算例走一遍。取 M 等于 1024、D 等于 2048、fp16 的形状：输入是 1024 乘 4096 乘 2 字节，等于 8,388,608 字节，也就是 8 MiB；输出是 1024 乘 2048 乘 2 字节，等于 4,194,304 字节，也就是 4 MiB。融合的做法是读入 8 MiB、写出 4 MiB，一共 12 MiB。不融合的做法要多两步：先把 SiLU 的中间结果写回显存，再把它读回来做乘法，中间结果是 4 MiB，一写一读就是 8 MiB；加上读入 8 MiB 与写出 4 MiB，一共是 20 MiB。20 减 12 等于 8，8 除以 20 等于 40%——融合省掉了四成的访存量。这组数是算例，说明的只是融合的收益来自哪里：省掉的是中间结果在显存里的一次往返，计算本身的量没变。SiluAndMul 的计算量很小，访存才是它的成本大头，这正是 M2 第 6 周选它当融合载体的原因，也是第 4 周覆盖分析里它会出现在 Top 10 的原因。

kernel 的写法有四个特征，移植的时候要逐个盯住。二维 grid、mask、fp32 里算 SiLU、cast 回输入精度再乘。mask 是处理边界的：D 除以 BLOCK 不一定整除，最后一块列里多出来的位置要靠 mask 挡住，不让 kernel 读到越界的位置。fp32 里算 SiLU 是精度账：sigmoid 里有 exp，fp32 下 exp 的输入超过约 89 就会溢出成 inf——e 的 89 次方约等于 4.49 乘以 10 的 38 次方，已经超过 fp32 能表示的上限；先在 fp32 里把 SiLU 算完，中间结果的精度余量大得多，再 cast 回去，误差只来自最后一次舍入。cast 的顺序是 load-bearing 的，也就是改了顺序结果就会变：先 cast 回输入精度再乘，和直接拿 fp32 的 SiLU 结果乘 fp16 的另一半，乘法在混合精度下做，误差的来源就变了，max abs err（最大绝对误差）就会变。tile 里的中间量也可以算一笔小账：BLOCK 等于 1024 的一个 tile，fp32 存是 1024 乘 4 等于 4096 字节，fp16 存是 1024 乘 2 等于 2048 字节，两者相差 2048 字节——fp32 中间结果的代价是每个 tile 多占 2048 字节的寄存器与片上空间，换来的是 SiLU 的精度余量。这笔账没有标准答案，只有取舍：精度要余量，空间要省着用，哪个更重要看算子落在什么精度要求下。

动手的过程按循环走。先用 `tab init-solution` 生成 `L2_04_silu_and_mul` 的解法骨架，把 M2 第 6 周写的 Triton 版 SiluAndMul 填进 `npu_triton_impl(inputs) -> dict`。骨架生成这一步没有技术含量，但它定下了规矩：解法的入口只有一个，评测只从这个入口调你的 kernel，入口之外的任何取巧都进不了判分。然后跑 GPU 自查，`tab run --backend gpu`，先确认 kernel 在 CUDA 上正确。这是迁移的基线，上一节已经讲过它的逻辑：GPU 上不对的东西，搬到 NPU 上也不会对。自查通过之后，再跑 NPU，`tab run` 默认就是 `--backend npu`。每遇到一个不兼容点，按第 2 节的表头记一行：现象（报错原文）、定位（kernel 里的哪一行、哪个 API）、改法、重测结果。改完一个测一个，不要攒一堆改动再测——否则失败归因不清，这条纪律上一节也讲过，这里是它第一次真正落地。

判分要分两条线看，不要混成一条。正确性在 CPU 上对照 PyTorch oracle 判分，有容限分级；性能需要在 910B 上实测。两条线回答的是两个问题：正确性回答“算得对不对”，性能回答“算得快不快”。没有 NPU 的时候，结果标 `npu_antihack_unverified`，这个标记要原样写进记录，不要把它当成“通过”。标记本身就是诚实设计：它告诉读者，这份记录里的 NPU 部分没有验证过，验证过的只有 GPU 自查。把标记改写成“通过”，等于把“没测过”说成“测过了”，整份记录的可信度就垮了。

无卡的时候，本节的产出是两件东西：GPU 自查结果与移植计划。GPU 自查结果就是 `tab run --backend gpu` 跑通的证据：对照 oracle 的误差、跑过的形状、用的 BLOCK 配置。自查结果之外，再写一份移植计划：按 kernel 的每一行，写出“这一行在 triton-ascend 上可能有什么问题、准备怎么验证”。计划的写法有讲究：写“可能”与“准备怎么验证”，不写定论。沿着 kernel 的结构走一遍，每一行都可以配一个待验证的问题：load 那一行带 mask 读入，triton-ascend 的 mask 语义是不是和 CUDA 版一致，准备用边界形状（D 不能被 BLOCK 整除的形状）去验证；fp32 里算 SiLU 那一行，exp 与 sigmoid 在 triton-ascend 上的精度行为是不是一致，准备拿上一段手算过的几个数（`silu(1)` 约等于 0.7311、`silu(2)` 约等于 1.7616）逐个对照；cast 回输入精度再乘那一行，cast 的舍入行为是不是一致，准备对照 oracle 的 max abs err 看它变没变；乘法与 store 那一行，写回的布局与对齐要求有没有变化，准备用小形状先跑通再放大形状。每一行都是一句“可能有什么问题”加一句“准备怎么验证”，没有一句“这里一定有问题”或者“这里肯定没问题”——没有实测，定论写不出来，写出来也是猜测。

没有 NPU 环境时，本节的产出是 GPU 自查结果加一份移植计划：每条写清“可能”与“准备怎么验证”，NPU 步骤一律标注“待有卡后补测”。有了卡之后，跑一次、记一行，每条“可能”变成“是”或“不是”，每条验证变成一行带重测结果的记录。

**产出**：一份移植记录（不兼容点逐条：现象 + 定位 + 改法 + 重测结果；无卡时为 GPU 自查结果 + 移植计划）。

### 第 5 节 · 小结：移植的通用检查清单

**目标**：写出移植的通用检查清单。

**怎么做**（60 分钟，无硬件可做）：

把第 4 节的记录提炼成清单（按流程顺序）：

| 步骤 | 检查项 |
|---|---|
| 基线 | GPU 自查通过了吗（`--backend gpu`） |
| 环境 | 版本锚点写清了吗（CANN / torch_npu / triton_ascend 各是哪一版） |
| 迁移 | 每个不兼容点都记了现象 + 定位 + 改法 + 重测结果吗 |
| 判分 | 正确性判分与性能判分分开看了吗（CPU oracle vs 910B 实测） |
| 诚实 | 没有 NPU 的结果标了 `npu_antihack_unverified` 吗 |
| 取舍 | 统一实现 vs 手写移植的取舍写了吗 |

清单只有六行，每一行都能对回本周的一节。基线那一行对的是第 2 节的循环起点：GPU 自查是迁移的基线，基线没通过，后面的记录全是沙上建塔——NPU 上报的每一个错，都可能是 kernel 本身就有的错。环境那一行对的是第 2 节与第 3 节反复出现的版本锚点：本周出现了三套版本，vllm-ascend 的 CANN 9.2.1、TritonAscendBench 的 CANN 8.5.0、FlagTree Ascend 分支的 Triton 3.5，清单问的是“你写清用的是哪一套了吗”；最新版不是标准，写清楚才是标准。迁移那一行对的是第 2 节的记录表头：四列缺一列，这一行就不算完成；缺了重测结果的不兼容点，只算“遇到过的问题”。

判分那一行对的是第 4 节的两条线：正确性在 CPU 上对照 PyTorch oracle 判分，性能需要在 910B 上实测。两条线混成一条，最常见的错法是拿“正确性过了”当成“性能也行”，或者拿“跑得快”当成“算得对”——清单把它们分开，就是为了防这两种错法。诚实那一行对的是第 4 节的标记：没有 NPU 的结果有没有原样标上 `npu_antihack_unverified`。这一行是整张清单里最短的一行，也是最容易被绕过的一行：标记写上去，记录的可信度就立住了；标记被改写成“通过”，整份记录就垮了。取舍那一行对的是第 3 节：统一实现与手写移植的取舍写了没有。移植记录里只写“改了什么”是不够的，还要写“为什么这条路线的取舍是这样”——取舍不写下来，下一个人读记录的时候，只会看到一串改动，看不到改动背后的判断。

把本周的检查清单并进总清单，加两条：“移植记录里有失败的尝试吗”“每个不兼容点都有重测结果吗”。六加二等于八，并进总清单之后，本周的检查项一共是八条。加的第一条问的是失败的尝试有没有留下来：一份只写成功的移植记录是不完整的，因为失败的尝试本身就是信息——它告诉后人哪条路走不通。加的第二条是对迁移那一行的再确认：每个不兼容点都有重测结果吗，没有重测结果的改法等于没有验证过的猜测。两条加进去之后，清单的作用就完整了：它记下的是“什么还没做”。无卡的同学，第二条与诚实那一行先标“待有卡后补测”，有卡之后补上——空着的格子就是诚实本身。第 1 周定下的制度在这里收了尾：没有核实日期的事实陈述视为未知，没有重测结果的改动视为未验证，清单上空着的格子是诚实，不是缺憾。

**产出**：一份移植通用检查清单。
## 第 30 章 · 精度回归与调优报告

> 硬件：本周需要两边（NVIDIA + 至少一种国产芯片）的可运行环境；缺一边就先写好报告框架与方法论，实测部分标注“待补测”。
>
> 本周主线：同一模型、同一评测集，两边各跑一遍——精度差多少、性能差多少、差异从哪个算子来，最后写成一份别人能复现的报告。

### 第 1 节 · 精度回归：同一评测集，在 NVIDIA 与 Ascend 上各跑一遍

**目标**：出一份精度对比表——同一评测集、同一模型，两边的输出质量差多少。

**怎么做**（60 分钟，需两边环境；缺一边时先写好方法与表格框架，实测标注“待补测”）：

先算一笔时间总账：6 周 × 5 节 × 60 分钟 = 1800 分钟 = 30 小时。本周 5 节是 300 分钟、5 小时。这 30 小时的账要这么读：第 1 周搭了分层图与 Four Walls 这把尺子，第 2 周摸清了插件机制，第 3 周跑通了第一个模型，第 4 周攒了算子覆盖矩阵，第 5 周走了一遍移植流程——本周的任务是把这五周的东西收成一张能拿给别人看的对比表。收口是换一把尺子量一遍：前面五周量的是“能不能跑”“哪个算子在哪”，本周量的是“跑出来的东西差多少”。如果前面五周的记录是散的，本周就是第一次把它们拼成证据链的地方。

先把对比成立的前提钉死：评测集不变，变的只有芯片。用的是 M0 基线报告里的那套评测集，与 M1、M2 里用的是同一套。为什么这一点值得注意？因为对比表里的每一个差异都要能归因——如果评测集也换了，表里的数字就同时混进了两个变量，差 0.8 个百分点到底是芯片的差别还是题目的差别，谁也说不清。控制变量在这里不是洁癖，是对比表成立的前提。同一个道理也管着模型：同一模型不只是同一个名字，是同一个权重来源、同一个量化方式。一边跑 FP16、一边跑 INT8，量出来的就是量化的差别，芯片的差别被它盖住了——那是第 4 周量化方案的账，不该混进本周的表里。设问：如果两边用的量化方式本来就不一样，这份对比表还能写吗？能写，但表头要写清“FP16 vs INT8”，结论也要改写成“在各自默认量化下的对比”，不能写成“芯片对比”。诚实的做法是把变量写在表头里，别藏在脚注里。

再看表里要记什么。评测指标按评测集的定义来：准确率（accuracy，答对的样本占总样本的比例）、困惑度（perplexity，简称 PPL，模型对文本的平均“意外程度”，越低越好）、人工抽查通过率，评测集定义了哪个就记哪个。三个指标看的是三件不同的事：准确率看的是对错，困惑度看的是分布离参考答案有多远，抽查通过率看的是人眼觉得能不能用。只记准确率会漏掉一类差异：两边答案都对，但一边的表述系统性地变差了——准确率看不出来，抽查看得出来。反过来，只记抽查也会漏掉：人眼抽 5 条看不出 0.8 个百分点的差别，指标看得出来。指标和样本是互补的，不是谁替代谁。

拿一组算例把“差多少”算清楚——注意，下面是算例，不是实测，用来示范读表的方法。假设评测集一共 1000 条样本，NVIDIA 一侧答对 850 条，Ascend 一侧答对 842 条：准确率分别是 85.0% 与 84.2%，差 0.8 个百分点，折成样本数是 8 条。这个 0.8 个百分点要怎么读？先别急着下结论“一边更好”。1000 条样本里 8 条翻过来，结论就没了——0.8 个百分点的差距薄到这个程度。再换一组数看清样本量的作用：评测集只有 100 条样本时，1 条样本就是 1 个百分点，0.8 个百分点的差距连 1 条样本都不到，根本量不出来。样本量决定了这张表能分辨多细的差异：样本越少，表越粗，越不能对小差距下结论。这就是为什么评测集的样本数要写进报告（第 4 节的模板第 2 节会要求写）——没有样本数，差异的数字是没有量程的。困惑度也一样可以手算着读：假设两边的平均负对数似然（NLL，模型给正确答案的负对数概率，越小越好）差 0.01，困惑度是 NLL 的指数，e^0.01 ≈ 1.01005，两边的困惑度比值约 1.01，也就是差 1% 左右。1% 的困惑度差距是什么量级？和上面 0.8 个百分点的准确率差距一样，是“能测出来、但别急着解释”的量级——要解释它，得去第 3 节做归因，本节只负责量。

输出样本的抽查是另一路证据：至少抽 5 条并排对照，看有没有系统性差异。5 条样本是干什么的？不是用来算指标的——5 条样本算不出 0.8 个百分点。5 条样本是用来看“错的样子”的：指标告诉你差多少，样本告诉你差在哪类问题上。如果 5 条里有 3 条是同一类问题（比如都需要多步推理的题）在一边总答错，3/5 = 60%，这个比例指向的就不是随机波动，是系统性差异——某类能力在一边系统性地弱了。反过来，如果 5 条里只有 1 条错、错得还各不相同，那就什么也说明不了，别硬解释。抽查的价值在“并排”两个字上：同一道题、两边的输出放一起看，差异才看得见；分开看，两边各自都像是对的。抽查还有一个容易被忽略的用途：它是第 3 节归因的起点。归因要从“哪类题错了”出发——“哪类题”指向的是哪个算子、哪种计算，“差多少”指向的只是程度。

抽查的 5 条怎么抽，也有讲究。随机抽 5 条，抽到的很可能全是评测集里的多数题型——拿一组算例说清：假设评测集 1000 条里 800 条是选择题（80%）、200 条是开放问答（20%），随机抽 5 条全是选择题的概率是 0.8^5 ≈ 0.328，约 33%，开放问答可能一条都抽不到。分层抽是按题型分层、每类至少抽几条，保证每一类题都有样本露面。分层是为了让“系统性差异”有机会被看见：某类题在一边系统性地弱，随机抽可能永远抽不到它，分层抽才能把它摆到桌上。抽法本身也要记下来——别人复现你的抽查，要按同一个抽法抽，否则抽到的 5 条不一样，结论对不上。

表格的列为什么要带版本号与日期？因为这张表里的每一个数字都只在某个版本下成立。同一块芯片，CANN 换一个版本，数字就可能变。版本号与日期是数字的锚：没有锚，数字就是漂着的，三个月后没人知道它对应的是哪个软件栈。第 4 节写报告时，模板第 1 节会要求把两边每一项的版本都列出来，源头就在这里——本节填表时顺手把版本和日期写上，第 4 节就不用回头翻了。日期还有一个作用：它标明了这张表的保质期起点，第 5 节讲“保质期”时会用上。

指标的口径也要钉死：同一指标名、不同实现也会差——准确率是精确匹配还是宽容匹配（大小写、空白、标点算不算错），评测集定义了什么就按什么记，口径写进表头或脚注。两边用的判分脚本不同，数字差的是判分，不是芯片——口径不写清，归因的第一步就走错了方向。

最后管理预期：精度回归的结论是“差异从哪来”，不是“谁高谁低”。本节只负责把差异量出来、记下来，归因是下一节（第 3 节）专门讲的事。把“量”和“归因”分开，是因为两件事用的工具不一样：量用的是评测集与指标，归因用的是二分法与覆盖矩阵。混在一起，最常见的结果就是一句话带过——“Ascend 精度稍差”——这句话里既没有数字，也没有原因，写了等于没写。一个常见的误解：“精度回归就是比谁高”。不对。比出高低只需要一行数字，回归要的是差异的去向：差 0.8 个百分点不可怕，可怕的是不知道这 8 条样本错在哪、对应哪个算子。第 2 周讲插件机制时说过，模型代码不知道 Triton 实现存在；这里也一样，评测集不知道芯片存在——它只负责量，解释是人的事。

对照第 4 周的量化方案：那一周攒的误差账本（每个算子的量化误差记在哪、量级是多少）是本节的底稿。如果本节量出的差异和第 4 周账本里的某个算子误差对得上，归因就有了第一条线索；对不上，说明差异来自账本之外的地方——第 3 节会接着查。缺一边环境时，本节只做框架：方法写好、表格画好、评测集与指标定好，实测的格子写“待补测”。框架先行的好处是，环境一到，照着跑就行，不用重新想“该测什么”；更重要的是，框架本身就能被检查——别人能看出你的方法对不对，哪怕数字还没填。

### 第 2 节 · 性能对比：TTFT / ITL / 吞吐，用 M0 的压测脚本在两边各跑三级并发

**目标**：出一份性能对比表。

**怎么做**（60 分钟，需两边环境；缺一边时先写好方法与表格框架，实测标注“待补测”）：

先把三个指标的定义摆出来，因为它们量的是三件不同的事。TTFT（Time to First Token，首 token 延迟）量的是第一个 token 多久出来，背后是 prefill（预填充：把提示一次性算完、建好 KV cache 的阶段）；ITL（Inter-Token Latency，每 token 间隔）量的是之后每个 token 之间隔多久，背后是 decode（解码：一个 token 一个 token 往外吐的阶段）；吞吐量的是单位时间一共出多少 token，背后是整机的产出。三个数分工不同：TTFT 看 prefill 与首 token，ITL 看 decode 的稳定程度，吞吐看整机的产出。只看吞吐会漏掉一类问题：吞吐一样的两边，TTFT 可能差一倍——交互场景下用户先感受到的是首 token，不是吞吐。只看 TTFT 也会漏掉：首 token 很快，但 ITL 越来越大，用户会觉得“越吐越慢”。三个数都要记，缺一个，画像就缺一块。

三个数之间是可以互相换算的，换算关系本身就是读表的方法。先推一遍公式：一个请求生成 L 个 token，总延迟约等于 TTFT + ITL × (L − 1)——第一个 token 花 TTFT，剩下 L − 1 个 token 每个花 ITL。单请求的 token 速率就是 L 除以这个总延迟。并发为 C 时，如果延迟不变，吞吐约等于 C × L / 总延迟。拿一组算例走一遍（算例，不是实测）：设 TTFT = 100 毫秒、ITL = 20 毫秒、生成长度 L = 101 个 token，总延迟 = 100 + 20 × 100 = 2100 毫秒 = 2.1 秒，单请求速率 = 101 / 2.1 ≈ 48.1 token/秒。并发 8 且延迟不变时，吞吐 ≈ 8 × 48.1 ≈ 384.8 token/秒。换算的意义在于，它给了你一张“无争用”的基准线：并发 8 的吞吐如果远低于 384.8，就说明延迟变了——争用已经发生了。这张基准线不用实测，是算出来的；实测的任务是量出它偏离基准线多远。

测之前还有一件事：预热与重复。第一次跑总是最慢的——kernel 要编译、缓存是冷的、服务刚起来，首跑的数字里混进了启动的成本。所以每一档并发都要先跑一轮预热、再取多次重复的中位数；只跑一次就填表，填进去的是启动成本，不是稳态性能。M2 第 2 周讲过 do_bench 取中位数的道理，同一条道理搬到这里：中位数扛得住偶尔一次的抖动，均值扛不住——一次排队、一阵系统负载，均值就被拉偏了，中位数还在原地。预热几轮、重复几次、取什么统计量，这些是方法的一部分，要写进框架里，和并发档位写在一起。

并发档位也要按硬件能力选：并发 32 在小显存的卡上可能直接跑不下——跑不下的档位写“跑不下加原因”，不要硬跑，也不要悄悄降档再填表。单位也要统一写进表头：TTFT 与 ITL 用毫秒，吞吐用 token/秒——单位不写，100 这个数是毫秒还是 token/秒，三个月后没人分得清。

再算一组偏离的情形，看曲线形状怎么读。假设并发 8 时 ITL 从 20 毫秒涨到 40 毫秒（TTFT 不变，还是 100 毫秒），总延迟 = 100 + 40 × 100 = 4100 毫秒 = 4.1 秒，单请求速率 = 101 / 4.1 ≈ 24.6 token/秒，并发 8 的吞吐 ≈ 8 × 24.6 ≈ 197.1 token/秒。并发涨了 8 倍，吞吐只涨了 197.1 / 48.1 ≈ 4.1 倍。为什么？因为单请求的延迟翻了一倍，8 个请求并行吐，但每个都吐得更慢了。吞吐的涨幅追不上并发的涨幅，差的那部分就是争用的代价。这就是三级并发的曲线形状本身携带的信息：曲线越陡，扩展性越好；曲线越早变平，瓶颈来得越早。两边的曲线画在一起，哪一边在高并发下掉得更快，一眼就能看出来——掉得快的那一边，它的调度或显存管理先到了瓶颈。第 3 节会用这个形状做归因：TTFT 先涨还是 ITL 先涨，指向的是不同的瓶颈。

为什么是三级并发（例如 1 / 8 / 32），不是一级、不是五级？一级并发只能量出单请求的延迟，量不出争用；五级当然更细，但每一级都要在两边各跑一遍，时间成本翻倍。三级是“能画出曲线形状”的最少点数：并发 1 是起点，并发 8 是中间，并发 32 是高并发——三点连起来，曲线是陡是平、哪里开始弯，大致形状就出来了。打个比方：两点只能画直线，三点才能看出弯。并发档位本身没有标准答案，1 / 8 / 32 只是例子，关键是两边用同一套档位——档位一变，曲线就没法并排比。命令、模型、评测集、并发三档全都相同，只换芯片与对应的服务。这句话值得再强调一遍，因为它是整张表成立的前提：采样参数（temperature、top_p、max_tokens）也要固定。温度一改，输出长度变了，上面公式里的 L 就变了，ITL 和吞吐跟着变，表里的数就没法归因。输出长度是吞吐公式里的变量，不是背景——固定它，和固定模型是同一级别的要求。

读表还有两个常见的误解。第一个是“只比单点”：并发 1 时一边快 10%，就下结论“这一边快”。不对。并发 1 量的只是单请求延迟，高并发下的调度、批处理、KV 管理都没被量到——单点快的一边，高并发未必快；单点慢的一边，高并发可能反超。第二个误解是反过来的：只看高并发吞吐，忽略 TTFT。高并发吞吐高、TTFT 差的服务，在交互场景下体感是“等半天才出第一个字”，吞吐的数字再好看也没用。三个指标、三级并发，九个格子是一张画像，不是一行排名。画像的读法是：先看 TTFT 的差距，再看 ITL 随并发怎么涨，最后看吞吐的曲线形状——三个问题按这个顺序问，瓶颈的轮廓就出来了。

比值列的读法也值得注意。比值是 Ascend 除以 NVIDIA：拿一组算例说清，假设 NVIDIA 的 TTFT 是 100 毫秒、Ascend 是 140 毫秒，比值 = 140 / 100 = 1.4，也就是慢 40%。比值要和绝对值一起读：TTFT 从 10 毫秒变 14 毫秒，比值同样是 1.4，但绝对差距只有 4 毫秒，用户几乎感知不到；TTFT 从 100 毫秒变 140 毫秒，比值还是 1.4，绝对差距 40 毫秒，交互体感已经不一样了。比值相同，意义不同——只看比值会把两种情况混成一种。反过来，比值接近 1 也不能直接读成“两边一样”：TTFT 比值 1.02、ITL 比值 1.30 的两边，首 token 差不多、decode 差一截，画像是不一样的。还有一种曲线形状要认出来：如果并发 32 的吞吐反而比并发 8 低，曲线掉头了，说明进了过载区——请求排队等调度，TTFT 被排队时间撑大，吞吐不升反降。掉头本身就是信息：它标出了这套服务的并发上限，再往上加并发，数字只会更难看。

对照 M0 的压测脚本：用的是 M0 的 `scripts/bench_openai.py`，不是现写的新脚本。为什么？M0 的基线章节已经把它调通过了，同一把尺子量两边，尺子本身不引入误差。现写脚本的风险不在功能，在细节：预热够不够、计时从哪到哪、统计取的是均值还是中位数——每一个细节都可能让两边的数差出几个百分点，而你分不清是芯片的差别还是脚本的差别。M2 第 6 周接入 CustomOp 时用的也是同一把尺子，道理相同：端到端对比的价值，全在“除了被比的东西，别的都不变”上。无卡或缺一边时，本节和第 1 节一样：方法与表格框架先写好，实测的格子写“待补测”。框架里要写清的东西包括并发三档、采样参数、生成长度、预热与重复次数——这些是方法的一部分，不是附注。

### 第 3 节 · 差异分析：数字不同的原因——归因到具体算子

**目标**：把差异归因到具体算子，“芯片不行”这种笼统说法不算归因。

**怎么做**（60 分钟，分析无卡可做；归因需要第 1–2 节的数据与第 4 周的覆盖矩阵）：

先把两类差异分开，因为归因方法不同。精度差异问的是“输出为什么不一样”，性能差异问的是“速度为什么不一样”。精度差异的源头在计算本身——算子用的精度、量化方案、舍入方式；性能差异的源头在资源——算子跑在哪、搬了多少数据、调度排得怎么样。两类差异混在一起归因，最常见的结果就是一句正确的废话：“国产芯片还有差距”。这句话的问题不在对错，在它没法指导下一步：差距在哪？改哪个算子？换哪个实现？一个字都答不上来。归因的终点是一个算子名，不是“精度墙”三个字；性能归因的终点也是一个算子名，或一面墙（M0 的 Roofline 里那面墙：算力墙、访存墙，撞上的是哪一面）。终点具体到这个程度，归因才算完成——因为只有具体到算子，才知道下一步改什么。

精度差异的归因，先查三处。第一处是量化方案的差异：两边的量化实现是不是同一套——per-channel（每通道一个 scale：权重每列共用一个缩放系数）还是 per-token（每 token 一个 scale：激活每个 token 各自一个缩放系数）的 scale 取法，舍入方式是就近舍入还是截断。同一套量化方案的名字，不等于同一套实现：scale 取法不同，误差的分布就不同；舍入方式不同，误差的方向就不同。第 4 周的覆盖矩阵里记了每个算子的实现位置，对照着查——矩阵在这里第一次派上用场：它告诉你每个算子在芯片侧到底跑的是什么实现，别凭印象猜。第二处是低精度算子的差异：FP16（16 位浮点）与 INT8（8 位整数）的实现是不是同一精度，比如一边用了 FP8（8 位浮点）、另一边没有。精度这件事没有“差不多”：一边 FP8、一边 FP16，输出差一点是意料之中，差多少才需要解释。第三处是容易被忽略的：同样的算子名、不同的库版本——版本一变，kernel 的实现可能就换了，精度跟着变。这就是为什么第 1 节的表要带版本号：归因时先对版本，版本对不上，先查版本再查算子。

归因的方法是二分法：一次只换一个变量。做法是拿可疑的算子换成 PyTorch 参考实现跑一遍，看差异是否消失——差异消失的那个算子就是回归的来源。为什么一次只换一个？因为一次换两个，差异消失了也不知道是谁的功劳；差异没消失，也不知道是谁的问题。二分法把“一次换一个”组织成对半分：先把一半可疑算子换成参考实现，差异消失了，源头在这一半；没消失，源头在另一半；再对剩下的一半对半分。轮数是可以算的：8 个候选算子，8 → 4 → 2 → 1，三轮定位到一个；16 个候选算子，四轮；10 个候选算子，ceil(log2 10) = 4 轮，因为 2^3 = 8 不够盖住 10 个，2^4 = 16 才够。每轮的代价是一次重跑——轮数少的前提是候选集小，候选集来自第 4 周的覆盖矩阵和第 1 节的抽查（哪类题错了，指向哪几个算子），不是凭空列出来的。候选集列得越准，轮数越少；候选集列得越宽，轮数越多，但总比一个一个试强。一个一个试 16 个算子要 16 轮，二分法只要 4 轮——省下来的 12 轮，就是“方法”的价值。

归因还有两种失败模式要先认出来。第一种是候选集漏了真凶：二分法再严密，也只能在候选集里找——真凶不在集里，几轮下来差异还在，谁也定位不到。候选集的来源要写清：第 4 周的覆盖矩阵、第 1 节的抽查（哪类题错了）、第 2 节的曲线形状（TTFT 先涨还是 ITL 先涨），三路线索拼出来的集才比较全。第二种是一次换多个变量：差异消失了，不知道是谁的功劳；差异没消失，也不知道是谁的问题——省掉的轮数，回头一个一个试又补回来了，还多了一轮。候选原因的验证顺序也有讲究：先做最可能、且最便宜验证的那个——占比大的算子先查，实现明显不同的先查，版本对不上的先查版本。验证成本最低的先做：它最快能排除，排除得越快，候选集缩得越快。反问一句：如果一次换一个变量这么慢，为什么不一次多换几个？因为多换几个省的是轮数，丢的是归因：差异消失了，你不知道是这几个里的哪一个，还得回头一个一个试——省掉的轮数又补回来了，还多了一轮。

性能差异的归因，对照第 4 周的结论与 Four Walls（四面墙：推理优化里常用的归因框架，把瓶颈归到算力、访存、延迟、并行这几面墙上）。先查三处。第一处是算子覆盖：第 4 周的矩阵里，有没有算子回退到 CPU 或低效实现。回退的代价是可以估算的——注意，下面是带明确假设的算例，不是实测：假设某算子占端到端时间的 10%，回退后变慢 5 倍，新时间 = 0.9 + 0.1 × 5 = 1.40 倍，也就是整体慢 40%。换一组假设：占比 5%、变慢 5 倍，新时间 = 0.95 + 0.05 × 5 = 1.20 倍，慢 20%；占比 20%、变慢 3 倍，新时间 = 0.8 + 0.2 × 3 = 1.40 倍，同样慢 40%。算例的结论是：回退的伤害由占比和变慢倍数共同决定——占比小的算子回退了，端到端可能没感觉；占比大的算子回退一点，端到端就掉一大截。所以归因的第一步是看占比，不是看“回退了几个算子”：回退 10 个各占 0.1% 的算子，不如回退 1 个占 10% 的算子要紧。M2 第 6 周的 Amdahl 定律是同一笔账的另一面：占比 1% 的算子无限优化也只省 1%，占比 10% 的算子回退 5 倍却能让整体慢 40%——优化的天花板是占比，回退的地板也是占比。第二处是显存带宽：M0 的 Roofline 思路，搬运量有没有变。举一个算例：70 亿参数的模型，FP16 权重占 70 亿 × 2 字节 = 14 GB，INT8 权重占 70 亿 × 1 字节 = 7 GB，搬运量差一半。如果 decode 是访存受限的（M0 Roofline 的判断），权重搬运占大头，那么精度变了，搬运量就变了，ITL 跟着变——这时性能差异的源头不是芯片慢，是搬运量不同。注意这个推理的边界：权重只是搬运的一部分，KV cache 也要搬；权重省一半不等于总搬运省一半，更不等于 ITL 省一半——算例讲的是机制（搬运量变了，速度会跟着变），不是结论（变多少要实测）。第三处是调度：高并发下掉得快的一边，先看它的批处理与 KV 管理。第 2 节的曲线形状在这里派上用场：ITL 随并发涨得快，指向 decode 侧的调度与显存管理；TTFT 随并发涨得快，指向 prefill 侧的批处理。形状先告诉你去哪查，查到了再用数字确认。

归因的落点是一份归因记录：每个差异一行——差异（数字）、候选原因（2–3 个）、验证方法（怎么确认是哪一个）、结论（归因到哪个算子或哪面墙，证据是什么）。候选原因写 2–3 个，不是 1 个：只写 1 个等于先下结论再找证据；写 2–3 个是把几种可能并排放着，让验证去裁决。验证方法要写具体：换哪个算子、换成什么实现、跑什么评测集、看哪个指标——写到这个细度，别人才能复现你的验证。结论只写验证过的：验证不了的写“待验证”，不要写成定论。“待验证”不是报告的污点，是归因的诚实——它标明了证据链断在哪，下一步该补什么。第 1 节的精度表与第 2 节的性能表是归因的输入，第 4 周的覆盖矩阵是归因的地图，第 4 节的报告是归因的出口：归因记录本身就是报告第 6 节的内容，写的时候按模板的格式写，不用写两遍。

归因记录的每一行都要有日期：同一差异隔两周重测，结论可能变（版本换了），日期标明结论的有效期。候选原因写 2–3 个也是上限：超过 3 个，说明候选集还没收敛，先收敛再验证——验证 5 个候选，不如先排除 2 个再验证 3 个。

**产出**：一份差异归因记录（差异 + 候选原因 + 验证方法 + 结论）。

| 差异 | 候选原因 | 验证方法 | 结论 |
|---|---|---|---|
| … | … | … | …（验证不了的写“待验证”） |

### 第 4 节 · 写报告：按「某年某月某版本实测」的格式，把环境、版本、命令、结果写全

**目标**：写出 **M3 的可交付物：跨芯片对比报告（初稿）**。

**怎么做**（60 分钟，无硬件可做；没有实测数据的章节写框架 + “待补测”）：

先把报告的定位说清楚：这份报告是 M3 的可交付物，初稿的意思是框架完整、证据有一说一——有数据的章节填数据，没数据的章节写框架加“待补测”，不编数字凑完整。模板在 `docs/modules/M3-domestic-chips/cross-chip-report-template.md`，一共 11 节（0 号报告头加 1–10 节），每一节都要填。模板是证据清单：缺一节，证据链上就少一环。下面按模板的顺序走一遍，每节讲清它要什么、为什么要。

0 号报告头：报告日期、报告人、模型、评测集、结论保质期。保质期写在首页，格式是“本报告基于某年某月某版本，过期需重测”。为什么保质期要放首页？因为报告的读者第一眼要知道的是“这份报告还管不管用”，“它测了什么”是第二眼的事。一份没有保质期的报告，三个月后被人翻出来，数字照样会被引用——引用的人不知道版本已经换了两轮，数字早就不对应现在的软件栈了。保质期是报告有效期的刻度，第 5 节会展开讲。

第 1 节环境：两边各一列，硬件型号、驱动与固件版本、Python 与 PyTorch 与 TorchNPU（或对应框架适配）版本、CANN（或对应 SDK）版本、vLLM 与 vllm-ascend 版本（或对应插件）、核实日期。为什么要细到这个程度？因为跨芯片对比里，变量不只是芯片：驱动、框架、插件，每一项都可能让数字变几个百分点。环境表的作用是把这些变量钉在纸上——复现的人照着同一套版本搭环境，数字才对得上量级。核实日期也要写：版本号是静态的，核实日期说明“这个版本号是我在某天亲手确认过的”，不是从文档里抄来的。核实日期写到天（“某年某月某日核实”），不要只写月份——版本发布以天计，月份不够细。抄来的版本号和核实过的版本号，在报告里是两种可信度。

第 2 节模型与评测集：模型写名称、权重来源、量化方式；评测集写名称、版本、样本数；采样参数写固定值（temperature、top_p、max_tokens）。采样参数为什么要单列？第 2 节算过，输出长度 L 进了吞吐公式——max_tokens 一改，L 就变，ITL 和吞吐跟着变。固定采样参数和固定模型是同一级别的要求，写进报告就是为了让复现的人改不了、也忘不了。样本数也要写，第 1 节讲过：样本量决定了表能分辨多细的差异，100 条样本的表和 1000 条样本的表，分辨率差一个量级。

第 3 节命令：全文，可复现。两边的启动命令全文、压测命令全文（M0 的 `scripts/bench_openai.py`，含并发档位）。“全文”两个字是这一节的全部要求：启动命令里少一个环境变量、压测命令里少一个并发档位，复现就断了。命令全文还有一个作用：它是第 1–2 节“只换芯片与对应的服务”的证据——两边的命令并排放在一起，读者能自己检查：除了芯片与服务，别的变量是不是真的没动。检查不出来，就说明命令写得不够全。命令是报告里最容易被轻视的一节，也是复现失败时最先被怀疑的一节——写全它，成本是几行字，省掉的是复现者一下午的排错。

初稿的完成标准要先定下来：框架完整、已有数据已填、缺失项都有“待补测”与下一步计划。达不到这个标准，缺的是证据：要么回第 1–2 节补测，要么在第 9 节把缺失写成计划。初稿和终稿的区别不在厚度，在证据齐不齐：终稿是所有“待补测”都填上了、所有“待验证”都有了结论；初稿是框架立住了、缺口都标明了。

报告本身也要有版本号：初稿记 v0.1，补测一次升一版，每次只改相关章节，并在报告头记一笔变更——改了什么、为什么改、哪天改的。没有版本号，两份报告摆在一起不知道哪份新；没有变更记录，新版的数字从哪来没人说得清。硬件型号也要写全，具体型号加显存容量：同系列不同显存的卡，性能数字不一样，型号写一半等于没写。

第 4–5 节结果：第 1–2 节的两张表原样放进来，带版本号与日期。表里的“…”占位符在有实测之前不要动——占位符的意思是“这里等实测来填”，第 6 节归因：第 3 节的归因记录原样放进来，验证不了的结论保持“待验证”。第 7 节算子覆盖矩阵摘要：引用第 4 周的覆盖矩阵，Top 10 算子的芯片侧状态（原生实现、插件实现、回退、待核实）与核实日期。第 8 节移植记录摘要：引用第 5 周的移植记录，不兼容点逐条（现象、定位、改法、重测结果）。第 7–8 节是“引用”不是“重写”：矩阵与记录的正本在第 4–5 周，报告里放摘要加指向——正本改了，摘要要跟着改，两个版本对不上，报告的可信度就掉下来了。

第 9 节结论只写有证据的结论：有数据的写数据加归因，没数据的写“待补测”与下一步计划。下一步计划要写触发条件，比如“待两边环境齐备后补测”——条件写清了，补做才有触发点；写“以后再说”，等于没写。结论的写法有两条线：数据线（数字是多少、归因到哪个算子、证据是什么）与计划线（缺什么数据、什么条件下补测）。两条线分开写，读者一眼能分清“已经知道的”和“还不知道的”。一个常见的误解：“报告是写出来的”。不对。报告是证据的合集，写只是把证据按顺序摆好——没有证据的结论，写得再漂亮也是装饰。反过来，证据齐了，结论几乎不用“写”，按“差异—归因—证据”的顺序摆出来就是结论。

版本号的写法也有规矩：写具体版本号加核实日期，不要写“最新版”。“最新版”三个字在报告里等于没写，因为“最新”每天都在变——三个月后读报告的人，不知道“最新”指的是哪一天的最新。模型也一样：不要只写名字，要写权重来源——同一名字、不同来源的权重，数字可能不一样。报告的读者也要想清楚：三个月后的自己、组里同事、下一批做移植的人。读者决定详略：写给自己可以略，写给接手的人要把“为什么这么测”写进去——方法背后的理由不写，接手的人只会照抄命令，命令一出问题就不知道该怎么调。第 10 节保质期说明：会过期的结论与不会过期的方法论分开写，内容就是第 5 节要做的那一页——本节先把位置留出来，第 5 节填。

最后是报告的可复现性标准：别人拿着这份报告，能在同一版本的软硬件上复现出同一量级的数字。注意“同一量级”四个字：复现不是逐位相同——调度抖动、系统负载都会让数字浮动几个百分点，逐位相同本来就不该出现；同一量级的意思是，报告说 TTFT 是 100 毫秒级，复现出来也是 100 毫秒级，不是 300 毫秒级。量级对不上，说明有变量没钉死：版本、命令、采样参数，回去查这三处。做不到的章节写“待补测”，不要编数字凑完整。

写报告的顺序也有讲究：先填有数据的章节，再写归因，最后写结论。结论最后写，因为结论依赖前面的数据与归因；先写结论再填数据，结论会牵着数据走——数据不好看就想改结论，结论一改，归因也跟着改，整份报告就成了先有答案再找证据。写完自查三问：命令能复现吗、版本都写全了吗、每个结论都有证据吗——三问都答得上，初稿才算完成。

**产出**：**M3 的可交付物：跨芯片对比报告（初稿）**。

### 第 5 节 · 小结：这份报告里哪些结论会随版本过期、哪些方法论不会

**目标**：写一页“保质期”说明。

**怎么做**（60 分钟，无硬件可做）：

先分两类写。会过期的结论：所有带版本号的数字——性能、精度、覆盖状态。过期时间就是下一次版本发布：CANN 发新版，算子实现可能换了，数字要重测；vllm-ascend 发新版，调度可能改了，曲线要重跑；PyTorch 发新版，精度可能动了，表要重填。报告首页写清“本报告基于某年某月某版本，过期需重测”——这句话是报告的使用说明：版本一换，数字的保质期就到了，引用之前先看日期。不会过期的方法论：Four Walls 归因、分层定位、覆盖矩阵方法、二分法归因、移植记录格式。这些是本模块真正要留下的东西：芯片会换代，版本会发布，但“差异归因到算子”的方法、“一次只换一个变量”的二分法、“每个不兼容点记现象加定位加改法加复测”的记录格式，换一块芯片照样能用。M0 的 Roofline 也是这个性质：硬件参数会变，定位的思路不会变。分两类的标准很简单：带版本号的会过期，不带版本号的方法论不会过期——写的时候按这个标准分，写完对照检查一遍，别把数字混进方法论、也别把方法论写成数字。

对照本模块检查清单，逐项打勾：能画出国产芯片软件栈的分层图并说清插件机制；同一模型在 Ascend 上跑通过（或明确标注了待补测的原因）；有一份算子覆盖矩阵，指出 Top 3 耗时算子的芯片侧状态；走过一次小规模移植流程并留下了记录；有一份按「某年某月某版本实测」格式写的跨芯片对比报告（初稿）。打勾的标准是证据，不是印象：打勾意味着这一项有对应的实测数或验证记录，翻报告能找到；没打勾也不要紧，要紧的是写清为什么没做、什么时候补做。补做计划要写具体条件，比如“跨芯片实测待两边环境齐备后补测”——条件写清了，补做才有触发点；写“以后再说”，等于没写。

完成第四部分意味着什么？不等于“Ascend 跑得和 NVIDIA 一样快”，它的意思是“每个数字都知道怎么来的，每个差异都知道归因到哪，缺的都知道缺什么、什么时候补”。这份报告就是证据的合集，保质期说明就是它的使用手册。带着方法论走：下一块芯片（摩尔线程、海光、昆仑芯，模板里列的切入点都在“其他芯片的切入点”那一节）来了，分层图要重画，覆盖矩阵要重填，数字要重测，但归因的方法、记录的格式、二分法的轮数，一行都不用改——那才是这 30 小时真正留下的东西。

**产出**：一页“保质期”说明 + 更新后的检查清单。
