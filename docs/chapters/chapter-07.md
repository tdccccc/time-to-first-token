# 第 7 章 可观测性与容量评估 { .chapter-title }

<p class="chapter-summary">度量必须先于优化：只有把延迟分解链、Prometheus 拉取验证、吞吐—延迟拐点曲线与过载三信号全部钉在明确的操作定义上，我们才能客观判断一次系统改动是真提速还是拿尾延迟换吞吐。</p>

线上监控大盘正中挂着一个醒目的数字：**GPU 利用率 87%**。运维同学认为机器快满了、必须马上加卡；算法同学却觉得还有 13% 余量、可以继续往上压流量。同一块看板、同一个数字，却推导出截然相反的扩容决策。

分歧从来不在数字本身，而在“利用率”缺乏清晰的操作定义——它究竟是流式多处理器（SM）活跃周期占比、HBM 显存带宽利用率，还是采样窗口内任意时刻有 Kernel 在运行的比例？三种定义指向三种截然不同的瓶颈与动作。本章将监控指标体系与容量压测评估合为一条闭环：先定指标语义与延迟分解，再打通并验证采集链路，接着用完整曲线定位系统拐点，最后厘清客户端并发与 GPU 过载抢占的真实边界。

## 7.1 先定义指标，再搭看板

### 为什么“GPU 利用率 87%”会吵不出结论？

搭监控大盘最常见的误区，是先导入一套花哨的默认 JSON 模板，把几十个曲线堆满屏幕，却说不清其中一半面板的分母、时间窗口和行动阈值。一个没有操作定义的指标不是工程证据，而是会议室里的修辞工具。

制定监控看板有一条极简铁律：**每个保留在看板上的面板，都必须同时写清“量什么、怎么算、跨过多少要采取什么动作”。** 回到开头那块 87% 的面板：如果明确它来自 DCGM 的 `DCGM_FI_PROF_SM_ACTIVE`（1 分钟平均 SM 活跃周期占比），就把它留下来并写进面板说明；如果只是笼统的 `nvidia-smi` 粗粒度占用率且没人能解释清楚，直接删掉反而能清除误导决策的噪音。

### 三类指标语义与平均数陷阱

Prometheus 生态和 vLLM `/metrics` 端点暴露的指标分为三种基本类型，混用类型会直接得出错误结论：

| 指标类型 | 语义本质 | 回答的问题 | 典型例子与常见误读 |
|---|---|---|---|
| **Gauge（仪表）** | 瞬时快照，可升可降 | “系统**此刻**状态如何？” | `vllm:num_requests_running`；对 Gauge 求长窗口平均会抹平瞬时毛刺 |
| **Counter（计数器）** | 单调递增累计值，进程重启归零 | “**累计**发生了多少？” | `vllm:generation_tokens_total`；必须用 `rate()` / `increase()` 计算增量，不可直接读绝对值 |
| **Histogram（直方图）** | 按区间分桶累计，展开为 `_bucket`、`le`、`_sum`、`_count` | “耗时**分布**长什么样？” | `vllm:time_to_first_token_seconds`；`_sum / _count` 是**均值**而非分位数，分位数精度受桶边界宽度限制 |

为什么延迟监控必须用直方图看分位数，而绝不能只看平均数？看一组 1,000 条请求的延迟分布算例：990 条耗时 $0.5\text{ s}$，9 条耗时 $2.0\text{ s}$，1 条极端长尾耗时 $20.0\text{ s}$。

- **平均值**：$(990 \times 0.5 + 9 \times 2.0 + 1 \times 20.0) / 1000 = \mathbf{0.533\text{ s}}$。
- **线性插值分位数**（按零基秩 $r = (n - 1) \times q$ 计算）：
  - $\text{p50} = 0.5\text{ s}$，$\text{p95} = 0.5\text{ s}$；
  - $\text{p99}$ 对应秩 $r = 999 \times 0.99 = 989.01$，落在第 989 号（$0.5\text{ s}$）与第 990 号（$2.0\text{ s}$）之间，得 $0.5 + 0.01 \times (2.0 - 0.5) = \mathbf{0.515\text{ s}}$；
  - $\text{p99.9}$ 对应秩 $r = 999 \times 0.999 = 998.001$，落在 $2.0\text{ s}$ 与 $20.0\text{ s}$ 之间，得 $2.0 + 0.001 \times (20.0 - 2.0) = \mathbf{2.018\text{ s}}$。

这组数字揭示了两个关键事实：第一，平均值 $0.533\text{ s}$ 甚至可以比 $\text{p99}$（$0.515\text{ s}$）更高，只看平均值既不代表大多数用户的 $0.5\text{ s}$ 体验，也掩盖了 $20\text{ s}$ 的灾难长尾；第二，分位数承诺的是**覆盖人群比例**（p50 只对一半用户负责，p95/p99 才对绝大多数用户负责），且直方图插值无法突破预设 `le` 桶边界的分辨率——若 p95 落在 `[0.5, 1.0]` 秒的宽桶内，就不该把插值后的三位小数当成精确测量。

### vLLM 四延迟分解链与核心面板映射表

一条推理请求的生命周期在 vLLM 指标体系中拆成清晰的分解链：

1. **首字延迟（TTFT）**：从 API 前端收到请求、开始分词计时，直到产出第一个输出 token。它在引擎核心内部可以继续拆成两段独立直方图：
    - **排队时间**（`vllm:request_queue_time_seconds`）：请求进入 EngineCore（`QUEUED`）到首次被调度器选中（`SCHEDULED`）；
    - **Prefill 时间**（`vllm:request_prefill_time_seconds`）：首次被调度到产出首 token（`NEW_TOKENS`）。
    - 例如排队 $0.5\text{ s}$、Prefill $0.3\text{ s}$，两者合占 $0.8\text{ s}$，与总 TTFT 的差值则落在前端分词与进程间通信开销上。
2. **解码阶段（TPOT 与 ITL）**：从第 1 个 token 到最后 1 个 token。
    - **TPOT（Time Per Output Token）**按**每条完成请求记一个样本**，反映单条请求解码阶段摊到每个后续 token 的平均耗时；
    - **ITL（Inter-Token Latency）**按**每次流式输出事件记一个样本**，直接刻画用户屏幕上相邻两次吐字的卡顿间隔。

$$
\text{TPOT} = \frac{\text{E2E} - \text{TTFT}}{N_{\text{out}} - 1}
$$

分母减 $1$ 是因为首 token 的生成时间已计入 TTFT。例如端到端 $10.5\text{ s}$、TTFT $0.5\text{ s}$、输出 $100$ 个 token，则 $\text{TPOT} = (10.5 - 0.5) / 99 \approx \mathbf{0.101\text{ s/tok}}$。

!!! warning "常见误区：混淆 ITL 与 TPOT，或跨工具直接比对 TPOT"
    即便每步只吐 1 个 token，ITL（按事件加权，长输出贡献样本多）与 TPOT（按请求加权，每条请求权重相等）的统计均值和分位数也可能不同；开启投机解码一次吐出多个 token 时，两者更会明显分叉。此外，对于只输出 1 个 token 的请求，分母 $N_{\text{out}} - 1 = 0$ 在数学上未定义——部分引擎直方图记作 0，而 `vllm bench serve` 会将其从统计中剔除。比对面板与压测工具读数时，务必先对齐口径。

同样需要明确区分的是**吞吐双单位**：**请求吞吐（req/s）**回答“系统每秒能服务多少并发用户”，**Token 吞吐（tok/s）**回答“GPU 每秒产出多少解码文本”。输出长度固定时两者只差一个常数倍，但切忌拿不同长度分布的业务直接比较 tok/s。

综合用户体验层与引擎状态层，一套干净、无废话的 vLLM 监控看板只需牢牢盯住以下 **9 个核心指标**：

| 指标维度 | 核心面板 | 推荐 PromQL 查询（5 分钟窗口示例） | 单位与解读要点 |
|---|---|---|---|
| **用户侧：TTFT** | 首 token 延迟 p95 | `histogram_quantile(0.95, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m])))` | 秒；升高时立刻查排队时间与 Prefill 时间 |
| **用户侧：TPOT** | 单请求每 token 耗时 p95 | `histogram_quantile(0.95, sum by (le) (rate(vllm:request_time_per_output_token_seconds_bucket[5m])))` | 秒/token；反映 Decode 吞吐与批大小压力 |
| **用户侧：ITL** | 流式吐字间隔 p95 | `histogram_quantile(0.95, sum by (le) (rate(vllm:inter_token_latency_seconds_bucket[5m])))` | 秒；捕捉长 Prefill 或抢占造成的瞬时卡顿 |
| **用户侧：E2E** | 端到端总延迟 p95 | `histogram_quantile(0.95, sum by (le) (rate(vllm:e2e_request_latency_seconds_bucket[5m])))` | 秒；与输出长度强相关，需结合长度看 |
| **用户侧：吞吐** | 生成 Token 吞吐 | `sum(rate(vllm:generation_tokens_total[5m]))` | token/s；看请求吞吐则对 `request_success_total` 求 rate |
| **引擎侧：运行/排队** | 队列深度 | `vllm:num_requests_running` 与 `vllm:num_requests_waiting` | 条；瞬时 Gauge（注意 vLLM V1 已移除 `_swapped`） |
| **引擎侧：排队耗时** | 引擎内排队时间 p95 | `histogram_quantile(0.95, sum by (le) (rate(vllm:request_queue_time_seconds_bucket[5m])))` | 秒；务必用 `_bucket` 算分位，勿用 `_sum` 速率 |
| **引擎侧：显存水位** | KV 缓存使用率 | `vllm:kv_cache_usage_perc` | `0–1` 比例（看板乘 100 显示百分比） |
| **引擎侧：完成与异常** | 按结束原因拆分的完成数 | `sum by (finished_reason) (increase(vllm:request_success_total[5m]))` | 条/窗口；区分 `stop`、`length` 与 `abort`（取消） |

## 7.2 Prometheus Pull 采集与看板验证原理

### Pull 拉取架构与三段排障法

Prometheus 采用**拉取（Pull）**而非推送（Push）架构：vLLM 进程不主动向外部发送任何监控包，只是在本地 HTTP 端口的 `/metrics` 路径持续维护最新指标快照；Prometheus 按配置的 `scrape_interval` 定期发起 `GET /metrics` 拉取并落盘为时间序列；Grafana 本身不存数据，只在打开面板时把 PromQL 发给 Prometheus 渲染曲线。

  <figcaption><span class="book-figure__label">图 7-1</span>按箭头反向即可构成最廉价的三段排障顺序：面板无数据时，先查 Prometheus Targets 是 UP 还是 DOWN，再查 vLLM <code>/metrics</code> 是否输出 <code>vllm:</code> 前缀，最后查 Grafana 数据源与标签变量。</figcaption>
</figure>

这种拉取式解耦让排障变得高度确定——遇到看板空白时，绝不要盲目乱改 Grafana 图表，按三段顺序倒查即可秒级定位：

1. **查引擎端点**：直接 `curl http://localhost:8000/metrics | grep vllm:`。若只有 Python 进程默认指标而没有 `vllm:` 行，问题在引擎启动参数或版本，与监控系统无关。
2. **查 Prometheus Targets**：打开 `:9090/targets` 确认目标状态是 `UP` 还是 `DOWN`。`DOWN` 说明端口写错、服务未起或容器网络不通（Linux 容器访问宿主机需配 `host-gateway`）。
3. **查 Grafana 查询与变量**：所有图一起空白，通常是数据源地址配错；仅单张图空白，通常是漏写了 **`vllm:` 前缀**、或面板自带的 `$model_name` 过滤变量未匹配。多模型共用一套 Prometheus 时，务必在查询里加上 `model_name="..."` 或按 `model_name` 分组，否则不同模型的延迟会被混成一个毫无意义的聚合分位数。

### 采样概率账：为什么用 5 个请求验证看板？

采集链路搭通后，最隐蔽的陷阱在于：**空闲服务的面板是一条平滑直线，而采集彻底断掉的面板同样是一条直线。** 把“看板真的活着”和“当前刚好没流量”分开的唯一办法，是打入一小批已知负载，看 Gauge、Counter、Histogram 三类面板是否按事前写好的预期幅度同步跳动。

但为什么验证时不能只发 1 条请求，而推荐在 5 秒抓取间隔下连发一小批请求？背后是一笔清晰的**采样概率账**：

- 抓取间隔 `scrape_interval` 是分辨率与存储成本的权衡：15 秒间隔每天抓 $86{,}400 / 15 = 5{,}760$ 次；缩短到 5 秒增至 $17{,}280$ 次（3 倍样本量）；拉长到 60 秒则仅 $1{,}440$ 次，任何持续半分钟以内的短尖峰都有一半概率完全漏采。
- 设默认 `scrape_interval = 15s`，一条短请求全程执行耗时仅 $2\text{ s}$。由于抓取时刻与请求到达相互独立，一次抓取恰好撞进这 2 秒窗口的概率只有 $2 / 15 \approx 13.3\%$——换言之，**单发 1 条请求有高达 86.7%（约 87%）的概率在 Gauge 面板上纹丝不动**！
- **验证的最佳做法**：并发发出 **5 条请求**（将 `num_requests_running`、KV 水位与 token 增量放大 5 倍，一眼就能核对是不是抓错了隔壁端口），并把验证期 `scrape_interval` 设为 **5 秒**、持续发送约 10–15 秒。这样既能保证至少命中 2 次清晰采样，又不会像猛灌 500 条请求那样把排队和抢占噪声混进最基本的链路冒烟测试里。

### 最小可复用配置与三类核心 PromQL 参考

一套可直接用于本地与集群验证的最小 `prometheus.yml` 配置如下：

```yaml
global:
  scrape_interval: 5s      # 压测与验证用 5s 捕捉秒级波动；长周期线上监控可按需放宽至 15s

scrape_configs:
  - job_name: vllm
    metrics_path: /metrics
    static_configs:
      - targets: ["host.docker.internal:8000"]
```

接入 Grafana 后，绝大多数业务监控面板都可以归结为三段核心 PromQL：

```promql
# 1. Gauge：观测此刻引擎活跃负载与排队水位
vllm:num_requests_running{model_name="meta-llama/Llama-3.1-8B-Instruct"}

# 2. Counter 速率：观测每秒生成 token 吞吐（rate 自动处理进程重启归零）
sum(rate(vllm:generation_tokens_total{model_name="meta-llama/Llama-3.1-8B-Instruct"}[5m]))

# 3. Histogram 分位数：观测过去 5 分钟 TTFT p95（务必确认窗口内 _count 增量足够大）
histogram_quantile(
  0.95,
  sum by (le) (rate(vllm:time_to_first_token_seconds_bucket{model_name="meta-llama/Llama-3.1-8B-Instruct"}[5m]))
)
```

读直方图分位数时还要养成核查样本量的习惯：如果过去 5 分钟只完成了 5 条请求（`_count` 增量仅 5），即便 `scrape_interval` 是 5 秒、抓取了 60 次，算出来的 p95 依然只是极小样本的粗略插值。要获得稳定的 p95/p99 尾延迟评估，每个评估窗口通常至少需要积累数百条完成请求。

## 7.3 从单点到曲线：容量扫描与拐点定位

### 为什么单点数字讲不清系统容量？

监控看板就位后，接下来要回答架构师最核心的问题：**这台机器在满足延迟 SLO 的前提下，最多能扛多大流量？**

只测某一个固定并发（例如“并发 64 下吞吐 44 req/s”）就像只给高速列车拍了一张静态照片——看不出轻载时有多快、重载时何时撞墙、撞墙后延迟恶化得多陡。标准的容量评估必须画出**从轻载到饱和的完整吞吐—延迟曲线**，由两端锚点与中间扫描共同构成：

1. **左端点（同步基线，Concurrency = 1）**：一次只发 1 条请求，等返回再发下一条。此时零排队、零抢占，测得的是单请求所能达到的理论最低延迟。基线本身就慢，问题在单次前向或算子；基线快但加并发就慢，问题在调度或 KV 容量。
2. **右端点（整批最大吞吐，Throughput Ceiling $T$）**：一次性下发大批量请求打满 GPU 并行度，探明无延迟约束下的物理吞吐上限 $T$。这个点延迟极高，仅用于标定上限而非线上容量。
3. **中间扫点（恒定到达速率或翻倍并发）**：按 $0.1T, 0.25T, 0.5T, 0.75T, 0.9T, 1.0T$（或并发 $1, 8, 16, 32, 64, 128$）扫出完整曲线；**先粗扫定位拐点区间，再仅在拐点区间内加密档位**，兼顾精度与压测时间成本。

在整个扫描过程中，第一条科学原则是**固定输入输出长度**（例如统一设为 512 token 输入 + 128 token 输出，共计 640 token）。因为输入长度决定 Prefill 计算量，输出长度决定 Decode 步数，两者之和决定单请求 KV 体积——只要长度浮动，延迟上涨就无法归因到并发调度还是“恰好来了一条长 Prompt”。

拿到任意一份容量扫描表，按以下三步解读，能立刻辨别数据真伪并锁定工作点：

1. **第一步：用 Little 定律验算自洽性**。在稳态系统和同一观测边界下，平均在途请求数 $L$、实际完成吞吐 $\lambda$ 与平均停留时间 $W$ 必然满足：

    $$
    L = \lambda \cdot W
    $$

    注意公式里必须是**平均延迟 $W$**（不能用 p95），且 $\lambda$ 与 $W$ 必须取自同一稳态窗口、同一统计边界（排除冷启动与网关外排队）。上表每一行都精确对平（如并发 32 时 $40.0 \times 0.800 = 32.0$，并发 64 时 $44.0 \times 1.455 = 64.02$）。若某份压测报告里 $\lambda W$ 严重偏离在途并发数，说明存在大量超时丢弃、未达稳态或统计口径错位。
2. **第二步：看边际增幅框定拐点**。并发从 $16 \to 32$ 时，吞吐大涨 $+25\%$，平均延迟涨 $+60\%$；从 $32 \to 64$ 时，吞吐增幅跌至 $+10\%$，平均延迟却暴涨 $+81.9\%$；从 $64 \to 128$ 时，吞吐几乎原地踏步（$+2.3\%$），平均延迟接近翻倍（$+95.5\%$）。可见**拐点牢牢落在并发 32–64 区间内**。随后只需在区间内加密 40、48、56 三档（假设收敛在 48 附近），线上留出波动余量把限流阈值定在 40 即可——压测并不需要把机器压崩，扫过拐点一两档看清饱和趋势就已足够。
3. **第三步：观察 p50 与 p95 的张口顺序**。拐点前（C=16），p95/p50 比值仅 $1.63$，所有请求体验接近；进入拐点（C=32→64），**p95 率先大幅张口**（比值跃至 $2.83$），说明队列效应开始逐步收紧；跨过拐点后 p50 也跟着陡然抬头，说明全员都在排队。如果某档并发下 p50 与 p95 突然同步垂直拉升，往往意味着撞上了硬墙（如 KV 池耗尽触发成片抢占）。

上线前做粗略 SLO 预估时，还可以用一条经验公式做量级校核：

$$
\text{E2E}_{p90} \approx \text{TTFT}_{p90} + \text{ITL}_{p90} \times N_{\text{out}}
$$

例如 $\text{TTFT}_{p90} = 0.6\text{ s}$、$\text{ITL}_{p90} = 0.05\text{ s}$、输出 100 token，则端到端 p90 约落在 $0.6 + 5.0 = 5.6\text{ s}$ 量级。它适合在正式压测前快速排除明显不达标的部署方案（精确值仍以完整扫描为准）。

### 典型压测命令与工具交叉验证排障法

工程中常用的两款标准化压测工具分别是 vLLM 自带的 `vllm bench serve` 与社区维护的 `GuideLLM`。在 A100 80GB 上针对 Llama-3.1-8B 固定 512 输入 / 128 输出工作点的典型调用如下：

```bash
# 方式一：vLLM 官方压测 CLI（固定输入/输出长度，扫描指定请求速率）
vllm bench serve \
  --backend vllm \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name random \
  --random-input-len 512 \
  --random-output-len 128 \
  --request-rate 16 \
  --num-prompts 500 \
  --ignore-eos

# 方式二：GuideLLM 自动完成同步基线 → 最大吞吐 → 恒定速率曲线扫描
guidellm benchmark \
  --target "http://localhost:8000" \
  --model "meta-llama/Llama-3.1-8B-Instruct" \
  --rate-type sweep \
  --data "prompt_tokens=512,output_tokens=128" \
  --max-seconds 120
```

当用两个独立工具在同一硬件、同一负载下交叉验证时，经常出现读数不完全重合的情况——例如 GuideLLM 报出 p95 为 `820 ms`，而 `vllm bench serve` 报出 `950 ms`，相对差距达 $(950 - 820)/820 \approx \mathbf{15.9\%}$。

!!! tip "核心直觉：工具不一致反而是最有价值的排障线索"
    千万不要为了报表好看去反复“调参把两个工具凑平”。先对同一工具连跑两遍测出固有波动基线（例如 $\pm 3\%$），确认 $15.9\%$ 是真信号后，按以下**六类常见原因**由浅入深逐一排查，往往能挖出隐藏极深的系统或配置偏差：
    1. **采样参数未对齐**：`temperature`、`top_p` 或是否开启 `--ignore-eos` 不同，导致实际生成的输出长度存在差异。
    2. **实际分词长度未对齐**：随机文本在不同 tokenizer 或聊天模板包裹下多出几十个特殊 token。
    3. **预热与稳态轮数不同**：一个工具把冷启动编译/首轮队列爬坡混进了统计，另一个只取稳态段。
    4. **负载注入模型不同**：一个是闭环固定并发（Fixed Concurrency），另一个是开环泊松/恒定到达速率（Constant Rate，更容易产生瞬时突发排队）。
    5. **客户端自身开销不同**：压测机在异步 HTTP 协程或 SSE 解析上成为瓶颈，把客户端耗时算进了服务端延迟。
    6. **时间戳与分位数口径不同**：首包计时位置、是否过滤 1-token 请求，以及分位数采用线性插值还是 nearest-rank。

排查时还有一个快捷判据：如果 p50、p95、p99 **同比例平移**，大概率是客户端开销或时间戳位置引起的系统性基线偏移；如果 p50 几乎一致、**仅 p95/p99 尾部张开或交叉**，则几乎一定是到达节奏差异、超时重试策略或偶发抢占造成的长尾分化。

## 7.4 过载边界与抢占机制

### 区分“客户端并发数”与“GPU 同时驻留序列数”

在容量评审会上最容易混淆的概念，是把“业务端有 1,000 个并发连接”直接等同于“GPU 上同时跑着 1,000 条序列、驻留着 1,000 份 KV”。事实恰恰相反：**小卡也能在排队队列里接住 1,000 个连接，大卡也可能在 50 并发时就已击穿延迟 SLO。**

算清 GPU 上真正能**同时驻留**多少条序列，只需回到[第 5 章](chapter-05.md)的显存账。在 **A100 80GB SXM**（扣除权重与工作区后，KV 池约 **56 GB / 52.2 GiB**）上，对比 Llama-3.1-8B 与 Qwen3-8B 在不同固定工作点下的最大常驻序列上界：

| 工作点（输入 + 输出总长） | Llama-3.1-8B 单请求 KV（128 KiB/tok） | A100 80GB KV 池常驻上界 | Qwen3-8B 单请求 KV（144 KiB/tok） | A100 80GB KV 池常驻上界 |
|---|---:|---:|---:|---:|
| **640 tok**（512 + 128） | 80 MiB | 约 **668 条** | 90 MiB | 约 **594 条** |
| **2,560 tok**（2048 + 512） | 320 MiB | 约 **167 条** | 360 MiB | 约 **148 条** |
| **8,192 tok**（8K 长上下文） | 1.00 GiB | 约 **52 条** | 1.125 GiB | 约 **46 条** |
| **32,768 tok**（32K 超长上下文） | 4.00 GiB | 约 **13 条** | 4.50 GiB | 约 **11 条** |

这张表一语道破本质：

$$
N_{\text{resident, max}} = \min\!\left(\left\lfloor \frac{\text{KV Pool Size}}{\text{KV per Request}} \right\rfloor,\ \text{max\_num\_seqs}\right)
$$

在 8K 上下文业务中，即便客户端同时涌来 1,000 条请求，单张 A100 80GB 上最多也只有约 **52 条**（Llama-3.1-8B）在 GPU 里真正驻留并持有物理 KV 块，其余约 **948 条**全部安静地躺在 `vllm:num_requests_waiting` 队列里等待准入。决定需要采购几张卡的，是**目标驻留量、计算吞吐与延迟 SLO**，绝不是拍脑袋看一眼“客户端并发 1,000”。

### 过载下的排队论直觉：延迟不再是系统属性

当外部到达速率 $\lambda$ 持续高于系统的最大稳态服务吞吐 $\mu$ 时，排队论给出了一个铁律：**队列深度随时间无界增长，请求延迟也随之无界增长。**

举个直观的算例：设单卡最大处理能力 $\mu = 10\text{ req/s}$，外部恒定以 $\lambda = 12\text{ req/s}$ 灌入流量（每秒净积压 2 条请求）：

- 持续压测 **30 秒**：队尾积压 $(12 - 10) \times 30 = 60$ 条请求，新来请求的排队等待约 **$6\text{ s}$**；
- 持续压测 **120 秒**：队尾积压 240 条，排队等待膨胀至 **$24\text{ s}$**；
- 持续压测 **600 秒**：队尾积压 1,200 条，排队等待飙升至 **$120\text{ s}$**。

此时测得的 p95 延迟根本不是系统本身的固有性能，而是**压测持续时间与积压存量的函数**！如果在 60 秒时强行截断测试并丢弃未完成请求，会产生严重的幸存者偏差；如果等排空，队尾请求又会把 p95 拉上天。因此，容量评估必须严格区分**稳态 SLO 容量**（到达与完成速率平衡、延迟与错误率均达标的最高速率）与**过载退化观测**（保留完整超时、取消、队列积压记录用于检验限流与熔断策略，绝不把过载窗口伪装成稳态容量，也不删掉难看的坏点）。

### 三信号联动诊断系统健康边界

线上服务逼近过载边界时，单看任何一个监控指标都会产生误判。必须把 **KV 缓存水位**、**排队深度**与**抢占计数器**三个信号放在同一时间轴上联动观察：

| `vllm:kv_cache_usage_perc` | `vllm:num_requests_waiting` | `vllm:num_preemptions_total`（增量） | 系统状态与根因诊断 | 推荐工程动作 |
|---|---|---|---|---|
| $< 75\%$ | 持续为 0 | 0 | **健康轻载区**：算力与显存均有余量 | 可安全承接更高并发 |
| $< 75\%$ | 波动抬升 | 0 | **算力或序列数上限受限**：多为长 Prompt Prefill 占满 token 预算或撞上 `max_num_seqs` | 检查 `max_num_batched_tokens`、Chunked Prefill 与前缀复用率 |
| $85\%\text{–}95\%$ | 持续攀升 | 0 | **显存临近满载但调度可控**：调度器主动拦在队外排队，尚未被迫驱逐在跑请求 | 接近稳态上限；开启入口限流（Admission Control）保护已有流量 |
| $> 95\%$（高频贴顶） | 持续积压 | **持续跳升（$> 0$）** | **显存过载重算区**：已准入请求不断变长挤爆 KV 池，引擎反复丢弃 KV 并触发 Recompute，有效吞吐反而倒退 | 立刻下调并发/最大上下文、启用[第 8 章](chapter-08.md)权重或 KV 量化，或横向扩容 |

!!! note "诊断铁律"
    `kv_cache_usage_perc` 冲到 90% 只说明块池用了九成，`num_requests_waiting` 升高只说明请求在排队——**两者都不能单独证明发生了抢占**。确认系统是否陷入昂贵的重算死循环，必须以 `vllm:num_preemptions_total` 计数器的非零增量或引擎日志中的 `PREEMPTED` 事件为直接证据。
