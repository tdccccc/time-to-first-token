# 第 9 章 投机解码与长上下文 KV 淘汰 { .chapter-title }

<p class="chapter-summary">投机解码借 Decode 带宽受限时的空闲算力“批量验牌”，用数学上严格无损的拒绝采样换取低并发 2–3× 加速；长上下文 KV 淘汰则借 Attention Sink 稳住 Softmax 概率质量，以有损遗忘远端信息为代价锁死显存与单步读量。</p>

自回归解码慢在“步步串行”，长上下文解码重在“KV 越滚越大”。第 1 章的 [Roofline 分析](chapter-01.md)已经指出：单请求解码绝大多数时间都在等 HBM 搬运权重与 KV 缓存，Tensor Core 算力几乎完全空转。本章从两个正交方向切入这一瓶颈——**投机解码（Speculative Decoding）**把空闲算力变现为单轮多 token 产出，**KV 淘汰（KV Eviction）**把随序列线性膨胀的 KV 缓存压回常数级——同时划清两者的数学保证与工程边界。

## 9.1 投机解码的核心直觉：借空闲算力“一次验多张牌”

### 痛点：自回归锁死与 99% 空转的 Tensor Core

以 **NVIDIA A100 80GB SXM**（FP16 Tensor Core 稠密峰值 312 TFLOPS，HBM2e 带宽 2 TB/s，脊点 156 FLOP/B）运行 **Llama-3.1-8B（FP16）** 为例。模型参数量 $N \approx 8.03\text{B}$，权重体积 $W \approx 16.06\text{ GB}$。在 `batch=1` 的单请求 Decode 阶段，每生成 1 个 token 需要把整份权重从 HBM 读进片上，而每个权重仅参与一次乘加（2 FLOP）：

- **权重搬运下界**：$16.06\text{ GB} \div 2\text{ TB/s} \approx 8.03\text{ ms}$
- **纯计算下界**：$2 \times 8.03 \times 10^9\text{ FLOP} \div 312\text{ TFLOPS} \approx 0.051\text{ ms}$

计算耗时不到搬运耗时的 $0.7\%$。换言之，每吐一个字，GPU 都在花 8 毫秒从显存搬砖，然后用 0.05 毫秒干完活，剩下 99% 以上的计算周期全部白白浪费。更棘手的是，由于下一个 token 的输入依赖上一个 token 的采样结果，标准自回归无法靠“提前把后面 4 个字一起算了”来并行——至少在还没猜出后面几个字之前不能。

### 直觉突破：为什么“猜 4 个、一次验证”几乎免费？

传统自回归就像一位挑剔的食客点菜：点一道、厨师进冷库搬 16 GB 食材做一道、吃完再点下一道。**投机解码**换了一种协作方式：先派一个动作飞快的“学徒”（草稿模型，Draft Model）根据当前上文一口气猜出 $\gamma$ 个候选 token（例如 $\gamma = 4$，记作 $d_1, d_2, d_3, d_4$），再把整段草稿一次性交给“主厨”（目标模型，Target Model）做并行审查。

为什么目标模型能**一次前向**就把 $\gamma$ 个草稿全部验证完？关键在于**草稿已经把候选 token 写在纸上了**。在验证前向中，第 2 个位置不需要苦等第 1 个位置的采样结果，因为 $d_1$ 已经给定；第 3 个位置的输入 $d_2$ 也已经给定。目标模型只需把已知上下文拼上 $[d_1, d_2, \dots, d_\gamma]$，当作一次微型的 Prefill，借助因果注意力掩码（Causal Mask）一次前向并行算出全部 $\gamma + 1$ 个位置的词表概率分布 $p_1, p_2, \dots, p_{\gamma+1}$：

- **权重仍只读一遍**：依然是 $16.06\text{ GB}$，HBM 搬运时间保持 $8.03\text{ ms}$ 不变；
- **算术强度跃升 $(\gamma + 1)$ 倍**：从 GEMV（矩阵乘向量）变成小规模 GEMM（矩阵乘矩阵）。$\gamma = 4$ 时需算 5 个位置，计算量升至 $5 \times 16.06 = 80.3\text{ GFLOP}$，在 A100 上耗时仅 $0.257\text{ ms}$，依然远远藏在 $8.03\text{ ms}$ 的权重搬运地板之下！

!!! tip "核心直觉"
    投机解码的本质是**用冗余算力换串行步数**。只要 GPU 还处在 Roofline 脊点左侧的带宽受限区，目标模型“验 1 个字”和“验 5 个字”花的时间几乎一样；只要草稿足够便宜且猜得够准，每读一遍大模型权重就能收获 2–4 个经大模型盖章认可的 token。

## 9.2 无损拒绝采样的数学魔法与四角色流水

直觉听起来很美，但一个严肃的问题立刻浮现：草稿模型能力远弱于目标模型，用它的输出当候选，会不会悄悄拉低生成质量、改变大模型的概率分布？

答案是**不会**。Leviathan 等人与 Chen 等人在 2023 年独立提出的**修改拒绝采样（Modified Rejection Sampling）**机制证明：只要按特定规则接收与修补，投机解码最终吐出的每一个 token，其概率分布**在数学上严格等于**目标模型独立采样的分布 $p(x)$（工程实现中仅存在微小的浮点舍入差异，不存在统计分布偏移）。

### 两条规则与一个彩蛋：严格无损的判定律

记当前位置目标模型给出的词表概率分布为 $p(\cdot)$，草稿模型实际用于采样的概率分布为 $q(\cdot)$，草稿模型从中采出的候选 token 为 $x \sim q(\cdot)$。验证器按以下三步执行：

1. **接受判定**：以概率 $a(x)$ 接受候选 $x$：

$$a(x) = \min\!\left(1, \frac{p(x)}{q(x)}\right)$$

若 $p(x) \ge q(x)$（目标模型比草稿更认可 $x$），则 $100\%$ 接受；若 $p(x) < q(x)$（草稿过于乐观），则只按比值 $p(x)/q(x)$ 放行，把草稿“多猜出来”的概率扣掉。

2. **残差重采样**：一旦 $x$ 在某个位置被拒绝，立即丢弃该位置及之后的所有草稿，并从**归一化残差分布** $p'(x)$ 中重新采样一个替代 token：

$$p'(x) = \frac{\max(p(x) - q(x), 0)}{\sum_{y} \max(p(y) - q(y), 0)}$$

3. **全中彩蛋（Bonus Token）**：如果全部 $\gamma$ 个草稿均通过检验，目标模型在一次验证前向中已经顺手算出了第 $\gamma + 1$ 个位置的分布 $p_{\gamma+1}(\cdot)$，直接从中再采出 1 个免费 token。因此，一轮投机解码**最少产出 1 个 token**（首字即拒但残差重采样产 1 个），**最多产出 $\gamma + 1$ 个 token**。

### 手算 3-Token 词表：亲眼见证分布严格守恒

纸上抽象公式容易发虚，我们用一个简单的 3-token 词表 $\{A, B, C\}$ 手算一遍。设目标模型分布为 $p = (0.50, 0.30, 0.20)$，草稿模型分布为 $q = (0.80, 0.15, 0.05)$——草稿过度看好 $A$，同时低估了 $B$ 和 $C$。

| Token $x$ | 目标 $p(x)$ | 草稿 $q(x)$ | 接受概率 $a(x)=\min(1, p/q)$ | 直接接受概率 $q(x)a(x)$ | 拒绝概率 $q(x)(1-a(x))$ | 未归一化残差 $\max(p-q, 0)$ | 残差分布 $p'(x)$ | 最终输出概率 $P(\text{out}=x)$ |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| $A$ | 0.50 | 0.80 | $0.50/0.80 = 0.625$ | 0.50 | 0.30 | 0.00 | 0.00 | $0.50 + 0.30 \times 0.00 = \mathbf{0.50}$ |
| $B$ | 0.30 | 0.15 | $1.000$ | 0.15 | 0.00 | 0.15 | 0.50 | $0.15 + 0.30 \times 0.50 = \mathbf{0.30}$ |
| $C$ | 0.20 | 0.05 | $1.000$ | 0.05 | 0.00 | 0.15 | 0.50 | $0.05 + 0.30 \times 0.50 = \mathbf{0.20}$ |
| **合计** | **1.00** | **1.00** | — | **0.70** | **0.30** | **0.30** | **1.00** | **1.00** |

请留意表中一个极其优雅的巧合（也是必然的恒等式）：总拒绝概率 $P(\text{reject}) = 0.30$，**恰好等于**未归一化残差之和 $\sum_y \max(p(y) - q(y), 0) = 0.15 + 0.15 = 0.30$！对任意词表，把“直接接受”与“拒绝后重采样”两条路径相加，分母恰好约掉：

$$P(\text{out} = x) = q(x)\min\!\left(1, \frac{p(x)}{q(x)}\right) + P(\text{reject}) \cdot \frac{\max(p(x) - q(x), 0)}{P(\text{reject})}$$

$$P(\text{out} = x) = \min(p(x), q(x)) + \max(p(x) - q(x), 0) = p(x)$$

这三行代数就是投机解码无损性的全部秘密：草稿多猜的那部分概率（如 $A$ 溢出的 $0.30$），被拒绝采样精准“没收”，再按每个被低估词的缺口比例（$B$ 缺 $0.15$、$C$ 缺 $0.15$，各分一半）精准补偿回去。

!!! warning "常见误区：拒绝后绝不能直接从 $p(x)$ 重采样"
    若在上面的 3-token 例子里，拒绝 $A$ 之后偷懒直接从目标分布 $p(x)$ 重采样，那么 $A$ 还有 $0.50$ 的概率被再次抽中，最终 $P(\text{out}=A) = 0.50 + 0.30 \times 0.50 = 0.65 \neq 0.50$，分布立刻被破坏。同样地，验证器必须使用草稿模型**实际起草时的温度与 top-p 后分布 $q$**，不能拿未过滤的原始 logits 顶替。

### 引擎内的四角色流水与 KV Rollback

在 vLLM、SGLang 等生产引擎中，一轮投机解码被清晰拆分为四个逻辑角色（注意：物理上最多只有目标模型与草稿模型两个权重集合，不可将角色数与模型数混淆）：

1. **Proposer（提议器）**：驱动草稿执行器（或 N-gram 查表、EAGLE 轻量草稿头）连续提出 $\gamma$ 个候选 token，并保存对应的起草概率分布 $q_1, \dots, q_\gamma$。若采用独立草稿模型，还需在同卡显存中维护草稿模型的权重与独立 KV 缓存。
2. **Scorer（打分器）**：调用目标模型对“上一轮确认的末尾 token + $\gamma$ 个草稿 token”执行**单次前向**，并行产出 $\gamma + 1$ 组目标分布 $p_1, \dots, p_{\gamma+1}$，同时顺手写入这批候选对应的目标 KV 块。
3. **Verifier（验证器）**：纯计算逻辑，逐位比对 $p_i$ 与 $q_i$ 执行拒绝采样，确定本轮连续接受长度 $k \in \{0, 1, \dots, \gamma\}$，并在第 $k + 1$ 位产出修正 token（或全接受时的 bonus token）。
4. **KV Rollback（状态回滚）**：若草稿在第 $k + 1$ 位被拒，说明 Scorer 刚刚写入的第 $k + 1 \dots \gamma$ 位草稿 KV 已经作废，且草稿模型自身多推演的 KV 也已偏离主线。引擎必须把目标与草稿两套 KV 的逻辑序列长度指针回退到有效边界，释放多余物理槽位，确保下一轮注意力计算不被脏 KV 污染。

下面的纯 Python 核心函数完整浓缩了单轮验证、残差重采样与截断长度计算：

```python
import random
from typing import Sequence


def speculative_verify_step(
    draft_tokens: Sequence[int],
    draft_probs: Sequence[Sequence[float]],
    target_probs: Sequence[Sequence[float]],
    rng: random.Random | None = None,
) -> tuple[list[int], int]:
    """执行单轮无损拒绝采样验证。

    参数:
        draft_tokens: 长度为 gamma 的草稿 token ID 序列
        draft_probs:  长度为 gamma 的草稿概率分布列表 q_1..q_gamma
        target_probs: 长度为 gamma + 1 的目标概率分布列表 p_1..p_{gamma+1}
    返回:
        (accepted_and_next_tokens, num_accepted_drafts)
    """
    gen = rng or random.Random()
    gamma = len(draft_tokens)
    output_tokens: list[int] = []

    for i in range(gamma):
        tok = draft_tokens[i]
        p_i = target_probs[i]
        q_i = draft_probs[i]
        q_val = max(q_i[tok], 1e-12)
        accept_prob = min(1.0, p_i[tok] / q_val)

        if gen.random() < accept_prob:
            output_tokens.append(tok)
        else:
            # 拒绝：从归一化残差分布 max(p - q, 0) 重采样替代 token，并截断后续草稿
            residual = [max(pv - qv, 0.0) for pv, qv in zip(p_i, q_i)]
            total_res = sum(residual)
            if total_res > 0.0:
                weights = [r / total_res for r in residual]
            else:
                weights = list(p_i)
            replacement = gen.choices(range(len(p_i)), weights=weights, k=1)[0]
            output_tokens.append(replacement)
            return output_tokens, i

    # 全部 gamma 个草稿均被接受，从第 gamma + 1 个目标分布采样 bonus token
    p_bonus = target_probs[gamma]
    bonus = gen.choices(range(len(p_bonus)), weights=p_bonus, k=1)[0]
    output_tokens.append(bonus)
    return output_tokens, gamma
```

## 9.3 收益模型、方法选择与 QPS 交叉点

理解了无损机制，下一个工程核心问题是：**投机解码到底能快多少？什么情况下反而会变慢？**

### 等比期望产出与净加速比模型

假设草稿序列中，在前 $k-1$ 个候选全部被接受的条件下，第 $k$ 个位置继续被接受的**条件接受概率**恒为 $\alpha \in (0, 1)$。每轮保底产出 1 个 token，多产出第 $k$ 个额外 token 要求前 $k$ 个草稿全过关（概率 $\alpha^k$）。把 $k = 0 \dots \gamma$ 求和，得到每轮期望产出 token 数（含 bonus token）：

$$E(\alpha, \gamma) = 1 + \alpha + \alpha^2 + \dots + \alpha^\gamma = \frac{1 - \alpha^{\gamma+1}}{1 - \alpha}$$

产出变多了，但起草不是免费的。将目标模型一次前向（验证 $\gamma + 1$ 个位置）的耗时归一化为 $1$（在低并发带宽受限区近似等于普通单步 Decode 耗时 $T_d$），设草稿单步起草耗时为目标单步的 $c$ 倍（$c = T_{\text{draft}} / T_{\text{target}}$）。则一轮耗费 $1 + \gamma c$ 个目标前向当量，净加速比为：

$$\text{Speedup}(\alpha, \gamma, c) = \frac{E(\alpha, \gamma)}{1 + \gamma c} = \frac{1 - \alpha^{\gamma+1}}{(1 - \alpha)(1 + \gamma c)}$$

盈亏平衡条件为 $E(\alpha, \gamma) > 1 + \gamma c$。取典型轻量草稿成本 $c = 0.1$（草稿单步仅为大模型 $1/10$），不同接受率 $\alpha$ 与草稿长度 $\gamma$ 下的期望产出与净加速比如下表所示：

| 条件接受率 $\alpha$ | $\gamma=2$ 期望 $E$ / 加速比 | $\gamma=4$ 期望 $E$ / 加速比 | $\gamma=8$ 期望 $E$ / 加速比 | 最优 $\gamma^*$（$c=0.1$） | 最优加速比 |
|---:|---:|---:|---:|---:|---:|
| 0.30 | 1.39 / **1.16×** | 1.43 / **1.02×** | 1.43 / **0.79×** | 1 | 1.18× |
| 0.50 | 1.75 / **1.46×** | 1.94 / **1.38×** | 2.00 / **1.11×** | 2 | 1.46× |
| 0.60 | 1.96 / **1.63×** | 2.31 / **1.65×** | 2.47 / **1.37×** | 3 | 1.67× |
| 0.70 | 2.19 / **1.82×** | 2.77 / **1.98×** | 3.20 / **1.78×** | 4 | 1.98× |
| 0.80 | 2.44 / **2.03×** | 3.36 / **2.40×** | 4.33 / **2.40×** | 6 | 2.47× |
| 0.90 | 2.71 / **2.26×** | 4.10 / **2.93×** | 6.13 / **3.40×** | 10 | 3.43× |

这张表揭示了三条立即可用的工程规律：

1. **$\alpha$ 的权重远大于 $c$**：$\gamma=4, c=0.1$ 时，盈亏平衡点在 $\alpha \approx 0.287$；当 $\alpha$ 从 0.50 升到 0.80，净加速比直接从 1.38× 跃升到 2.40×。选草稿模型切忌盲目求小——跨系列、分布偏差大的超小草稿即使 $c$ 极低，一旦 $\alpha$ 塌陷，速度反而倒退。
2. **$\gamma$ 绝非越长越好**：$\alpha = 0.50$ 时，$\gamma$ 从 2 拉长到 4，期望产出仅多 0.19 个 token，却白付了 2 步草稿前向，加速比从 1.46× 掉到 1.38×；拉到 $\gamma = 8$ 更跌至 1.11×。最优 $\gamma^*$ 随 $\alpha$ 单调上升。
3. **严格区分条件概率 $\alpha$ 与实验观测比例 $\beta$**：线上监控（如 vLLM V1 `metrics.py`）暴露的是三个累计计数器——被接受草稿总数 $A$、提出草稿总数 $D$ 与起草轮数 $R$。直接相除得到的经验接受比例 $\beta = A / D$ **不是**等比公式里的条件接受概率 $\alpha$！实际平均每轮接受长度（含 bonus）应按 $E_{\text{obs}} = 1 + A / R$ 计算（固定 $\gamma$ 时 $D = \gamma R$，即 $E_{\text{obs}} = 1 + \gamma\beta$）。举例来说，$\gamma=4, \alpha=0.80$ 时 $E = 3.3616$，对应观测比例 $\beta = (3.3616 - 1)/4 = 0.5904$；若误把 $0.5904$ 当作 $\alpha$ 代回几何公式，会算出大错特错的 $2.2663$！

### 四大起草方法全景对比

起草器如何在“高接受率 $\alpha$”与“低起草成本 $c$”之间寻找平衡，催生了四条主流技术路线（此外，DeepSeek-V3 / Qwen3-Next 等模型还在预训练阶段引入原生多 token 预测头 MTP，参见[专题 A](../topics/advanced-architectures.md)）：

| 起草方法 | 核心起草原理 | 额外显存与 KV 开销 | 是否需额外训练 | 典型接受率与成本 $c$ | 严格无损性 | 适用负载与典型引擎支持 |
|---|---|---|---|---|---|---|
| **独立小模型（Draft Model）** | 同家族小尺寸模型自回归起草（如 Llama-3.2-1B 配 Llama-3.1-8B/70B） | 高：需常驻草稿权重 + 独立草稿 KV 缓存 | 否（直接复用同族小模型，要求共用词表） | $\alpha$ 中高（0.6–0.8），$c$ 中等（约 0.08–0.15） | 严格无损 | 通用对话、代码；vLLM / SGLang / TensorRT-LLM 均支持 |
| **N-gram / 后缀匹配（Prompt Lookup）** | 在 Prompt 与历史输出中做 N-gram / 后缀树精确检索匹配 | 极低：无额外模型权重与 KV | 否（零训练、开箱即用） | $c \approx 0$；$\alpha$ 高度依赖文本重复度 | 严格无损 | 摘要、RAG 摘录、代码编辑、多轮改写；vLLM / SGLang 支持 |
| **Medusa（多头并行草稿）** | 在目标模型顶层隐藏态上挂载 $k$ 个轻量 MLP 预测头，一次前向并行预测后 $k$ 位，并用树状注意力验证 | 较低：仅增加数个轻量投影头，无独立 KV | 是（需冻结底座微调 Medusa 头） | $c$ 极低；头间相互独立，越往后 $\alpha$ 衰减越快 | 树验证配合拒绝采样可无损（启发式阈值版有损） | 单卡低显存余量场景；vLLM / TensorRT-LLM 支持 |
| **EAGLE-2 / EAGLE-3（特征级自回归）** | 复用目标模型高层（EAGLE-3 融合多层）隐藏特征与已选 token，经单层轻量解码器自回归起草并构建动态草稿树 | 极低：仅约单层 Transformer 权重，无需完整独立 KV | 是（轻量特征草稿头，开源社区已有主流模型现成权重） | $\alpha$ 最高（常见 0.75–0.90+），$c$ 极低（约 0.03–0.06） | 严格无损 | 当前综合收益最高，适配对话/代码/推理；vLLM / SGLang / TensorRT-LLM 主推 |

### 为什么高 QPS 下反而变慢？——Roofline 交叉点

投机解码有一个著名的“反直觉”工程现象：vLLM 团队在 4×H100 上评测 Llama-3-70B 时曾观测到，低并发（QPS = 1）下 N-gram 摘要负载提速最高达 **2.8×**、小草稿模型对话负载提速 **1.5×**；可一旦把 QPS 拉高，同一套配置不仅不再提速，反而比关闭投机**慢 1.4–1.8×**。

原因完全写在 Roofline 上。回到 **A100 80GB + Llama-3.1-8B（FP16）** 的算术账：

- 权重读取地板恒为 $8.03\text{ ms}$（仅看权重搬运），脊点为 $156\text{ FLOP/B}$；
- `batch = 1`、$\gamma = 4$：验证每步算 $1 \times 5 = 5$ 个 token，计算耗时仅 $0.257\text{ ms} \ll 8.03\text{ ms}$，多算的 4 个草稿位置完全藏在空闲算力里，近乎免费；
- 当 QPS 上升、并发 `batch = 32` 且 $\gamma = 4$：每轮验证的等效 token 数瞬间膨胀到 $32 \times 5 = 160$，**直接越过 A100 156 FLOP/B 的脊点**！此时仅计算耗时就达 $160 \times 0.0515\text{ ms} = \mathbf{8.24\text{ ms}} > 8.03\text{ ms}$，GPU 从带宽受限区翻入**计算受限区**！

一旦越过脊点，验证多出来的 $\gamma$ 个位置不再免费，而是与正常并发请求真刀真枪地抢夺 Tensor Core 算力——更糟的是，**每一个被拒绝的草稿 token 消耗的算力都彻底打了水漂**。除此之外，高并发下的草稿前向排队、草稿 KV 挤占显存（缩小可用最大 batch）也会进一步拉低有效吞吐。

!!! note "工程取舍：围绕交叉点做动态决策"
    不要被“最高 2.8×”的离线单并发头条数字迷惑。投机解码的真正定位是**低/中并发下的延迟加速器（压低 TPOT）**，而非高满载集群的吞吐万能药。生产部署中，若集群昼夜流量峰谷悬殊，应启用引擎的**动态投机（Dynamic Speculative Decoding）**或按实时并发深度阈值自动缩减 $\gamma$ 乃至关闭投机：低谷期开足 $\gamma$ 压榨极速响应，高峰期自动退回标准连续批处理保护吞吐。同时注意，调节 `temperature` 与 `top_p` 时，接受率取决于目标与草稿分布的重叠度，未必随温度单调下降，上线前应按固定采样参数实测自身负载的 QPS 交叉区间。

## 9.4 长上下文 KV 淘汰与 Attention Sink

如果说投机解码解决的是“权重读太多次”，那么长上下文场景里真正把推理拖入泥潭的是另一座大山：**随序列长度 $L$ 线性膨胀的 KV 缓存**。

### 痛点：长上下文 KV 膨胀与滑动窗口的突然崩溃

仍以 **Llama-3.1-8B（FP16，32 层，8 个 KV 头，头维 128）** 为例，每 token 的 KV 占用为：

$$k = 2 \times 32 \times 8 \times 128 \times 2\text{ B} = 131,072\text{ B} = 128\text{ KiB}$$

（若换成 **Qwen3-8B** 的 36 层结构，则为 $144\text{ KiB/token}$；若换成无 GQA 的传统 MHA 模型，更会直接放大 4 倍至 $512\text{ KiB/token}$。）当单条会话推进到 128K token 时，仅**单条请求**的 KV 缓存就高达 $128\text{K} \times 128\text{ KiB} = \mathbf{16\text{ GiB}}$（17.18 GB），已经超过模型本身 16.06 GB 的 FP16 权重！在 A100 80GB（2 TB/s）上做 `batch = 1` Decode，权重与 KV 共用同一条 HBM 通道，搬运量**必须相加**（绝不可各自取 $\max$）：

$$t_{\text{step}} \ge \frac{W + \text{KV}}{2\text{ TB/s}} = \frac{16.06\text{ GB} + 17.18\text{ GB}}{2\text{ TB/s}} = \mathbf{16.62\text{ ms}}$$

一半以上的时间不再花在读权重，而是花在反复搬运 16 GiB 的历史 KV。

最直觉的压缩思路是**朴素滑动窗口（Sliding Window）**：只保留最近 $W$ 个 token 的 KV，把更早的统统踢出显存。然而工程师很快撞上一堵诡异的墙——只要对话长度还在 $W$ 以内，模型对答如流；一旦长度刚越过 $W$、**把开头第 0–3 个 token 踢出缓存的那一瞬间，模型的困惑度（PPL）会断崖式暴涨，输出立刻退化为乱码**！

### StreamingLLM 的发现：Attention Sink 与缓存内位置重排

Xiao 等人在 ICLR 2024 的 **StreamingLLM** 论文中揭开了这个谜团的底层机理：根源在于 Softmax 的归一化约束：

$$\sum_{j=0}^{t} \alpha_{t, j} = 1, \qquad \alpha_{t, j} = \frac{\exp(q_t^\top k_j / \sqrt{d})}{\sum_{m=0}^{t} \exp(q_t^\top k_m / \sqrt{d})}$$

注意力权重之和必须严格等于 $1$。但在大量注意力头和生成步中，当前 Query 其实并不需要重点关注历史里的任何具体语义词，可 Softmax 不允许把所有权重都设为 0，这些无处安放的概率质量必须找一个“泄洪口”倾倒。在自回归预训练期间，**序列开头的几个 token（如 BOS 与前 1–3 个 token）是全序列中唯一对所有后续位置永远可见的 token**。模型自然演化出一种稳定的内部习惯：把这几个开头 token 的 Key 训练得容易承接多余的注意力分数，同时让它们的 Value 几乎不干扰语义输出——这就是 **注意力汇（Attention Sink）**。

一旦朴素滑动窗口把 $T_0 \dots T_3$ 踢出缓存，“泄洪口”瞬间消失。Softmax 被迫把原本属于汇的巨量冗余权重泼洒到窗口内正常的近期语义 token 上，导致它们的 Value 被严重过度加权，隐藏表征彻底污染。

StreamingLLM 给出的解法出奇简洁，但包含**两个缺一不可的关键机制**：

1. **永久保留开头 $S$ 个 Attention Sink + 最近 $W$ 个滑动窗口 token**（典型配置如 $S = 4$），丢弃中间的 $T_4 \dots T_{t-W}$，把总 KV 显存锁死在常数 $O(S + W)$；
2. **缓存内连续相对位置 RoPE 重排**：这是实现中最容易踩坑的一步！假如当前保留的原始位置索引是 $[0, 1, 2, 3, 100, 101, 102, 103]$，中间已经存在 $\Delta = 97$ 的巨大断层；如果直接拿原始绝对位置做 RoPE 旋转，不仅断层会破坏局部注意力模式，随着流式生成突破预训练上下文长度，位置编码还会直接外推崩溃。StreamingLLM 要求在计算注意力时**按缓存内的连续槽位索引 $[0, 1, 2, 3, 4, 5, 6, 7]$ 重新赋予相对位置**——工程上通常在 KV 缓存中保存旋转前的 $K$（或对窗口内保留的 $K$ 施加等价的相对旋转偏移），确保任意时刻模型看到的相对距离永远落在 $[0, S + W - 1]$ 的安全训练窗内。

### 显存、TPOT 与 TTFT 收益账本

以 **Llama-3.1-8B（FP16，128 KiB/token）** 在 **A100 80GB（2 TB/s）** 单请求解码为例，对照全量 KV 与 StreamingLLM 两种窗口配置的资源账本：

| 上下文长度 | KV 保留策略 | 保留 token 数 | KV 显存占用 | 单步总搬运（权重 + KV） | 单步搬运下界（TPOT 地板） | 对 TTFT 的影响 |
|---|---|---:|---:|---:|---:|---|
| 32K | 全量 KV | 32,768 | 4.00 GiB（4.29 GB） | 20.36 GB | 10.18 ms | 基准 |
| 32K | Sink 4 + 窗口 2048 | 2,052 | 0.25 GiB（0.27 GB） | 16.33 GB | 8.16 ms | 标准全注意力 Prefill 下基本不变 |
| 32K | Sink 4 + 窗口 8192 | 8,196 | 1.00 GiB（1.07 GB） | 17.13 GB | 8.57 ms | 标准全注意力 Prefill 下基本不变 |
| 128K | 全量 KV | 131,072 | 16.00 GiB（17.18 GB） | 33.24 GB | 16.62 ms | 随长度超线性增长（Attention $O(L^2)$） |
| 128K | Sink 4 + 窗口 2048 | 2,052 | 0.25 GiB（0.27 GB） | 16.33 GB | 8.16 ms | 标准全注意力 Prefill 下基本不变 |
| 128K | Sink 4 + 窗口 8192 | 8,196 | 1.00 GiB（1.07 GB） | 17.13 GB | 8.57 ms | 标准全注意力 Prefill 下基本不变 |

表格中有一个极易被忽视的架构事实：**为什么开了 KV 淘汰，TTFT 却几乎纹丝不动？** 因为 TTFT 主要由 Prefill 决定——在标准全注意力 Prefill 下，引擎依然要把整段长 Prompt 从头到尾算完（其中 Attention 计算量随长度平方增长，128K 的 Attention FLOPs 是 32K 的 16 倍），淘汰动作只决定了**算完之后把哪些 KV 留进显存给 Decode 用**。淘汰真正省下来的是 **KV 显存容量**（128K 下缩小 64 倍，释放出巨大并发空间）与 **Decode 每步搬运量（TPOT）**。只有当引擎同时将 Prefill 也改为分块流式喂入或局部窗口注意力时，TTFT 才会显著下降。

### 无损压缩 vs 有损淘汰：选型边界全景表

在真实系统中，切勿把 KV 淘汰与无损显存优化混为一谈。下表梳理了主流长上下文 KV 优化手段的原理与信息保真边界：

| 方案类别 | 代表方法 | 核心机制与保留依据 | 信息是否无损 | 主要收益方向 | 典型适用场景与硬边界 |
|---|---|---|---|---|---|
| **无损系统管理** | PagedAttention（第 5 章） | 固定物理块分页 + 写时复制，消除外部碎片 | 严格无损 | 显存利用率与最大并发 | 所有在线推理服务的底座标配 |
| **架构级压缩** | GQA / MLA（第 2 章、专题 A） | 训练期减少 KV 头数或投影到低维潜在向量 | 模型原生能力（推理无损） | 显存与 Decode 带宽成倍缩减 | 选型期锁定底座架构（如 Llama-3 GQA、DeepSeek MLA） |
| **数值级压缩** | FP8 / INT8 KV Cache（第 8 章） | 降低 KV 数值位宽（16-bit → 8-bit） | 近似无损（轻度量化误差） | KV 显存与读取带宽减半 | 通用长上下文提并发首选，几乎不破坏远端检索 |
| **位置型有损淘汰** | StreamingLLM | 永久保留开头 Sink + 最近滑动窗口 + 缓存内连续 RoPE | **有损**（窗口外中间信息永久丢失） | 锁死 $O(1)$ 显存与 TPOT，支持百万 token 稳定流式生成 | 无限轮闲聊、实时流式日志/字幕处理；**严禁用于精确跨段检索** |
| **分数型有损淘汰** | H2O（Heavy-Hitter Oracle） | 依据 Decode 过程累积注意力分数保留高热“重击”token + 近期窗口 | **有损**（丢弃低分历史 token） | 在固定预算内比纯滑动窗口保留更多关键远端实体 | 摘要与多轮问答；需额外追踪注意力分，与 FlashAttention 融合较复杂 |
| **Prefill 期有损压缩** | SnapKV | 利用 Prompt 末尾观察窗口的注意力分布，一次性筛选关键前缀 KV | **有损**（仅针对当前查询偏好保留） | Prefill 结束后立即压缩 KV 体积，大幅降低 Decode TPOT 与显存 | 长文档单轮问答 / RAG 精读；多轮转向新话题时已丢信息无法找回 |

!!! warning "常见误区：Attention Sink 不是“开头事实记忆槽”"
    保留 4 个 Attention Sink 的目的只是保住 Softmax 的**功能性泄洪口**，让模型在无限生成时不崩坏；开头那 4 个 token 通常只是系统聊天模板标记（如 `<|begin_of_text|>`, `<|start_header_id|>`, `system`），它们并不负责记住文档第一段的业务事实。此外，工程上切勿把普通引擎开关里的“滑动窗口注意力（SWA）”等同于 StreamingLLM——若没有显式保留 Sink 并做缓存内 RoPE 位置重排，滑出窗外依然会触发崩溃。

## 小结

投机解码与 KV 淘汰分别抓住了 LLM 解码阶段的两个物理杠杆：

- **投机解码**撬动的是**算力与带宽的不对称**：在低并发带宽受限区，借草稿预猜 + 目标一次前向并行验证 + 数学严格无损的残差拒绝采样，换取 2–3× 的单请求提速；但当并发跨过 Roofline 脊点进入计算受限区，额外算力反成拖累，需要动态调节 $\gamma$ 或按负载开关。
- **KV 淘汰**撬动的是**显存与信息完整性的权衡**：以 StreamingLLM 为代表的方案通过保留功能性 Attention Sink 并重排缓存内 RoPE 相对位置，将 KV 显存与每步读取量压成常数，换来超长流式稳定性，代价是彻底放弃窗口外的精确远端记忆。
